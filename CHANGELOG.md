# Changelog

Entries for the release being prepared live here. Released entries move into
`changelog/`, one file per version range, so the active file remains within
the repository's file-size limit.

The version-bump commit moves them with `stado product changelog --version V`;
`stado build submit` refuses a revision whose Unreleased section still holds entries.

## Unreleased

- **A host is live while its own promise holds, not inside a window someone picked (fab304dc):** every capacity broadcast now carries `next_by`, the time by which its worker will publish again (its `--poll-seconds` plus how long its last write took), and every reader (`host gates`, the scheduler's live set, makespan placement, the live GPU ladder, the build fallback, `fleet claim`) counts a row only until that time. The 180-second `CAPACITY_STALE_SECONDS`, `LIVE_CAPACITY_TTL_S`, makespan `HEARTBEAT_TTL_S`, the one-hour capacity GC age, the 200-row GC cap per tick and the 30-second live-GPU cache are gone: an overdue cloud consumer's row is deleted where it is found, a local host keeps its last row as evidence. While the tick works, the heartbeat republishes as long as the call the tick is in has run no longer than that call has ever taken to return in this process, and stops (`heartbeat: the tick has been in <phase> for <n>s (the longest it has taken to return in this process is <m>s …)`) once it runs past that or in a call that never returned. Host beacons published by `stado serve --health-interval-seconds` carry `next_by` the same way, and `registry doctor` reports `stale-beacon` once it passes or when a beacon states none; a capability measurement holds until the host is measured again. Rows and beacons from older releases are held to the `stale_after_seconds` they stated.
- **`stado host ping` grades a beacon by the promise its host made (fab304dc):** a beacon was `stale` after the 15 minutes the job-lease window happened to be; it is now `stale` once the `next_by` its publisher wrote has passed (a beacon from an older Stado is held to the `stale_after_seconds` it stated), and a beacon that states neither is `stale` with that reason in `beacon.error`. `--json` carries `beacon.next_by`; the top-level `stale_after_seconds` is gone.
- **The registry and the model policy are read when they are asked for, not held for a chosen number of seconds (fab304dc):** `GCS_REGISTRY_TTL_SEC` (30 s) and `MODEL_POLICY_TTL_S` (300 s) are gone. Every registry read goes to the authority, so a host moved by the operator is never answered from a copy made before the move (the separate `fetch_registry_authoritative` and the cache-clearing call after a registry import go with it); the coordinator and agent ticks read `config/model_overrides.json` on each pass, so a policy change is in force from the next one.
- **A reservation is renewed on its host's own period, and its lifetime is the holder's promise (fab304dc):** the 60-second renewal, the 180-second lifetime (three renewals) and the one-hour keep of expired rows are gone. `stado capacity hold` and every placed workload renew at once and then on the period the host's capacity row states (re-read each round), each renewal promising that period plus how long the holder's last round took; the agent deletes a row as soon as its holder's promise has passed. A host that has never published a row stating its period is refused (`… publishes no capacity row that states its period …, so nothing would read a reservation there`), recorded for `stado fleet needs` as `no_eligible_target`.
- **Measurements and run times reach scheduling on the next tick, not after a ten-minute cache (fab304dc):** the observed-VRAM map was held for `OBSERVED_MAP_TTL_S` (600 s) and the makespan run-time history for `HISTORY_TTL_S` (600 s), so a model's first measured peak waited up to ten minutes before queued jobs of that model were sized from it. Both now read the `completed/` (and for sizing `failed/`) listing and the live GPUs every pass and download the records again only when that listing or the live GPUs changed; the sizing pass and dispatch bucketing read the map once per pass. Journey `tests/scheduler/sizing.rs` (target `scheduler-sizing-measurement`): the tick after a measurement lands sizes the queued job from it.
- **GCP exhaustion marks hold until an event disproves them (fab304dc):** a zone stockout was skipped for 300 s, a regional quota refusal for 60 s, and both blobs were cached in process for 10 s. A mark now holds until a VM is created in that zone (clearing the zone and its region's quota mark for that accelerator) or deleted in that region (clearing the region's quota marks); each create call tries every unmarked zone and then the one zone whose mark is oldest, logging every zone it skips with the time it was marked, so every exhausted zone is retried in turn and no time decides when. A failed mark write is logged instead of being dropped.
- **The NVIDIA driver probe answers for the tick that asks (fab304dc):** `CUDA_PROBE_CACHE_S` (30 s) is gone; an idle NVIDIA host runs `nvidia-smi` once per tick, and `gpu_driver_detail` carries the probe's whole output instead of its last 300 characters.
- **A Box lease belongs to a live process, not to a five-minute clock (fab304dc):** `OWNER_TTL_SECONDS` (300 s), the keepalive's 300 s renewal and `START_RECOVERY_SECONDS` (120 s) are gone. A provider lease now records `owner_host` and `owner_pid`; it is taken over only once it was released, its owner process on this host no longer exists, or (inside the owning process) the invocation that took it has ended, and a lease held by a process on another host is refused with `provider lease is held by owner … (pid N on HOST)`. A lease written by an older Stado is still held to the `owner_expires_at` it stated. A Box start the API refuses as not retryable (or that is invalid as written) fails the job at once with `Box refused the start: …`; a transport failure or retryable refusal is tried again each tick. A prompt is resubmitted when the box's whole prompt log carries no prompt with the operation's marker, instead of failing after 120 s. `stado instances holders` names each lease's owner process.
- **Box output is read whole (fab304dc):** the 64 KiB JSON response bound, the 56 KiB stdout/stderr tails, the 16-artifact and 16 MiB artifact caps and the 10-page, 100-event listing caps are gone: run.sh writes the whole stdout and stderr, every requested artifact is collected, and prompt and response events are read to their last page at the server's own page size. Box commands are sent with the API's whole 60-second window (the bound the Box API itself defines) instead of a value of Stado's, and the launch no longer pauses a second before checking the process.
- **A running job is held to its worker's own promise, not to a fifteen-minute window (fab304dc):** `HEARTBEAT_STALE_MINUTES` (15 min) as the job lease, the reaper's 30-minute heartbeat, 90-minute checkpoint and 30-minute boot windows, and the idle worker's once-per-15-minutes reaper pass are gone. The claim and every renewal write `lease_expires_at` = the worker's `--poll-seconds` plus the longest it has measured a renewal landing late in this process plus its last renewal write time; a worker with no declared poll period refuses to claim (`not claiming …: no agent poll period is declared in this process`). Every reaper (the lease reaper, the local-orphan and cloud-VM checks, the dead-agent sweep) asks one verdict, `job_liveness`: alive while the promise holds, or when the job wrote a pulse or a checkpoint after it passed; a job with no promise (claimed by an older Stado) is kept and counted as `unpromised`. Log lines read `requeued (worker lease expired; <n>s past its worker's promise; …)`. A renewal that loses a compare-and-swap re-reads until it lands instead of giving up after three tries.
- **Cloud VMs are reaped by measured boot and first-work times (fab304dc):** the 30-minute boot and idle graces and the 30-minute wedged-diagnostic age are gone. The sweep records, per VM kind in `state/vm-durations/<kind>.json`, the age at which each VM was first seen publishing and first seen with a completion, and keeps the longest of each; a silent VM is reaped only once it is older than any VM of its kind has taken to boot, an idle one only once older than any has taken to finish its first job, and with nothing measured yet the VM is kept with `keep <vm>: … no <kind> VM has been seen to boot yet`. A wedged VM (publishing, not accepting, no free VRAM) is reaped when no job on it is alive by its promise.
- **Submissions and schedule occurrences are held by the process that claimed them (fab304dc):** a run-manifest entry and a schedule occurrence carried a 15-minute `lease_expires_at`; they now record the claiming process (`owner_host`, `owner_pid` / `owner_process`) and may be taken over once that process is gone from this host, and the refusal names the holder (`… is being submitted by another owner (pid N on HOST)`). Entries and reservations written by an older Stado are still held to the expiry they stated. The 16-try contention limits on manifest claims and checkpoints are gone: a conflict re-reads and retries until it lands.
- **A host is silent once its beacon's own promise has passed (fab304dc):** the 300-second silence threshold and its `STADO_SILENCE_THRESHOLD_SECONDS` override are gone. `stado host link`, `stado repair stado --step link`, `stado service list` and the silence records all read the verdict `stado host ping` reads: a beacon is current until the `next_by` its publisher wrote, and silent after it (or when it states none). `service list` explains an `unknown` row as `health beacon is <age>s old, past the next publication its host promised by <next_by>; unit state is unknown`, `host link` names the promise in its blocker, and `link` repair reports `beacon_next_by`.
- **`stado fleet needs` reads every recorded refusal and counts unmet demand at once (fab304dc):** the ten-minute queue age, the three-refusal CPU threshold, the seven-day default window and the expansion plan's 3660-day window cap are gone. A queued job no declared host or live GPU could run is a need as soon as it is queued; one refusal as full makes a CPU need; `--days N` (on `fleet needs` and `fleet expansion plan`) reads only the last N days and is otherwise omitted, in which case every retained refusal is read and `--json` reports `"window_days": null` (the empty report reads `the fleet reports no unmet need in every recorded refusal`).
- **A host's reservations are exhausted when they leave nothing, not under one core or 1 GB (fab304dc):** `RESERVATION_MIN_FREE_CORES` and `RESERVATION_MIN_FREE_RAM_GB` are gone; `admission_reason: reservations_exhausted` is published when reservations leave no core or no RAM, and what a job needs beyond that is checked against the same net numbers at claim.
- **`registry doctor` reads a published job requirement declaration whatever its age (fab304dc):** the one-week republication window is gone. A declaration is republished when its job changes, so its age says nothing about whether it still matches; the consulted list now shows each object with its age and publication time (`job_requirements/weles-trajectories.json (published 3d ago, …)`) instead of refusing it past a week.
- **A queued job whose cloud dispatch failed is offered again on the next tick (fab304dc):** the dispatch backoff schedule (0, 1, 5, 15, 30, 60, 120 minutes, capped at 240) is gone. The providers' own exhaustion marks keep a retry off the zones that just refused (every unmarked zone, then the one marked longest ago), so a job no zone can host costs one bounded round of provider calls per tick, and the local worker can claim it meanwhile whenever it fits.
- **A janitor's request for its turn stands while the janitor runs, not for 30 minutes (fab304dc):** `CLEANUP_TURN_TTL_S` (1800 s) is gone. `disk-cleanup-turn.json` now names the requesting janitor's pid; new workloads wait while that process is alive and the request is unanswered, and a request whose janitor is gone (or that an older Stado wrote without a pid) is removed where it is found, so it can never keep the host from work.
- **A yieldable job is protected from a second eviction for one full tick of its agent, not five minutes (fab304dc):** `MIN_RUNTIME_BEFORE_YIELD_S` (300 s) is gone. A just-(re)started yieldable slot can be evicted again once it has run for one of the agent's own `--poll-seconds`, so it is seen running by a whole tick first; `max_yields_before_protected` still bounds how often one job can be yielded.
- **A settled job's cleaned sentinel is retired on the next reaper pass, not after 24 hours (fab304dc):** `SETTLED_SENTINEL_MIN_AGE` is gone. A sentinel is deleted once its transition is retired and its job sits in a terminal prefix — a transition still finishing is not retired and keeps its sentinel, and the workdir cleaner reads an absent source the same as a cleaned one — so `queue/` and `running/` hold live work instead of a day of finished jobs. The unused `STALE_TRAINING_MAX_AGE_S` constant is removed.
