# Changelog

Entries for the release being prepared live here. Released entries move into
`changelog/`, one file per range, because a file this repository cannot edit is
a file that stops receiving entries: the length gate refuses every write to a
file past 300 lines, and this one had reached 414. Two product fixes on
2026-09-08 could not be recorded at all until it was split.

The version-bump commit moves them with `stado product changelog --version V`;
`stado build submit` refuses a revision whose Unreleased section still holds entries.

## Unreleased

- **An unknown release product is a refusal that lists the released products:** `stado release doctor|promote|rollback|active-binary` and the quarantine commands answered a product the release control plane does not hold with "the command failed and we could not attribute the failure — your request or credentials [unknown]", so a typo, or a program Stado does not release (Stado itself), read like a broken control plane. They now state the failure as refused and print `release products: …` beside it.

- **A source install places a product's whole `share/<id>` directory:** a stage map member naming the directory itself (`"stage/share/tama": "share/tama"`) was skipped by `stado product install|update --surface cli` built from source, which placed only `bin/`, retired `~/.stado/share/<id>` and left the install incomplete when the product's `after_install` needed it (`tama hooks release`: "holds no hook release"). The member `share/<id>` is now placed at `~/.stado/share/<id>` exactly as members below it are, as the release-archive install already did.

- **A source install of Stado recycles the units still running the image it replaced:** `stado product install|update stado --surface cli` built from source skipped its `after_install` reconcile ("no verified release archive"), so the object API and other resident units kept executing the replaced binary after every source install. An `after_install` option whose value is `{release_archive}` or `{release_archive_sha256}` is now left out when there is no archive, and `stado release converge-local-readers` without `--archive/--sha256` writes the installed release marker and recycles the units on the replaced image; service-local readers keep their own release until a release install, which still passes the archive.

- **`stado config get KEY` prints one resolved value:** the same map `stado config show` prints under `resolved`, one key at a time — a string bare, a list or object as JSON — and a key that resolves to nothing is refused by name. Scripts that parsed `config show` with a JSON reader (Brama's launcher used `python3`) read the value directly.

- **Stado Desktop's cloud control-plane image runs the Stado Linux release, not the retired Python package:** the image was `python:3.12-slim` with `pip install 'stado[aws,azure]'` and a copy of `stado/` found through `stado package-root`, which in the Rust CLI printed the build machine's `data/` directory, so the AWS, Azure and Google Cloud provisioners always stopped at "The installed Stado package source could not be located". The context now holds the installer `stado bootstrap --print-install-script` prints — the same verified download of `stado`, `stado-fix` and `stado-watchdog` for the configured API and this release version that `stado bootstrap` runs on a host — and a `debian:bookworm-slim` Dockerfile that runs it and starts `/root/.stado/bin/stado cloud-control-plane`. The hidden `stado package-root` and `stado::data_dir` it relied on are removed.

- **`stado_database::sync::Client::run` hands SeaORM entity work to the shared client:** a product whose tables are SeaORM entities but whose callers are synchronous (Jeden, Singularity) passes `|db| async move { … }` — entity queries, a transaction, its migrator — and waits for the closure's own result. Such a product keeps no runtime or connection thread of its own; the only error `run` adds is a task that stopped before answering.

- **The object-API recovery (`stado host repair` for the object API) runs no Python on the host:** `deploy/recover_object_api/*.sh` carried eleven `/usr/bin/python3` programs — config and path readers, the launchd definition writer, the route inspector, a plist comparison, the object-boundary check and four Skarbiec bootstrap readers. They are now the hidden `stado host object-api-local paths | render-plist | plist-equal | boundary-ready | route | skarbiec-plan | skarbiec-ownership | skarbiec-upstream | skarbiec-proxy-match`, run by the host's own Stado under the same lock, with the same fields, refusals (printed alone on stderr, exit 1) and exit statuses; the shell keeps the launchd, sudo and curl steps. A Skarbiec plan whose declared readiness wait is out of range now says `readiness wait is invalid`. The unused `deploy/reports/release/report_release_signing.sh` and `report_release_store.sh`, which also ran Python, are removed.

- **The health beacon scripts read their coordinates and relay list from Stado, not Python:** `deploy/beacon/host_health_beacon.sh` and `host_health_beacon_macos.sh` parsed the config and `registry pull` with `python3 -c`, and the macOS relay fetched every target's beacon with a Python HTTP client. Two hidden commands answer instead: `stado host beacon-coordinates --host SLUG` prints the configured object-store URL and the Skarbiec endpoint the service directory declares for SLUG, tab separated; `stado host beacon-stale --api-url URL --token-file FILE --fresh-seconds N` prints the targets with no beacon younger than N seconds under their name or any declared hostname, read from that store directly. With no `WC_BEACON_RELAY_TARGETS`, the stale list is the relay's work list. An installed Stado without these commands answers nothing: a Linux host then collects for a relay, and the macOS unit keeps the coordinates its environment carries.

- **`stado host gates HOST --require-disk low-watermark|target` answers the build-capacity question by exit status, and the release train no longer runs Python for it:** without the flag the exit status still follows `claiming`. With it, the command exits 0 only when the host's free space is at least the chosen declared threshold, printing `HOST disk meets low_watermark_gb|target_free_gb: FREE >= THRESHOLD GiB`, and refuses with the shortfall or with the missing reading. `deploy.yml`'s three capacity steps used `python3 -c` over the JSON report: the step that runs the freshly built candidate now uses `--require-disk target`, and the two steps that run the installed binary, which may predate the flag, read the same JSON with `/usr/bin/jq`.

- **`stado release version-gate` runs the pull-request version gate, which carried about 700 lines of embedded Python:** `.github/workflows/version-check.yml` wrote `surface.py`, `baseline.py`, `semver_at_least.py` and `unreachable_modules.py` into the runner and installed AutoVersion into a Python venv. They are replaced by `stado release version-gate surface --binary B | --help-text F`, `baseline --stado B [--output F]`, `decide --current V --published-surface F --candidate-surface F [--breaking] [--json]`, `semver-at-least ACTUAL MINIMUM` and `unreachable-modules [--crate DIR] [--known FILE] [--json]`, with the same outputs and refusals. `decide` is Stado's port of AutoVersion's rule, and the new `conformance --fixtures FIXTURES.md` step reproduces every AutoVersion v0.1.0 fixture before the gate trusts a verdict from it. The module check now runs after the build, because it is the built binary that runs it. One difference: `baseline` no longer waits and retries a channel that cannot answer; it exits with the fleet's retryable status (`EX_UNAVAILABLE`) and says so, and the gate reports that as unreachable, not as a verdict on the revision.

- **Released changelog entries move out of `CHANGELOG.md` by command, and a release refuses to go out without the move:** `stado product changelog --version V [--root DIR]` moves every entry under `## Unreleased` into `changelog/` as section `## V`, appended to the newest range file (renamed to `<first>-V.md`, its `## Released` link updated) while it stays under 300 lines, otherwise into a new `changelog/V.md` linked first. `stado build submit` refuses a revision whose `CHANGELOG.md` keeps range files and still holds Unreleased entries, naming the count and the command. A repository with no `changelog/` range files is not affected.

- **The release-catalog ownership repair runs in the host's Stado, not Python:** `deploy/release/repair_release_store.sh` was a `python3` program. It is removed; the repair now runs the hidden `stado host release-store-repair-local --config … --product …` on the host, with the same bounded path set (object, metadata and lock plus their parents in the primary and a local backup store), the same refusals (`invalid_product`, unresolved or out-of-home or symlinked store root, `refused_symlink`, `refused_wrong_type`, `refused_foreign_owner`, `postcondition_failed`), the same `sudo -n chown -h` for a root-owned node, and the same output lines.

- **`stado bootstrap` needs no Python on the host and units no longer carry `WC_PYTHON`:** the release download checked the manifest, the archive digest and the three members with `python3`, and the re-qualification of an installed Stado validated and compared versions with it. Both are now POSIX `sh` with the same refusals (unexpected manifest fields, identity mismatch, invalid source commit or digest, digest mismatch, a member missing, repeated or not a regular file; an invalid version; a marked candidate not newer than the registry's). The scripts print two lines, platform and Stado path, instead of three. `WC_PYTHON` is removed from the bootstrap and local-install units and from the GCP, AWS and Azure GPU startup templates: no agent code read it, and a job's runtime belongs to its workload. The watchdog unit drops `PYTHONUNBUFFERED`. The nine unused files under `stado-rs/src/deploy/testdata/` are removed.

- **The queued batch is started by Oko, not by a clock:** `stado build newest --queued` is run by Oko's control pass once every open task and defect carries its repair, and the daily schedule that ran it regardless (`sch-1eb40296`) is removed. The `--queued` help says so.

- **`stado service env set/unset` on a systemd unit edits the unit file with Stado, not Python:** the edit of one `Environment=` key in a unit or drop-in was a `python3` program run as the unit's account. It is now the hidden `stado service unit-env-local --path-b64 … --key-b64 … [--value-b64 …] --uid N`, run by the host's Stado under the same account, with the same rules: no symbolic link anywhere on the path, a regular file owned by the unit's account, continuation lines and quoted words kept, the file's mode and owner preserved, a rename only if the file did not change meanwhile, and a drop-in left with nothing but `[Service]` removed. It prints `changed` or `unchanged` as before. When the unit's account cannot execute the connecting account's `~/.stado/bin/stado`, it runs a copy staged in a fresh `/tmp/stado-unit-env.*` directory on that host, removed as soon as the edit ends.

- **The autonomy reconciler retires failing units in the fleet namespace that nothing declares:** `stado service list --undeclared` named them and no pass acted on the row, so a hand-bootstrapped `com.wisent.compute.service.com.wisent.always-on.weles` running a loose `~/weles` copy exited 1 at every login on lukasz-macbook. Each pass now boots out and withdraws the autostart of every unit on a local host that is classified `undeclared` (the `com.wisent.` prefix, not in the registry), holds no process and last exited non-zero, and records it as a `retire_stray` row in the reconcile report; a program under `~/.stado/` is left alone, and report mode or the emergency pause only plans it. The unit file stays in place.

- **`stado credentials item show` summarises on the host with Stado, not Python:** the decrypted item from `skarbiec get --json` was piped into a `python3 -c` reducer. It now pipes into the hidden `stado credentials item summarize-local`, which prints the same summary — kind, schema and, per field in name order, whether it is text, its length and its SHA-256 (a text field as its bytes, any other value as compact JSON with sorted keys) — and never a value. A structured field holding non-ASCII text now hashes its UTF-8 JSON rather than Python's `\u` escapes.

- **Object API recovery takes its lock through the host's Stado, not Python:** a `python3` wrapper took the storage-root transaction's `flock` on `~/.stado/recovery/storage-root-reconcile.lock` and fed the recovery program to `bash`. The hidden `stado host run-locked LOCK -- PROGRAM…` now holds the same exclusive, non-blocking lock (owner-only file, refused with `storage authority recovery is already running on this host` when taken) while PROGRAM runs with the recovery program on stdin, and returns its exit status.

- **Service release installs and `stado host exec` run no Python on the host:** installing a service release archive renamed the unpacked version directory and swapped the `current` link with `python3` `os.rename`/`os.replace`; it now uses `/bin/mv` for the directory and `/bin/mv -fh` for the link, so a `current` that points at a directory is replaced itself, in one rename. Host exec found a product's released program by reading the release agent's record with `python3 -S -c`; it now asks the host's Stado through the hidden `stado release active-dir PRODUCT RELATIVE`, which prints `<active.release_dir>/RELATIVE` or nothing.

- **Service file sync, token-file sync, environment key set/unset, environment-file reads and secret sync run no Python on the host:** each confined its target to the account's home with `python3 -c os.path.realpath/commonpath`, and secret sync shell-quoted the value with `shlex.quote`. The confinement is now `cd … && pwd -P` of the parent and the home compared as physical paths (a directory that cannot be resolved is refused), and the assignment follows shlex's rule in `sh`: a value of only `A-Za-z0-9_@%+=:,./-` stays bare, anything else is single-quoted with `'` written as `'\''`.

- **`stado service fetch` and `stado stream status` no longer run Python on the host:** the fetch confinement resolved the parent directory and the home with `python3 -c os.path.realpath`; it now uses `cd … && pwd -P` in the same script and refuses a directory it cannot resolve. Stream status counted Sunshine's paired devices with an inline Python program; the host now sends the state file base64 and Stado counts the devices itself (`paired_clients` stays `0` without a file and `unreadable` when it cannot be decoded).

- **`stado credentials token sync` runs each host's installed Stado, not Python:** the export on the source and the install or check on the destination were one Python program run with `python3 -c`. Both are now the hidden `stado credentials token custody-local OPERATION VAULT CONSUMER FILE` (`export`, `install`, `check`, `install-shared`, `check-shared`), with the same checks: an owner-only regular token file inside the account's home, a bounded non-whitespace bearer whose SHA-256 matches the unexpired grant, identical owner and grant on both sides (the owner's own for a shared vault), an atomic owner-only write, and the grant re-read before and after delivery. No vault is written.

- **`stado credentials token mint --token-item` runs the vault owner's installed Stado, not Python:** registering an existing vault field as a bearer piped a Python program to `python3` on the owner. It is now the hidden `stado credentials token register-item-local SKARBIEC ITEM FIELD -- grant issue …`, with the same behaviour: the field is read with `skarbiec get`, handed to `grant issue` through an owner-only file removed afterwards, kept at `STADO_TOKEN_DESTINATION` (refusing a file that holds another bearer or is a symlink), and the report printed without the bearer.

- **Signing the Apple challenge helper no longer needs Python on the build host:** the certificate and key reached `stado product signing sign` through a `/usr/bin/python3 -c` wrapper that moved them from stdin into the signer's environment. A fixed `/bin/sh` program now does the same — two base64 lines on stdin, decoded into `WISENT_CODESIGN_CERTIFICATE_PEM` and `WISENT_CODESIGN_PRIVATE_KEY_PEM`, never in argv — and execs the host's Stado; the signer's JSON list is read as before.

- **`stado space file remove` runs the target's installed Stado, not Python:** the host half was a Python program piped to `python3` (or `sudo -n python3` for a `com.wisent.*` unit in `/Library/LaunchDaemons` or `/etc/systemd/system`). It is now the hidden `stado space file remove-local PATH --home HOME`, the same descriptor-held removal in Rust — every parent opened without following links, the file inspected without following it, unlinked through the held parent and its absence verified — printing the same `STADO_REMOVE_FILE` report, so the refusals (`outside the managed areas`, `not a regular file`, `not owned by this account`, a symbolic link) are unchanged.

- **`stado release catalog adopt --kind ios-xcode` writes no Python:** it wrote `release/archive-tree.py` into every adopted checkout and a `build.sh` that ran it with `python3`, although `stado product tree-archive` already packs the `.xcarchive` reproducibly. The build template now calls `stado product tree-archive` and writes `SOURCE_REVISION` from `WISENT_SOURCE_COMMIT` (a worker's source is an unpacked snapshot with no `.git`), and adopt writes three files instead of four. The unrun `tests/source-identity/test_source_identity.py` is removed with it.

- **`declare-publisher --reload HOST=UNIT` refuses a retired unit:** a reload refreshes the publisher table inside a running process, and a unit the service catalog lists under some product's `retired_units` no longer runs that work — its product's one process does. The command now stops before touching the vault with the same sentence `service deploy` prints for a retired unit, naming the process to use instead.

- **`withdraw-publisher` from a host that reads the vault owner skips that host's verifier repair, as `declare-publisher` does:** `stado release catalog withdraw-publisher wisent-images` on lukasz-macbook removed the declaration from both hosts and then failed `release item grant reconciliation failed: token file does not match the consumer's recorded bearer`, because the repair reconciled lukasz-macbook's retired local vault copy. A host that declares no `secrets.skarbiec.vault_file` reads the owner's vault, which the owner's own repair covers; the report says `not needed: reads the vault on the owner`.

- **A catalog installation may name the release product its manifest publishes:** `stado product update weles --surface service --host charless-mac-mini` refused `release manifest product does not match weles`, because Weles publishes its releases as `weles-worker` while its catalog id is `weles`, and `weles-worker` alone is `no catalogued product`. A `stado-release` installation now accepts `release_product`, and the Weles service installation declares `weles-worker`; the check still names both when they disagree.
- **`stado product changelog` splits a backlog that alone passes 300 lines:** it wrote the whole Unreleased section into one `changelog/V.md` past the limit. The entries now go into `changelog/V-part-N.md` files, each under the limit, an entry never split across two, linked newest first; a later release starts its own file instead of growing or renaming a part.

- **No shell script in the repository runs Python any more outside the storage-root transaction and the backup audit:** four `deploy/reports/*` diagnostics (queue consumer, input visibility, release-agent state, stable bind) and `deploy/release/reconcile_release_once.sh` were never run by any command — `stado release agent --once` and `stado release status` answer what they printed — and `scripts/grant-stado-local-agent-huggingface.sh` wrote into a host-local vault the fleet no longer keeps; all six are removed. The examples read JSON with `jq`, and the Azure GPU start-up waits for its grant file with `sleep` instead of a `python3` one-liner.
