# Changelog

Entries for the release being prepared live here. Released entries move into
`changelog/`, one file per version range, so the active file remains within
the repository's file-size limit.

The version-bump commit moves them with `stado product changelog --version V`;
`stado build submit` refuses a revision whose Unreleased section still holds entries.

## Unreleased

- **`stado credentials grant role-read` grants the role itself, so a role read stops answering 403:** `credentials get --role … --route` (and every consumer that reads a secret by role through Skarbiec, Oko's model router among them) asks Skarbiec for `role:<role>`, and Skarbiec matches that coordinate exactly before resolving the role. `role-read` translated the role to the item playing it and granted only `read:<item>#<field>`, so the consumer it had just authorized was refused with `consumer not authorized to read item field`. It now grants `read:role:<role>#<field>` and keeps the item read for readers that list and then name the item; a role no item plays, or several play, is still refused.
- **Every resident Stado role is a role of `stado serve`; the standalone resident commands are removed (fe7466c9):** `stado agent`, `stado coordinator` (and `--once`), `stado dashboard`, `stado resolver serve`, the `stado release agent` loop (`--interval-seconds`), `stado disk-cleanup --watch`/`--interval-seconds`/`--once`, and the hidden `host beacon-units`, `host beacon-coordinates` and `host beacon-stale` helpers of the deleted bash beacon are gone. Their work runs as `serve --worker`, `--coordinator`, `--api`, `--resolver`, `--release-interval-seconds`, `--disk-cleanup` and `--health-interval-seconds`. `release agent --once` is the one reconcile pass promotions run and requires `--once`; `disk-cleanup [--dry-run]` is one pass. `serve` gains `--enrollment-only` and `--inherited-listener` for the public enrollment listener `fleet ingress up` starts, and an ephemeral cloud worker (`serve --standalone --worker --kind <provider> --gpu-type <accel> --poll-seconds <s> --idle-shutdown`, which ends the process successfully when no eligible work remains); the GCP, AWS and Azure startup scripts run it with the deployment's new required `agent.poll_seconds` (`STADO_AGENT_POLL_SECONDS`), and dispatch refuses a machine without it. The release-proxy control socket is owned only by a process that reconciles releases, so a second serve process on one host no longer contends for it. Remote `stado bootstrap` installs the one `com.wisent.stado` unit through `stado bootstrap --local --target <host>` on Linux too, after retiring any unit still running the removed `stado agent`; the `wisent-compute-agent.service` system unit is no longer written. The host installer folds in only `stado serve` units and refuses any other Stado unit by name; the object-API recovery and storage-root rollback write `serve --api`; the janitor no longer restores coordinator or release-agent units (they are roles of the process it runs in); `coordinator` no longer raises a declared `interval_seconds` below 15 to 15 and refuses a non-positive one. Removed with them: `install.sh`, the `deploy/units` and `deploy/beacon` beacon units and scripts, and one-off `deploy/` scripts nothing referenced.
- **The unshipped `stado_migrate` binary is removed (fe7466c9):** it moved the coordinator between hosts by booting out the old host's whole `com.wisent.stado` unit — worker, API and every other role with it — and no release carried it. The coordinator is the `--coordinator <entry>` role of a host's serve process; moving it is a registry declaration followed by `stado bootstrap --local --target <host>` on each host.
- **Stado installs and updates itself only from the signed release; the tag-train release path is removed (fe7466c9):** releases have been published only by `stado release submit` (`release.json`, `release.sig`, `release.tar.gz`, `qualification.json`) since the last `stado-v*` tag (0.21.49), yet `stado self-update`, `install-stado.sh`, the remote installer `stado bootstrap` runs, the local `ensure_bins`, the GCP/AWS/Azure agent startup scripts, `doctor`'s release-channel check and `host release`'s coordinate identity still read the tag train's `SHA256SUMS`, `release-manifest-<platform>.json`, `stado-v<version>-<platform>.tar.gz` and loose binaries, which no current version carries. Every one of them now reads `release.json` and `release.tar.gz`, checks product, version, platform, source revision, archive size and SHA-256 against the manifest, and installs the archive's one `stado` member. `install-stado.sh` is the single installer: `stado bootstrap` and `--print-install-script` run that same file with `STADO_API_URL` and `STADO_RELEASE_VERSION` bound in front, it reads the platform from the machine (no `STADO_RELEASE_PLATFORM`), and its last two output lines are the platform and the installed path. Removed with the tag train: the `deploy.yml` and `deploy-existing-release.yml` workflows, `stado-rs/Dockerfile`, `release-channel/vercel`, `deploy/install/{stado-up.sh,deploy_stado_rust.sh,coordinator/*,toolchain/*}`, `deploy/release/stage_release_attestation.sh`, `uninstall-stado.sh` (which removed `com.wisent.compute.*` units Stado no longer installs; `stado product remove stado --surface cli` removes what the product installed), and the `wc`, `stado-coverage` and `stado-mcp` programs with the coverage orchestrator. The read-only MCP server is `stado mcp` and runs its tools through the same binary.
- **The release audit and the janitor know only the signed release (fe7466c9, fab304dc):** `doctor`'s published-release integrity audit judged a coordinate holding only its claim, or short of objects, as still publishing for 60 minutes after the claim was written — a budget measured on the tag train's publishing jobs. It now reads the release pipeline's own run records (`runs/release-pipeline/<run>/run.json`): a coordinate is publishing while a run of that version (and, for a claim, of the claim's revision) has not finished, and BURNT or PARTIAL once none is; unreadable run records report the coordinate unmeasured instead of guessing. The coordinate listing no longer carries claim write times. `host release` and `doctor` no longer compare `release.json` against a tag-train `release-manifest-<platform>.json` beside it (no publisher writes one), and the claim agreement check reads only the signed manifest. The `release_store` janitor keeps the newest complete signed release (`newest_signed_release_kept`); the tag-train installer family, its `newest_installable_kept` key and the `installer_publication_untracked` refusal are gone.
- **`doctor`'s release integrity audit reads the versions a host can be given (fab304dc):** it read the newest six published versions (`INTEGRITY_VERSIONS`), whatever hosts declared. It now reads the newest version the channel holds, every version a registry target declares for Stado, and every version a release run is still publishing; an unreadable registry is reported and the audit continues with the other two.
- **The API listener has no built-in port (fab304dc):** `serve --api` listened on 8765 when neither `--port` nor `dashboard.port` said otherwise. It now refuses without one (`serve --api needs the port it listens on: …`); `--port 0` asks the system for a free port, which the listener announces as `[dashboard] listening on http://…`. Stado Desktop's **This Mac** backend starts its `com.wisent.stado` with `--port 0` and takes its endpoint from that announcement instead of a port hashed into 8800–9799, drops the `ThrottleInterval` and the unread `WC_DASHBOARD_REFRESH_SECONDS` and `WC_BUCKET` from its unit, and finds this device's API from the environment, the configuration, or the unit's own `--bind`/`--port` (and announced address) rather than assuming 8765. `config show` prints `dashboard_port` as declared, or null.
- **A release or source archive is bounded by the room its destination has, not by invented sizes (fab304dc):** extraction refused an archive over 2 GiB, an expansion over 4 GiB, a release over 4096 entries and a source snapshot over 65 536; the publisher and manifest validation refused artifacts over 2 GiB. Extraction now measures the destination volume once (`statvfs`: bytes and file entries available to an unprivileged writer) and refuses, while reading, an archive that would expand past either, naming the volume and the room it had; a release's size is checked only against its signed `artifact_bytes`.
- **`stado product` keeps a run until a later one supersedes it, not a fixed count (fab304dc):** a checkout kept its newest 3 builds (`KEPT_BUILDS`) and newest 200 command records (`KEPT_COMMAND_RECORDS`). A build now keeps the previous attempt — the evidence of the last outcome and the measure of the room the next build needs — and removes every older build no process still holds. A command record is removed once a later record is created and its own command succeeded; a failed command's record, which its error names as evidence, stays for the reader.
- **Fleet expansion plans over every option declared (fab304dc):** the catalog refused more than 24 options (the width of the exhaustive search's bit mask), identifiers over 80 bytes, text over 4096 bytes, need subjects over 128 bytes and lead times over 36525 days. The exact selection now walks any number of options, pruning only a branch whose gain plus every positive gain still open falls short of the best portfolio found; ties still spend less, then follow id order. Identifiers keep their character rule and text fields must not be empty.
- **A store document is bounded by the memory the host has, not 16 MiB (fab304dc):** a text or versioned object read refused anything declaring more than 16 MiB (`STORE_DOCUMENT_MAX_BYTES`). It is now refused, before its body is requested, only when it declares more than the memory the operating system reports available at the moment of the read; the refusal names that amount. A host whose memory cannot be read reads the document unbounded.
- **`stado product install` replaces a previous path that a new placement contains (8cdbce74):** an installation whose previous release placed `share/tama/hook-release` and whose new release places `share/tama` put the new tree in place, then treated `share/tama/hook-release` as a retired path, found the bytes it had just placed there, refused `refusing to replace content not matched by this installation or its retained backup` and left the installation incomplete without its `after_install` step. A previously installed path inside a path this installation places is now that placement's own content: it is neither guarded nor removed, including in an unfinished installation that recorded it as retired, so rerunning the install completes it.
- **`stado service status NAME --lines N` reads the stderr window the reader asks for (fab304dc):** a `failed` row's evidence carried at most 10 stderr lines (`FAILURE_STDERR_LINES`), read as a 20-line tail, whatever the failure needed. The window is now the reader's own `--lines`, as in `service logs`; without it the failure block reports launchd's last exit and prints `stderr: not read` with the `service status … --lines <N>` and `service logs … --host … --lines <N>` commands that read it. `--json` adds `stderr_read`. Stado Desktop's Services table and inspector print the same sentence and no longer cut the stderr lines to three.
- **`stado-fix` and `stado-watchdog` are removed (fe7466c9):** both were separate programs ported from the retired Python package, and both run as roles of `stado serve` (`--failure-fixer-interval-seconds`, `--watchdog`). Their binaries, argument parsers and entry points are gone; the release, install and recovery scripts and workflows no longer list them; `stado bootstrap`'s remote installer extracts only `stado` (the release `stado release submit` publishes stages only `stado`, so the remote installer's demand for the two members already refused every current release). The host installer no longer folds watchdog or failure-fixer units into `serve`, Stado's catalog no longer attributes a unit running either program to the stado product, and `stado bootstrap --local --target failure-fixer|watchdog` answers like any undeclared target. `serve --watchdog` reports why its loop stopped instead of an argparse exit status.
- **`stado local-control-plane` and `stado cloud-control-plane` are removed:** they were hidden ports of the retired Python `deploy.local_control_plane`/`deploy.cloud_control_plane`, and every role they bundled is a role of `stado serve`. No fleet host ran them; the one fleet entry named `local-control-plane` is a coordinator in the registry, which `serve --coordinator` runs. A device that belongs to no fleet now runs `stado serve --standalone --worker --kind local --poll-seconds <s> --control-plane local --control-plane-interval-seconds <s> --api --bind <addr> --port <port>`: `--standalone` runs the worker without a registry target and is refused beside `--resolver`, `--release-interval-seconds`, `--target` and `--auto`. Stado Desktop's **This Mac** backend starts that line and waits for `stado serve: target=` in its error log; its cloud container image runs `stado serve --control-plane cloud … --api`. The host installer no longer merges units running the removed commands, and its unused `coordinator` and `disk-cleanup` install kinds are gone.
- **A failed release can be resumed after its build job was reaped (5282f935):** `stado release submit` of the same source, `stado release resume` and `stado build` refused a failed platform whose job record the run reaper had already deleted with `build job <job> was not found in recorded states; refusing a replacement without terminal failure`, so the same commit needed a new version. The job's retained receipt (`status/<job>/output/receipt.json`), or failing that its run's retained outcome in `runs/<run>.json`, now says how it ended, and a failed or cancelled build is built again under a new identity. Only a job with no record, no receipt and no retained outcome is refused, with `build job <job> is in no queue state, left no receipt and no reaped run retains it`.
- **`stado cancel` of a job pinned to a fleet host no longer answers infra_down (94a07941):** the cancellation fence records a pinned job's agent reference (`local@<host>`) with no provider name, because such a job owns no provider resource, and reading the fence back refused that as `cancellation allocation … has invalid ownership fields` [infra_down, retry later]. An agent reference is accepted without a provider; a provider allocation still has to name its provider, and the refusal now prints the provider, instance and restarts it read.
- **The DNS MX preference read is an if/else (a050a5b9):** `bool.then(..).unwrap_or_default()` in `src/cli/dns/records/write.rs` failed clippy's `obfuscated_if_else` and with it the 0.23.36 release on both platforms; 0.23.36 was not published.
