## Unreleased

### Added

- **`stado public-status check | show | serve` publishes whether the components people rely on work, and serves the public status page:** a catalogued product declares under `public_status` each component a person uses and the one request that shows it works — the method, an HTTPS `url`, a vault base address by role (`url_secret` with `path`) or the service directory entry this host reaches (`service` with `path`), header values only from vault roles, an optional JSON body, the status by its reason phrase (`expect_status: OK`, `Unauthorized`) and optionally a text the answer carries. `check` asks every declared component once and publishes `public-status/components.json` in the object store: per component `up` or `down`, `since` (kept while the state holds), the answer that decided it and the last failed check `{at, error}` with the status and body the component sent or the transport's own words; `show [--json]` reads it and refuses naming the document when none is published. `serve --bind <host:port>` is the page: every request reads the document again, `/` renders it and `/status.json` returns it, and a document that cannot be read is answered `503` with the reason, so the page, run as its own unit on a host apart from the products it reports on and published with `stado web declare --upstream-service`, answers while they do not. Stado Desktop runs `check` and `show`. The catalog declares wisent-app's front page, guest sign-in, chat API and backend API and most's messaging. Real journeys: `tests/public_status/`.
- **Every commit that carries a recorded repair is queued for its release, and `stado release newest` delivers the queue:** for each product checkout the queue reads the commit, the version it declares and the recorded runs as `stado release newest` does, and reads Oko's open defects once a pass (`oko defects list --open --json`) for those whose recorded repair names the checkout's repository and is that commit or one of its ancestors — by repository, not release product, since a repository can release a product of another name; a pass Oko cannot answer queues nothing and says so on stderr. A commit carrying none owes nothing (`nothing_carried`); one carrying some is `queued` at the first step it needs — `version` (the least next version the versioning rule allows, when the declared one is taken), `release` or `record` — with its defects named, in `~/.stado/release-loop.json` (`STADO_RELEASE_LOOP_REGISTER`). Queueing builds and commits nothing: `stado serve --release-loop-root DIR` queues at start and whenever a checkout's branch moves (the kernel's notification on `.git/refs/heads`, nothing polled), and `stado release newest --plan` queues and prints the queue (`queue` in `--json`). The steps run only in `stado release newest`, the release command the build gate admits or refuses: the version is committed in the product's own version source (its `Cargo.lock` entry moved by `cargo update --workspace --offline`), the commit goes through the pipeline `submit` drives, and the release is recorded on its defects with `oko defects released --product P --close`. A step that refuses keeps its exact error on the commit, is noted on every carried defect (`stado release loop: <product> at <commit> did not reach a release; the <step> step refused: <error>`), fails the command naming the product, and the commit is not taken again; the product's next commit is. A version file or lock carrying someone's uncommitted change, or a checkout that moved while it was planned, is refused by name rather than committed over.
- **A commit the delivery queue takes runs its compile-free gates at once:** a commit that carries a repair is checked, before it is queued, by the product's format gates and the lock check over its committed tree (`stado quality check`'s formatting selection, which compiles nothing), so a commit committed unformatted or with a `Cargo.lock` its manifest outgrew fails at step `gates` with the gate's refusal, noted on every defect it carries, instead of failing the first installation that builds on it. A product that declares no format gate gets the lock and module checks alone; a commit kept queued has passed them.
- **A commit that declares a module file it does not hold is refused before anything compiles:** `stado quality check` — the pre-push check, a change hand-off, a release submission and the delivery queue's `gates` step — reads every Rust crate of the committed tree from its roots through its `mod` declarations and refuses a `mod name;` with neither `<name>.rs` nor `<name>/mod.rs` (nor the file its `#[path]` attribute names): `<revision> of <checkout> declares module files it does not hold, so no build of it compiles: <file> declares `mod <name>;`, and the tree holds none of …`. A product that declares no format gate still gets this and the lock check in the queue's `gates` step. Real journey: `tests/quality/module_declarations.rs`.
- **A commit whose code names a module no declaration reaches is refused before anything compiles:** the same module reading follows every `crate::a::b` path in a reached module through the declared modules, and a segment naming a module file the commit holds but no `mod` line reaches — a module's file and its callers committed without its declaration — is refused: `<revision> of <checkout> uses modules no declaration reaches, so no build of it compiles: <file> uses `crate::<path>`, and the tree holds <module file>, which no `mod <segment>;` reaches`. Real journey: `tests/quality/module_declarations.rs`.
- **`stado release newest --first` sets the delivery order, and `--plan` names every repair the queue cannot place:** the queue and the submissions went in product-name order, so a dependency named later in the alphabet was delivered after the products that rely on it. `--first P,Q,…` (or the flag repeated) delivers the named products first in that order and the rest in name order; a name the plan does not hold is refused naming the products it holds. A repair recorded at a commit the checkout's history does not hold — a rewritten branch, a side branch — or in a repository with no product checkout was silently never queued; `--plan` over the whole workspace now lists each under `unplaced` (`--json`) or `unplaced  <defect>  <repo>@<commit>: <why>`. Stado Desktop's Releases operations take the same order. Real journey: `tests/release/delivery-queue-order.mjs`.
- **The delivery queue's record step closes the tasks a release finishes, and a failed record is retried:** the step runs `oko defects released --product P --close --tasks --json`, so besides the defects whose repair the published release carries, every task whose acceptance checks are all recorded met and whose evidence commit the release carries gets its `done` verdict by the release, with no judge asked; the entry's `recorded` lists the defects and the tasks (`task-…`). A record that fails no longer settles the commit: the release stands published and the next pass records it once Oko answers — an Oko that predates `--tasks` refuses until it is delivered itself. The plan's not-in-history reason names `oko defects rebased --apply`, which records the commit that carries the same patch.
- **`stado release newest --register` prints the delivery queue's register, with when each release was published and recorded:** per commit its state, step, carried and recorded defects, the refusing step's error, and the new `released_at` (the queue's release step published it) and `recorded_at` (Oko recorded it on the carried defects); a retried record keeps the earlier pass's publication time. `--json` is `{path, entries}`, newest first; a register that is not one is refused naming its path. Oko's fleet report reads its queue success and release times from it. Real journey: `tests/release/newest/queue-register.mjs`.
- **`stado release newest --push --first P,…` delivers the gate first, then pushes, then reads CI, measuring unpushed commits before and after:** every push runs the pre-push gate, which is itself a delivered product, so pushing first met the old gate. `--push` delivers the `--first` products, installs each on this host (`stado product install`), then `git push`es every workspace checkout holding commits its upstream does not and reads `stado ci status <product> --revision <pushed commit>` for each pushed product, and only then delivers the rest; a first product that failed its queue step or its install leaves every push undone, each naming why. Without `--first`, `--push` is refused before any step. Unpushed commits per checkout are counted before and after (`push {before, installed, pushed, after}` in `--json`) and by `--plan` (`unpushed`); a checkout without an upstream names git's refusal. Stado Desktop's newest operation carries the flag. Real journey: `tests/release/newest/push-order.mjs`.

### Fixed

- **Push quality checks inspect the commits Git is pushing, not another writer's working tree:** `stado quality check --pre-push --if-declared` reads Git's ref updates, names each selected commit and reads both the manifest and gates from its clean export. Repeated refs share a check; deleted refs have no source gate. `--revision COMMIT` selects an explicit committed tree without fetching a different tip, also available in Desktop Releases through the native operator API. Invalid records and noncommit objects refuse rather than selecting another source. The real journey under `tests/quality/push/` covers non-HEAD pushes, dirty declarations and source, committed formatting failures, ref deletion and noncommit refusals. Git dispatchers must forward the preserved update stream.

- **`stado product install --source-commit` installs a commit on the canonical checkout's own `main`:** only commits `origin/main` carried were accepted, so a repair to the push gate could not be installed before it was pushed, nor pushed before it was installed. The installation says when it is ahead of origin and records `source_on_origin`; a commit on neither `main` is refused naming both.

- **A source installation of Skarbiec signs with the keychain its catalog recipe declares:** the CLI, service and desktop recipes select the installing machine's local keychain before building. A missing keychain refuses by path without consulting the vault or placing bytes; a conflicting explicit signing source refuses. The installed receipt names the selected keychain and each native file's observed authority, team, identifier and CDHash, also shown in Desktop Products. Exact published releases remain verified rather than re-signed.

- **`stado job watch` refuses a log page without its text, cursor or end flag:** such a page was read as empty text, the same cursor and the end of the log, so the tail stopped as if the job's log were complete. The refusal names the job, the cursor and the page.

- **`stado credentials grant revoke` refuses a grant whose capabilities cannot be compared:** a capability without its action or item was rendered with an empty item, fell out of the check that `stado` covers it, and the retired grant could be revoked while `stado` did not hold it. A capability without a field is rendered without a trailing `#`.

- **`stado host recover`'s host step blocks on a unit the pass did not report:** a completed pass that named no outcome for a declared LaunchAgent was read as nothing to account for and reported `ok`. Such a unit is now a blocker with `finding: "unreported"`, and the status is `blocked`.

- **`stado release status` fails a rollout target the fleet registry does not declare** instead of judging its software against an empty declaration, and a run without its product is named as such instead of reporting its manifest missing under an empty product. The run filter no longer matches a run without a run id against an empty `--run` prefix.

- **`stado inference routes show --probe-bearer-role` refuses a probe report without aliases** and an answer without an alias; both were skipped, and every alias printed as unprobed although a probe was asked.

- **Cloudflare:** `stado cloudflare route` reports a DNS record whose id Cloudflare did not return as `dns_record_id: null`, not `""`; zone import no longer counts a declared entry as present because an existing record lacks its type, name or content.

- **`stado release catalog adopt` refuses Cargo metadata without the package's name or version**, and the object API origin reader refuses a launchd argument that is not text and a unit declared without a name, instead of reading each as empty text.

- **The disk-cleanup journeys pass on a busy machine:** the janitor skips the build-cache walk above `host.scan_load_ceiling`, and the journeys asserted that walk's reclamation, so the product install gate failed whenever builds raised the load. Each isolated home now declares its own ceiling through `stado config set host.scan_load_ceiling` and records it beside the run's observations.

- **`stado database create --provider supabase` no longer creates a second, billed project:** an answer to `GET /projects` that was not a list read as no projects. It, a key listing that is not a list, a key without its value and a project without its `ref` are now refused; a pooler answered without its user or host leaves `pooler_url` and `session_url` out and the item carries `pooler_unreported`, keeping the generated password.

- **`stado dns delegate` refuses an MX preference or a stated TTL it cannot read** instead of dropping the preference and making the TTL automatic; a TTL the registrar leaves out is still automatic.

- **`stado web route` retract refuses a removal report without its count**, which read as zero and called a removed record unchanged; publish writes the record only with the registrar credential it read.

- **`stado setup` refuses an onboarding transition without a priority**, which ranked as 0 and could decide the next screen.

- **`stado release provenance` reports an artifact line it cannot read** among its unreadable entries instead of dropping the artefact; the Enterprise snapshot answers an upstream failure when the job listing lacks a state instead of showing it empty.

- **Text output names absent fields:** `dns set|remove`, `credentials item put`, `directory report publish`, `web plane list` and `web route publish` print a field their report lacks as `not reported` or `not declared`, not as nothing or zero.

- **The agent Skarbiec repair refuses a host configuration answer it cannot parse** instead of taking it as an unset `agent.skarbiec.url`, reporting `previous: null` and rewriting the setting blind; the Skarbiec bootstrap check compares only release targets that declare a home, and names a policy without targets and a state without a proxy upstream.

- **`stado runner` lifecycle commands judge the command by the status its report states**, and a failure without an error message names the target, the exit code and the command's stderr.

- **`stado storage abort-upload` refuses an upload part without its size**, which counted as zero bytes discarded; `stado quota` escalation lists a ticket row without its action instead of dropping it, and the Azure catalog names a row's missing family or location.

- **Reports no longer turn a missing list into an all-clear:** `host uptime` prints `users: not reported` instead of `none logged in`, `release doctor` prints `blockers not reported` instead of `none`, `route capability` says the host reported no route list instead of `routes: 0`, and `secrets doctor` prints a recipient's missing owner or secret-half flag as `not reported` instead of `no`.

- **A release archive whose size the channel did not state is delivered with its size unknown, not zero:** the size is optional from the published-size read to the host program, which discovers it only when the bound is empty; `stado storage stat` leaves the size out when the answer carried none. Jeden session placement refuses agent capacity publications it cannot read instead of treating every host as silent.

- **A forward marker without an address is refused by its path:** a `~/.stado/forwards/<service>.local` whose first line was empty read as a marker naming the address `""`, and a marker that could not be read read as no marker at all, so `stado ci status` sent its Skarbiec request without asking whether the resolver serves it and `stado route list` showed an open forward to nowhere. An empty marker is now refused as `forward marker <path> names no address on its first line`, and a marker that cannot be read stops a request to the resolver's adapter before it is sent, with the read's own cause.
- **No Skarbiec address is said with its cause:** with neither `WC_SKARBIEC_URL`, `secrets.skarbiec.url` nor a readable `~/.stado/forwards/skarbiec.local`, the address read as `""`, so a client refused it as `invalid Skarbiec URL ""` and `stado ci status` went on to ask an empty endpoint; a marker that could not be read read the same as no marker. The address now keeps why it is absent, and the Skarbiec client and Stado's own vault administration refuse with `this machine has no Skarbiec address: <cause>` — nothing names one, or the marker's own refusal.
- **A reservation renewal says when its holder's publication period could not be read:** the heartbeat re-reads the holding host's capacity publication every round for the period it publishes on, and a publication that could not be read or parsed read the same as one stating no period, so the renewal kept its old period without a word. It now logs `the holder's publication period was not read, so this renewal keeps <period>: <path> could not be read: …` (or `is not a capacity publication: …`) and keeps the last period it read.
- **Vault copy retirement refuses items it cannot compare:** `stado secrets retire` skipped a live copy item without an id and compared an owner item without `updated_at` as older, so it could remove an item it never compared. A copy item without an id or `updated_at`, or a matched owner item without `updated_at`, now refuses the retirement before anything is moved or removed, naming the item, in the dry run and in the verification after the move alike.
- **A failing GPU driver is said, not read as a CPU host or as no cards:** the local agent read any failure of `nvidia-smi` as a host without a GPU and as zero cards. Only a missing program now means there is no NVIDIA driver; any other failure ends the agent's start with its cause, and while the driver read fails at a tick the inference gate holds GPU claims as an unreadable reservation does, publishes `gpu_driver_error`, and clears it after the next successful read.
- **Agent VM ages are read or refused, never zero:** the GCP, Azure and AWS listings of running agent VMs answered an unreadable creation time as age 0, a missing zone as `@zone`, or skipped the instance, which the dead-agent reaper then read as a fresh boot. A VM whose name, id, location or creation time is missing or unreadable now refuses the listing naming the VM.
- **Runner fields a host never printed are null, not `unknown`:** the runner report answered a listener state and a job slot the host did not print as `unknown`; both are now null in JSON, and Stado Desktop's runner summary and Release runner section say `not reported by the host`.
- **A web deploy step that answers no verdict is refused:** the readiness wait and the bearer step took an empty or missing marker verdict as `unknown` and went on; they now refuse with the host named and what was never established.
- **fleet doctor does not pass a host beacon that names no report time:** a beacon without `reported_at` now fails the beacon check naming the missing field, and `stado fleet show` says the member's report time is not known instead of printing `unknown`.
- **A garbled job requirement is a registry doctor finding, not a requirement every host meets:** a published requirement whose trajectory value is not a list of capability ids, or holds a non-text id, read as an empty list; it is now refused by name, and a requirement naming no schema says so.
- **An unreadable capability measurement is reported with its cause:** a `host_capabilities/<host>.json` that was not JSON read as a host nobody measured, one without a capabilities map as measuring nothing, and a capability without a true or false value as measured false. The measurement now carries `unreadable` with the cause, printed by `stado registry doctor` and `stado overview` (`fleet.targets[].measurement.unreadable`). Real journey: `tests/capability/unreadable.rs`.
- **Grant listings that cannot be read are refused:** `stado credentials grant show` read a grant without a capabilities array as one holding none and printed placeholders for a capability without item or action; the vault rebind probe asked Skarbiec about empty words. Both refuse with the row the vault answered.
- **`stado release newest` refuses a run record that names no product, version, run id or commit:** such a record was skipped (its version read as never run) or read with an empty commit (its version read as taken by nobody); it is now refused by its object path. `tests/release/newest/version-taken.mjs` covers it.
- **A host beacon without a units map blocks the fleet claim:** it read as an agent that is loaded; it is now a blocker naming the beacon, and a unit reported without a state is said with its entry.
- **Azure deny assignments Azure did not name or classify are never deleted:** an unnamed assignment addressed the whole collection and a missing `isSystemProtected` read as unprotected; they are now `unreadable` and `protection_unreported`. A refused role assignment carries Azure's own answer instead of an empty code and a sentence Stado wrote.
- **Incomplete host reads are said as incomplete:** a build-cache status line without path or size is a failed scan (the census is no longer called complete), a physical checkpoint inventory entry without a path is refused instead of naming the checkpoint directory itself, a bootstrap install report without its platform and binary lines is refused, and the resources inventory says the host registry was `not read` instead of counting zero hosts.
- **Enrolling a runtime consumer says why its bearer was minted when the recorded grant could not be read** (`recorded_grant_unread` in the step report), and a gui-automation plan whose `bundle` is not text is refused instead of leaving that app's Accessibility grant in place.
- **Fields the source did not report are null or said as such, not empty text:** `stado route list` and `route open`, `stado resolver resolve`, `stado registry host path list`, `stado fleet key ls`, `stado web status` (`unit_reported_at`, `unit_detail`), `stado web origin status` (an unnamed origin's `hostname` and `origin`), `stado storage objects`, `stado credentials apple profile`, `stado credentials token mint`, `stado stream probe`, the runtime repair, `stado registry host add` (a duplicate without a kind), EC2 service errors without a code or message, and the Azure operator session's `client_info`.
- **The agent says why it could not verify an installed release:** reading the managed binary's version now names a spawn failure, a nonzero exit with its stderr, or an answer naming no version, and the `release-marker-unverified` line carries that cause; each failed read while finding the replaced image is a `release-image-unread` line with its cause.
- **A service the directory places on no host is said as that:** `stado service directory endpoint` answers `active_host: null` in JSON and `placed on no host (service_directory names no active_host)` in text, and `show` prints `active_host: none declared`, instead of naming a host `unknown`.
- **A local installation decides which host is this machine from this machine's own registry record:** `stado product install` asked `stado registry self`, which reads the registry from its authority over SSH, to tell whether a receipt's host is this machine, so every installation here stood for the resolver's whole refresh interval whenever the host keeping the registry accepted connections and answered nothing. It now asks `stado registry self --local --json`, which reads the local store or the last-known-good copy and never another host; `--json` answers a machine the record does not carry with `"name": null`, and a machine with no record is refused naming `~/.stado/cache/registry-last-good.json` and what writes it. `tests/install/local_identity.rs` runs it against an authority that never answers and checks the authority was never asked.
- **A superseded run another Stado already removed counts as removed:** every Stado writing under one record directory prunes it, and a command whose pruning lost that race to a concurrent Stado failed with `removing the earlier record …: No such file or directory [not_found]` before doing anything. A run already gone is now the state the removal wanted; every other removal error still refuses naming the run.
- **A worker whose fleet store does not answer at start holds instead of ending the host's one Stado process:** binding the store at start reads the fleet's storage layout from the object API, and a store that did not answer ended the agent with `agent loop failed: Stado object API not asked: …`, which ended `stado serve` with every role it runs — the resolver and each adapter forward of the host with it — and launchd started the process again into the same unanswered store, a restart loop that took the host's Brama and Skarbiec adapters down for as long as the store stood. The store not answering is the condition a tick already skips; the start now logs `the agent did not start: the fleet store did not answer (<cause>); the next poll tries again` and tries again at the declared poll, while every other role keeps serving. Any other start error still ends the agent visibly. Real journey `tests/worker_start/held_store.rs`.
- **Committed lock mismatches are source configuration failures, not credential refusals:** missing path dependencies are diagnosed too, each missing package names its declaring manifest, and the CLI and Desktop preserve Cargo's original failure and evidence location. The real committed-lock journey exports stale and repaired revisions, compiles with Cargo, executes the repaired binary, and keeps unrelated compiler errors distinct.
- **A dependency already named in Cargo.lock can still be unlocked:** installation diagnostics compare Cargo's declared semantic-version requirements with every locked version of the package. An incompatible requirement is a source configuration failure naming the committed revision, declaring manifest, requirement and observed locked versions; CLI and Desktop retain the same refusal. The real committed-source journey covers the stale version, corrected executable and unchanged exported lock.
- **Source installations keep Cargo dependencies between runs:** the exact committed lockfiles select a persistent cache with separate source and target trees per platform, revision and recipe. Both Cargo target and intermediate directories point there, and the declared compiler cache shares matching outputs between revisions. Dependencies already installed at the required revision are verified and reused rather than rebuilt; an incomplete or changed installation still prepares its recipe. CLI receipts and Stado Desktop Products show each product's build/reuse reason and cache identity, and retained build-step evidence records the compiler output.
- **Reusing an installation cache restores committed node types without following build-created links:** a cached file or directory replaced by a symlink is restored without modifying the link target. A cache source root that is itself a symlink is refused with its path before any source refresh. The real repeat-install journey covers restoration and preserves the existing receipt when that root is refused; CLI and Desktop retain the same diagnostic.

- **An installation whose committed manifest its own Cargo.lock does not cover names the revision, the manifest and the dependencies:** a build step's `cargo build --locked` refused such a tree and Stado passed the failure on as `the command failed and we could not attribute the failure — your request or credentials [unknown]`, so a dependency committed without its lock was chased as a credential problem or another session's working-tree edit. A failed build step is now read against the tree it built — each workspace's declared dependencies (`cargo metadata --no-deps`) against the packages its committed `Cargo.lock` names — and a dependency the lock lacks is refused as the committed source's fault: `<product> at <revision>: <manifest> declares <dependencies> that its committed <lock> does not lock, so cargo build --locked refuses this revision; commit <lock> updated for <manifest> (cargo update -w --manifest-path <manifest>) in <product> and install again. The build said: …`, exit class `refused`. The workspace finder is one function (`stado_product::cargo_lock::workspaces`) for this reading and `stado quality check`.
- **A resolver whose registry store does not answer at start serves the last-known-good registry instead of standing in `starting`:** this host's registry store is read through the object API and Skarbiec, whose adapters this same resolver relays only once it serves, so the first store read stood behind the resolver itself — `starting: reading this host's registry store before binding any port` — and every consumer on the host, `stado ci status` among them, stood with it. The read is now given the refresh interval the last-known-good registry declares for this target; past it the resolver says `stado resolver recovery: registry authority failed (this host's registry store did not answer within the <N>s refresh interval …); bootstrapping routing from the last-known-good registry`, serves that copy, binds, and the refresh loop reads the store again.
- **`stado ci status` refuses naming Skarbiec instead of standing behind a resolver that does not serve it:** reading which vault item holds the forge identity, `ci status` posted to Skarbiec's adapter on this host directly, past the held-route checks every other Skarbiec request makes, and a resolver still reading its registry holds that port without relaying — the command stood for minutes with only its `czekam` line. The GitHub route resolve now refuses before sending, `Skarbiec was not asked <endpoint> for the GitHub route "<route>": this host's resolver (pid <pid>, state starting at <time>) holds no listener: <reason>` when the address is the resolver's own Skarbiec adapter and the resolver does not serve it, or with the held wait's sentence when the adapter stands held; a request already sent is abandoned once the resolver publishes the adapter held.
- **`stado release newest` no longer calls new source under a spent version "already published":** a run that published a version from one commit settled that version for every later commit of the checkout, so a product that moved on by a hundred and more commits without changing its declared version was listed as `<version> is already published by run …`, and nothing asked for the version its fixes needed — none of them could reach a release. A published run now settles only the commit it published; any other commit under that version stands as taken, and the plan names the least version it needs, the versioning rule's step for an internal change: `… <commit> is new source under it, so it needs at least <next>, the versioning rule's step for an internal change (a change to its surface takes what \`stado release gate decide\` answers) before it can be released` (`next`, or `unadvanceable` with the rule's refusal, in `--json`).
- **A request already sent through a held adapter is abandoned on the interval its resolver publishes:** the readers that measure a held wait (`held_at`, `held_on_host`, the in-flight abandonment behind `stado registry pull` and every object API request) took the refresh interval from the last-known-good registry copy under the target the resolver's state names, and a copy not written yet, or one that could not be read, answered nothing in silence — a request already up a held adapter's channel was then waited on with no bound at all, for over an hour. The resolver now publishes the interval it runs on in `~/.stado/resolver-state.json` (`refresh_seconds`, on `serving` and `backing_off`), and those readers take it from there: the process that holds the waits names the measure they are held by.
- **An SSH destination with an unbracketed port names the grammar instead of calling itself an IPv6 address:** `127.0.0.1:2222` was refused as `invalid SSH IPv6 destination`; it is now refused as `invalid SSH destination <destination>: <host> is no IPv6 address; a destination names a port as user@[host]:port`. The held-resolver journeys write their loopback authority as `[host]:port` and read the relay line with the request line it now names.

- **The object-API recovery's readers and the storage-root transaction's host steps are object verbs too:** `host local api plist render|equal`, `boundary ready` and `skarbiec plan|ownership|upstream|proxy` replace the derived `render-plist`, `plist-equal`, `boundary-ready`, `skarbiec-plan`, `skarbiec-ownership`, `skarbiec-upstream` and `skarbiec-proxy-match`; `host local reconcile step unit snapshot|restore`, `listener closed`, `object runtime` and `store served` replace `unit-snapshot`, `restore-unit`, `listener-closed`, `object-runtime` and `served-store`. `deploy/recover_object_api/*.sh` and the transaction's step scripts call the new names.
