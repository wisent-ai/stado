# Changelog

Entries for the release being prepared live here. Released entries move into
`changelog/`, one file per version range, so the active file remains within
the repository's file-size limit.

The version-bump commit moves them with `stado product changelog --version V`;
`stado build submit` refuses a revision whose Unreleased section still holds entries.

## Unreleased

- **A build's disk record states its numbers instead of calling a failure "ran out of disk" below 256 MiB (fab304dc):** `DISK_EXHAUSTED_BELOW_BYTES` and `ScratchReceipt::exhausted_disk` are gone. A failed build's receipt says `the build tree held <n> GiB and its volume had <m> GiB free`, without `(ran out of disk)`/`(had room)`, and a builder refused for room names the last failed build as `at least <n> GiB on <builder> before failing with <m> GiB free`; the build's own error beside it says whether the disk was why.
- **`stado host reclaim` finds a build tool's `CACHEDIR.TAG` at any depth of a declared root (fab304dc):** the six-level `BUILD_CACHE_DEPTH` is gone. The `tagged_build_caches` stage walks the whole root; `find` follows no symlink, a tag nested in a cache already taken is gone when it is reached, and the argv and lsof guards still keep a build in flight untouched. A `target/` seven levels down is no longer left behind.
- **The failure fixer and the coverage orchestrator retry on what happened, not up to a count (fab304dc):** `FAILURE_FIXER_ATTEMPT_CAP` (3) and `COVERAGE_ATTEMPT_CAP` (5) are gone, and so is the `exhausted` status. The failure fixer dispatches one Claude Code session per failure: a job whose state records the same `failed_at` answers `already_dispatched` with that `failed_at`, and only a later failure of the job earns another session. A coverage group_key is UNFIXABLE once two different failed jobs of it gave the same error (`repeated_error` in its state, set when the failed/ index is correlated); a gap that keeps failing in new ways is submitted again. The unused `coverage::record_failure` is removed.
- **A release whose build failed ends on the build's own failure, and a pass that finds builds still running leaves the run waiting:** the release agent's pass rebuilt a platform whose job had run and failed, then tried to publish the replacement while it was still queued and recorded `release job … is still queued (queued) on <host>; no host has claimed it` as the platform's failure, so skarbiec 0.4.14's `cargo fmt -- --check` failure appeared nowhere in `stado release status`. The agent no longer rebuilds a platform whose job ran and failed (a cancelled job, which never ran, is still rebuilt); the run fails with `<platform>: build job <job> ended failed` followed by the job's last lines and `stado release resume <run> builds it again`. `stado release resume`, `stado release submit` of the same source and `stado build` still build a failed platform again. A pass that finds a required platform still queued or building prints `builds still queued or running` and leaves the run waiting instead of publishing.
- **Grants Stado issues live until revoked, and a re-issue keeps the lifetime the vault records (fab304dc; needs Skarbiec 0.4.15 on the host that holds the vault):** the 30-day `GRANT_TTL_SECONDS` of `stado web deploy` and of the agent, the agent's 10-day renewal window and 600-second check, the 30-day `--ttl-seconds` default of `stado service grants` and `service grant-sync`, the one-year default of `stado credentials token mint` and the ten-year model-review and Brama-introspection lifetimes are gone. Each of those grants was re-issued with the bearer it already held, so its end was only ever pushed forward and protected nothing a revocation does not, while a missed renewal was an outage. They are now issued `--until-revoked`; `--ttl-seconds` stays available on `service grants`, `service grant-sync` and `credentials token mint` for a grant that is meant to end. `stado web remove` revokes the product's consumer grant after its unit stops (`grant: {consumer, change: revoked}` in the report; a failed revoke says `the unit is stopped but the Skarbiec grant of consumer <c> was not revoked: …; run stado web remove again to finish`). The agent re-issues a grant the vault still records with an end once, until revoked, then stops looking for the life of the process, and logs a failing look once until its sentence changes. Widening a grant (`credentials grant role-read`, declared reads), `host secrets vault rebind` and `consolidate` keep the grant's lifetime, until revoked included; before this a grant stored with no end (`expires_at` 18446744073709551615) was refused as `carries no expiry` by the widening path. `stado credentials` store's request-only mint, which passed no lifetime and was refused by Skarbiec, now issues until revoked.
- **The Hugging Face staging flush runs when the previous one ended, held only by Hugging Face's own `Retry-After` (fab304dc):** `FLEET_FLUSH_INTERVAL_S` (180 s) is gone. An idle agent starts a flush on any tick where none is running (the existing PID lock keeps it single-flight), so staged rows go up one commit per finished flush. A flush Hugging Face refuses with `Retry-After` records the moment it named in `<staging>.async_flushes/.not_before`, and the agent logs `fleet staging flush held: Hugging Face answered Retry-After until <epoch seconds>` and starts none before it. The tick no longer logs `optional Hugging Face staging flush running asynchronously` each time; the start of a flush is still logged with its pid and directory.
- **`stado service logs` and `stado host unit-log` return the lines asked for, with no 4 MiB cut first (fab304dc):** `LOG_WINDOW_BYTES` is gone. A launchd unit's stdout and stderr tails are read with `tail -n` from the end of each file, so the `--lines` the reader states are the whole window; a log whose last lines are longer than 4 MiB together is no longer returned short of the lines requested.
- **`stado web deploy` waits for the unit, not for twenty tries three seconds apart (fab304dc):** the readiness probe's 20 attempts, 3-second gap and 5-second per-request cap are gone. The probe asks the unit's `readyz` path from the host one request after another until it answers 200, and after every request reads the supervisor's record of the unit (launchd `pid`/`runs`/`last exit code`, systemd `MainPID`/`NRestarts`/`ExecMainStatus`); a unit whose process exited, was started again or was unloaded is refused at once with `pid <pid> ended without answering 200 (last exit code <code>; runs <before> -> <after>; now <pid>) after <n> attempt(s); the last probe: …`. A slow cold start is no longer reported as a failed deploy, and a crashing one is reported on its first crash instead of after a minute.
- **A finished job is still answered after its run is reaped (78d38b42):** reaping a fully terminal run retains each job as it ended in `runs/<run>.json` and deletes the job's documents and log, after which `stado machine status` answered `job … was not found`. It now reads the job back from the run's retained outcome, stamped with the terminal prefix it ended in, and `stado machine logs` refuses with `LOG_REAPED` (`the command log of <job> was deleted when its run was reaped; the run manifest retains the job as it ended …`) instead of returning an empty log; artifacts and every other reader that looks a job up by id get the same retained job.
- **DNS records carry the TTL and MX preference somebody stated (fab304dc):** the 1800-second default TTL and the MX preference 10 are gone from `stado dns` and `stado web route`. `stado dns set --ttl` is optional: without it a record keeps the TTL its zone already states, and a new record is written with none so the registrar applies its own default; a record's MX preference is carried as the zone states it. A zone row the registrar answers without a TTL or preference is written back without one rather than with an invented value. `web route` publishes its A record the same way and its plan no longer reports a `ttl`.
- **The scheduler packs local jobs against what each agent admits, not against its own 8 GB guess (fab304dc):** `LOCAL_ADMISSION_BUFFER_GB` (8) is gone. Every agent publishes the VRAM safety buffer its claim rule uses as `diag.vram_safety_buffer_gb` in its capacity row, and the local pack yields a job only into an agent's free VRAM less that agent's own buffer. A row that states no buffer (an agent older than this) is not packed onto, because its admission rule is not stated. The scheduler log says `Live local-agent claimable VRAM (free less each agent's own safety buffer): …`.
- **The agent re-asserts its host's declarations every tick, and the spawn watch takes the length and gap it is given (fab304dc):** the 300-second GPU power-limit and placement-policy reconcile intervals are gone; both are re-asserted at the agent's declared poll, so a drifted power cap or policy file is corrected within one poll. `stado service watch-spawn` no longer refuses a `--seconds` above 3600 or an `--interval-ms` outside 200–10000; it refuses only 0 (`watch length must be a positive number of seconds; 0 watches nothing`, `sample interval must be a positive number of milliseconds; 0 samples nothing`).
- **Coverage verification runs as wide as the machine and lets the server set the pace (fab304dc):** `COVERAGE_VERIFY_THREADS` (4, chosen to stay under a remembered Hugging Face limit) and `COVERAGE_PROGRESS_LOG_EVERY` (200) are gone. `stado coverage` verifies and scans failed commands at the operating system's parallelism; a HEAD answered 429 with a `Retry-After` (seconds or an HTTP date) is waited out and asked again, and a 429 that states no wait still fails with its status. The walk logs one `[<universe>] N/N verified` line when it has classified every entry.
- **No failure-fixer cadence or selector is written into Stado (fab304dc):** `FAILURE_FIXER_TICK_SECONDS` (180) and `FAILURE_FIXER_COMMAND_PATTERN` are gone. They only filled the argv of a legacy failure-fixer unit plan that is never installed; a captured unit is folded into the host process with its own `sleep` as `--failure-fixer-interval-seconds` and its own `--command-pattern`, and the plan now names only the program it is compared against.
- **The claim walk lists what it can still use, and every queue read fans out as wide as the machine (fab304dc):** the 256-name `MARKER_PAGE` is gone; each page of the priority index asks for as many names as the scan still wants or may still download, whichever is fewer, and an unbounded scan takes the backend's own pages. The remaining fixed fan-outs — 10 marker and job reads per page and per listing, 32 in the oldest-first scan, makespan's agent reads and sizing's history reads, 16 makespan writes, 8 release-run report reads — now use the parallelism the operating system reports, like the bulk copies. The activation-manifest refusal names every benchmark missing target metadata instead of the first ten.
- **A shut API boundary is revalidated one sweep at a time, not once per 30 seconds (fab304dc):** the 30-second recheck cooldown and its `WC_DASHBOARD_BOUNDARY_RECHECK_SECONDS` override are gone. A request that finds a boundary closed revalidates it inline unless another request's revalidation is already running, in which case it is refused at once; a request whose client goes away mid-sweep frees the claim, so a closed boundary is retried by the very next request after a failed sweep instead of half a minute later.
