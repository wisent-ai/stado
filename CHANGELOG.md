## Unreleased

### Fixed

- **Product sync outlives a stopped role, so a broken release can still be replaced on its own host:** `stado serve` ended whenever any role stopped, so a release whose resolver refused to start stopped the whole process within seconds of every restart, product sync with it, and the host never installed the repair of the release it ran. Product sync is now the process's delivery role: it starts before every other role, and when another role stops, or startup cannot finish, the process writes `stado serve pid=<pid> failed: <the stop>; it keeps product-sync running so a release that replaces this one can still be installed` and keeps syncing at its cadence (a configuration failure still rolls back to the previous release first, as below). After each pass the role compares the program the process runs with what it started as; once a release was installed over it, the role ends with `product sync installed a new release over <program>, the program this process runs; the service ends so its init system starts the installed release`, and the process with it. The real test is `tests/delivery/broken_resolver.rs`, which holds the resolver's API bind so the real resolver fails.

- **The target's SSH identity is attached without judging the program by its name:** `add_identity` refused any invocation whose first word was not one of two program names, though every caller builds its own OpenSSH client invocation; it now puts `-i <key> -o IdentitiesOnly=yes` after the program word and refuses only an empty invocation (`SSH identity cannot be attached to an empty invocation: no program was given`).

- **A delivered Stado that refuses this host's configuration puts the previous release back:** a release whose resolver refused the configuration the release before it served crash-looped under launchd for a day, taking Brama, Skarbiec and the object API with it, and nothing stopped it. When a `stado serve` component stops with a configuration failure, the release now records itself as failed on this host (`~/.stado/releases/stado/<version>/<platform>/failed-on-this-host.json`), reinstalls the release that ran before it through the `release local restore --previous` install, and ends so the init system starts that one. A release recorded as failed is refused by every later install on this host (`Stado <version> failed on this host and is not installed here again: …`), so product sync cannot reinstall it and two failing releases do not restore each other in turn.

- **`stado space reclaim` keeps the release a host can roll back to:** the `delivery_leftovers` stage pinned only the installed version and the newest one, which on a host that just received a release are the same, so it took the previous version's retained archive while `~/.stado/bin/stado.previous` still held that binary. When the new release then refused to serve, `stado release local restore --version <previous>` found no archive to reinstall: only the broken release's tree was left. The version whose attestation copy is byte-identical to `<product>.previous` is now pinned beside the installed one, so the restore always has its archive.

- **`stado quality check` fetches Git dependencies with the `git` program and tells a fetch failure from a lock that does not resolve:** the lock gate ran one `cargo metadata --locked`, whose built-in Git transport carries no credentials, so a repository naming a private `wisent-ai` Git dependency (brama's `wisent-onboarding-client` from echo-web) was refused at every push with `failed to authenticate when downloading repository`, labelled `an explicit policy refused this command`. The gate now runs `cargo fetch` with `net.git-fetch-with-cli`, which reaches the repository with the credentials the push itself uses, puts the committed `Cargo.lock` back byte for byte, and asks it with `cargo metadata --locked --offline`. A failed fetch is reported as `cargo fetch --manifest-path Cargo.toml failed … so whether its Cargo.lock resolves was not asked: <cause>`, a general failure and not a refusal; only the second step refuses, as `the committed Cargo.lock does not resolve its manifest`. The real test is `tests/quality/lock_steps.rs`: a current lock with a fetchable Git dependency passes, a stale lock is refused as a lock, and a dependency whose origin is gone is a fetch failure.

- **A replace rollout that fails readiness records what the unit wrote while the gate waited:** the failure was `readiness timed out after <n>s: <url> never answered; rolled back to <previous>` and nothing more, while the unit's own account of why it never bound sat in its log on the host. The gate now reads the unit's log whole before the restart and again after the failure, and the run's failure carries the lines the second read holds beyond the first — `<unit> wrote to <file> in the readiness window:` and those lines, or `wrote nothing` — with stderr as its own section where launchd keeps it apart; no line count is chosen, a log rotated between the reads is reported whole, and a log that cannot be read names which read failed instead of stopping the release. `stado release status` prints it under the platform.

- **`stado release logs` reads a replace-strategy product's logs from its managed unit:** the command read `<logs_root>/<product>-<version>.{out,err}`, the files the release agent gives a blue-green candidate, for every product, and answered `no such file` for a product the policy rolls out by restarting a managed unit in place (weles-worker), which never runs as a separate candidate and writes to the unit's own `StandardOutPath`/`StandardErrorPath`; `stado release doctor` pointed at that empty read while the readiness failure's cause sat in the unit's stderr. For a `replace` policy the command now reads the unit the policy names (`service`) on the target, with the read `stado service logs` makes, whole or `--lines N` from the tail, honouring `--stream`; `--head` is refused by name for such a product. The real test is `tests/release/unit-logs.mjs`.

- **`stado release status` prints a platform's failure whole:** a failed platform's failure field carries the job's last output lines (the worker's step names and what the step printed), and the line register printed only the failure's first line, which ends at `the job's last output:` with nothing under it, so the reader went to `stado build status` for text the register already held. The line register now prints every line of a platform's and a run's failure, indented under its line, the same text `--json` carries in `platforms.<platform>.failure`. The real test is `tests/build_status/failure_lines.rs`, against a declared run of the real queue.

- **A job requeued while its worker still runs it is taken back, not started a second time:** when a running job's lease lapsed under a live process, the reaper put it back in the queue and the same worker claimed it again and started a second process in the same work directory beside the first, so one scheduled routine ran twice at once and the schedule's skip policy could not prevent it. On the slot's next tick, a lease renewal that finds no running document now looks for the job in `queue/` and moves the record back to `running/` as the attempt already under way (same `started_at`, a fresh lease its heartbeat renews), whatever the host's admission gates decide, and logs `<job>: already running here as process group <pid> for <n> s: … the running process took the job back and no second process was started`; if another worker or a cancellation took the record first, it says so and still starts nothing. The claim scan never starts a queued job one of its own slots runs. The coordinator's skip line now says what the prior fire is doing: `schedule <id>: skip fire: prior job <job> is still running, started <time> (<n> s ago), worker lease until <time>, on local@<host>`, with `put back after: worker lease expired` when it was requeued. Real test: `tests/scheduler/readopt.rs` (`scheduler-requeued-readopt`).

- **A worker's lease promise follows its newest renewal, not the longest it ever measured:** the promise written into each running job was the poll period plus the longest lateness the worker process had ever measured, so one renewal a store held for hours made every later lease of that process promise hours ahead. When such a worker died, its jobs stayed `running` with no process until that far-off time, and every schedule whose skip policy waited on one of them stopped firing — a routine scheduled every minute last ran four hours earlier, its job's `lease_expires_at` nineteen hours ahead. The promise is now the poll period plus the lateness and write time of the newest renewal; a lease that lapses under a live process after one late renewal is taken back by its slot, never run twice.

- **A worker that starts settles the running jobs the worker it replaced left behind:** a job whose worker process ended (a crash, a reinstall) stayed `running` until that worker's lease promise passed, holding every schedule whose skip policy waited on it. A worker now reads, before its first tick, every running job whose record names this host's worker; one whose work directory no process holds open (`lsof`) is settled as a lapsed lease is — requeued with `its worker was replaced while it ran`, failed on the same loss again, completed when its release output verifies — and logged as `init: <job>: requeued (…)`; one a process still runs keeps its lease, logged as `init: <job>: left by the worker this one replaced, but still run here by pid <pid>; it keeps its lease`. The settlement is the reaper's own (`queue::reaper::release_left_behind`). Real test: `tests/scheduler/restart.rs` (`scheduler-replaced-worker`).

- **A host's scans of its own disk are incremental, run in the background band, and are skipped above a load ceiling the beacon publishes:** the installed host process read launchd's event log (`log show --last 1h`, seconds each) for every declared unit on every health pass, and its janitor listed every directory under the home and measured every tagged cache on every pass under disk pressure, at the operator's own priority, on a workstation already loaded by the agents working on it. The beacon's health pass now reads a unit's event log only when the unit is not as it was at the previous read (pid, launchd run count or state) and carries the previous read otherwise, saying so in the unit's `events` field; the janitor keeps the child directories of every directory it examined and the bytes of every tagged cache, keyed by device, inode and modification time (`~/.cache/wisent-compute/build-caches.json`), lists only directories whose identity changed (`listing_remembered`, `measurement_remembered` in the cleaner's `skipped` map) and rewrites the memory only when it learned or forgot something; the walk's thread takes the background band (`PRIO_DARWIN_BG` on macOS, `PRIO_MAX` nice on Linux) and every `find`, `du` and `log show` a host script runs is prefixed with `taskpolicy -b` or `ionice -c idle nice`. Every such scan (`unit_events`, `build_caches`, `disk_inventory`) is admitted only while the one-minute load average is under `host.scan_load_ceiling` (`WC_HOST_SCAN_LOAD_CEILING`; the logical core count this process measures when nothing is declared), and a skipped scan is published in the beacon's `scans` block (`last` reading, `skipped` per scan with `since` and `latest`) and shown by `stado host health` and `stado host link` as `scans: load … against ceiling … (…); <scan> skipped since …`; `host link --json` carries the block as `scans`, and Stado Desktop's Hosts inspector shows it as **Disk scans**, a standing skip as a warning. A space report on its own host answers `inventory_incomplete: inventory walk skipped: …` above the ceiling. Real test: `tests/host_health/scans.rs` runs the real host process on a one-second cadence, reads the carry on the second beacon, declares the ceiling as the lowest load a host can be above and reads the skip on the next.

- **An upload the network ends is the transport's failure, worth retrying, and names the chunk it was sending:** a connection the object API's side reset while a chunk's body was still being sent (`connection reset by peer`, `broken pipe`, a stream that ended early) reached the operator as `your request or credentials [unknown]; retrying will not help`, because the HTTP error carried a code only for a refused connection or an elapsed deadline, and the chunk upload threw the error away without saying which piece of which upload it was. Every HTTP failure now states its code from its cause chain: an elapsed deadline or an `ETIMEDOUT` is `timeout`, an operating-system failure anywhere in the chain or a request or body the peer ended is `infra_down` (`our failure`, exit `69`, `retry later`); a chunk the transport ended is reported as `object chunk PUT <index> of <count> (<bytes> bytes at offset <offset>) for upload <id> of <uri>: <cause>`. Real test: `tests/storage/transport_fault.rs` (in the `tests/storage/vault_consultation` package) drives the real `stado storage put` at a loopback listener that resets every connection after its request line.

- **A vault older than item revisions no longer closes the object API:** once the control host's vault answered reads again, every object request was still answered `503 object authorization unavailable`, because the vault's answers carry no `item`, `item_uid` or `revision` and the verifier refused such an answer outright (`the vault's answer names no item version …; update Skarbiec on the vault host`) — while the newer Skarbiec that would carry revisions is delivered to that host through the same object API, so the refusal locked out its own repair. A single-field answer with no version now reads as a store without versions: the bearer is read on every check (the vault consultation keeps that to one decryption per namespace at a time, refusing the requests that would queue behind it), and the client says once on stderr which vault to update. `/v1/items/revision` answering without a version is read the same way.

- **`stado-wait` is its own crate, and the product and database crates wait through it too:** the wait mechanism lived inside the `stado` crate, so `stado-product` and `stado-database`, which `stado` depends on, could not use it, and every child process, lock, HTTP request and database statement they wait on (`stado database resolve` as a child of a product, `cargo`/`git`/`codesign`/`npm`/`psql`/`supabase` in release steps, the installation lock, GitHub and provider APIs) waited without a word. `stado-rs/wait` is now a workspace crate, re-exported as `stado::wait`, which any Wisent product depends on without linking the control plane. It adds `request_blocking` for a blocking HTTP client. `stado_database::connect` names the database and its credential item while it connects, and the synchronous client names each statement, transaction step and SeaORM work it waits on; `psql` is named by the statement or file it runs, never by its command line, which carries the database URL. The remaining TCP connects (resolver probes and proxy, service verification, the edge check, reverse forwards, the release proxy, the placement doctor), the storage-root launch lock and the attached, console, slot and ingress child waits go through it as well.

- **Every registry read of a store that is an object API takes the registry authority's snapshot over SSH, in one place:** `stado database resolve`, `service directory connect`, `registry self`, `storage` and every other command that opens the registry read it from the fleet's object API first, and that API authorizes each read against the vault on its host, so a vault that stopped answering held every one of them for hours; only host commands and directory reads had been given the authority's snapshot, each in its own prelude. `RegistryStore` now reads the service directory's registry authority's `stado resolver snapshot` over native SSH (located through this host's last-known-good copy) before its store whenever that store is an object API and this host is not the authority, so `fetch_registry_remote`, `fetch_document`, `read_local_document` and everything above them go that way through one chokepoint; the two preludes are gone. A snapshot that cannot be read is said on stderr with the authority's own sentence and the store is read, which the store read's own `czekam` line then names. Real test: `tests/service_directory/authority_read/` (its own package; a real dedicated authority over SSH, a store that never answers and receives no connection).

- **A request that would stand behind the vault is refused with the server's wait line, never held:** the object API compared every bearer against Skarbiec, and while a process kept the vault's key database lock each read waited until gpg gave up — tens of minutes — while every other request queued behind it on the listener's own lock and then paid the same wait, so the fleet store answered nothing for hours. Every bearer read (a namespace bearer's version and the bearer itself, the release publisher's, the host-health role's, the service and machine clients') is now one vault consultation under its key: a namespace bearer read holds its namespace, a request that finds its key held is answered `503 {"error":"object authorization unavailable","cause":"czekam: …"}` at once with that read's own `czekam` line, and after a failed read every request under the key is refused with its `blad czekania` line except the one that reads again. A closed boundary's `503` carries the boundary's verifier sentence the same way, and `/api/state.json` shows each key's open and failed line under `vault.consultations`. When a vault answer names the process holding the keyring lock (`waiting for lock (held by <pid>)`, `<lock> is held by pid <pid>`), the vault host's object API runs the declared `skarbiec` `crypto` repair once for that holder in the background and reports it under `vault.keyring_lock_repair`; `stado doctor`'s gateway-auth row names the holder and the repair. The repair payload (`stado repair skarbiec --step crypto`) now admits a held keyring lock as a ground and runs Skarbiec's own `skarbiec recover-daemons`, which releases such a lock, instead of killing daemons itself. `stado host exec <host> -- skarbiec doctor` and `-- skarbiec recover-daemons` are approved host-exec commands. Real tests: `tests/storage/vault_consultation/` (a real Skarbiec on a keyring whose lock the test really holds) and `tests/host_exec/skarbiec_entries.rs`.

- **A release whose build job was cancelled and reaped is finished, not waited on forever:** the release agent's pass, publishing and a delivery's verdict read a build job as ended only from its terminal queue record or its receipt; a cancelled job leaves no receipt, and once the run reaper retired its record the agent answered "has not reached a terminal state, and left no receipt" on every tick while `stado release status` reported the leg lost. Every reader of an ended release job now comes to one read (`builds::jobs::terminal::settled`): the terminal record, the receipt, the outcome the reaper retained in the job's run manifest (through the `runs/jobs/<job>` index), then the job's transition record. The platform reads `failed` with `build job <job> ended cancelled` and the job's recorded error, a required one fails the run, and the agent finishes it. A job in none of those places is refused as `release job <job> has not reached a terminal state: no queue record, no receipt, no reaped run retains it and no transition record names how it ended`. The delivery pass's own walk of derived submission ids, which patched the same gap for deliveries only, is retired. Real test: `tests/build_status/` against a declared run of the real queue.

- **`stado status` finds a job by the start of its id and after the reaper, and refuses an id no job holds:** `stado status fc781ff7` printed an empty table and `stado status job-<whole id>` printed `(no job …)` with exit 0, because the start of an id went through the queue scan only and a missing id was a row, not a refusal. A whole id is read under every lifecycle prefix and then from its run's retained outcome; the first hex characters of an id, with or without `job-`, list every job they begin in the queue and, through the index the reaper writes under `runs/jobs/<job>`, among the reaped (`queue::runs::retained_jobs_with_prefix`); a row read from a retained outcome carries `(reaped)`. An id or start no job holds is refused: `no job with id <id> in the queue or in any run's retained outcomes; stado status lists the jobs the queue holds`, stated `not_found`. `--json` prints the rows as each job's record with `state` and `reaped`, and Stado Desktop's Queue screen reads one job by its id through it (**Read one job by its id, including a job the run reaper has retired**). Real test: `tests/status/by_id.rs` on an isolated local queue.

- **A reaped job retained before the run index existed is indexed by the read that found it:** `stado machine status` of such a job read every run manifest until the one that names it, and read them all again on every later ask, because the run reaper never revisits a run whose cleanup completed and so never wrote its `runs/jobs/<job>` entry. The reader that had to walk the runs now writes that entry (create-only), so the next read opens one manifest. Real test: `tests/machine/reaped_read.rs` counts the manifest locks a read takes from the `czekam` lines on stderr: one for an indexed job, several for an unindexed one, one again after it.

- **A request through an adapter the resolver already holds is refused, not joined:** the resolver published only the channel opens still waiting for the destination host, so a channel that opened at once and then carried a request the service never answered — the object API on a host whose Skarbiec stopped answering — showed in no list while `stado service directory connect`, the registry read behind every command and Oko's control pass stood on it for hours. The resolver now records every relayed connection from the client's first byte up the channel until the service's first byte back (`phase: answer` beside `phase: open` in `~/.stado/resolver-waiting.json`, each with the adapter's `bind`), says so in its log (`request sent to <endpoint> on <host>; N open(s) now waiting for an answer`), and `stado resolver status` lists both phases under `waiting_opens` and names one held longer than the declared refresh interval as a blocker (`… has waited Ns for the first byte of an answer on an open channel to <endpoint> on <host> …`). Every object API request, every Skarbiec request and the probe of `stado service directory connect` ask the resolver's published list before sending: one going to an adapter held longer than the refresh interval is refused at once with the held connection's own sentence (`Stado object API not asked: GET <url> not sent: this host's resolver holds N connection(s) on that adapter unanswered longer than the <N>s refresh interval it declares …`, `Skarbiec not asked: …`, `<service> is placed on <host> and did not answer at <url>: this host's resolver holds …`), exit code of a store that does not answer, so a caller learns in a second what it would otherwise have learned never. A published list that cannot be read is the refusal, naming the file.

- **No Stado command waits without saying on what:** `stado release status`, `release resume`, `release changes submit|list`, `build submit`, `storage ls`, `service directory connect` and every other command reading or writing the fleet store sat silent while one request went unanswered, and the local agent's tick, heartbeat and routines stopped for hours with nothing in the log. Every object API request (both clients of the store) and every wait on a local-store lock now goes through one module, `stado::wait`, which writes on stderr before it waits `czekam: <what>; gdzie: <where>; rodzaj: <kind>; od: <UTC time>; id: <pid>-<n>`, then `koniec czekania: <what>; trwalo: <seconds>s; id: …` or `blad czekania: <what>; gdzie: <where>; trwalo: <seconds>s; przyczyna: <cause>; id: …`. An object request reads as `GET /api/object uri=stado://…` at `object API <store origin>`, so a gateway that never answers is named with the address it waits on and since when; `build submit` names its `git archive` and manifest reads the same way. Nothing limits how long a wait takes. The `[release status] …: started` / `took <n>s` phase lines and their helper are gone: the waits under them now say this themselves. Stdout, and with it `--json`, is unchanged; the line format is documented on the Machine Interface page. `release changes list` compiles again: its status list had lost its declaration.

- **The object API says what a request it holds is waiting on:** on a host whose Skarbiec stops answering, the object API opened every client's channel and answered none of its requests for hours, because each request asks Skarbiec for its namespace bearer's revision and a closed boundary is revalidated against Skarbiec inline, both without a word. Every Skarbiec request Stado makes (item read, field read, list, revision, rotation) and every boundary verifier validation now goes through `stado::wait`, so the server's log names the Skarbiec request or the boundary (`validate the object boundary's verifier`) a held request stands on and since when.

- **Host commands and directory reads resolve the registry while the vault host's Skarbiec is stuck:** a machine whose registry store is another host's object API read the registry through that API, and the API checks every object request against Skarbiec, so a Skarbiec that never answered held every `stado host …` command, `stado repair … --target` and service directory read with no answer, including the repairs of that Skarbiec. These readers now take the registry first from the service directory's registry authority over SSH (`stado resolver snapshot`, the read the resolver keeps its directory with, located through this host's last-known-good copy), then from the store, then from the last-known-good copy. A failed authority read is said on stderr (`the registry authority's snapshot could not be read (…); reading the registry store instead`). Registry writes still go through the store.

- **Stado calls Skarbiec's groups:** `stado host secrets vault push|pull` runs `skarbiec mirror push|pull`, and the agent's grant gate reads `skarbiec bond status`, instead of `sync-push`, `sync-pull` and `sync-status`, which Skarbiec withdrew. A host whose installed Skarbiec predates the groups answers these with Skarbiec's unknown-command refusal until its Skarbiec is delivered.

- **`stado release submit --commit` takes the abbreviated id `git log --oneline` prints:** it refused anything but 40 hexadecimal characters (`--commit must be 40 lowercase hexadecimal characters`), so the short id an operator or agent copies from `git log` sent them back to look up the full one. Git now resolves the id in the `--source` checkout: a full id or an abbreviation of exactly one commit becomes the full commit id; an abbreviation that matches nothing or several objects, or names something that is not a commit, is refused as `--commit <id> names no single commit in <checkout>: <Git's reason>`, and an id that is not lowercase hexadecimal is refused as before.

- **A new build sheds the run it keeps:** a build run keeps the previous attempt to measure the next one's free space, and a run an older Stado left whole kept its source export and build output until two more builds replaced it. The previous attempt now keeps only its files and the size it recorded; the free-space check reads that size.

- **An installation writes no rebuildable tree into its checkout:** the checkouts sit in `~/Documents`, which macOS keeps from the janitor, so every install run (`.wisent-output/install`, `local-install`, `cargo-install`), a local build's isolated home, a package install's scratch, the source snapshot's private index and a desktop product's SwiftPM `.build` grew there with no pass able to reclaim them. Each now lives in the checkout's build area under Stado's home, `~/.stado/products/builds/<the checkout's path below the home>`, and a run is tagged with `CACHEDIR.TAG` once it is shed, so the janitor's build-cache cleaner takes it under disk pressure; a run still being written carries no tag and is never taken. A desktop build moves the kept `.build` back into the checkout (its own build script names that path), and once the installation is recorded installed — or the build failed — moves it out again and tags it; a move that fails is recorded in the installation's state as `build_tree_left`.

- **`stado quality check` runs its gates outside the checkout:** each check exported the revision and staged its inputs under `<checkout>/.wisent-output/quality/<pid>-<revision>`, and a check that was killed left that tree in `~/Documents`, where no janitor pass reaches. The run area now lives in the checkout's build area under Stado's home, `quality/<pid>-<revision>`; a check still removes its own area when it ends, and before it starts it removes the areas of checks whose process is gone. The admission checks of `stado release submit` and `stado release changes submit` run the same way. A checkout that is not below the home has its build area at `~/.stado/products/builds/outside-home/<its absolute path>`. Real test: `tests/quality/link_input.rs` asserts the checkout holds no `.wisent-output/quality` and the build area is empty after each run.

- **`stado product swift` builds outside the package:** SwiftPM's build tree, the multi-root workspace and the compiler's temporary directory were written to `<package>/.build/wisent-native/`, tagged but in `~/Documents`, where no janitor pass reaches. They now live in `swift/` of the package's build area under `~/.stado/products/builds`, the tree tagged with `CACHEDIR.TAG`. The index reads the relocated tree: a source in it is generated unless git places it in a repository whose git directory lies inside the tree (a dependency clone, refused as `compiler source belongs to a dependency clone <git dir>: <source>`), and a source outside it must belong to one of the package graph's checkouts. The editor settings stay in the package. Real test: `tests/native/scratch_area.mjs`.

- **`stado product surface` builds outside the checkout, and a release archive's Swift build stays in its job tree:** the API check built the candidate and the released tag into `<package>/.build/wisent-surface`, untagged and never removed, in `~/Documents`. It now builds in `surface/` of the checkout's build area under `~/.stado/products/builds`, tagged with `CACHEDIR.TAG`, and the report names it as `scratch`. `stado product swift` over a release archive (`WISENT_SOURCE_DIR`, no repository) keeps its build in the archive's own `.build/wisent-native`, inside the job tree the janitor sweeps with the job, because a build area named after a job tree would outlive the job. `stado product build-trees` also takes the former `.wisent-output/quality`, `.build/wisent-surface` and `.build/wisent-native/build` areas a checkout still holds.

- **Azure and Apple signing credentials are read by role:** the billing collector's Azure section reads the service principal of the item tagged `stado:role:azure-billing`, the Azure token chain reads `cloud-azure` like every other cloud provider, and native signing reads the certificate of the `macos-development-signing` role. `WC_AZURE_BILLING_SECRET` and `WC_AZURE_SECRET` are gone: the billing setting named an item id that was then looked up as a role, so a configured principal reported `no_credentials`. Tag the billing principal with `stado credentials item retag --host <vault owner> <item> --tags stado:role:azure-billing`.

- **A host no longer refuses every job after its disk drops below the threshold:** a janitor that found the volume full while jobs held their shared locks asked them for its turn, and only a pass that took the exclusive lock withdrew that request. Once a finished job freed enough space, every pass ended as `healthy_noop` without the lock, so the request stood for as long as the agent lived and `stado host gates` reported `cleanup_in_progress` with the volume below 80%, holding release builds in the queue. A pass below the threshold now withdraws the turn.

- **A release continues once its build job wrote a passed receipt:** `stado release resume` read the queue before the job's receipt, and a running job the reaper had put back in the queue (`worker lease expired`) while its worker went on to finish kept answering `release job … is still queued … no host has claimed it`, while `stado build status` called the same platform passed. The receipt, which only the worker that ran the job writes and every publish verifies, is now read before the queue.

- **A release job requeued while its worker kept building is not built twice:** when the reaper requeued a running release job (`worker lease expired`) and its first worker went on to write a passed receipt and archive, the job stayed queued for a second build. Each reaper pass now completes such a job from the queue once its receipt and archive verify against the job's immutable request and were written after the job was created, the same evidence a lapsed running job is completed from (`<job>: requeued on an expired lease, completed from the verified release output its first worker published after the requeue`). The worker renews a job's lease for as long as the workload's process group lives, not only its launching shell, so a build that outlives the shell that started it keeps its lease. The heartbeat log now says when a lease stops landing because the job left `running/` while the workload still runs, and when the workload's process group ends.

### Added

- **`stado product build-trees list|remove [--json]` reclaims the rebuildable trees in the workspace's checkouts from the process that runs it:** the janitor cannot read `~/Documents`, so the trees already there — Cargo targets, Stado's former install runs, desktop `.build` directories — waited on a privacy grant nobody gives a background program. Run from a terminal macOS lets read the folder, `list` names every tree in every git checkout directly in the workspace with its bytes and why it is rebuildable (`cachedir_tag`: a valid `CACHEDIR.TAG`; `stado_run_area`: a run area older installs wrote into the checkout; `desktop_build_tree`: the `.build` of a catalog desktop repository), and `remove` deletes every one no build holds, reporting the bytes removed and the volume's free bytes before and after. A tree whose Stado run marker, SwiftPM lock or Cargo lock a process holds is kept as `in_use`; links are never followed and `.git` is never walked. A tree that cannot be removed fails the command with `build-tree removal incomplete: <n> tree(s) under <workspace> could not be removed`, each named with the operating system's reason. Real test: `tests/product/build_trees.mjs`.

- **`stado web route` publishes a `cloudflare`-edge hostname through the Cloudflare tunnel:** it refused every such hostname and named `stado tunnel route` with item names to type, so a host behind a residential uplink, whose 80 and 443 nothing outside can reach, published nothing. The route now resolves the connector host and origin (a product's own host and loopback port, or the active host and endpoint of the service it fronts), reads the items playing `stado:role:cloudflare-api` and `stado:role:cloudflare-tunnel` in the owner vault, and runs the same ingress, connector token and proxied `CNAME` steps `stado tunnel route` runs; `--check` prints that plan and changes nothing. Refusals: a role no item plays (`no item in the owner vault on <owner> plays role cloudflare-api; tag the item … with stado credentials item retag …`), a mount or a redirect on the cloudflare edge (a tunnel route carries a whole hostname to one origin), a fronted service the directory does not declare or that has no endpoint on its active host, and a connector service not declared on that host. The zone must be served by Cloudflare first (`stado dns delegate <zone> --provider cloudflare`). `stado web remove` still leaves the tunnel route and names `stado tunnel remove`.
