# Changelog

Entries for the release being prepared live here. Released entries move into
`changelog/`, one file per range, because a file this repository cannot edit is
a file that stops receiving entries: the length gate refuses every write to a
file past 300 lines, and this one had reached 414. Two product fixes on
2026-09-08 could not be recorded at all until it was split.

When a release goes out, move its section into the newest file under
`changelog/`, and start a new range file when that one nears the limit.

## Unreleased

- **The report says what the host's paging did (0.21.26):** `stado space report TARGET` prints a `memory paging:` line — the compressor's size, converted with the host's own page size, and the lifetime swapout count. Both numbers were already read on every pass and printed nowhere, so a host inside both watermarks looked healthy while it was thrashing: on charless-mac-mini on 2026-09-19 the memory line read 4487 MiB available and swap 71% used, under the declared 2048 MiB and 80%, while the compressor held 3563 MiB across 414,900 swapouts and the released Brama was quarantined twice in an hour for a readiness probe it could not answer. The watermarks and the janitor's verdict are unchanged; this is what they were measured against being shown. `page_size_bytes` joins the reading in `--json`.

- **A host that could not answer does not wall the release off (0.21.26):** a run of quarantines whose cause is `readiness_probe_unanswered` no longer holds the next candidate. Every other cause is about what a release meets on the host — a vault that will not open, a route that maps nothing — and a second candidate walks into the same wall, which is why a run of three holds; a probe the host never answered says nothing about the candidate, and counting those kept charless-mac-mini on a hand-built Brama while every released one was refused before it could start. The record, its class and its remedy stay. The decision itself now lives in one function (`hold_for`), which the tests drive instead of a copy of it.

- **An agent session the fleet keeps running (0.21.25):** `stado workload start jeden-session --workspace W --task "…"` places a Jeden session on the fleet host with the most live room and submits it to the queue pinned there, so the work survives the terminal, the editor and the machine that asked for it; `stado workload sessions` lists what the fleet holds, and `stado job watch`, `stado results` and `stado cancel` follow, download and stop one. Until now `stado workload attach` was the only way to place a session and it dies with the caller's stream, which is how sessions were lost every time VS Code did. A session is sized from the kind's declared reservation (2 cores, 4 GiB), queued at priority 50,000,000, granted nothing unless `--allow-write` or `--allow-command` says so, and declared as CPU work: the queue's model-name sizing scan read `jeden run … --model <route>` as a GPU workload, and on a host with one GiB of VRAM the claim refused every such session silently on every poll. The claim now honours an explicit CPU resolution instead of re-guessing from the command text. The session's command preflights itself on the host, so a workspace the worker cannot enter — `~/Documents` under macOS privacy protection — reports that sentence instead of the harness's usage text. `"detachable": true` in `stado-rs/data/work/workloads.json` decides which kinds may be started this way; Stado Desktop carries the same start form, session list and stop action.
- **A probe nobody answered is not a broken candidate (0.21.26):** a quarantine whose reason says the readiness endpoint `did not answer within Ns` is classified `readiness_probe_unanswered`, and its remedy names the host rather than the release: `stado space report <TARGET>` for its memory, swap and disk, then `stado release doctor <PRODUCT> --target <TARGET>`, clearing the digest only once the host can run it. A candidate that answered `HTTP 503`, one whose process was gone, and the bare `did not become ready before deadline` keep their own readings, and any credential or capability sentence in the retained stderr still wins, because the timeout is the outermost symptom. On charless-mac-mini on 2026-09-19 three records carried it, the desired Brama digest among them, while the host held 3.6 GiB of swap in use at load 3.9 and every one of them read `unclassified`, so the register blamed the release and nobody looked at the host.

- **A field is changed where it is read (0.21.22):** `stado registry set --path P --value V` writes one field of the canonical registry under the generation the same call read it at, through the same validation `push` runs; the path is the one `pull --path` reads, the value is JSON when it parses as JSON and the literal text when it does not, an identical value reports `unchanged` and writes nothing, and a path that does not already exist is refused naming the keys or element names that do. `--json` emits a `stado.registry-set-receipt.v1` object with the previous value, the generation read and the generation written. The week of 2026-09-12 held six edits of the shape `registry pull > ~/.oko/registry-pull.json`, `sed -i '' '309s|…|…|'`, `registry validate`: a line number standing in for a field, a scratch file standing in for the registry, and nothing surviving to the next edit.

- **A question is answered, not dumped (0.21.20):** `stado registry pull --path P` prints one part of the canonical document — a dotted path of object keys, array indexes or array element names (`release_control.products.brama.desired`, `targets.lukasz-macbook.skarbiec`), a string bare and anything else as pretty JSON — and refuses a missing segment naming the keys or names that exist there. `stado release status --run ID` reads one pipeline run by its id or its first characters, however far back it is, and `--version V` the runs that published that version; both print runs only, and no match refuses naming the newest runs. Between 2026-09-12 and 2026-09-19 the whole registry went into `~/.oko/registry-pull.json` eleven times and the whole release status into a file three times, each grepped afterwards for one block. Product and version filters read at most the newest 120 run objects, one request each.

- **Finished jobs' outputs have a cleaner (0.21.24):** `job_outputs` reclaims the payload files under `status/<job_id>/output/` of jobs the queue positively lists as terminal, once they are older than the declared `min_age_seconds` (floor seven days); `*.json` and `*.log` records stay, so `stado release status` and `resume` keep reading receipts and logs. A job the queue lists as live or does not list at all is never touched, and an unreadable queue store removes nothing. Declared like every cleaner: `stado space cleaners declare HOST job_outputs --min-age SECONDS`; the report and `stado space report` carry its counts and skip reasons. Measured on charless-mac-mini on 2026-09-19: 12.1 GiB of such outputs, the oldest from 2026-08-16, held the host under its disk watermark while every declared cleaner reported nothing eligible.

- **Consumer declaration includes its route (0.21.0):** `service directory consumer-add --target HOST --bind LOOPBACK:PORT` commits authorization and the host's resolver binding together. Repeated declarations update the same binding, and omitting capabilities preserves the existing policy. Invalid targets, non-loopback addresses, zero ports and conflicting bindings leave the registry unchanged. `consumer-rm` retires that consumer's bindings on every host together with its authorization. Hosts → Routes exposes both commands through the selected Stado API with review and full receipts. The resolver's existing supervised refresh applies listener changes; neither command changes credential grants. This adds optional CLI fields and uses the existing registry schema. Older readers understand the resulting adapters; rollback does not require a data migration.

- **Publication has its own credential (0.20.15):** `release.publisher_skarbiec` selects the publisher's acquisition identity, independently of the control plane, API verifier and signer. Reusing one of those identities or token files is refused. Publication reads only explicitly granted fields and never rewrites grants in a local replica. `storage put --json` preserves `refused` and `auth` failures as JSON, including write and read-back failures. The configuration catalogue and `config show` expose the selected route, consumer and token file.
- **Scratch cleanup follows the recorded root:** a lease records its caller-local registry directory and identity, including `scratch create --root`. Destruction checks that identity and removes the recorded directory instead of silently checking the default location. A different caller reports that the root belongs elsewhere; unreadable or replaced roots are not reported as absent. The real signed-release test now uses an isolated build-directory root and verifies its removal.
- **Bootstrap bearer delivery (0.20.14):** `credentials token sync` verifies an existing source bearer against its declared grant, requires the destination vault's owner and complete grant to match, and atomically delivers only the named owner-only token file. It never rewrites grants or reverses revocation. Repetition leaves matching files untouched; `--check` performs no write and reports mismatches as typed refusals. Hosts → Credentials exposes the same operation and complete receipts in Stado Desktop. Real CLI tests use isolated GnuPG vaults and authenticated Skarbiec reads to cover recovery, idempotence, revocation, mismatched bearers and symlink refusals.
- **A run that published nothing fences no delivery (0.20.12):** the delivery worker refuses a delivery whose run is older than the newest run holding a published platform, where it used to compare against the newest run of any state. On 2026-09-11 two 0.20.10 runs that failed before a builder was found, created thirty seconds after the 0.20.11 run, made every 0.20.11 delivery refuse itself as `superseded` on every host — 0.20.11 is published on both platforms and installed nowhere — and the day before an abandoned 0.20.9 run whose builds had both failed did the same to the 0.20.8 delivery to lukasz-macbook. A run starts fencing the moment it publishes a platform, which is when its deliveries can begin. The installed workers judge with the old rule until this release reaches them, so 0.20.12 is the first release whose deliveries pass on them: it is the newest run.
- **The build-cache verdict is bounded on this host too:** the walk `stado space report` starts is killed after 120 seconds on the local branch as well as over the remote channel, and `STADO_CACHE_VERDICT_BUDGET_SECONDS` sets another bound in seconds (fractions included); a malformed value is refused before anything is walked. A walk that passes the bound leaves `the build-cache verdict for <root> did not finish within <seconds>s; raise STADO_CACHE_VERDICT_BUDGET_SECONDS or declare a narrower cleaners.build_caches.root` in its section, and the report still prints in full before the command exits 1. Only the remote branch had a deadline: `stado space report lukasz-macbook`, whose declared root is that account's whole home, returned neither an answer nor a refusal after 420 seconds on 2026-09-10.
- **A source snapshot is its files (0.20.11):** `stado release submit` writes the committed tree's regular files only into `source.tar.gz`; `git archive` also wrote one entry per directory and a header naming the commit, neither of which any extractor needs, and together they were what pushed the 0.20.9 snapshot — 3,255 files in 975 directories, 4,230 entries — past the 4,096-entry bound the build and delivery workers unpacked it under, a bound sized for a release payload of a few executables. Every installed worker refused it with `release archive exceeds 4096 entries`, so the 0.20.9 coordinate stays bound to `07fd9ba7` and holds no build, and 0.20.10 — bound to `e27281fa` — was submitted twice from a coordinator older than this change and holds none either. Workers now extract a source snapshot under a 65,536-entry bound while release archives keep theirs; a snapshot of files only fits the older bound until a repository grows past 4,096 files, which is how this release reaches builders still running 0.20.8. A ci-cd journey releases a real 4,200-file tree.
- **A consent dialog no longer holds the janitor (0.20.11):** the build-cache cleaner's first directory open under `~/Documents`, `~/Desktop` and `~/Downloads` — the three macOS folders behind a consent dialog that stay in scope because build trees live in them — is bounded to five seconds; a pending answer records `consent_pending` in that cleaner's `skipped` map, leaves the folder for a later pass, and the pass finishes. On 2026-09-10 lukasz-macbook's janitor sat two hours inside one such open holding its exclusive lock, every job admission on the host answered `cleanup_in_progress`, and the 0.20.8 delivery sat queued against it.
- **A host that cannot start work says so (0.20.11):** the agent's capacity publication probes the workload lock the way a claim does and publishes `accepting_jobs: false` with `admission_reason: cleanup_in_progress` while a standalone cleanup holds it (`cleanup_lock_error` with the code when the lock cannot be probed), under the same `disk_cleanup_admission` key the claim path writes. `stado host gates` reads the published reason back, names it on the capacity line instead of `busy or gated`, carries it as `capacity.admission_reason` in `--json`, and reports `cleanup_in_progress` as a blocker with `claiming: no`; Stado Desktop's gate screen names the same reason. The same host had published `accepting_jobs: true` for the whole two hours while `host gates` read `claiming: yes` with the stalled janitor as a note.
- **Disk watermarks are written from the command line (0.20.8):** `stado space watermark TARGET --disk-low-free-gb N --disk-target-free-gb M` (with `--disk-mode`, `--disk-check-interval-seconds` and the pass limits beside them) rewrites exactly those fields of `targets[].disk_cleanup` through the registry's validated compare-and-swap, seeding an undeclared host from the reporting default and preserving every cleaner; the read prints the disk declaration beside the memory one. Stado Desktop could already write these fields through `api/registry/policy`; the CLI could not, and the release coordinator's `release_scratch_short` refusal names the low watermark as the reserve a build must fit above. The refusal now names all three remedies: reclaim, declare cleaners for the uncovered space, or lower an overstated floor.
- **Delivery leftovers are reclaimed (0.20.8):** the `delivery_leftovers` stage of `stado space reclaim` takes the attestation copies and retained archives of delivered versions under `~/.stado/releases` and the dated binary backups under `~/.stado/bin` that every `release install-local` left behind and nothing reclaimed — roughly 200 MB per release per host; 3.0 GiB and 1.35 GiB on the Linux builder, 9.1 GiB on the mini. It keeps the version the installed coordinate names, every version whose copy is byte-identical to the installed binary, the most recent delivery and the newest backup of each name, and never touches a delivery younger than the age gate. Stado Desktop's reclamation confirmation runs the same stages.
- **Builds are placed by measured scratch, not name order (0.20.5):** the release worker measures its scratch tree and the free bytes on its volume when the build step ends and leaves `scratch.json` beside the receipt; a failed build's receipt and exit sentence carry the same two numbers. Before a build is queued, the coordinator reads the newest such record for the product and platform and refuses a builder whose published free disk cannot hold it above the host's low watermark with `release_scratch_short`, naming both numbers; among the builders that can, the most free disk goes first. The 0.20.3 darwin build was pinned to charless-mac-mini by name order with 14 GiB free and died of a full disk after twenty-five minutes.
- **The software report has a writer again (0.20.7):** `stado release host-state` refreshes the host software report `stado release status` judges, on every visit, over one authenticated session, with the bin directory classified in one command; `stado host software` wrote it until the 2026-09-06 collapse deleted the verb and left the report to go stale and the status hint naming a command that no longer parsed. `host-state` prints the report it recorded and carries it under `software` in `--json`, Desktop shows it in the Release state section, and the hint names `stado release host-state --host <TARGET>`.
- **A delivery run again in its own work tree delivers (0.20.6):** each delivery attempt extracts the verified source into a tree of its own, so a queue retry in the same job directory never meets the tree its previous attempt left behind. The 0.20.5 delivery to lukasz-macbook installed the release, and installing it recycled the object API the agent heartbeats through, so the lease lapsed and the queue ran the job again in the same directory, where the second attempt died on `immutable release directory already exists`. That refusal still protects release directories; a job's own scratch is not one.
- **`min_free_gb` reader ships before its declaration:** a platform recipe may declare `min_free_gb`, the free space its build needs on the work volume, and a worker that reads it refuses before the first gate when the volume is short. Stado's own manifest does not declare it yet: a recipe field is read by the worker installed on the builder, which refuses fields it does not know, and the 0.20.4 darwin job died at the manifest with `unknown field min_free_gb` on a builder running 0.20.1. The declaration follows once a release carrying the reader is installed on every builder.
- **Idle launchd units no longer fail deliveries (0.20.5):** the loaded-unit inventory reports a job launchd holds without running it with an empty pid, whether `launchctl list` wrote `-` or a domain table wrote `0`. The 0.20.1 delivery to charless-mac-mini read that zero as a live process and refused with "the kernel image for … pid 0 is unreadable" on an idle `stado-resolver` unit. The inventory also keeps every column in place when a value is empty; a system-domain job with no pid used to read its exit status as its pid and `system` as its status in `service list --undeclared`. The 0.20.2 and 0.20.3 coordinates hold at most one platform of this fix: 0.20.2's Linux build was refused by the documentation gate once the memory-policy page was published ahead of its source, and 0.20.3's darwin build ran out of disk; a bound coordinate is never rebuilt from another commit.
- **The disk janitor stops asking for the photo library (0.20.5):** the build-cache walk refuses `~/Pictures`, `~/Music`, `~/Movies`, `~/.Trash`, `~/Library/Mobile Documents` and `~/Library/CloudStorage` before it opens them, and reports each refusal as `privacy_protected`. This cleaner's default root is `$HOME`, so on 2026-09-09 the always-on agent's pass walked a photo library and macOS asked the operator for Photos access, repeatedly, on behalf of `~/.stado/bin/stado`. No build tool tags those directories, and reading the two cloud roots downloads placeholder contents, so nothing reclaimable is given up. `~/Documents`, `~/Desktop` and `~/Downloads` stay in scope: build trees live there.
- **Committed release sources:** `release submit --commit SHA` reads the manifest, version and source archive from one full local Git commit without changing the branch, index, staged edits or untracked files. Without `--commit`, submission still requires a clean checkout. Desktop's Releases operations expose the same source, commit, version and channel fields.
- **Release journey selection:** native verification now selects the qualified cancelled-build test name and runs both resumption and committed-source journeys. It uses the fixture's actual Skarbiec selection rather than downloading an unused 0.1.3 binary.
- **Stable macOS code identity (0.20):** Darwin release workers sign native staged code through Wisent Products before publishing the immutable archive. Apple challenge helpers and managed GitHub apphosts now require an Apple identity instead of accepting an ad-hoc build hash. Darwin builders need Wisent Products 0.2.1 and access to a provisioned Apple signing identity when their inputs are not already signed.
- **Signature diagnostics and migration:** `product signatures PRODUCT --surface cli|service [--apply] --json` reports actual identifiers, Apple teams, authorities and requirements, and reconciles recorded native files without resetting TCC or restarting services. Settings exposes the same operation through the selected Stado API. The first migration from ad-hoc signing can require new consent; subsequent builds retain the product identity.
- **Declared host memory policies:** `stado-rs/data/memory/policies.json` declares four complete `memory_reclaim` policies with the platforms and roles each is written for, and `stado space watermark TARGET --policy NAME` applies one whole through the canonical registry. A policy that ends a logged-in session's processes needs `--authorize-graphical-session` at that call, a policy written for another platform or role is refused with the ones that fit, and combining `--policy` with the field flags is refused. `stado space policies [TARGET]` lists the catalog and says whether a host's declaration repairs anything at all and which declared policy it is. Stado Desktop reads the same catalog from `api/memory-policies.json` and fills its Memory editor from it. The repair vocabulary moved from `stado-rs/data/memory.json` to `stado-rs/data/memory/repairs.json`.

- **Desktop packaging:** build the identity helper through the executable product exported by the pinned authentication package. A fresh checkout no longer depends on an absent helper script; the signed bundle keeps the SDK's required helper path.
- **Recorded release resumption:** `release resume RUN_ID` uses the original stored source and manifest even after the checkout changes. Running jobs keep their IDs and published builds are verified rather than rebuilt. Stado Desktop exposes the same operation from Releases with source identity, command review and complete command output.
- **Failed delivery retries:** a failed or cancelled queue job now anchors a new idempotent delivery attempt. A stale `submitted` summary is checked against the actual terminal job, so resumption no longer repeatedly returns the same failed job or misses a later delivery's failure.
- **Native release resumption:** Desktop resumes through its selected Stado API and retains that endpoint's command receipt. Already published platforms no longer require a private signing grant merely to verify their bytes or finish deliveries.
- **Release reader enumeration:** post-install reconciliation still reads every launchd label, loaded domain, declared executable and running command, then verifies kernel image identity. It no longer runs unrelated script/environment scans, process-age probes or PATH-version diagnostics inside each installation; full service inventory retains those diagnostics.
- **Host and public-origin diagnostics (0.18 preview):** independent registry, host, storage, capacity, queue, DNS, publication and public-proxy reads retain their own source, elapsed time, error and ten-second budget. A missing host route or configuration-reader binary no longer discards completed measurements; absent measurements no longer become disk-pressure blockers. Configuration failures name the installed executable and preserve command output.
- **Diagnostic JSON migration:** `host gates` returns `complete` and `observations`; `claiming` is `null` when diagnosis is incomplete. Disk readings retain exact bytes and their provenance. Public-origin reports preserve the actual release-proxy response separately from `edge_selection.diagnosis`, which contains complete DNS/TCP/TLS/HTTP observations. Stado Desktop shows both and does not offer convergence for an incomplete origin diagnosis. Update CLI and Desktop together; no persisted data migration is required, and rollback uses their prior matched release.

- **Runner credential and registration:** runner operations resolve the same Skarbiec route that `runner credential` checks. Repository registration uses the existing repository-admin credential without demanding organization runner-group permissions. Installation reconciles changed scope, group and labels, refuses reconfiguration during a job, and requires GitHub to report the named runner online. Linux Rust toolchain setup can write its `.profile` without opening the whole runner home.
- **Runner desktop and model review:** Desktop's operator API now accepts the runner family, including read-only credential diagnostics. The host inspector displays GitHub registration results and all declared profiles. Brama model-review setup is an explicit `runner model-review TARGET --repository REPO` operation, separate from runner installation.
- **Working directories:** `workdirs --apply` removes every direct child directory of `~/.stado/work`, including job and run areas, while preserving root-level files and links. Descriptor-relative traversal refuses linked roots and filesystem crossings. JSON and text both fail on unreadable or remaining directories; file lengths and actual free-space readings are reported separately.
- **Space diagnostics:** whole-tree inventory has an independent bound; failures retain the cheap readings and are marked incomplete in text, JSON and Desktop. Invalid inventory budget settings are refused rather than ignored. The native API and Settings expose the same working-directory preview, confirmation and complete cleanup receipt.
- **Preview integration migration:** `space report` replaces `host disk`; cleaner policy operations are under `space cleaners`. Working-directory reports now use `directories`, `remainingDirectories` and `apparentBytesRemoved`; consumers must not treat file lengths as reclaimed filesystem blocks.
- **Release request diagnostics:** storage HTTP failures preserve the original cause chain when displayed by the CLI, recorded by a release run, or returned through the native Desktop command API. Connection errors no longer stop at `error sending request`; storage operations, schemas, and retry loops are unchanged.
- **Retained Tailscale diagnostics:** `host exec` reads the previous hour of macOS native Tailscale logs or the Linux `tailscaled` journal through two fixed, read-only commands. Hosts in Desktop exposes the same reads with the selected platform, original messages, process status, and refusals; neither empty output nor a completed read is a public Funnel health verdict. These two reads preserve up to 16 MiB of command stdout for a decodable native receipt, while other command limits and mutation confirmations remain unchanged.
- **Managed target builds:** `host build TARGET --manifest-path PATH --bin NAME` runs only `cargo build --locked --release` against a manifest physically confined below the approved account's `~/.stado/work/runs`, using the fleet's existing Cargo-path policy. The JSON receipt retains Cargo stdout, stderr, and its own exit status; symlinks, foreign ownership, missing tools, and paths outside the managed run area fail closed.
- **Attached target programs:** `host run-attached` connects stdin and, outside JSON mode, both output streams directly to one owner-executable program below the same managed run area. SIGHUP, SIGINT, and SIGTERM are delivered through a run-scoped owner-only marker and a second registry-authorized channel; sensitive input stays on stdin. `host remove-run-directory` idempotently removes one complete direct child of the managed run root and refuses the shared root, nested paths, symlinks, and foreign ownership.
- **Release archive length:** a release object read through `/api/release/object` is compared against the `Content-Length` the route declared, the way the authenticated object route already was. A body that stops short is refused with both counts named instead of being returned as the archive; a body with no declared length is still delivered whole.
- **Storage authentication refusals name storage:** `StorageError::Auth` reads `storage authentication failed`. Every authenticating backend raises it — the Stado object API's token file, Azure's token exchange, GCS credentials — so a refusal about a local token file's mode no longer announces `GCP authentication failed` on a machine with no GCP configuration. The error code, retryability and exit status are unchanged.
- **Release submit reports why nothing was built:** when no builder can claim a platform, the run's own refusal survives to the operator and to the durable run document. The signing-key read that follows an empty submission no longer replaces `no live fleet builder can CLAIM release_platform …` with `cannot read signing key …`.
- **Repair refuses an undeclared host:** `repair --target` for a host the canonical registry does not declare refuses with the registry's own sentence and a non-zero exit, instead of reporting an `unavailable` observation and exiting 0.
- **The doctor stops conflating two silences:** a unit file this machine never read and a unit file that belongs to another host are reported as different observations, and a product with no release target for a host says so rather than reading as agreement.
- **Public origin JSON migration:** the next native release replaces `edge_selection.diagnostic_probe` with `edge_selection.diagnosis`, retaining the deployment's complete DNS queries and independent socket probe. Consumers of the old probe field must read `edge_selection.diagnosis.probe`; `edge_selection.readback` remains the evidence from the actual public release proxy. Published Stado 0.17.2 still exposes the old field. No registry or persisted-state migration is required, and rollback to 0.17.2 restores the prior JSON shape.
