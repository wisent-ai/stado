## Unreleased

### Fixed

- **A service that accepts and never answers is recovered on the host that runs it:** a service whose `/health` answered while the path it exists for held every request passed readiness and failed every client; every client's resolver recorded the waits and nothing on the service's host acted, because nothing there asked the question the clients were asking. A product's catalog `service` now declares that question as `answering` (`method`, `path`, JSON `body`, and the `repair` steps of its repair declaration to run first, in order); Brama declares `POST /v1/chat/completions`, Skarbiec `POST /v1/items/list` with `crypto` then `audit-lock`, because a Skarbiec stands for a wedged GnuPG daemon as often as for an audit lock and each step refuses when its own cause is absent. Every beacon pass sends it to the service's recorded listen port, records the wait like the resolver does, and reads it on the next pass; a question unanswered longer than this host's declared directory refresh interval is a service that stands: every declared repair step runs through the repair path, the restart through the `service restart` path, the question is forgotten so the next pass asks the new process, the recovery is appended to `~/.stado/service-recoveries.jsonl` and alerted on the configured channels. The beacon carries the probe under the unit's `answering` (`asked`, `waiting`, `stood` with its `recovery`, `finished` with `answered` or `refused`; `unreadable` with its cause for a port the directory does not record or a resolver without an interval). `stado service recoveries [--service NAME] [--json]` reads the register, oldest first, with the requests the resolver held, what each repair step and the restart answered and what each alert channel answered; an absent register holds no recovery, an unreadable one or a line that is not a recovery is refused naming the file and the line. The catalog refuses an `answering` with a method not in capitals, a path not starting with `/`, a `repair` that is not a list or names an empty or non-string step, or a field outside `method, path, body, repair`. Stado Desktop carries **Read the services this host found standing and recovered**. Real test: `tests/service_answering/stands.rs`.
- **A held route is one `resolver status` blocker:** a route the resolver holds keeps every new connection a client opens on it, so one service that stopped answering for hours published hundreds of waits and `stado resolver status` printed the same sentence once per connection. The blockers now name each held route (service, consumer, bind, phase, destination and host) once, as `<N> connections on one route, the oldest: …` with the oldest wait's client and its `lsof` line; `waiting_opens` in `--json` still lists every wait. Real journey `tests/service_directory/held/held.rs`: two requests relayed on one adapter to a service that never answers are one blocker that counts both.
- **A declared repair's read-only observation reaches the host it is for:** `stado repair SERVICE --target HOST` without `--apply` was refused on a host whose services this resolver held unanswered, while the mutating `--apply` was sent, so a held host could only be repaired blind. The observation now runs in the same declared-repair scope as the apply: the held reading is said on stderr and the read-only inventory goes over a fresh command channel.
- **What the forge's continuous integration last did is a product command:** whether a product's workflows pass could only be asked with the forge's own client, which the shell gates refuse as a one-off, or inferred from `stado release status`, which reads Stado's release runs and not the forge's. `stado ci status PRODUCT [--revision SHA] [--json]` reads, as the identity the GitHub declaration names in Skarbiec, every workflow the product's repository declares under `.github/workflows`, the newest run of each (of one commit with `--revision`) with its conclusion, and for a run that did not pass each failed job with the step that failed in it. A workflow that never ran, a revision no run was made for and a repository with no workflow are findings (`run: null` with `finding`; `workflows: []` with `declares no workflow under .github/workflows`), not refusals; an unknown product, Skarbiec or the declaration not answering, and the forge answering other than success are refused by name. Stado Desktop's Products screen carries **Read what the forge's continuous integration last did for a product**. Real journey `tests/ci/status.mjs` against the forge for a product with workflows and one without.
- **A dependency a product has by design says so:** a catalog dependency with no alternative was reported by `stado product dependencies` only as `bound` with no alternative, so a product that is a surface of another (Compute Marketplace, whose every instance is one Stado machine job) read the same as a dependency nobody had decided on, and each reader asked again whether a runner of its own was missing. A dependency now declares `bound_because`, the reason the product does not run without the other, instead of an alternative (never beside one; the catalog refuses both at once and an empty reason); the standing carries it as `because`, the refusal reads `the catalog declares that <product> needs the <other> <surface> by design: <reason>`, a need with neither reads `… with no alternative and no bound_because saying why`, and `install --without` refuses it as `the catalogue binds it by design: <reason>`. Compute Marketplace's service declares it for Stado's, and its Skarbiec need gained the `WC_CREDENTIALS_FILE` alternative. The real journey `tests/dependencies/independence.mjs` covers the bound-by-design standing, its JSON `because` and the catalog's refusal of a reason beside an alternative.
- **Alert channels run without Skarbiec:** the Resend key, the Twilio fields and the `alerts` item's fields were read through a Skarbiec client built in the alert resolver, so a machine without Skarbiec, or one whose Skarbiec stood unanswered, paged nobody and `stado alerts send` reported `no alert channel resolves`. They are now read through the selected credential store, like every other credential: Skarbiec with Stado's own grant, or the owner-only file store `STADO_CREDENTIALS_STORE=file://<path>` (persisted as `credentials.store`) selects, filled with `stado credentials put`. A key the store does not hold is said as `the selected credential store gave no <field> for role <item>: …`, naming the Skarbiec retag and grant and the file store's `put`. The catalog declares Stado's dependency on Skarbiec with that alternative. Real journey: `tests/alerts/file_store.rs` (`alerts-file-store`).
- **A remote command to a host whose services stand is refused before it is sent:** `stado host exec`, `stado service logs` and every other command that rides a host's channel were sent and held without end to a host whose services this host's resolver already held unanswered, so the diagnostics of a stalled host stalled with it. The host channel now reads the resolver's published waiting list before selecting a connection and refuses with `<host> is not sent this command: this host's resolver holds <N> connection(s) to it unanswered longer than the <interval>s refresh interval it declares (services <names>), so a command sent now would stand with them: …`; an unreadable list refuses with its cause; a command to this machine rides no channel and is not read against it. Real journey `tests/service_directory/held/held.rs`: `host uptime` to the held fixture's target, sent from a machine that is not it, is refused naming the host and its standing service.
- **A relayed request whose client is gone no longer holds the adapter:** the resolver kept a request in its published waiting list until the service's first byte came down, whatever became of the client, so a hook process that died with its judge request sent held the Brama adapter for every later caller, each refused with that dead request's sentence, indefinitely. The relay now ends when the client closes before an answer began: the channel to the service is closed, the place is given back, and the resolver says `request to <endpoint> on <host> abandoned by its client before an answer; the channel is closed`. A request whose client still waits is held as before, with no clock; a client that half-closes after the answer began is still read the rest of it. Real journey `tests/service_directory/held/held_answer.rs`: the client closes, the published list empties, and the next caller's request goes up.
- **A held connection names the client holding it:** the resolver's published waiting list, `stado resolver status` and every refusal built on them said which adapter was held, by which service, since when, and nothing about the client, so a judge request held for hours could not be told from one whose hook process died at once, and the operator read "it ends when that process ends" with no way to name the process. Every wait now records `client`, the loopback address the client connected from; `waiting_opens` lists it, the relay's log line says `request from <client> sent to <endpoint>`, and the blocker ends `held by the client at <address>: \`lsof -nP -i :<port>\` names the process still holding it`, which is the one question that answers whether anything still waits. A list an older resolver published, without the address, names no holder. Real test: `tests/service_directory/held/held.rs` reads the client address back from the register, the log and the blocker.
- **An installation executes a committed catalog, never the checkout's working tree:** `stado product install|update stado --source-commit X` read its recipe from the working tree, so an install of X ran the `after_install` step a verb rename in progress had written there — `stado release local converge`, which the installed X did not have — and failed after a successful build, signing and swap. An installation of Stado now reads `catalog/products.yml` at the revision it installs; every other installation, and product sync, reads the committed head of the catalog's checkout; a machine without the checkout reads the catalog compiled into Stado. The receipt and the report name what was read under `catalog` (`source`, `revision`, `chosen`: `installed-revision`, `committed-head` or `embedded`). Real test: `tests/product/install_catalog_revision.mjs`.
- **The visible verbs that joined words with a hyphen are objects with verbs:** `stado host gpu power set|unset TARGET` replaces `host gpu-power-limit set|unset`, `host port owner TARGET --port N` replaces `host port-owner`, `host document render TARGET SOURCE` replaces `host render-public-document`, `host compiler cache TARGET status|ensure|remove` replaces `host compiler-cache`, and `release gate surface|baseline|decide|conformance`, `release gate semver reaches ACTUAL MINIMUM`, `release gate modules unreachable` and `release gate app surface|baseline|check` replace `release version-gate …` with its `semver-at-least`, `unreachable-modules` and `app-surface|app-baseline|app-check`; each retired name is refused by the parser, and Stado's own version-check workflow calls the new names. The cli-surface journey lists each object's verbs and refuses the retired names.
- **A source install that fails after its build keeps the build, and the next install of that revision resumes after it:** an install that failed at signing or staging shed its run's export and build output on the way out, so every retry of the same revision exported, checked and compiled it again — twelve minutes per attempt for Stado itself — and the build that passed every gate could neither be finished nor inspected. A build that passed its quality gates and build step is now kept (`<run>/.kept`, `install-built/<key>.json` in the checkout's build area, keyed by product, platform, revision and recipe); the next install of that key holds the kept run, resumes at signing and says `<product>: resumed at signing from the build kept at <run>`, with `resumed_from` in `prepared.json`. A kept run is neither shed nor superseded by a later install's fresh run; the installation that completes sheds it as before, which releases it, and a kept run is cache-tagged so `stado space reclaim` and the janitor take it under disk pressure. Real journey `tests/product/resume/kept_build.mjs`.
- **A Stado that stops again on the same host rolls itself back, whatever the failure:** the previous-release rollback ran only when a `stado serve` component stopped with a configuration failure, so a release that stopped on every start for any other cause (a bind something else holds, a panic, a dependency its startup needs) raised its Oko defect on the second stop and was then restarted by launchd or systemd for as long as the host stood. The rollback now uses the register's own measurement: a stop that repeats an earlier stop of the same build in `~/.stado/serve-stops.jsonl` records the release as failed on this host with that earlier stop as the cause (`stado serve <version> stopped <n> time(s) on this host before this one, the first at <time> with: <failure>; this one with: <failure>`), reinstalls the release that ran before it and alerts every enabled channel with `Stado <version> failed on this host (<cause>); recorded as failed at <record> and reinstalled Stado <previous>…`; a configuration failure still rolls back on its first stop. Earlier stops that cannot be read are said (`stado serve's earlier stops cannot be read, so this stop is not measured against them: <cause>`) and nothing is rolled back on a guess. Real journey `tests/delivery/repeated_stops.rs`: the second stop of a build records the failed release naming the first stop and the bind, and the refused rollback names the absent `stado.previous`.
- **A keychain the operator names signs the build, whatever the fleet's signing role:** `stado product update stado` of a commit that repairs the resolver built for eleven minutes and then failed reading the fleet's `macos-development-signing` item from Skarbiec, which it reaches through that very resolver, because the fleet role was taken whenever no PEM pair was supplied and `WISENT_CODESIGN_KEYCHAIN` was read only when no role existed. A named keychain is now a signing source the fleet role does not override, so `WISENT_CODESIGN_KEYCHAIN=<path> stado product update stado …` signs with the operator's own identity while Skarbiec is unreachable. Naming it beside `WISENT_CODESIGN_ROLE` or the supplied PEM pair is refused (`… names your own keychain as the signing source, and WISENT_CODESIGN_ROLE or the supplied PEM pair names another; name one`), a keychain path that does not exist is refused naming it, and a role whose item cannot be read names the keychain choice.

The GPU-sharing exception and the disabled Hugging Face skip-done filter, which existed only for that extractor, are removed. Real journey `tests/submission/removed_extractor.rs` (`submission-removed-extractor`).

Refused: a URL that is not loopback with a port, `--url` with `--withdraw`, a service named with neither, withdrawing one not declared, and an unreadable or malformed `beside.json` naming its path. Stado Desktop runs the same three operations from its routes. Real journey `tests/service_directory/beside.rs`.
- **The resolver serves every route it can and names each one it cannot:** one adapter it could not serve — the store it reads its registry through, declared on the host's own `storage.stado.url`, or a port something else holds — stopped `stado serve --resolver` and every other route with it, so one contradictory declaration took Brama, Skarbiec and the object API off the whole host. That adapter is now left unserved with its reason, published in `~/.stado/resolver-state.json` beside the served ones and tried again on the next directory change; `stado resolver status` reports `degraded` with `the resolver does not serve the <service> adapter for consumer <consumer> at <bind>: <reason>`, and `stado service directory connect` refused on that bind adds `this host's resolver (pid <pid>) does not serve <bind> for <service>/<consumer>: <reason>`. Only a resolution API that cannot bind still stops the resolver. Real journey `tests/resolver/unserved.rs`.
- **`stado credentials token sync` reads the bearer under the name it was minted with:** `stado credentials token mint --token-file-name <name>` places the bearer at `~/.stado/<name>`, but sync refused that same bare name with `token file must be an absolute or home-relative path`. A bare name now means `~/.stado/<name>`; absolute and `~/` paths are read as before, and a refusal names the value and the three accepted forms.
- **A refused SQLite fleet placement no longer hides a directory it could not take back:** when storing the database item failed, `stado database` removed the file it created and then the directory with `let _`, so a removal refused for any reason other than the directory still holding other files was never said. It now adds `the directory <path> that held it stays: <cause>` to the refusal; a directory that is not empty or already gone is no failure.
- **The release agent no longer reports a retired product's release state removed when it stays:** for a product no longer released to a host, it removed `<product>-proxy.json` and `<product>.json` without looking and printed `its release state was removed` either way. It now prints `its release state stays: <path> is left behind: <cause>` for a file that stays. The replacement-in-flight markers, machine source work files and a retired cleanup lock's holder record are removed through `primitives::staging` too, and one that stays is printed.

- **The disk janitor says a turn request, lock holder record or workload hold it cannot remove:** an answered turn request that stayed kept workloads yielding while the janitor already held the lock, and a holder record that stayed named a holder that no longer held it; both were removed without looking, as were workload hold records, the holder records' staging files and the unlock itself. Each removal now goes through `primitives::staging` and a file that stays is printed (`janitor: the answered turn request stays: <path> is left behind: <cause>`), a gone workload's hold that stays joins the unreadable-holds list, and a failed unlock is printed.

- **A take-back that fails is said:** a release archive that could not be finished, a partial artifact download, a fleet SQLite file no item names after the vault refused the item, and the source `.pub` of a key `stado fleet key add` moved were removed without looking; a key item that failed read-back was deleted the same way. Each removal now goes through `primitives::staging` and a file that stays is added to the error or printed, and a failed deletion of the unverified key item is appended to the refusal (`the unverified credential item <id> could not be deleted: <cause>`).

- **A temporary host SSH key or staged operator console input that cannot be removed is reported:** the private key Stado writes to the temp directory for one SSH call, the operator console's input file (promised never to survive the request), the placement policy's staging file, the janitor's state staging file and the system daemon's staged plist were each removed without looking at the result. Each now goes through `primitives::staging`; a file that stays is said with its path and cause — on stderr when a key or input is dropped, in the error of a failed key write or placement install.

- **A refused `stado release local install`, a failed self-update attestation copy and a vault token link say what they leave behind:** a refusal by the incoming binary's configuration gate or by the callers check removed the staged program and `stado.release-version.release-incoming` without looking at the result, the attestation copy did the same after a failed rename, and `vault mirror` dropped the removal of its pending token copy whether or not the link succeeded. Each now removes through `primitives::staging` and prints `<staged> is left behind: <cause>` for a file that stays; a mirrored token whose pending copy cannot be removed is refused (`<destination> holds the token, and a second copy of it stays: …`).

- **A failed write no longer leaves a private key or token behind unannounced:** the held repair SSH key, the token `vault mirror` syncs, a unit's local environment file, the recovery cutover's config and the resolver's published state, waiting opens and vault consultations each stage beside their target, and a failed write dropped the result of removing that file. Each now removes it through `primitives::staging` and its error ends `<staging> is left behind: <cause>` when it stays; the cutover's staging name is derived like its rollback copy and refuses a config path whose file name is not UTF-8, and the resolver says a waiting list it cannot serialize.

The staging file is now removed after any failed encode, write or rename through the shared `primitives::staging`, and an error says `<staging> is left behind: <cause>` when it stays. A store path whose file name is not UTF-8 is refused instead of staged under an invented name.

- **Product sync does not rebuild the commit that crash-looped:** after a restore of the previous release, product sync's next pass built the canonical checkout again, the very commit whose `stado serve` stopped on every start. The stop register `~/.stado/serve-stops.jsonl` is now shared by `stado serve` and the source install (`stado_product::serve_stops`), and a source install of a revision with a stop that raised its Oko defect is refused before anything is exported: `<product>: revision <rev> is held: stado serve <version> built from it stopped <n> time(s) on this host (<path>), the latest with: <failure>; <report>. A later commit is built as usual`. A stop file that cannot be read refuses the install too (`whether revision <rev> is held cannot be told: <cause>`). `stado resolver status` carries `serve_stops.held` and prints `serve stops revision <rev> is held from source installs until the checkout moves past it`. Real tests: `tests/product/held/revision.mjs` (both refusals in isolated homes) and `tests/delivery/repeated_stops.rs` (`held` after the reported stop).

- **Product sync outlives a stopped role, so a broken release can still be replaced on its own host:** `stado serve` ended whenever any role stopped, so a release whose resolver refused to start stopped the whole process within seconds of every restart, product sync with it, and the host never installed the repair of the release it ran. Product sync is now the process's delivery role: it starts before every other role, and when another role stops, or startup cannot finish, the process writes `stado serve pid=<pid> failed: <the stop>; it keeps product-sync running so a release that replaces this one can still be installed` and keeps syncing at its cadence (a configuration failure still rolls back to the previous release first, as below). After each pass the role compares the program the process runs with what it started as; once a release was installed over it, the role ends with `product sync installed a new release over <program>, the program this process runs; the service ends so its init system starts the installed release`, and the process with it. The real test is `tests/delivery/broken_resolver.rs`, which holds the resolver's API bind so the real resolver fails.

- **The target's SSH identity is attached without judging the program by its name:** `add_identity` refused any invocation whose first word was not one of two program names, though every caller builds its own OpenSSH client invocation; it now puts `-i <key> -o IdentitiesOnly=yes` after the program word and refuses only an empty invocation (`SSH identity cannot be attached to an empty invocation: no program was given`).

- **A delivered Stado that refuses this host's configuration puts the previous release back:** a release whose resolver refused the configuration the release before it served crash-looped under launchd for a day, taking Brama, Skarbiec and the object API with it, and nothing stopped it. When a `stado serve` component stops with a configuration failure, the release now records itself as failed on this host (`~/.stado/releases/stado/<version>/<platform>/failed-on-this-host.json`), reinstalls the release that ran before it through the `release local restore --previous` install, and ends so the init system starts that one. A release recorded as failed is refused by every later install on this host (`Stado <version> failed on this host and is not installed here again: …`), so product sync cannot reinstall it and two failing releases do not restore each other in turn.

- **`stado space report` walks the home once for its inventory:** the macOS inventory ran `du` over the home and then again over six of its subtrees (`~/.local/share`, `~/.local/state`, `~/Library/Caches`, `~/.cargo/git`, `~/.stado/local-storage`, `~/.stado/local-backup`), each already traversed whole by the first walk, since a depth bound caps `du`'s output, not its traversal; on a workstation home the report ran for hours. The section now measures the deepest depth any root below the home asks for, walks the home once at that depth, and takes each root's rows from that one listing by their depth below the root; roots outside the home are walked as before. Real test: `a_space_report_walks_the_home_once` in `tests/disk_cleanup/space/report.rs` reads the process table while a real report runs on an isolated home whose `~/.local/share` takes longer to walk than two looks at it: one `du` of the home is seen and none of a root below it, a row four levels below `~/.local/share` is reported, and a row three levels below the home under no deeper root is not.

- **`stado release failed` shows every release a host rolled back from:** a release that refused one host's configuration was visible only on that host (`release local list`) or as a refusal of the next delivery, so a rollback went unseen until a delivery hit it. `stado release failed [--json]` reads every host's beacon and lists, per host by its beacon slug, each Stado release it recorded as failed with the version, platform, time and cause it wrote; a beacon that could not read its own retained releases is listed as such, never as a host with no failure, and unreadable beacons refuse the command naming the cause. Stado Desktop's Releases screen shows the same answer in *Releases rolled back on a host*.

- **A unit that keeps dying is named, raised in Oko once, and its release does not spread:** a unit loaded with no live process whose last run exited nonzero is now one verdict everywhere: `stado service unit show` prints a `failing` row (`failing` in `--json`), `<unit> runs no process: its last run exited <code> and its supervisor has started it <runs> time(s)`; the beacon marks it `failed` with that sentence in `detail` (the beacon's own exit-code word list is gone); and a host release delivery whose restart cannot prove a fresh process appends it to its refusal. Each health pass keeps such units in `~/.stado/failing-units.json` and records one Oko defect per crash loop (`oko defects record --product stado`), retried on the next pass when Oko refuses; Oko's answer joins the unit's `detail`, which `stado service list` and Stado Desktop show, and `crash_loops_unrecorded` names a loop file that cannot be kept. A pass that changes nothing writes nothing, and a unit no longer declared drops its loop. Each beacon also publishes the host's failed Stado releases (`failed_releases`), and a delivery to any host (`release local install`, so product sync) refuses a version another host published as failed, `Stado <version> failed on <host> and is not delivered to another host: <record>`, or refuses with the cause when the beacons cannot be read; a restore does not read them. Stado Desktop's host release operations read the retained releases and reinstall the previous one. Real journey `tests/service/failing_unit.mjs`.

- **`stado space reclaim` keeps the release a host can roll back to:** the `delivery_leftovers` stage pinned only the installed version and the newest one, which on a host that just received a release are the same, so it took the previous version's retained archive while `~/.stado/bin/stado.previous` still held that binary. When the new release then refused to serve, `stado release local restore --version <previous>` found no archive to reinstall: only the broken release's tree was left. The version whose attestation copy is byte-identical to `<product>.previous` is now pinned beside the installed one, so the restore always has its archive.

- **`stado quality check` fetches Git dependencies with the `git` program and tells a fetch failure from a lock that does not resolve:** the lock gate ran one `cargo metadata --locked`, whose built-in Git transport carries no credentials, so a repository naming a private `wisent-ai` Git dependency (brama's `wisent-onboarding-client` from echo-web) was refused at every push with `failed to authenticate when downloading repository`, labelled `an explicit policy refused this command`. A tree whose Stado run marker, SwiftPM lock or Cargo lock a process holds is kept as `in_use`; links are never followed and `.git` is never walked. A tree that cannot be removed fails the command with `build-tree removal incomplete: <n> tree(s) under <workspace> could not be removed`, each named with the operating system's reason. Real test: `tests/product/build_trees.mjs`.

- **`stado web route` publishes a `cloudflare`-edge hostname through the Cloudflare tunnel:** it refused every such hostname and named `stado tunnel route` with item names to type, so a host behind a residential uplink, whose 80 and 443 nothing outside can reach, published nothing. The route now resolves the connector host and origin (a product's own host and loopback port, or the active host and endpoint of the service it fronts), reads the items playing `stado:role:cloudflare-api` and `stado:role:cloudflare-tunnel` in the owner vault, and runs the same ingress, connector token and proxied `CNAME` steps `stado tunnel route` runs; `--check` prints that plan and changes nothing. Refusals: a role no item plays (`no item in the owner vault on <owner> plays role cloudflare-api; tag the item … with stado credentials item retag …`), a mount or a redirect on the cloudflare edge (a tunnel route carries a whole hostname to one origin), a fronted service the directory does not declare or that has no endpoint on its active host, and a connector service not declared on that host. The zone must be served by Cloudflare first (`stado dns delegate <zone> --provider cloudflare`). `stado web remove` still leaves the tunnel route and names `stado tunnel remove`.

### Changed

- **Every hidden hyphenated verb is a visible verb of the object it acts on, and the hyphenated names are gone:** `release delivery worker` (was `delivery-worker`), `release active binary|dir` (`active-binary`, `active-dir`), `release local install|restore|converge` (`install-local`, `restore-local`, `converge-local-readers`), `host local run|api|repair|audit|port` (`run-locked`, `object-api-local`, `release-store-repair-local`, `backup-audit-local`, `free-port-local`), `host local reconcile phase|step|worker` (`storage-root-reconcile-local|host|worker`), `credentials item summarize` (`summarize-local`), `credentials token register|custody` (`register-item-local`, `custody-local`), `space file local retire|remove` (`retire-local`, `remove-local`), `service roles` (`serve-roles`), `service image refresh` (`refresh-image`) and `service env write` (`unit-env-local`). Every caller moves in the same change: the delivery job commands, the CLI recipe's `after_install`, Stado's, Skarbiec's, Jeden's and wisent-integrations' delivery argv, Weles's Skarbiec lookup, the host-exec allowlist, the adopt handoff, the credentials host lookup, the object-API recovery and backup-audit programs, the storage-root transaction's scripts, the `service update` host script and Tama's Brama relay. A host whose installed Stado predates this release answers these argv with clap's unknown-subcommand error until `stado release version converge --host <host>` puts the release there.

- **The object-API recovery's readers and the storage-root transaction's host steps are object verbs too:** `host local api plist render|equal`, `boundary ready` and `skarbiec plan|ownership|upstream|proxy` replace the derived `render-plist`, `plist-equal`, `boundary-ready`, `skarbiec-plan`, `skarbiec-ownership`, `skarbiec-upstream` and `skarbiec-proxy-match`; `host local reconcile step unit snapshot|restore`, `listener closed`, `object runtime` and `store served` replace `unit-snapshot`, `restore-unit`, `listener-closed`, `object-runtime` and `served-store`. `deploy/recover_object_api/*.sh` and the transaction's step scripts call the new names.
