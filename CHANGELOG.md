## Unreleased

### Added

- **Stado serves the S3 API at `/s3` on the object API listener:** a bucket is a namespace `object_api.namespaces` declares, its access key id is the namespace and its secret access key is the namespace's object API bearer, so the AWS CLI, the AWS SDKs, rclone and any other S3 client read and write the same `stado://<namespace>/<key>` objects `/api/object` serves, under the same per-prefix policy. Served: ListBuckets, HeadBucket, GetBucketLocation, ListObjects and ListObjectsV2, GetObject and HeadObject with ranges and preconditions, PutObject (create-only with `If-None-Match: *`, compare-and-swap with `If-Match`), CopyObject, DeleteObject, DeleteObjects and multipart uploads staged where `stado storage put` stages its chunks. SigV4 header and presigned signatures, aws-chunked bodies with chunk and trailer signatures, and every stated checksum (CRC32, CRC32C, CRC64NVME, SHA-1, SHA-256, Content-MD5) are verified before a byte is stored; anything else answers `NotImplemented` naming what was asked. The listener answers `Expect: 100-continue`.
- **Every S3 API object store is a storage backend of its own:** `storage.backend` takes `cloudflare` (R2), `backblaze` (B2), `wasabi`, `digitalocean` (Spaces), `hetzner`, `scaleway`, `ovhcloud`, `akamai` (Linode), `vultr`, `oracle`, `ibm`, `alibaba`, `tencent`, `huawei`, `exoscale`, `ionos`, `contabo`, `upcloud`, `storj`, `filebase`, `tigris`, `yandex`, `idrive-e2`, the self-hosted `minio`, `garage`, `seaweedfs` and `ceph`, and `s3-compatible` for any other endpoint URL. Each named provider builds its endpoint, addressing and signing region from its published S3 API contract and asks only for what that is built from (account, region or endpoint, bucket, credential role) under `storage.s3_compatible.*`, none defaulted, with the same keys under `storage.backup.s3_compatible` and on both sides of `stado storage copy` and `verify`. `stado capabilities object-storage` lists every one.
- **`stado storage bucket create|list|show|update|rotate|delete --host HOST`** runs a self-hosted store: a bucket is one namespace of the host's `object_api.namespaces` with its per-prefix grant and its key in the vault item the namespace is bound to; `create` mints the key, grants Stado's verifier its read, writes the declaration, reads it back from the host and, with `--reload-service`, restarts the unit that serves it, removing the key again when the declaration is refused. No answer carries the key. The `stado` backend answers to `self-hosted` as well, and Stado Desktop's Space panel runs every bucket verb.
- **`stado storage url URI --presign get|put --expires SECONDS`** prints a presigned S3 URL a holder uses without a bearer until it expires, and **`stado storage s3-endpoint NAMESPACE [--json]`** prints the endpoint, bucket, access key id, region, addressing and secret source an S3 client needs after one signed HeadBucket proves them. Stado Desktop's Space panel offers both, and the store copy and compare forms carry the S3-compatible fields.
- **`stado storage cp|mv SOURCE TARGET [--json]` copies or moves an object to another key of its namespace on the server:** the copy is the S3 endpoint's CopyObject signed with the client's object API bearer, so the bytes never come to the machine that asked and the namespace's grant decides it (`get` on the source, `put` on the target, `delete` on the source for `mv`); `mv` removes the source only after the copy answered, so a failed move leaves it. Two namespaces, a release object and one object named twice are refused before anything is asked; a refused copy names the endpoint's code (`NoSuchKey`, `AccessDenied`). Stado Desktop's Space panel offers both.
- **The S3 endpoint answers GetBucketVersioning and refuses a bucket configuration it does not serve:** a bucket reads as never versioned, since Stado keeps no object versions, so a client that checks versioning before it writes (a backup tool, a GUI browser) proceeds; a bucket `PUT` with a sub-resource (`?versioning`, `?acl`, `?policy`, …) now answers `501 NotImplemented` naming it instead of `409 BucketAlreadyOwnedByYou`, which told a client turning versioning on that its bucket already existed.
- **Stado Desktop runs every single-object storage verb:** the Space panel had operations for listing, copying and comparing stores but none for one object, so reading, uploading or removing an object, or discarding an interrupted upload, needed the command line. It now offers `stado storage objects`, `stat`, `cat`, `get`, `put` (media type, `--if-absent`), `rm` and `abort-upload` (`--dry-run`) with the fields their arguments take.
- **`stado storage ls PREFIX --size` no longer downloads every object to measure it:** every backend's listing states each object's size, yet `--size` read each body to count its bytes, so sizing a large prefix moved all of its data. The size is now the one the listing states, and a body is read only for an object the listing stated none for (one removed between the listing and its stat); `size_from` says `listing` or `body`.
- **Stado's S3 endpoint lists the uploads in progress and their parts:** ListMultipartUploads (prefix, `key-marker`, `upload-id-marker`, `max-uploads`, `encoding-type=url`) answers every upload under a prefix the namespace may list, and ListParts (`part-number-marker`, `max-parts`) the parts of one upload with their sizes and the ETags UploadPart gave, which each part now keeps as its `stado-upload-sha256` metadata, so a part is never read to list it. A client finds an upload it abandoned and aborts it by id instead of leaving its parts on the disk; the object API's own chunked uploads have no manifest and are not listed. Both needed answering `501 NotImplemented` before.
- **A server-side copy of a large object through Stado's S3 endpoint keeps its bytes:** the AWS CLI copies an object above its multipart threshold with UploadPartCopy, a PUT that names its source in `x-amz-copy-source` and carries no body, and the endpoint took it for an UploadPart, staged each part empty and completed an object with none of the source's bytes. UploadPartCopy now reads the source the way CopyObject does (same namespace, `get` on it, the `x-amz-copy-source-if-*` preconditions), stages the whole of it or the one `x-amz-copy-source-range` it names, and refuses a range past the source's last byte as `InvalidRange`.
- **Agents on rented machines open every S3 API store:** the startup templates carry the `storage.s3_compatible.*` bindings, primary and backup, and the scheduler decides each storage backend explicitly before a machine is created: it requires what that backend declares (for a named provider, what its endpoint is built from), refuses an S3 API store whose credential role the agent's scoped vault grant does not name, refuses a backend name the catalog does not know instead of reporting it as an unsupported kind, and refuses a `stado` store with the reason (its bearer is a file never delivered to the machine) and the S3 route to the same self-hosted store. A provider that is not an execution variant of the catalog is refused instead of reaching the agent under its raw name. The AWS and Azure templates no longer set guessed Hugging Face download and ETag timeouts. `stado recovery` refuses an endpoint kind the catalog does not know and checks a named provider's account, region or endpoint up front.
- **An S3 API store other than Amazon's proves it honours conditional writes before the queue relies on them:** before the first if-absent create or compare-and-swap, Stado creates, re-creates and replaces one object under `system/conditional-writes/` and removes it; a store that stores the second create or the stale replacement is refused for every such write, naming the store and the precondition it ignored, instead of letting two holders win the same lease. A check that could not finish decides nothing and is asked again. A compare-and-swap whose store answers no ETag is refused instead of returning an empty version, and a metadata rewrite keeps the object's own content type instead of inventing one.

- **`stado product advisories list|apply [PRODUCT] [--advisory ID]... [--database ORIGIN] [--json]` reads published security advisories against every committed `Cargo.lock` of the workspace:** a product compiles in what its lock resolves, so a flaw published against a TLS verifier or a root bundle stays shipped until each lock moves, and nothing read the locks against the advisories. `list` reads the crates.io archive of an OSV database once and names, per lockfile, each affected package version with its advisory, aliases, fixed versions, the first fix Cargo may lock without a manifest change and the packages that depend on it; `apply` moves each one that has such a fix with `cargo update --precise`, refuses a lockfile with uncommitted changes, names as `unfixed` each one whose fix needs a manifest change, and commits nothing. Stado Desktop's Products screen runs both. Real journey: `tests/product/advisories/locks.mjs`.

- **`stado product restart [--if-running] [--json] APP.app` restarts an installed macOS application, and a desktop installation restarts its own:** the verb reads the bundle's identifier, ends the running application through LaunchServices, waits on its process in the register of open waits, opens the bundle and reads it running, and refuses naming the bundle, the plist or the LaunchServices answer it could not use. `stado product install` and `update` of a desktop surface now restart each placed bundle whose application runs, leave a stopped one stopped and keep the answers on the receipt as `restarted`, so no build script restarts its app itself; Stado Desktop's copy of that script is gone. Stado Desktop's Products screen runs the same verb.

- **`stado release history` rewrites a checkout's unpushed commits by a plan:** a push review refuses format-only commits, fixups, commits that take back what another swept in and messages their patch does not match, and each was repaired by hand in a checkout other work shares. The plan names every unpushed commit once as `pick`, `reword`, `fold`, `drop` or `split` (by path); the new commits are made in a private index inside the git directory, the branch moves by compare-and-swap only when the new history keeps `HEAD`'s tree, the working tree and index stay as they were, and with `--notes-ref` an unaltered commit keeps its note while every other is listed as needing its own. Stado Desktop's release operations run the same command. Real test: `cargo test --test release-history`.

- **`stado sandbox` drives Boat sandboxes directly, as an agent does:** `list`, `show`, `create [--ttl-seconds] [--no-env]`, `exec <id> [--cwd] '<command line>'`, `read <id> <path> --encoding`, `write <id> <path> --from <file> --encoding`, `fork`, `stop`, `resume` and `delete`, each one Boat Public API v1 call through the boat provider's own client and settings, printed as JSON. A command that does not succeed fails `exec` naming its exit code, signal or limit; a refusal Boat answered keeps its status, code and request id as the error's details, reported `not_found` for a sandbox Boat does not hold. Stado Desktop's Compute providers screen has the same operations under Sandboxes.
- **`stado sandbox` covers what an agent does in a sandbox besides its life:** `update <id> [--name] [--ttl-seconds | --no-auto-stop]` renames it or changes or clears when it stops by itself; `prompt <id> '<prompt>' --provider [--model] [--reasoning-effort]` hands its coding agent a prompt and `prompt-status <id> <prompt-id>` reads the run; `interrupt` stops every conversation in it; `events <id> --sort asc|desc [--cursor] [--type]` prints one page of its events with the next cursor; `ssh-key <id> --public-key-file` allows an OpenSSH key; `download <id> <path> --to <file>` writes a file or folder into a new local file and refuses one that exists. An option given with an empty value is refused by name rather than sent as absent. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox` keeps a sandbox's disk as a template and gives its ports public URLs:** `snapshot save <id> <name>` freezes a sandbox's disk under a name (Boat saves it in the background, its status turning `ready` or `failed`), `snapshot list`, `snapshot show <name>` and `snapshot delete <name>` read and remove named snapshots, and `create --from <name>` starts a new sandbox from one; `host <id> <port> [--public] [--localhost]` gives a port inside the sandbox a stable HTTPS URL, carrying its access token unless `--public`. A name is sent as one URL path segment, so it cannot address another resource. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox` runs long commands in the background and reports cost:** `exec --detach` starts a command line in the background and prints its process id at once, instead of waiting for Boat's limit on a command; `process status <id> <process>` reads whether it runs, its exit code and its recent log, and `process stop <id> <process>` stops it; `usage <id>` prints what the sandbox has run and cost. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox` steers a working agent and shows the desktop:** `steer <id> '<instruction>' [--conversation <id>]` gives the coding agent's running turn an extra instruction without stopping it, and `desktop <id>` prints the URL that streams the sandbox's desktop, which carries a secret. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox` takes files back out of a sandbox's snapshots, also while it is stopped:** `snapshot history <id>` lists every snapshot of a sandbox's disk, `snapshot latest <id>` shows the one resume and fork start from, `snapshot tree <snapshot>` lists the files a snapshot holds with their sizes, and `snapshot get <snapshot> <path> --to <file>` writes a file, or a folder as a tar, into a new local file and refuses one that exists. A snapshot id is sent as one URL path segment. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox environment` sets up what every new sandbox starts with:** `list`, `create <name>`, `delete`, `set-var <environment> <key>` (the value is the one line on standard input, so it never stands on a command line; an empty or multi-line value is refused), `rm-var`, `set-file <environment> <path> --from <file>`, `rm-file` and `add-repo <environment> <repository> [--base-branch]` manage Boat environments, and `create --environment <id>` starts a sandbox with one. An environment change answers `success=true` rather than `ok` and a type, which the Boat transport now reads as such. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox` recovers a stuck sandbox, forces a stop and shares one:** `recover <id>` power-cycles the machine of a sandbox that stopped answering without touching its disk, and Boat's refusal (`sandbox_is_reachable`, `too_soon`, `no_machine`, `recover_unsupported`) is kept with its code; `stop <id> --force` stops a sandbox whose disk save keeps failing, keeping its last successful snapshot and losing what was written since; `share <id>` lets every member of the organization paying for it use it and wipes the creator's logins from it at its next start, printing `restartRequired` while a running sandbox still holds them. Sharing answers without Boat's `ok` and type, which the transport reads as such. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox` reads what ran in a sandbox, also while it is stopped:** `conversations <id>` lists its agent conversations with the one a prompt would continue marked current; `history <id> [--mode sync,stream,detached,process,commands] [--query <text>] [--limit <n>] [--cursor <next>]` prints one page of the commands and other processes that ran in it, newest first; `command <id> <command id>` prints one of them; `logs <id> <command id> --stream stdout|stderr --encoding utf8|base64 [--offset <next>]` reads its stored output from an offset, with `nextOffset` and `done` to read on; and `processes <id>` lists its processes, busiest first, or the last sample Boat kept of a stopped one. An empty `--query` or `--cursor` is refused by name. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox file-url` moves files of any size without the key:** `file-url <id> <path> --method download|upload [--ttl-seconds <n>]` prints a short-lived URL the sandbox serves itself for that one file; a plain GET of a download URL gives the file whole and a plain PUT of the bytes to an upload URL writes it, replacing an existing file only once the upload completes. The URL is a secret until it expires; without `--ttl-seconds` Boat chooses its lifetime, and one that is not positive is refused before any request. Stado Desktop's Sandboxes section has the same operation.
- **`stado sandbox webhook` tells an agent factory about sandbox lifecycle events without polling:** `webhook create <url> --event <event>[,<event>...] [--name]` registers a public HTTPS endpoint for `sandbox.ready`, `sandbox.error`, `sandbox.archived`, `sandbox.hydrated`, `sandbox.degraded` and `sandbox.recovered` and prints its signing secret, which Boat never shows again; `webhook list` and `webhook show <webhook>` read endpoints without their secrets; `webhook update <webhook> [--url] [--event] [--name]` changes one and keeps its secret; `webhook rotate <webhook>` prints a new secret; `webhook delete <webhook>` removes one and its queued deliveries. An empty `--name` or `--url` is refused by name, and an update naming nothing is refused by the client. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox snapshot share` hands a prepared disk to another Boat account:** `snapshot share <name>` makes a secret code, printed only now, with which any Boat account starts a sandbox from that named snapshot through `create --from <code>`, billed to itself; `snapshot shares <name>` lists the codes, active and revoked, without the codes themselves; `snapshot unshare <name> <share id>` revokes one, after which a sandbox from it is refused (`snapshot_not_found`) while those already made keep their copy. Everything on the disk is shared. Stado Desktop's Sandboxes section has the same operations.
- **`stado sandbox` shows and limits what a sandbox's agents spend on AI:** `ai-usage <id> [--days <n>]` prints the requests its agents made through Boat's AI proxy per UTC day, credential and model, with their tokens, errors and cost, and whether it is blocked; `ai-access <id> --state allowed|blocked` lets those requests through or has the proxy refuse them, running or stopped (a sandbox holding real keys is not affected). Stado Desktop's Sandboxes section has the same operations, and its environment and webhook operations now live in their own list beside the per-sandbox ones.
- **`stado sandbox environment repos` finds the repository id `add-repo` takes:** it lists the GitHub repositories Boat can clone, grouped by installation, each with the `databaseId` that `environment add-repo` takes, and the ones already selected; `--query` filters by name, `--sync` reads GitHub again first and `--cursor` reads the next page, and an empty `--query` or `--cursor` is refused by name. Stado Desktop's Sandboxes section has the same operation.
- **`stado service file sync --source-file -`, `stado service declare --file -` and `stado service file fetch --dest-file -` use standard input and output:** a caller holding a secret or a declaration in memory had to write it to a file of its own first, typically under the system temporary directory, so a service's secret stood on the operator host's disk for as long as the call ran, and a caller reading a service's file had to name a local file to receive it. With `-` the content is read from standard input, never written on this host, and carried to the target as a file's would be; `file sync` refuses `-` when standard input is a terminal and refuses empty input naming `standard input`. `file fetch --dest-file -` writes the verified bytes to standard output and nothing else there: it refuses `--json` beside it and a name that matches more than one unit, and a fetch that cannot be believed writes nothing and exits non-zero with its cause. A file source still has to be absolute, a regular file and owner-only unless `--executable` is set. `file sync` no longer refuses a file above a size written into it (1 MiB, 96 MiB executable), a number nothing declared; the channel carries what it is given. `service declare` also states its loopback endpoint through the address type instead of a written address, and refuses a `port` that is no TCP port with the conversion's reason. `service onboarding set --surfaces` takes its surfaces comma-separated or with the flag repeated, no longer as several words after one flag.

- **The wait-for graph follows every resource a wait can stand on, not only lock files:** a process could hold a product's lock while waiting on a service whose repair needs a new revision that only an installation waiting on that same lock can deliver, and each wait was listed alone with nothing naming the cycle. A wait now awaits a resource `<kind>:<id>` — `lock`, `host`, `service`, `revision`, `unit` or `port` — and what a process holds is recorded beside the register (`~/.stado/waits.holds`): by the process itself through `stado_wait::hold`, or for it with `stado waits hold --resource <kind>:<id> --pid <pid>`, `stado waits release <id>` and `stado waits holds`. `stado_wait::begin_on`, `blocking_on`, `until_on` and `stado waits open --awaits <kind>:<id>` follow the graph from the resource's holders through their own waits and refuse at once a wait whose chain reaches the waiter or a process whose completion needs it, naming every process, the resource it waits on and its holder; `stado waits cycles` names cycles standing among every kind, its `awaits` as `<kind>:<id>`. Stado Desktop's Waits section adds **Read held resources**. Real test: `cargo test --manifest-path stado-rs/Cargo.toml --test wait-cycle-resource`.

- **`stado quality command-tree` lists the one-off commands a CLI still holds:** the quality check refuses a revision whose built CLI has a command that duplicates or fragments a general primitive, so the list of what is left to fold in could be read only as a refusal, and a class of such commands had no inventory to measure its repair by. `stado quality command-tree [--root] [--revision] [--json]` builds the committed revision's CLI as its installation builds it, runs no gate, reads the whole command tree and has a model judge it, and exits 0 with `{"product", "revision", "cli", "remaining"}`; a tree no model judged is refused rather than listed empty. Stado Desktop's release operations run the same command. Real test: `cargo test --manifest-path stado-rs/Cargo.toml --test quality-command-tree-inventory`.

- **`stado placement profile list|show|declare|remove` manages placement profiles:** a profile, the service group `placement standby` prepares a host for and `placement move` relocates, could only enter the registry by importing a whole document, so a service with no profile could never be moved. `declare --file PATH|-` adds or replaces one from its JSON and links each of its services' directory routes to it in the same commit, advancing the directory generation once; it refuses a service another profile holds, a service the directory does not declare, a redeclaration that drops a held service, and a profile a move holds. `remove` turns its services back into fixed routes naming the unit declared on their active host. A profile may now name only the host it is placed on, for `standby` to add destinations to, and may declare no state when its services keep nothing durable. Stado Desktop's Routes operations run the same verbs. Real test: `cargo test --manifest-path stado-rs/Cargo.toml --test placement-profile`.

### Changed

- **The sandbox provider is Boat, and Stado speaks Boat Public API v1:** Box was renamed Boat, and its legacy API (`ascii.dev/api/box/v1`, `/boxes`) answers with a `Sunset` notice. The provider id is now `boat` (the `box` and `box-ascii` names are gone), its settings are `boat.ttl_seconds`, `boat.release_mode` and `boat.api_url` in the profile with the environment overrides `BOAT_TTL_SECONDS`, `BOAT_RELEASE_MODE` and `BOAT_API_URL` (the `BOX_*` variables are no longer read), and its key is the Skarbiec item tagged `stado:role:cloud-boat`, which a workload grant may not carry. Requests go to `https://boat.dev/api/v1/sandboxes` with Boat's own response types; a deletion carries the confirmation Boat requires and accepts Boat's background deletion; a sandbox Boat cancelled for want of a machine fails its job by name; an account at its active-sandbox limit is refused with both counts; and an answer that echoes the API key has it replaced by `[REDACTED]` before it becomes an error.

### Fixed

- **The delivery routine is admitted to build what it installs:** `stado ci plan set` and `stado ci run` asked Oko only whether each step may be installed for the plan's purpose, while the `stado product install` a step starts asks whether the product may be built, with no purpose. Under a ruling that forbids building until the build-first items are done, a plan declared for such an item passed every quality gate and was then refused at its first install (`build of <product> is not run …`). Every step now asks `oko admit build` and `oko admit install` for the plan's purpose before anything runs, and both admissions are inherited by the install it starts; a purpose the rulings do not admit for either is refused before anything is built.

- **The name register says what a claimed repository is when GitHub does not:** `stado product catalog --names` wrote `(no description on GitHub)` for every repository without a GitHub description, including the ones a catalog product claims and describes, so most rows of the register named nothing. A repository with no GitHub description now says what the catalog says it is: a product's owner repository carries the product's catalog description, and any other repository the product claims carries its surface kind and the product before it (``desktop surface of `weles`: …``), so a desktop app or client library never reads as the product itself. A new `from` column says whether each row's text came from `GitHub` or the `catalog`; a repository described by neither reads `(no description on GitHub or in the catalog)`. A repository `gh repo list` gives no `nameWithOwner` is refused by name instead of being looked up under its bare name.

- **Stado no longer trusts the eight compromised eMudhra intermediates:** it locked rustls-webpki 0.103.13 and webpki-roots 1.0.9 (RUSTSEC-2026-0382, RUSTSEC-2026-0381), and the AWS SDKs' default `rustls` feature pulled in their legacy hyper 0.14 client on rustls 0.21 and rustls-webpki 0.101.7, for which no fixed release exists. The SDKs now take their default features less `rustls`, so every AWS call uses `default-https-client`, and the lock carries rustls-webpki 0.103.16 and webpki-roots 1.0.10: a connection to a host serving one of those chains is refused with `invalid peer certificate: CertDistrusted`.

- **A Swift package's tests and programs run under `stado product swift` keep their Git transports:** the one `swift` process that compiled the package also ran its tests or program with `GIT_ALLOW_PROTOCOL` set empty, so a test that used Git itself (a fixture repository over `file://`) failed with `transport file not allowed`, as the Cargo operations did before their run left resolution. Sources are still resolved with Git transports off; the `swift build`, `test` or `run` that follows now passes `--skip-update`, so it updates no dependency, and leaves the caller's transports to what it runs.

- **`stado host exec <target> -- stado resolver status --json` is approved:** a workstation's resolver refusal names a request another host holds unanswered and tells the reader to ask that host's `stado resolver status`, but the host-exec allowlist did not approve the command, so the held adapter, its phase and age, and the object API's vault consultations on that host could not be read through Stado. The fixed read-only verb is now an approved connectivity read; it reads the state files the resolver already published and changes nothing.

- **`stado placement move` keeps what the destination held at a state path instead of deleting it:** the move writes each state the profile declares over the destination's path behind a backup, and after the commit it deleted that backup, so a destination that held its own file there (its own audit journal, say) lost it although it was never part of the source. The backup is now renamed to `<path>.replaced-by-placement-<transaction>` beside the moved state, and the receipt lists each such path under `kept_replaced_state` (`kept what <host> held there before the move: <path>`); a backup that could not be settled is listed under `unsettled_state` with its cause instead of a warning nobody reads. A state read that marks its file present without a payload is now refused naming the state, rather than read as an empty file.

- **`stado placement move` can move a profile to a host that stands by for it:** `placement standby` writes the destination into the directory as a `standby` address, while the move's cutover required an `endpoints` entry for it, so a move to a standby host started the destination, retired the source and was then refused at the commit with `service route for profile … has no endpoint on …` and rolled back. The cutover now moves the destination's standby address into `endpoints` in the committed document, and a destination the directory names under neither map is refused before the source is fenced, naming the service and the `placement standby` that would name it.

- **A service repair renders its unit the way `service ensure` does, and no platform is guessed:** the service reconciler's repair resolved a unit's program and environment with its own copy of `service ensure`'s steps, so the two could render one service differently. Both now render through one resolution, and every placeholder expansion takes the target's stated release platform; the expansion no longer has a form without one. A unit's identity and its bundled declaration are read without standing an empty value in for a missing one.

- **A refused gate's findings are read from Cargo's records, not from the words of its report:** a gate's diagnostics were read by matching the compiler's human text — a header line at the margin, a `-->` arrow, a lint named in a note — so a change of wording lost a finding or made one of a line that was none. A gate that compiles with Cargo now runs with `--message-format=json`, and each diagnostic with a primary span is read from Cargo's own record: its location, the lint or error code the record carries, its level and message; the rendered text is printed as the compiler wrote it. `stado product cargo` reads its `findings` the same way. A gate that sets `--message-format` itself is refused naming it, and a Cargo record that does not read is refused quoting it.

- **A host's Stado whose object API accepts and answers nothing is repaired by its beacon and its peers:** the catalog declared no answering question for the stado service, so a held object API was never asked and never repaired; every Stado command and judged hook that read the registry through that host stood until someone ran the repair by hand. The stado service now declares `GET /api/release/object?uri=stado://releases/answering-probe` with the `object-api` repair: the public release route answers before host trust and Skarbiec and reads the store, so a healthy host answers at once (404, absent) and a held store holds the question past the bound, and the declared repair runs on the resolver's refresh interval.

- **A Boat environment change that does not take says why:** `stado sandbox environment` changes refused with `Boat answered … without success=true` and nothing of Boat's answer. The refusal now carries Boat's `error` member, or names the members the answer held when it has none; the rest of the answer is not quoted, since a change may echo the variable or file it was given.

- **The backup audit keeps every unreadable row's cause:** each marker row the reader could not read replaced the cause of the one before it, an unavailable marker that named no reason cleared the audit's unavailability, a namespace inventory ended without a root was passed over, and a size, count, hex path or namespace that did not read was said without its parser's error. `stado host backup-audit` now marks the audit unavailable with every such row's cause and line, in the order printed.

- **A host's link block names every datum it could not read and why:** a beacon whose tailnet, sleep or interface-change probe failed published a null with no cause, and a journal line or timestamp it could not read was dropped silently. Each such datum now stays null with its cause in the block's `unread` list (the probe and its exit status and stderr, the line that is not JSON, the stamp no format reads, an undeclared window or `PATH`); `stado host link` prints each on an `unread:` line and as `link_unread` in `--json`, the Desktop Link section shows them as Unread link data, and a link block that is not one is reported there with its parse error.

- **The public status page reads requests as the API listener does and stops when it cannot accept:** `stado public-status serve` read the request head with a parser of its own, with no bound on its size, and an accept that failed (the process out of descriptors) was tried again at once without end. The page now reads each request through the listener's own reader under its declared or measured request limits, answers a method that is no HTTP method with 400, and ends with the accept error when the failure is not a client that gave up before it was accepted.

- **The wait-for graph says what it could not read instead of missing that edge:** a lock file that could not be read, a holder pid that was no number, a `ps` that could not run and a parent pid `ps` printed unreadably each ended the graph walk as if no process held the lock, so a wait that closed a cycle could start and stand. Each is now the graph's read error, said beside the wait's line (`graf czekan nieodczytany`) and by `stado waits cycles`; a lock file that is gone or names no holder still takes no part.

- **A GCP exhaustion mark that is not epoch seconds is logged, and no mark is dated at the epoch:** a mark map entry whose value was not a number was left out without a word, and the next write dropped it; a clock before the Unix epoch dated a new mark at zero, the oldest, so that zone was retried first. Each such entry is now logged with its key and why, and a mark the clock cannot date is refused.

- **A waiting or refused installation names why it cannot read the surface lock's holder:** a holder record that could not be read, or one that was not a record, was said as "cannot be read" without the cause or as a record from a Stado before holders were recorded, and a pid no process can have read as a holder no longer running. The read error and the parse error are now said with the record, only an empty record is taken for an older Stado's, and an impossible pid is named as such.

- **A recorded repair that names no repository is refused, not dropped:** the release queue, its plan and the delivery routine each read Oko's open repairs, and a repair recorded without `<repository>@<commit>` was left out, so its defect stayed open with no release ever carrying it and nothing saying why. The three now share one reader, which refuses while Oko holds such a record, naming each defect and its record and how to record it again (`oko defects repaired ID --revision REPOSITORY@COMMIT`); a queue pass queues nothing and says so on stderr. Real journey: `tests/release/delivery-queue-order.mjs`.

- **The space reclaim janitor keeps the lock, hold and state file names every release shares:** moving the janitor under the space reclaim engine renamed its run lock, holder records, state file, workload holds and turn request, so on a host being moved to the new release a build still running from the previous one held a lock and wrote a hold the new janitor never looked at, and the janitor could delete the tree that build was writing. The files keep their names (`disk-cleanup.lock`, `disk-cleanup-holds/`, `disk-cleanup-turn.json`, `disk-cleanup-state.json` and their companions), listed on the space page. A lock holder token made on a clock before the Unix epoch, and a holder record that cannot be inspected, are refused with their cause instead of being written over. The native journeys fill their volume until the product's own `host gates` reads it as full.

- **`stado overview` says which billing figures it could not read instead of printing stand-ins:** a figure carried in no numeric shape read as not reported, a part of a GCP `Money` that was not a number read as zero, a budget without a display name printed as `unnamed`, one without a calendar period as `CUSTOM`, a budget sized by the last period's spend as `USD 0.00`, a `Money` without its currency as USD, and Azure's unavailable answer without a status or detail as `unavailable — no detail`. Each figure is now printed as reported, `not reported`, or `unreadable` with the value; a budget is named by its resource name when it has no display name, and its custom period and last-period amount are said as such. A billing report without its monthly list, or a promotion credit without a readable cumulative, is said as such instead of summed as zero.

- **`stado credentials seed-freshness` says what it could not read instead of reading it as nothing:** a sign-in attempt without its flags or markers was read as one where nothing fired, a vault row without a seed state as an unreadable seed, and a vault answer whose rows lacked an item or state dropped them, so the enrolment command could take a held row for an absent one. Each is now refused quoting the row. The host reader reports journal lines that are not JSON, sign-ins without detail text and sign-ins naming no login item, and recording stores it could not list, and the report prints them beside its counts; an attempt dated by neither `at_ms` nor a readable `at` carries no time and is refused rather than sorted as the oldest. A report without its findings list says so instead of saying no row holds a seed.

- **The Desktop's read-only judgement and the quota responder's billing judgement read a choice, not a line's first word:** both asked a model through `oko gateway send` to answer one line and took the line's first word as the verdict, so a model that framed its answer otherwise was read as the other option. Both now ask through `oko gateway object` for one object whose `choice` is one of the named options (`READ` or `CHANGES`, `BILLING` or `OTHER`) with its reason, bound to a strict JSON Schema; an answer outside the options is the error. The quota responder also refuses a ticket listed without a name and a clock before the Unix epoch by name, instead of replying to ticket "" or stamping its reply at zero.
- **The billing watchdog's mail reading is one schema-bound object:** the model was asked to answer with one JSON object written in the prompt and its whole answer was parsed, so a model that wrapped the object in prose left the notice unread. The reading is now asked through `oko gateway object`, bound to a strict JSON Schema of `categories`, a list of names, and `action`, a sentence or null.
- **Every model reading in Stado is one schema-bound object, and the prose call is gone:** whether a failed GPU job ran out of memory, which configd log messages record an interface change, which subcommands a CLI's help advertises and which commands of its tree break the CLI rules were asked through `oko gateway send` with the answer's shape written into the prompt, and read by the line's first word or parsed as JSON afterwards, so an answer framed otherwise read as the other option or failed. Each is now asked through `oko gateway object` under a strict JSON Schema: the out-of-memory reading chooses `OUT_OF_MEMORY` or `OTHER`, the interface changes may name only the messages shown, and a CLI rule violation may name only a command of the tree. `model_judgement::ask` is removed. A `log show` line that is not JSON is now said with its cause instead of skipped, and the PyTorch out-of-memory figures are read by a pattern every match of which is a number.
- **The resolver says whether a service answers, not only what it still holds:** a request left `~/.stado/resolver-waiting.json` the moment its client closed, so a service every client gave up on before it answered showed only young waits and read as healthy while Brama answered none of the judged hooks' requests. Every relayed request that ends is now recorded per service in `~/.stado/resolver-answers.json`: `last_answered_at`, and while the service has answered none since, `first_unanswered_at` and `last_unanswered_at`; the first answer clears both. Reading a request line no longer drops a decoding error: bytes that are not text are shown as the replacement character.
- **`stado product install|update --wait` waits through every janitor turn instead of refusing after one pass:** the operation waited for the running workloads, ran the janitor's pass and refused when the janitor asked for its turn again. That pass walks the build caches before it takes the exclusive lock, so a workload that took a hold during the walk turned the pass away and made it ask for the next turn, and on a host whose volume stays past the disk-full threshold a source install found no window. The operation now says each such round on stderr, with the pass's report and the holders it waits on, and waits for the next turn until a pass has run and its own hold is taken.
- **A `linux-account` scratch lease is entered instead of deleted again on Linux:** the program that trusts a new lease account with the keys that reach its host called `/usr/sbin/chown`, a path macOS has and Ubuntu does not, so `stado scratch create` on a Linux host removed the account it had just created and refused with `chown: not found`. The program now writes `authorized_keys` with `/usr/bin/install -m 600 -o <account>`, the tool it already uses for the `.ssh` directory and which every declared platform carries.
- **`stado service serving <name> --wait` reads the declared port through the unit the host declares for `<name>`:** asked by product name (as `stado product install stado` asks after replacing the resident unit), it found the host's unit `com.wisent.stado` but looked the directory up by the product name alone, so a directory that keys the endpoint under another service name (`managed_service: com.wisent.stado`) answered "declares no endpoint" and the install rolled back a candidate that was serving. When the name is not a directory key, the declared unit's label now selects the endpoint, and the refusal names both the name and the unit it tried.
- **`stado resolver snapshot` gives up on a resolver that accepts and answers nothing at that resolver's refresh interval:** the authority's snapshot command asked its own resolver's API with no measure, and the reader that started it over SSH gave up at the refresh interval and closed its channel, so each abandoned read left a snapshot process and its connection on the authority; hundreds of them held the authority's connections and file descriptors. The command now stops at the refresh interval this host declares and refuses with `the resolver answering at <bind> accepted the request and answered nothing: `stado waits --json` lists what it waits on, and `stado service logs com.wisent.stado` says what its unit is doing`. A resolver API that answers an error body that is not JSON is refused with that body and the parse error instead of a bare status.
- **A directory read that cannot reach its authority no longer waits on that authority's store to record the refusal:** the `authority_unreachable` refusal was written to the fleet store and awaited, and that store is served from the authority host the read had just failed to reach, so each failing read (every command that reads the registry) waited on that host a second time before its caller saw the refusal and added one more write to the queue in front of it. The record is now written detached, as the resolver's `directory_cache_stale` refusal already was: a one-shot command returns its refusal at once and loses its own copy if it exits first, and the resolver on the same machine, which reads the same authority, records the refusal from its long-lived process. `report_refusal`, the awaited publisher, is gone.
- **`stado product dependencies` no longer reads a product's documentation or examples as calls:** a product named in a top-level `docs/` page (any case) or in a file under an `examples/` directory at any depth was reported as a dependency the product had not declared, so a page describing another product, or an example script a person copies, asked for a catalog alternative the running product never needed. Both are now left out with the tests, prose, forge automation, lockfiles and release tooling the audit already skips; line numbers are still counted from one.
- **`stado quality check` refuses a Swift package target that holds two sources of one file name:** SwiftPM names each object file of a target after its source's file name, so two `Models.swift` in different folders of one target are two producers of one object file and the target does not build, and nothing said so before a build. The source step now reads every Swift package of the exported tree and refuses such a target, naming each shared name, compared folded to lowercase, and the sources holding it.
- **The pre-push quality check passes a repository that declares nothing:** `stado quality check --pre-push --if-declared` read a pushed tree with no `.wisent-release.json` as a manifest it could not read and refused with `cannot read …/.wisent-release.json: No such file or directory`, so no repository without a release manifest could be pushed through the Git dispatcher. An absent manifest is now an undeclared product: `--if-declared` prints `<path> is absent, so it declares no quality gate; nothing to check` and exits 0, and a check without `--if-declared` refuses with that sentence. A manifest that is present but cannot be read, or a path that cannot be inspected after the read failed, is still refused with its cause. A host whose release platform cannot be named is refused with why, instead of being read as no platform.
