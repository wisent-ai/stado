# Changelog

Entries for the release being prepared live here. Released entries move into
`changelog/`, one file per range, because a file this repository cannot edit is
a file that stops receiving entries: the length gate refuses every write to a
file past 300 lines, and this one had reached 414. Two product fixes on
2026-09-08 could not be recorded at all until it was split.

When a release goes out, move its section into the newest file under
`changelog/`, and start a new range file when that one nears the limit.

## Unreleased

- **`stado credentials token mint --token-item <item> --token-file-name <file>` writes the registered bearer to the consumer's file:** a bearer registered from a vault item could not be written to the file its consumer reads, so the two disagreed and every read with that file was refused with "does not hash to the bearer the vault recorded". The owner now writes the item's own value to `~/.stado/<file>` (a file holding another bearer is refused, not overwritten); `stado credentials token sync` delivers it to other hosts.

- **`stado credentials vault sync --host <owner> --push` publishes the owner's vault to the mirror:** Stado could only pull the mirror, so a grant or item rename made on the vault owner never reached another host's copy until someone ran Skarbiec by hand, and `credentials token sync` there refused with "synchronize the vault first". `--push` runs `skarbiec sync-push` on the owner; the other copies then pull with `--check` first, as before.

- **`stado product` reads receipts of tools installed hundreds of times:** each install nested the whole previous receipt, history included, so a tool reinstalled a few hundred times wrote a receipt deeper than the JSON parser's recursion limit, and that one file refused every `stado product` install, `paths` and ownership check with `recursion limit exceeded`. A receipt now keeps only the state directly before it, which is all rollback reads, and existing deep receipts are read whole and rewritten flat on the next change.

- **`stado host build` no longer fills the target's disk:** each build compiled into a fresh `target/` inside its run directory, several gigabytes apiece, and six recovery builds took the control host to `No space left on device`, which stopped its object API for the fleet. Builds now share one target under `~/.stado/build-cache/host-build/cargo-target`, a root the `build_caches` cleaner owns, copy only the executable to `<run>/…/target/release/<bin>` for `stado host run-attached`, and are refused before compiling when the host is already under its disk low watermark, naming the free space, the watermark and `stado space reclaim`.

- **`stado bootstrap --local --target <this machine>` installs one Stado process:** the host-unit install that merges every Stado unit on the machine into one `stado serve` unit, loads it and retires the replaced units as `.retired-<date>` files was never called; bootstrap installed the local target as a separate queue agent. A local target is now installed as the host unit.

- **A host moves to one Stado identity and product-named items with two commands:** `stado credentials item rename --host <host> <from> <to>` moves a vault item to a new id with Skarbiec's own rename on the host, keeping its payload, history and tags, and refuses when the destination already exists; `stado config migrate-identities` now also points every `release_api.publishers` and `service_api.deployers` entry at the item named after its product, drops deployer consumers, and moves a retired workload-agent consumer to `stado`. Grants that named the old item ids are reissued with `stado credentials grant consolidate`.

- **`stado product` works on hosts that ran the former `wisent-products` program:** that program kept its own receipt and its onboarding outbox under `~/.stado/products/wisent-products`, and Stado reads that tree as installation receipts, so every `stado product install`, `paths` and ownership check refused with `parsing receipt .../onboarding.json: missing field product`. The directory now moves once to `~/.local/state/stado/retired/wisent-products` before receipts are read; nothing is deleted, and a destination that already exists is refused with both paths named.

- **`stado product swift test` no longer deadlocks a test that builds its own product:** Stado exported `SWIFTPM_BUILD_DIR` to the `swift` command it runs, and so to the program under test; a test that ran `swift build` (the oko-desktop signed install journey) reused the scratch the outer `swift test` holds locked and waited on it until it was killed. The scratch now reaches SwiftPM only as `--scratch-path`, and the variable is removed from the child's environment.

- **`stado release restore-local --version <v>` reinstalls a Stado release this host retained:** when the installed Stado refuses the host's configuration, every boundary of its object API answers `503 object authorization unavailable`, and the registry, the release records, `release rollback` and `release declare-version` are all behind that closed API while `release host-state --apply` refuses to downgrade a host that runs a newer version than it declares. The command reads `~/.stado/releases/stado/<v>/<platform>/stado-reader-convergence.tar.gz`, which every Stado delivery retains, and installs it through the same checked install and service-local reader convergence as `install-local`, so the restored binary validates the host's configuration before it replaces anything; an unknown version is refused with the versions the host does retain. Run it on the host with `stado host run-attached` after `stado host build`.

- **`stado product install` builds npm products whose git dependencies compile themselves:** the npm recipe ran `npm install --global --prefix <version>`, and npm exports every command-line setting to the git-dependency preparation it starts, so that nested install placed the dependency itself into the product's prefix instead of installing its build tools: Weles failed on `@wisent/cost-tracker` with `tsc: command not found`. The versioned package root is now an npm project of its own and the product's binaries are linked from its `node_modules/.bin`.

- **`stado product swift` keeps what the compiler said:** SwiftPM prints its errors on standard output, which `--json` replaces with the report, so a failed `--json` build answered only `Swift build failed (exit status: 1)` and its evidence held no compiler line. Both streams are now written to `swift.stdout.log` and `swift.stderr.log` in the run's `.wisent-output/native/<run>/`, named under `compiler_output` in the report, and a failure names the file.

- **A Stado delivery refuses a host whose configuration the incoming binary refuses:** `stado release install-local` runs the incoming Stado's `config validate` against the host's configuration before replacing the installed binary; a refusal leaves the installed Stado and its release coordinate untouched and names the problems and the migration (`stado credentials grant consolidate`, `stado config migrate-identities`, product-named publisher and deployer items). The 0.22.0 delivery replaced the control host's Stado although its configuration still used the retired identities, and every boundary of its object API answered `503 object authorization unavailable` with no path left through Stado to read, repair or roll back.

- **A build says where its minutes go (0.22.0):** `stado build submit` writes every phase to standard error as it starts and how long it took when it ends — the snapshot, the source upload, the catalog record, staging the inputs, the release batch, and per platform the saved request, choosing a builder host, staging the worker request, charging the budget and submitting the job (`[build submit] linux-amd64: choose and admit a builder host: took 3s`); `--json` output is unchanged. The release worker writes `step <name>: started at <time>` and `step <name>: exit Some(0) after 166s`, and `stado build status` prints under each platform whether its job still waits in the queue and for which host, every finished step with its exit and duration, and the step a building job is in and for how long; a step whose newest output is Cargo's `Blocking waiting for file lock …` adds `blocked: … another Cargo process on this host holds it`, because a darwin job spent 49 minutes behind another build's lock on the shared build directory and read as a slow compile. `--json` carries the same under `progress.<platform>` (`waiting`, `steps`, `running` with `blocked_on`), which is what Stado Desktop's build status operation shows, and a text `--wait` reports each queue wait, step start, lock wait and step end as it happens. A job log the queue cannot read is reported with its error. `source-documentation` no longer waits for the `stado` crate to compile: its checks moved to the `stado-source-checks` package (`stado-rs/checks/tests/documentation/`), which compiles in seconds, and the release recipe runs it right after `fmt`, before `clippy` and the 11 to 28 minute release compile.

- **A build refused while its product is enrolled still fails the changes it covers:** `stado build submit` and `stado build newest` record the build and bind the pushed changes it covers before enrolling the product and publishing its source, and a refusal there is written on the build (`stado build status` reads `failed` with the refusal) and turns those changes `failed` in `stado release changes list`. Enrollment ran first since fb8e3656, so a refused enrollment recorded no build and left every covered change `queued` for good; `tests/release_newest` caught it and failed every Stado build since. `stado release submit --source` still enrolls and publishes before recording its run, which carries the refusal.

- **Enrollment declares no publisher for a store that takes none:** a build or release written to the local object backend with no release API configured carries no publisher bearer, so enrollment no longer asks which host owns the fleet vault there. It did, and refused every isolated release journey with `no installed Skarbiec launcher at $HOME/.stado/bin/skarbiec-keychain-launcher` before its first write.

- **The release journey has its Skarbiec broker on every builder:** Stado's manifest pins a Skarbiec source as the `skarbiec` build input, and `deploy/release/build_stado.sh` compiles it into the builder's cache (`skarbiec-input/`) and hands it to the journeys as `SKARBIEC_BIN`. Skarbiec publishes no linux-amd64 release, so the release-pipeline journey refused every Linux build since it was added with `no real skarbiec binary`. On Linux the journey no longer reads or grants the Apple signing identity: a Linux build signs no Apple code and its builder holds no fleet vault, and reading it refused every Linux journey with `vault not initialized`; on macOS it still signs with the fleet's real identity. The broker's isolated GnuPG home falls back from the checkout's `.build` to the job's own temporary directory when the socket path would not fit, which it never did in a fleet job's checkout (`GnuPG sockets cannot fit inside the checkout build directory …`); a system temporary directory beside an operator checkout is never used. `tests/product_releases` also leaves out of its isolated PATH any directory that already holds `jeden`, since a builder's own Homebrew `jeden` made `stado product install` refuse the journey's first install as changing what `jeden` runs.

- **A build goes to the builder not already compiling its product:** before queueing a platform job, the same listing of the product's builds that finds its scratch record (`runs/build/<product>/`) also counts, per builder, this product's builds in flight on that platform — a request from the last two hours with no receipt after it — and among hosts otherwise alike the one compiling fewer of them is chosen. Builds of one product on one host share that product's Cargo build directory and Cargo admits one at a time: a Stado darwin job was pinned to the host already building Stado and waited 49 minutes on `Blocking waiting for file lock on build directory` while the other darwin builder was idle. A host that can only wait for resources still goes after one that can start now, and deliveries are placed as before. The registry and the fleet's capacity publications are read once for all the platforms a submission places, instead of once per platform.

- **The darwin release qualifies Stado Desktop from its own source:** `tests/fleet-expansion/qualify.sh desktop` runs `swift test --filter FleetTests` on the job's checkout, whose package pins its dependencies to published tags, instead of `stado product swift`, which resolves the operator's canonical checkouts and was refused on the release worker by macOS (`reading workspace ~/Documents/CodingProjects/Wisent: Operation not permitted`). The Products screen's operations and the Releases screen's build operations now run in every darwin release beside Fleet Expansion's. `Package.swift` no longer declares the `ProductTests` target whose `tests/product` directory 03aafe45 deleted, which left the package unloadable (`invalid custom path 'tests/product' for target 'ProductTests'`). The Releases screen gained **Read what each platform's build job is doing now (steps, durations, waits)**: `stado build status <id>` as text, the same queue waits, step durations, running step and lock waits a terminal shows.

- **Placement finds scratch evidence in one listing:** before queueing a platform job, the scratch record a builder must have room for is now read from the product's own builds (`runs/build/<product>/<build>/platforms/<platform>/output/scratch.json`, or a retry's `attempts/<id>/output/`), with one listing of that product's build tree. It used to list every product's release history — 1,753 objects under `runs/release-pipeline/` — and download up to forty `run.json` files, once per platform on every submission, and since release runs stopped compiling it judged hosts against a stale build's evidence. A product with no measured build is placed as before. Queueing a platform also no longer reads the registry once only to ask the daily build budget before charging it: the charge asks, verifies a recorded user exception and records in one registry generation, with the same `a release build` refusal; a refused platform keeps the request it saved and resumes from it.

- **The Wisent product catalog lives in Stado (0.22.0):** `catalog/products.yml` and the whole `wisent-products` program moved into this repository, the program as the `stado-product` crate. Every former `wisent-products <args>` is `stado product <args>` with the same arguments, JSON and exit statuses — `catalog`, `registry add|set|rm`, `create`, `install|update|status|rollback|remove`, `sync`, `schedule`, `signing inspect|sign|report|reconcile|residue|stage`, `paths`, `cargo`, `swift` (including `swift sourcekit` for editors) and `documentation cli-pages|markdown-policy` — and the global `--catalog PATH` is `stado product --catalog PATH`. `stado product signatures PRODUCT [--apply]` is gone: use `stado product signing report PRODUCT` and `stado product signing reconcile PRODUCT`. Stado no longer downloads a `wisent-products` release before it can install or sign (that release never existed, so every Darwin signing step failed on 2026-09-22 with HTTP 404): a release worker signs with its own executable, and a provisioned Darwin host signs with its installed `~/.stado/bin/stado`, refused as `<host>: <path> cannot sign native code: \`stado product signing sign\` is not available there (…); converge Stado on this host first` when that Stado predates the command. Build steps find the worker's own `stado` first on `PATH`. The shipped service catalog is derived from the compiled product catalog instead of the generated `data/catalog/service-catalog.json`. Renamed inputs: `STADO_PRODUCT_INTEGRATION_URL`, `STADO_PRODUCT_INTEGRATION_TOKEN_FILE` and `STADO_PRODUCT_STATE_DIR` (default `~/.local/state/stado/product`; requests kept in `~/.local/state/wisent-products` move there on first use). Product reports name `stado_version` and `stado_source_revision`. `stado product schedule --install` writes the `com.wisent.products.*-sync` agents to run `~/.stado/bin/stado product sync`. Real journeys: `tests/product`, `tests/product_registry`, `tests/product_sources`, `tests/product_releases`, and on Darwin `tests/product_signing`, all run by the release build.

- **`release newest` says why a version cannot be released:** it counted any run recorded at a version as published, so on 2026-09-23 the fix for 0.21.54's failed darwin quality gate, committed at the same version, was listed as `0.21.54 is already published by run 44c402fd…` though nothing was published. The version was spent because that run had attested another commit as its source, and the store refuses a second (`stado/0.21.54 already attests source revision …; publish a new version`). Only a run that published (`promoted`, `reconciled`, `completed`) reads `published` now. A run of another commit reads as the new standing `version_taken` with `taken_by` in `--json` (`<version> belongs to commit <taken_by> (run <run>), and a version's source never changes; commit a new version before releasing <commit>`), a run still moving on this commit as `in_flight` (`… is being released by run <run>; follow it with \`stado release status\``), and a failed or superseded run of this commit leaves it `releasable`. `stado build newest` builds both new standings like any other. The cases are in `tests/release_newest/runs.rs`.

- **A shared checkout's commit can be released:** `stado release newest` and `stado build newest` read the commit a checkout stands on and release or build it even when the checkout also holds another session's uncommitted work. A release is made of the commit's objects only, so those paths never reach a build, and the plan says how many it leaves out (`… is not published yet; the checkout's N uncommitted path(s) are not part of it`, and `uncommitted` in `--json`). The checkout is still refused when `.wisent-release.json` has uncommitted changes (`.wisent-release.json has uncommitted changes and declares what this checkout releases; commit it or restore it before releasing <commit>, …`) or when the working copy declares another version than the commit (`the checkout declares <working> but its commit <commit> declares <version>; commit the version before releasing, …`); an uncommitted edit to the version file that keeps the version, such as a new dependency in `Cargo.toml`, is left out like any other path. `stado release submit` and `stado build submit` without `--commit` still refuse any uncommitted path. Stado Desktop's **Read what every product would release** shows the same plan text. On 2026-09-23 jeden and stado each held another session's unfinished edits minutes after a clean commit, and every pushed commit was refused as `release source must be a clean committed Git tree`. - **A release job is pinned only where its secrets resolve:** every agent's capacity publication now lists `secret_fields`, the `item#field` names its `agent.skarbiec.secret_fields` allows (names only, never values), and release build, delivery and redelivery placement refuses a host whose list lacks one of the job's `secret_env` references. The considered-hosts line of the refusal reads `<host> accepting jobs but cannot hold this build: <item#field> is not in its agent.skarbiec.secret_fields`. An agent's claim-time probe now asks the same allowlist and declines with `secret <ENV> needs <item#field> and this host's agent.skarbiec.secret_fields does not allow it; leaving it queued for a host that can resolve it` instead of failing the job. A publication from an older agent carries no list and is not judged by the coordinator. On 2026-09-23 jeden 0.1.23's darwin build was pinned to charless-mac-mini and failed with `secret WISENT_CODESIGN_CERTIFICATE_PEM is outside agent.skarbiec.secret_fields`, while lukasz-macbook allows the Apple signing fields.

The fleet registry retains the captured permission with the platform and run id in the same conditional write that charges the build. A different run cannot spend that permission again, and a worker does not charge the accepted job a second time after the UTC day changes. `stado queue budget --json` includes these retained receipts. The operator asked for "stado build release newest ktora robi to wszystko dla naszych wszystkich produktow" and said of `release newest`: "to jest release. a nie build" — until now nothing in Stado compiled without publishing. CLI and Desktop retain the actual owner and supported `service show` and `service serving` diagnostics. A proven legacy predecessor is handled by the readiness-first admission described above; an unrelated owner is not retired automatically.

- **The host reclaims the product evidence in its own store (0.21.45):** `object_evidence` is a janitor cleaner for the run evidence products write into this host's object store: only inside a root the operator declared, only files past the declared age with a one-week floor, bounded by the pass's own scan and time budgets, and counted but untouched in a planning pass. A declaration with no root sweeps nothing, because which namespace and prefix are meant is exactly what the root says. It exists because reclamation owned by the queue cannot reach the host that needs it most: charless-mac-mini published `not accepting jobs: disk_pressure_active` at 3.7 GiB free, so the job carrying the owning product's own retention command — the work that would have freed the 34.9 GiB under `ecosystem/probierz` — sat in the queue and could never be claimed. Declare it with `stado space cleaners declare <host> --cleaner object_evidence --root <path>`.

- **A rollout that recovers on its own, and a port with one owner (0.21.34):** three findings that had left the Skarbiec release dead on `lukasz-macbook` since 2026-09-17, with every command that resolves a release-controlled binary answering `no observed active release (phase Quarantined)`. A quarantine whose cause says nothing about the candidate — today only `readiness_probe_unanswered` — is now retired by the agent itself, audited in the same trail `quarantine clear` writes and bounded to one retirement per digest per hour; `quarantine list --json`, `release doctor --json` and Stado Desktop's Releases screen carry `agent_retires` per row. A proxy is identified by the executable it runs rather than by the spelling of its path, because `ps -o comm=` answers with the bare program name here and the comparison against a full path was false for every process on every Mac, so a process refused the proxy the agent itself had started. And a port has one owner: `validate_registry_contract` refuses a resolver adapter or `api_bind` that claims a port a release target on the same host declares, `stable_bind_occupied` names that failure instead of `unclassified`, and the agent asks the kernel who holds the stable bind and names that process instead of spending ninety seconds on a candidate that cannot bind.

- **The report says what the host's paging did (0.21.27):** `stado space report TARGET` prints a `memory paging:` line — the compressor's size, converted with the host's own page size, and the lifetime swapout count. Both numbers were already read on every pass and printed nowhere, so a host inside both watermarks looked healthy while it was thrashing: on charless-mac-mini on 2026-09-19 the memory line read 4487 MiB available and swap 71% used, under the declared 2048 MiB and 80%, while the compressor held 3563 MiB across 414,900 swapouts and the released Brama was quarantined twice in an hour for a readiness probe it could not answer. - **A host that could not answer does not wall the release off (0.21.26):** a run of quarantines whose cause is `readiness_probe_unanswered` no longer holds the next candidate. Every other cause is about what a release meets on the host — a vault that will not open, a route that maps nothing — and a second candidate walks into the same wall, which is why a run of three holds; a probe the host never answered says nothing about the candidate, and counting those kept charless-mac-mini on a hand-built Brama while every released one was refused before it could start. The record, its class and its remedy stay. The decision itself now lives in one function (`hold_for`), which the tests drive instead of a copy of it.

- **An agent session the fleet keeps running (0.21.25):** `stado workload start jeden-session --workspace W --task "…"` places a Jeden session on the fleet host with the most live room and submits it to the queue pinned there, so the work survives the terminal, the editor and the machine that asked for it; `stado workload sessions` lists what the fleet holds, and `stado job watch`, `stado results` and `stado cancel` follow, download and stop one. Until now `stado workload attach` was the only way to place a session and it dies with the caller's stream, which is how sessions were lost every time VS Code did. A session is sized from the kind's declared reservation (2 cores, 4 GiB), queued at priority 50,000,000, granted nothing unless `--allow-write` or `--allow-command` says so, and declared as CPU work: the queue's model-name sizing scan read `jeden run … --model <route>` as a GPU workload, and on a host with one GiB of VRAM the claim refused every such session silently on every poll. The claim now honours an explicit CPU resolution instead of re-guessing from the command text. The session's command preflights itself on the host, so a workspace the worker cannot enter — `~/Documents` under macOS privacy protection — reports that sentence instead of the harness's usage text. `"detachable": true` in `stado-rs/data/work/workloads.json` decides which kinds may be started this way; Stado Desktop carries the same start form, session list and stop action.
- **A probe nobody answered is not a broken candidate (0.21.26):** a quarantine whose reason says the readiness endpoint `did not answer within Ns` is classified `readiness_probe_unanswered`, and its remedy names the host rather than the release: `stado space report <TARGET>` for its memory, swap and disk, then `stado release doctor <PRODUCT> --target <TARGET>`, clearing the digest only once the host can run it. A candidate that answered `HTTP 503`, one whose process was gone, and the bare `did not become ready before deadline` keep their own readings, and any credential or capability sentence in the retained stderr still wins, because the timeout is the outermost symptom. On charless-mac-mini on 2026-09-19 three records carried it, the desired Brama digest among them, while the host held 3.6 GiB of swap in use at load 3.9 and every one of them read `unclassified`, so the register blamed the release and nobody looked at the host.

- **A field is changed where it is read (0.21.22):** `stado registry set --path P --value V` writes one field of the canonical registry under the generation the same call read it at, through the same validation `push` runs; the path is the one `pull --path` reads, the value is JSON when it parses as JSON and the literal text when it does not, an identical value reports `unchanged` and writes nothing, and a path that does not already exist is refused naming the keys or element names that do. `--json` emits a `stado.registry-set-receipt.v1` object with the previous value, the generation read and the generation written. The week of 2026-09-12 held six edits of the shape `registry pull > ~/.oko/registry-pull.json`, `sed -i '' '309s|…|…|'`, `registry validate`: a line number standing in for a field, a scratch file standing in for the registry, and nothing surviving to the next edit.

- **A question is answered, not dumped (0.21.20):** `stado registry pull --path P` prints one part of the canonical document — a dotted path of object keys, array indexes or array element names (`release_control.products.brama.desired`, `targets.lukasz-macbook.skarbiec`), a string bare and anything else as pretty JSON — and refuses a missing segment naming the keys or names that exist there. `stado release status --run ID` reads one pipeline run by its id or its first characters, however far back it is, and `--version V` the runs that published that version; both print runs only, and no match refuses naming the newest runs. Between 2026-09-12 and 2026-09-19 the whole registry went into `~/.oko/registry-pull.json` eleven times and the whole release status into a file three times, each grepped afterwards for one block. Product and version filters read at most the newest 120 run objects, one request each.

- **Finished jobs' outputs have a cleaner (0.21.35):** `job_outputs` reclaims the payload files under `status/<job_id>/output/` of jobs the queue positively lists as terminal, once they are older than the declared `min_age_seconds` (floor seven days); the job's own top-level `*.json` and `*.log` records stay, while artifacts in trees the job wrote under `output/` are payload whatever they are named, so `stado release status` and `resume` keep reading receipts and logs. A job the queue lists as live or does not list at all is never touched, and an unreadable queue store removes nothing. Declared like every cleaner: `stado space cleaners declare HOST job_outputs --min-age SECONDS`; the report and `stado space report` carry its counts, its skip reasons, and the bytes each reason kept. Measured on charless-mac-mini on 2026-09-19: 12.1 GiB of such outputs, the oldest from 2026-08-16, held the host under its disk watermark while every declared cleaner reported nothing eligible.

- **Consumer declaration includes its route (0.21.0):** `service directory consumer-add --target HOST --bind LOOPBACK:PORT` commits authorization and the host's resolver binding together. Repeated declarations update the same binding, and omitting capabilities preserves the existing policy. Invalid targets, non-loopback addresses, zero ports and conflicting bindings leave the registry unchanged. `consumer-rm` retires that consumer's bindings on every host together with its authorization. Hosts → Routes exposes both commands through the selected Stado API with review and full receipts. The resolver's existing supervised refresh applies listener changes; neither command changes credential grants. This adds optional CLI fields and uses the existing registry schema. Older readers understand the resulting adapters; rollback does not require a data migration.

- **Publication has its own credential (0.20.15):** `release.publisher_skarbiec` selects the publisher's acquisition identity, independently of the control plane, API verifier and signer. Reusing one of those identities or token files is refused. Publication reads only explicitly granted fields and never rewrites grants in a local replica. `storage put --json` preserves `refused` and `auth` failures as JSON, including write and read-back failures. The configuration catalogue and `config show` expose the selected route, consumer and token file.
- **Scratch cleanup follows the recorded root:** a lease records its caller-local registry directory and identity, including `scratch create --root`. Destruction checks that identity and removes the recorded directory instead of silently checking the default location. A different caller reports that the root belongs elsewhere; unreadable or replaced roots are not reported as absent. The real signed-release test now uses an isolated build-directory root and verifies its removal.
- **Bootstrap bearer delivery (0.20.14):** `credentials token sync` verifies an existing source bearer against its declared grant, requires the destination vault's owner and complete grant to match, and atomically delivers only the named owner-only token file. It never rewrites grants or reverses revocation. Repetition leaves matching files untouched; `--check` performs no write and reports mismatches as typed refusals. Hosts → Credentials exposes the same operation and complete receipts in Stado Desktop. Real CLI tests use isolated GnuPG vaults and authenticated Skarbiec reads to cover recovery, idempotence, revocation, mismatched bearers and symlink refusals.
- **A run that published nothing fences no delivery (0.20.12):** the delivery worker refuses a delivery whose run is older than the newest run holding a published platform, where it used to compare against the newest run of any state. On 2026-09-11 two 0.20.10 runs that failed before a builder was found, created thirty seconds after the 0.20.11 run, made every 0.20.11 delivery refuse itself as `superseded` on every host — 0.20.11 is published on both platforms and installed nowhere — and the day before an abandoned 0.20.9 run whose builds had both failed did the same to the 0.20.8 delivery to lukasz-macbook. A run starts fencing the moment it publishes a platform, which is when its deliveries can begin. The installed workers judge with the old rule until this release reaches them, so 0.20.12 is the first release whose deliveries pass on them: it is the newest run.
- **The build-cache verdict is bounded on this host too:** the walk `stado space report` starts is killed after 120 seconds on the local branch as well as over the remote channel, and `STADO_CACHE_VERDICT_BUDGET_SECONDS` sets another bound in seconds (fractions included); a malformed value is refused before anything is walked. A walk that passes the bound leaves `the build-cache verdict for <root> did not finish within <seconds>s; raise STADO_CACHE_VERDICT_BUDGET_SECONDS or declare a narrower cleaners.build_caches.root` in its section, and the report still prints in full before the command exits 1. Only the remote branch had a deadline: `stado space report lukasz-macbook`, whose declared root is that account's whole home, returned neither an answer nor a refusal after 420 seconds on 2026-09-10.
- **A source snapshot is its files (0.20.11):** `stado release submit` writes the committed tree's regular files only into `source.tar.gz`; `git archive` also wrote one entry per directory and a header naming the commit, neither of which any extractor needs, and together they were what pushed the 0.20.9 snapshot — 3,255 files in 975 directories, 4,230 entries — past the 4,096-entry bound the build and delivery workers unpacked it under, a bound sized for a release payload of a few executables. Every installed worker refused it with `release archive exceeds 4096 entries`, so the 0.20.9 coordinate stays bound to `07fd9ba7` and holds no build, and 0.20.10 — bound to `e27281fa` — was submitted twice from a coordinator older than this change and holds none either. Workers now extract a source snapshot under a 65,536-entry bound while release archives keep theirs; a snapshot of files only fits the older bound until a repository grows past 4,096 files, which is how this release reaches builders still running 0.20.8. A ci-cd journey releases a real 4,200-file tree.
- **A consent dialog no longer holds the janitor (0.20.11):** the build-cache cleaner's first directory open under `~/Documents`, `~/Desktop` and `~/Downloads` — the three macOS folders behind a consent dialog that stay in scope because build trees live in them — is bounded to five seconds; a pending answer records `consent_pending` in that cleaner's `skipped` map, leaves the folder for a later pass, and the pass finishes. On 2026-09-10 lukasz-macbook's janitor sat two hours inside one such open holding its exclusive lock, every job admission on the host answered `cleanup_in_progress`, and the 0.20.8 delivery sat queued against it.
- **A host that cannot start work says so (0.20.11):** the agent's capacity publication probes the workload lock the way a claim does and publishes `accepting_jobs: false` with `admission_reason: cleanup_in_progress` while a standalone cleanup holds it (`cleanup_lock_error` with the code when the lock cannot be probed), under the same `disk_cleanup_admission` key the claim path writes. `stado host gates` reads the published reason back, names it on the capacity line instead of `busy or gated`, carries it as `capacity.admission_reason` in `--json`, and reports `cleanup_in_progress` as a blocker with `claiming: no`; Stado Desktop's gate screen names the same reason. The same host had published `accepting_jobs: true` for the whole two hours while `host gates` read `claiming: yes` with the stalled janitor as a note.
- **Disk watermarks are written from the command line (0.20.8):** `stado space watermark TARGET --disk-low-free-gb N --disk-target-free-gb M` (with `--disk-mode`, `--disk-check-interval-seconds` and the pass limits beside them) rewrites exactly those fields of `targets[].disk_cleanup` through the registry's validated compare-and-swap, seeding an undeclared host from the reporting default and preserving every cleaner; the read prints the disk declaration beside the memory one. Stado Desktop could already write these fields through `api/registry/policy`; the CLI could not, and the release coordinator's `release_scratch_short` refusal names the low watermark as the reserve a build must fit above. - **Delivery leftovers are reclaimed (0.20.8):** the `delivery_leftovers` stage of `stado space reclaim` takes the attestation copies and retained archives of delivered versions under `~/.stado/releases` and the dated binary backups under `~/.stado/bin` that every `release install-local` left behind and nothing reclaimed — roughly 200 MB per release per host; 3.0 GiB and 1.35 GiB on the Linux builder, 9.1 GiB on the mini. Stado Desktop's reclamation confirmation runs the same stages.
- **Builds are placed by measured scratch, not name order (0.20.5):** the release worker measures its scratch tree and the free bytes on its volume when the build step ends and leaves `scratch.json` beside the receipt; a failed build's receipt and exit sentence carry the same two numbers. Before a build is queued, the coordinator reads the newest such record for the product and platform and refuses a builder whose published free disk cannot hold it above the host's low watermark with `release_scratch_short`, naming both numbers; among the builders that can, the most free disk goes first. The 0.20.3 darwin build was pinned to charless-mac-mini by name order with 14 GiB free and died of a full disk after twenty-five minutes.
- **The software report has a writer again (0.20.7):** `stado release host-state` refreshes the host software report `stado release status` judges, on every visit, over one authenticated session, with the bin directory classified in one command; `stado host software` wrote it until the 2026-09-06 collapse deleted the verb and left the report to go stale and the status hint naming a command that no longer parsed. `host-state` prints the report it recorded and carries it under `software` in `--json`, Desktop shows it in the Release state section, and the hint names `stado release host-state --host <TARGET>`.

- **`min_free_gb` reader ships before its declaration:** a platform recipe may declare `min_free_gb`, the free space its build needs on the work volume, and a worker that reads it refuses before the first gate when the volume is short. Stado's own manifest does not declare it yet: a recipe field is read by the worker installed on the builder, which refuses fields it does not know, and the 0.20.4 darwin job died at the manifest with `unknown field min_free_gb` on a builder running 0.20.1. The declaration follows once a release carrying the reader is installed on every builder.
- **Idle launchd units no longer fail deliveries (0.20.5):** the loaded-unit inventory reports a job launchd holds without running it with an empty pid, whether `launchctl list` wrote `-` or a domain table wrote `0`. The inventory also keeps every column in place when a value is empty; a system-domain job with no pid used to read its exit status as its pid and `system` as its status in `service list --undeclared`. The 0.20.2 and 0.20.3 coordinates hold at most one platform of this fix: 0.20.2's Linux build was refused by the documentation gate once the memory-policy page was published ahead of its source, and 0.20.3's darwin build ran out of disk; a bound coordinate is never rebuilt from another commit.
