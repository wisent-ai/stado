# Changelog 0.23.68 (part 5 of 10)

Released entries, moved out of `CHANGELOG.md` so that file stays editable.
The current entries live there; this file is history and does not grow.

## 0.23.68

### Fixed

- **A superseded surface of the same recipe no longer holds its sibling's files:** Skarbiec's
  `cli` install built, signed and verified its binary, then was refused with `installation would
  change ~/.stado/bin/skarbiec, which skarbiec/service (Superseded) still owns`: the service
  surface's interrupted installation had been superseded and never finished, and only `installed`
  or `rolled_back` siblings could be replaced. A `superseded` surface installed from the same
  kind, repository and manifest is now a sibling: the install replaces the shared files and
  re-records that receipt with the new fingerprints and revision.
- **A journey under an isolated HOME no longer opens keychain dialogs:** every git a journey's Stado
  ran found no `~/.gitconfig` under the isolated HOME, fell back to the system file's
  `credential.helper osxkeychain`, and asked macOS to store the GitHub token in a login keychain
  that HOME does not have: the person saw one "Keychain Not Found ... Reset To Defaults" dialog per
  fetch. Every journey that sets HOME now spreads `pinnedGit` from `tests/native/home.mjs`:
  `GIT_CONFIG_GLOBAL` names the real `~/.gitconfig` and `GIT_CONFIG_NOSYSTEM` drops the system
  file, so the person's `gh auth git-credential` helper answers and no keychain is asked.
- **Placement standby installs a `replace` product's tree itself:** standing a host by for Brama
  answered `awaiting_release_rollout` with `brama rollout_pending: … its agent stages the desired
  release`, and no pass ever did: the release agent drives only blue-green policies, and a
  `replace` release reaches a target only when it is promoted. Standby now installs a `replace`
  product's desired tree on the host through the same verified fetch and archive installer
  (`already_active` when that archive is the active one), then stages its unit and writes the host
  into the profile and the directory.
- **An installation reads only its committed catalog:** `product install`, `update` and `finish`
  first read and validated the checkout's working-tree `catalog/products.yml`, then read the
  committed one they execute. A checkout behind origin therefore refused an install whose own
  revision held a valid catalog: Stado's finish of a revision that names every product's
  `star_repository` was refused with `ster names no star_repository` because the checkout's file
  predated the field. The verbs that build now read the catalog only from the commit they install;
  `status`, `remove` and `rollback` read the working-tree file as before.
- **Stado finds `cargo` in `CARGO_HOME`:** a build or quality step's bare program was looked up in
  `~/.cargo/bin` only, though Cargo's home is `CARGO_HOME` when it is set. A Stado run under another
  HOME with `CARGO_HOME` naming the toolchain was refused with `no executable cargo in Stado's and
  the toolchains' homes`. The search now reads `$CARGO_HOME/bin`, and `~/.cargo/bin` only when
  `CARGO_HOME` is unset.
- **The submit queue's harsh review reads the candidate against its own parent:** `stado change
  run` ran Tama's review in the repository's shared checkout, whose HEAD is whatever the person
  last checked out, so the reviewer judged every commit between that HEAD and the candidate as the
  change, and Tama refused rounds over a tree staged on a newer parent. The review now runs in a
  bare repository of its own under the checkout's Git directory, borrowing its objects, with HEAD
  the candidate's parent and the candidate's tree in its index. The reviewer's repairs are
  committed there and fetched into the checkout before that repository is removed.
- **`stado product cargo` and `swift` find their product in the committed catalog:** to ask Oko
  about the build of the product a manifest belongs to, they read the checkout's working-tree
  `catalog/products.yml`, so a checkout older than a field the catalog now requires refused every
  Cargo build of every product with `ster names no star_repository`. They now read the catalog an
  installation reads: the checkout's committed head, or `origin/main` when the head is behind it.
- **No harsh review runs for a candidate whose author Oko refused to enter:** when Oko's
  harsh-review queue already held an open entry for the submitting session, `stado change run`
  ran the review anyway and Tama judged the tree as written by the session running the pass. The
  pass now runs no review then: the candidate leaves the head of the queue with `no-round`, naming
  the entry that holds its author. A machine without Oko still runs the review and says so.
- **`stado product cargo` builds a dependency checkout older than the manifest's pin from the
  pin:** a Git dependency is built from its canonical checkout, so a checkout whose `HEAD`
  predated the pinned `rev` compiled the dependency older than the manifest expects and failed
  with unresolved imports in the depending crate (`wisent_errors::Operation` in Stado). A build of
  a committed revision (`--revision`) now builds that dependency from its pin, fetched into its
  checkout when absent and exported beside the revision; a build of the working tree is refused
  first, naming the checkout, its `HEAD`, the pin, `git -C <checkout> pull --ff-only` and
  `--revision`.
- **An install on a machine with no registry document recycles no unit instead of failing:**
  `release local converge`, the Stado CLI recipe's first `after_install` step, read the machine's
  registry record to find its units and refused when there was none, so every install of Stado
  into a home outside any fleet failed after its build passed with `cannot read registry unit
  ownership: no registry document at …`. Such a machine declares no managed unit; the recycle now
  says so and the install goes on. A record that cannot be reached or read still fails it.
- **A committed build compiles every Git dependency at its pin:** `stado product cargo
  --revision` still compiled a dependency from its canonical checkout when that checkout's `HEAD`
  carried the pin, so another session's uncommitted edit there (`autoversion`'s working tree)
  reached the build and failed it with errors in Stado's own code. A committed build now compiles
  each pinned dependency from its pin, exported once beside the revision, whatever its checkout
  holds; a build of the working tree still reads the checkout.
- **A builder that does not answer no longer fails a whole build submission:** declaring a
  product's `secret_env` on every builder of its platforms ran `config show` on each one, so one
  builder asleep (`ssh: connect to host … Operation timed out`) refused every submission of the
  product. Each builder's host channel is now probed first; one that answers on no path is left
  out, named on stderr and under the step's `skipped`, and the submission goes on. A platform none
  of whose builders answers is refused, naming each.
- **A source install of Stado names its own revision to the build:** a release recipe's build got
  `WISENT_SOURCE_COMMIT` from the installation but inherited `STADO_SOURCE_REVISION` from whatever
  launched it, and Stado's `build.rs` refuses the two disagreeing (`STADO_SOURCE_REVISION must
  match authoritative WISENT_SOURCE_COMMIT`), so an install launched from a build job or another
  Stado's finish failed. The installation now sets both to the revision it builds.
- **Two waiting installations of one surface both finish:** an installation lets the surface's
  lock go while its after-install steps run, so another installation with `--wait` took it at once
  and recorded itself, and the first one's outcome was then refused (`another installation of
  stado/cli recorded itself while this one's after-install steps ran`). With `--wait` an
  installation that finds another still running its after-install steps now lets the lock go and
  waits for that process to end (a `czekam:` process wait ended by the kernel's exit report), then
  takes the lock again.
- **A release quarantined for a taken port is rolled out again once its ports are free:** a digest
  quarantined for `stable_bind_occupied` stayed refused until a person cleared it, so a vault's
  release stayed quarantined with its stable bind and both candidate ports free and every vault
  read refused. The release agent now asks the kernel who listens on those ports on each pass:
  with none but the release's own active process, it retires the record itself, writes its line in
  the audit trail and rolls the digest out again; while one is taken, `detail` names the pid and
  port.
- **Every journey selects a Stado config that exists:** 22 Rust journeys named a `STADO_CONFIG`
  under their own run root that they never write, which Stado refuses (`STADO_CONFIG names <path>,
  which does not exist`) and the configuration readers turned into a panic before the journey
  tested anything (`alerts-skrzynka` among them). Each now selects `tests/config/empty.json`, the
  empty config `tests/config/README.md` names for a journey that must read no operator
  configuration.
- **A configuration Stado cannot use is refused, never a panic:** a `STADO_CONFIG` naming a file
  that does not exist, or a malformed config file, reached the first configuration accessor a
  command called and ended the process with `thread 'stado-cli' panicked … invalid stado config
  file: Selected { … }` (`stado alerts preferences show` among them). Every command but `stado
  config` and `stado credentials migrate`, which write the selected file themselves, now refuses
  first as a configuration failure: `Error: STADO_CONFIG names <path>, which does not exist`.
- **Every spilled changelog part is linked, and an unlinked one is refused at push:** twelve parts
  under `changelog/unreleased/` were linked from no `CHANGELOG.md` line, and the version bump
  gathers only the parts the Unreleased section links, so their entries would never have been
  released. They are linked, and `stado quality check` now refuses a revision whose
  `changelog/unreleased/` holds a part the section does not link, naming each and the link to add.
- **A workload never reads the janitor's turn request or a hold record half written:** both were
  written by truncating the file and then filling it, so a build that read the turn request in
  between was refused with `cannot parse the janitor turn request …: EOF while parsing a value`.
  Both are now written whole (a staging file renamed into place), and the holds listing reads only
  `.json` records.
- **A scheduled host routine finds the programs this host installed:** a host job (the scheduled
  `stado product sync`, `oko routines`) ran with the unit's declared PATH, which names neither
  `~/.stado/bin` nor `~/.local/bin`, so every scheduled sync held each product as `… is not on
  PATH` and installed nothing (Skrzynka stayed six weeks behind its origin). A host job now runs
  with those directories ahead of the inherited PATH, the search path every product step uses.
- **`stado release status --run ID --wait` holds until the run is published or has failed:** no
  command waited for a submitted release to be published, so an install could not be chained after
  `stado release submit`. With `--wait` the run read holds on the store's change watch until the run
  has stopped moving, prints it, and exits non-zero when it finished without publishing, so
  `stado release status --run ID --wait && stado product install …` installs it as soon as it is
  out. A `--run` prefix naming several runs is refused with each id.
- **Fleet jobs on a Mac run at an app's priority, not throttled in the background:** the host
  unit (`stado serve`) declared no launchd `ProcessType`, so launchd throttled its CPU and I/O and
  every build it ran inherited that: a build an operator's session waited on compiled at
  scheduling priority 20 beside the session's 31. The unit now declares `Interactive`; the host
  scan still moves itself into the background band. A host takes it on its next unit install.
- **The host store keeps no record of a finished routine under `queue/` or `running/`:** every
  transition leaves a cleaned sentinel in the prefix it left, and only the fleet reaper deleted
  them, so every host routine fired every few minutes left two for good: a laptop held 8,849 under
  `running/` after four days, and each host pass downloaded all of them to list the live jobs. The
  host pass now deletes every sentinel whose job has settled in a terminal prefix, as the fleet
  reaper does, and says each sweep that retired something.
- **The health pass ends only its own home's stray roles:** it judged every `stado serve` on the
  machine against its own role locks and installed binary, so a test journey's isolated
  deployment, run under a HOME of its own, held no lock here and ran a checkout's build, and the
  resident killed it with SIGKILL within seconds: the host-routine journey could never see its
  routine fire. A role process started under another HOME, or whose environment cannot be read,
  is now left to that home's own pass; the home is read from the kernel's record of the process.
- **`product sync --clone-missing` clones what a product's build reads, not only the product:** the
  sync cloned a product's own source and then installed it with a runtime that could clone nothing,
  so a build whose Git dependency had no checkout in the workspace was refused (`no canonical
  checkout answers for lbartoszcze/autoversion …; no checkout was created`) on every pass and
  Skrzynka stayed six weeks behind its origin. The installation now runs with the sync's cloning
  runtime.
- **A janitor pass with no job work tree on disk asks the fleet queue nothing:** the work-tree
  cleaner listed every queue prefix of the fleet store through the object API to learn which of its
  candidates were live, also when it had none; on a laptop with no job tree each listing could
  stand for ten minutes while a build waiting for the janitor's turn compiled nothing. With no
  candidate the answer is the empty keep-list and the queue is not read.
- **`release catalog input pin --source NAME` reads the repository's canonical checkout:** a bare
  name was joined to the working directory, so `--source jeden` run from inside `jeden` was
  refused as `cannot change to 'jeden'`. A path that exists is still that path; a name with no `/`
  reads `wisent-ai/<name>`'s canonical checkout from Stado's workspace, and one with none is
  refused naming it. A cargo pin whose checkout holds a manifest or lock changed since the pinned
  revision is refused naming each file and how to repair it, instead of quoting `git diff`.
- **A Stado network connection whose peer vanished ends:** `stado network connect`, the
  `ProxyCommand` of every `ssh` to a `<host>.stado.internal`, copied until the peer closed, and the
  node's sockets carried no keepalive, so a peer gone without closing (a host asleep, a route
  dropped) held the connection and its `ssh` without end: a pre-push probe of `true` stood 61
  minutes, and on a laptop three such connects stood four days. Every socket the network dials or
  accepts now turns on TCP keepalive and is ended by the kernel's idle time, interval and probe
  count, as host-connections.md states.
- **`stado ci delivery` names a plan with no cadence as a stall:** a delivery plan declared without
  `--every` fires no pass, and the path's `stalled` list said nothing of it, so the routine read as
  standing while nothing had run it since 2026-10-28. Such a plan is now a stall naming when it was
  declared and the `stado ci plan set … --every SECONDS` that declares it again with its own
  purpose and steps.
- **Installing Skrzynka's CLI declares its database:** only the service recipe ran `stado database
  create skrzynka --provider fleet …` after installing, and both surfaces install the same
  `~/.local/bin/skrzynka`. A host that installed the CLI (the host sync installs `--surface cli`)
  got a Skrzynka that keeps every row in the fleet database `skrzynka`, which nothing declared there,
  so every command and the running service answered `unknown database "skrzynka"`. The CLI recipe
  runs the same create, which places nothing anew on a host that already has the database.
- **`product sync` installs a surface again when its catalog recipe changed:** a ready installation
  was kept whatever the catalog now said, so a step a recipe gained (an `after_install` declaring
  the database a product now keeps its rows in) never ran on a host whose files already matched
  their source: Skrzynka's CLI, installed before its recipe declared the database, stayed without
  it. An installation whose recorded recipe differs from the catalog's is installed again, and the
  row's note says why.
- **The product library compiles again:** the working tree's catalog notice called a `validate`
  its module does not have; it calls the catalog's own.
- **A `stado serve` under launchd reads the macOS Tailscale app as its command line:** run with
  no terminal, the program inside `Tailscale.app` started its window instead of answering
  `status --json`, and the serve waiting on it at its host-identity step never bound its API or
  resolver for hours while launchd called the unit running. It is run with
  `TAILSCALE_BE_CLI=true` and no input. `tests/network/tailnet_without_terminal.rs`.
- **`stado service ensure` restarts this machine's serve stuck at start:** a unit whose process
  stood in a start step for hours was answered `already_correct`, and `stado product install
  stado` then waited without end for a resolver that would never publish. Once the process
  stands in a `stado serve start:` step past the longest that step took here, ensure says the
  step and what it waits on, restarts the unit once and ensures again; the wait for the
  resolver refuses a new process stuck again with its own step.
- **An install of Stado starts a resident unit that serves nothing on the release it places:**
  the install restarted its own unit through the candidate before placing it, which started the
  release already installed, the one hung at start, so every install failed at that step and its
  fix never reached the path the unit runs. A resident unit that serves none of its declared
  ports is now left as it is until the candidate is placed, then started on it, and must serve.
  `tests/install/resident/resident_unit.mjs` stalls the unit with SIGSTOP before an install.
- **`stado serve` comes up whatever its Tailscale client does:** its start step `host identity`
  reached the tailnet map through the store client, and the map ran `tailscale status --json` on
  the start's path, so a client that never answered kept the API, the resolver and every role
  after them down for as long as it ran, whatever made it not answer. Serve now reads the map
  beside everything it does, with the same command line (`TAILSCALE_BE_CLI=true`, no input): the
  client is started once, its wait is in `stado waits`, and until it answers every reader routes
  as with no map. The beacon's new `tailscale_client` block says `answered`, `no_answer` (with the
  client's pid, since when and its open waits), `failed` with the cause, or `absent`; a client
  that never answers is reported on every beacon and is not ended on a timer, and a health pass
  starts no second read while one runs. The client is serve's own and ends with it: it leads a
  process group of its own, and a serve told to end (SIGTERM, SIGINT or SIGHUP) or ending on its
  own ends that group, reaps the client and closes its wait before it exits, so no client is left
  running under pid 1. A wait the cancellable child wait (`stado_wait::output_cancellable`) keeps
  names the child as `pid <pid> in <directory>`. `tailnet.clients` (`STADO_TAILSCALE_CLIENTS`)
  declares the paths a client is looked for at in place of the platform list. The object store
  and fleet HTTPS clients a process shares are keyed by the tailnet address they pin, so the
  first client built after the map answers carries the pin. Journey:
  `tests/serve/provider_client_hangs.mjs`.
- **A unit launchd runs is no longer started a second time by an old cron fallback:** when every
  launchd domain refused an install made over SSH, the install fell back to a crontab line
  `@reboot /bin/sh ~/.stado/bin/run-<unit>.sh`, and a later install that launchd accepted left
  that line in place. Every boot then started the unit twice; the copy that lost the race for its
  port restarted for ever, and its published state said the unit was down while the other copy
  served. Every install that launchd accepts, in the per-login domains and the system domain,
  now removes the line and its wrapper and says `removed the @reboot cron fallback of <unit>;
  launchd alone starts it`. A crontab it cannot rewrite is refused naming the unit and the wrapper
  the line still names.
- **The network node launchd starts takes its port back from the copy cron started:** a node
  unit loaded before installs removed the cron fallback kept the line, so at every boot cron's
  copy took the node's port and launchd's node failed to bind and restarted every ten seconds
  (3130 times on one Mac). The node its unit started now reads who holds its port; a listener
  whose parent ran this unit's cron wrapper is ended (SIGTERM, then SIGKILL after five seconds),
  the cron line and wrapper are removed, and the bind is tried again, saying `port <p> was held
  by pid <pid>, a copy of this node cron started from <wrapper>`. Any other holder is left alone
  and the bind refusal stands. `tests/network/cron_copy.mjs` runs it on a dedicated account.
- **A start or restart waits for launchd's next spawn of a job it scheduled:** macOS refuses the
  first spawn of a program whose code identity an install just changed (`OS_REASON_CODESIGNING`)
  and runs the next one; the postcondition read the unit between the two, answered `loaded with
  no pid`, and `stado product install stado` rolled back a release that was about to run. A job
  in `spawn scheduled` is now judged after launchd's next attempt, and a unit still without a pid
  is reported with launchd's state, run count and last exit reason.
- **A slow start is no longer refused as a hung one:** a start step past its longest was judged
  stuck even when nothing below it was overdue, and `stado serve` judged its own start, so a
  resolver that took six seconds longer than ever before ended the serve. A start is now judged
  stuck only when a wait below its step is past its own longest, and never by the serve itself.
- **An npm product installs from source again:** the recipe installed the checkout directory, whose
  `prepare` script (`npm run build`) npm ran in a copy without the package's own development
  dependencies, so Weles failed with `tsc: command not found` and no Weles from source could be
  installed. The committed tree is exported, `npm ci` installs its lockfile and runs its build, and
  the packed result is what the product's versioned prefix installs.
- **Host GUI automation runs on a busy host:** `stado workload run gui-automation` sets up the
  host's own Accessibility grants and Apple two-factor helper, yet it took a capacity hold, so a
  host whose load left no free core refused it with `has no room for gui-automation`. It is
  declared a maintenance kind and takes no hold.
- **A fleet whose object API stood on a host that is gone can be brought back without it:**
  `stado placement move --authority` took the registry authority on a host from a silent one,
  but the registry was still read from the fleet object API placed on the silent host, and
  `stado placement role move` fences and copies that host's store, so it needed the host it
  was leaving to answer. Every registry read on the new authority then stood on the machine that
  was gone. `stado placement role take SERVICE --reason WHY [--check] [--json]`, run on the
  host that holds the registry authority, makes its own object API the route's active endpoint
  and writes the registry from its own last-known-good copy into it, handing the same registry
  to every other host that answers. It is refused while the active host's store answers a
  registry read within the resolver's refresh interval (`move the role with its store instead`),
  on a host whose copy names another authority (`take the authority first: stado placement move
  --authority --to-host HOST`), on a host that keeps no copy, and when this host's own object
  API does not answer a registry read. The receipt, kept in `stado placement history`, names
  what was not recovered: whatever the silent host's store held and this host's does not.
- **A request only a statement can answer is answered in the same call:** `stado capabilities
  call FAMILY --consumer C --await-statement` waits, when the attestation alternative is reached
  and no statement answers the request yet, for `stado capabilities attestation record` to write
  one, and prints it. The consumer's attestation directory is watched by the kernel (kqueue,
  inotify), armed before each read, so a statement written between the read and the wait still
  wakes it; the wait is a `sesja` wait, listed with every other. A Weles run that a person
  attends (`WELES_AWAIT_STATEMENT=1`) is answered page question by page question in one session
  instead of refused at the first and started again, which repeated every sign-in before it.
  The Compute providers screen's call operation offers the same wait.
