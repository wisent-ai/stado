## 0.23.68

### Fixed

- **A database whose source no longer answers is moved onto the fleet from the backup this machine kept:** `stado database migrate NAME --to fleet` always took a new backup from the source first, so a hosted project whose host no longer resolves could not be moved at all, while `stado database backups NAME` listed a complete backup of it. `--from-backup DIR` restores that kept backup instead: its manifest must name NAME (`DIR is a backup of OTHER, not of NAME`), DIR must hold the manifest and `database.dump` (`DIR is no kept backup: …`, `DIR holds no archive database.dump`), and the archive must still hash to the SHA-256 recorded when it was read back (`… the archive changed and is not restored`); every table is counted again after the restore, and the item is pointed at the fleet server only then. Writes the source took after that backup are not in it; the report names `backup_taken_at`. Stado Desktop's **Move to fleet…** takes the kept backup in **Kept backup**. `stado database auth place NAME --settings-file FILE` reads the sign-in settings from a JSON object in the shape the management API answers instead of asking the provider, so sign-in is served for such a database too (`{}` takes the server's defaults); a file that cannot be read or is not JSON is refused naming it, and it cannot be combined with `--from-project`. Stado Desktop's **Serve sign-in…** takes it in **Settings file**. Journey: `tests/database/backup-migrate.mjs` refuses a directory without a backup, a backup of another database and a changed archive, then moves the database from its kept backup with the source untouched.

- **A kept backup is restored only when it is the newest and the source is silent:** `stado database migrate NAME --to fleet --from-backup DIR` restored whichever backup it was given, while the source still answered or a newer backup was kept, and so could drop the writes a newer copy held. It now asks the source for its server version first and refuses while it answers (`NAME's source HOST still answers (PostgreSQL N), so a new backup holds every write the kept DIR lacks: run stado database migrate NAME --to fleet without --from-backup`), and refuses a backup that is not the newest complete one `stado database backups NAME` lists (`DIR is not the newest complete backup of NAME: NEWER is newer …`). `stado database auth place NAME --settings-file FILE` reads the file on the machine that runs the command, refuses anything but one JSON object naming what it got (`… are an array, not one object …`), and carries it to the database's host itself through the host channel (`--settings-json TEXT` is how that host receives it), instead of refusing with "copy the file there yourself". Journey: `tests/database/backup-migrate.mjs` covers both new migrate refusals (the source made silent through its item in the test's own vault) and the settings refusals.

- **An authority takeover survives the old authority's next answer:** the resolver recorded the
  old authority's lower directory generation into the last-known-good copy before refusing it, so
  `placement move --authority` was undone. The copy is now recorded after the generation is judged,
  and every copy write refuses a lower generation as `directory-rollback`, naming `stado resolver
  accept --generation N`; an accepted generation is recorded as the resolver adopts it.

- **One command reads a remote registry authority once:** its snapshot is kept in the process for
  the refresh interval reads of that authority are measured by, said on stderr when it answers, and
  forgotten after a registry write, instead of one whole SSH snapshot per registry read.

- **A placement move names the step it stands on:** claim, preflight, fence, state read and write,
  routes, start, retire and commit are each a `stado::wait` naming transaction, profile and host,
  listed by `stado waits` and Stado Desktop's open waits.

- **A change hand-off records source and builds nothing:** `stado release
  changes submit` ran every gate a product installation runs (format, lint
  and test) before writing its ticket. It therefore compiled the product,
  spent build budget and was refused whenever building was not admitted,
  although its contract records a commit without compiling. It now runs the
  pre-push check on the handed-off commit (lock resolution, module
  declarations and format-kind gates). A commit those refuse is still not
  handed off, and the batch build that takes the change runs the remaining
  gates. Journey: `tests/quality/gate_kind/handoff.rs`.

- **A delivery pass that could not finish is a named stall:** `stado ci run`
  keeps why a pass stopped in its last pass's `failed`, and `stado ci delivery`
  (and Stado Desktop, which reads it) lists it under `stalled` until a pass
  finishes, instead of reading "the delivery path stands" while nothing was
  checked or installed since.

- **Host-local schedules submit into their selected store:** immutable plans,
  replay lookups, claims and queued jobs no longer reopen the configured fleet
  backend. Host routines can finish while the fleet store refuses connections;
  store-bound submissions refuse a mismatched bucket before writing anything.

- **A product build names the defect it serves:** `stado product cargo`, `install`, `update` and `swift`
  asked `oko admit build` with no purpose, so a consent the operator limited to one defect never admitted
  them. Every `stado product` operation takes a repeatable `--purpose DEFECT`, passed to Oko's admission
  and to the host a service operation runs on; Stado Desktop's Cargo and Swift operations carry the field.

- **A product outside release control is no longer called an unknown release product:** `stado release
  status|promote|rollback` and the quarantine commands refused it as `unknown release product`, which was
  read again and again as "no release of it exists" for products whose archives stood published. The
  refusal now says `release control holds no rollout policy for "<product>"; this does not say whether a
  release of it was published`, and its help names the read that lists them, `stado storage objects
  releases <product>/`, beside the products release control holds.
- **The monthly budget is judged against what the month has already billed:** the cost forecast read the month's spend from `gcp.latest_month.net_cost` or `gcp.net_cost`, fields the billing snapshot never writes, and read every month as unspent, so `budgets.monthly_usd` passed with the month already spent and the month-end projection was the current burn alone. The forecast now sums each enabled billing provider's `monthly` row for the calendar month (a month with no row has billed nothing); a missing snapshot, a section that is not `ok`, or a provider whose section reports no monthly spend (Azure's reports a credit balance) leaves `month_spent_usd` and `end_of_month_usd` null with the cause in `month_spent_unknown`, and while a monthly budget is declared the coordinator places no new cloud capacity and logs `autonomy budget guard: budgets.monthly_usd is declared but this month's billed spend is unknown (<cause>); new cloud placement blocked`. An overrun is present only when its budget is declared and exceeded, a budget anomaly's `expected_value` is the budget it exceeds (null for spend that should not exist), and `stado overview` prints `billed this month: <amount>` or `billed this month: unknown, <cause>`.
- **Listing schedules reads them side by side:** `stado schedule list`, the coordinator's due-schedule pass and the web schedules page read every schedule one after another, so a listing took as long as all of its reads together and a slow fleet store made it take minutes; the schedules are now read under the crate's one bulk budget, in the same order, each listed once and a removed one not at all (`tests/schedule/listing.rs`).

- **The name register says what a claimed repository is when GitHub does not:** `stado product catalog --names` wrote `(no description on GitHub)` for every repository without a GitHub description, including the ones a catalog product claims and describes, so most rows of the register named nothing. A repository with no GitHub description now says what the catalog says it is: a product's owner repository carries the product's catalog description, and any other repository the product claims carries its surface kind and the product before it (``desktop surface of `weles`: …``), so a desktop app or client library never reads as the product itself. A new `from` column says whether each row's text came from `GitHub` or the `catalog`; a repository described by neither reads `(no description on GitHub or in the catalog)`. A repository `gh repo list` gives no `nameWithOwner` is refused by name instead of being looked up under its bare name.

- **A registry read on a host that is not the authority answers from the generation this host's resolver holds:** every command's registry read (`database resolve`, `registry pull`, `schedule`, host commands) asked the authority's `stado resolver snapshot` over SSH first, so a slow or silent authority held every command on every other host for as long as it stood, though each host's own resolver held the same generation. The read now asks this host's resolver on its loopback API first and says `stado: registry generation <N> read from this host's resolver, …; the authority was not asked`; only when the resolver holds none it may answer from (none runs, or its generation is past max-stale) does it ask the authority, saying why. `placement move --authority` and `registry push --last-known-good` still ask the authority itself whether it answers.

- **`stado placement move` runs on the host it is called on:** a move whose registry authority was another host ran the whole transaction as a second `stado` over SSH on that host, so a move off the authority host waited on that host's own process, silently, for as long as it stood. The move now reaches the source and the destination through their own channels from the calling host and commits through the registry's compare-and-swap, as every registry writer does; a refused source channel fails the move with its error, and a standing one is a wait `stado waits` names.

- **Stado no longer trusts the eight compromised eMudhra intermediates:** it locked rustls-webpki 0.103.13 and webpki-roots 1.0.9 (RUSTSEC-2026-0382, RUSTSEC-2026-0381), and the AWS SDKs' default `rustls` feature pulled in their legacy hyper 0.14 client on rustls 0.21 and rustls-webpki 0.101.7, for which no fixed release exists. The SDKs now take their default features less `rustls`, so every AWS call uses `default-https-client`, and the lock carries rustls-webpki 0.103.16 and webpki-roots 1.0.10: a connection to a host serving one of those chains is refused with `invalid peer certificate: CertDistrusted`.

- **A Swift package's tests and programs run under `stado product swift` keep their Git transports:** the one `swift` process that compiled the package also ran its tests or program with `GIT_ALLOW_PROTOCOL` set empty, so a test that used Git itself (a fixture repository over `file://`) failed with `transport file not allowed`, as the Cargo operations did before their run left resolution. Sources are still resolved with Git transports off; the `swift build`, `test` or `run` that follows now passes `--skip-update`, so it updates no dependency, and leaves the caller's transports to what it runs.

- **A host runs its own routines from its own store, whatever the fleet store does:** a schedule lived in the fleet store, was fired by the coordinator and run by whichever worker claimed it, and a worker binds the fleet store at start and waits for as long as it does not answer, so with the host serving the fleet store down no routine was fired or run anywhere, including the supervision routines that keep a host's agents working. Every worker now also opens `~/.stado/host-store`, a store on the host itself with the same schedule and job records, and on its poll fires that store's due schedules, records the sweep, settles and renews the routine jobs it started, fails a running host job no child of it runs once its lease has run out (a worker that stopped mid-job would otherwise hold an overlap-skip routine forever), and starts queued host jobs as child shells logging to `~/.stado/host-store/logs/<job-id>.log`, never waiting on the fleet store. The worker entry also stopped answering an unreadable `WC_VAST_AUTO_LIST` and a target without a declared GPU type with silent defaults: the first is refused by name, the second leaves detection to the host. Real test: `cargo test --manifest-path stado-rs/Cargo.toml --test scheduler -- host_routine::`.

- **A delivery no longer starts a second copy of a service placed on another host, and two deliveries of one release no longer stage over each other:** after activation a delivery restarted every unit the product declares on the host, and restarting a booted-out launchd unit loads it, so delivering a program to a host that stands by for a service placed elsewhere (what `placement standby` does) started a second copy of that service there. A unit the init system answered for and did not hold is now decided by placement read from the registry: when its service is active on another host it stays unloaded with the step `restart not_loaded` naming that host; any other absent unit (crashed, booted out, delivered for the first time) is started and proven; a registry that cannot be read leaves it unloaded with `restart placement_unread` and the read's error. Every stage (a program, a tree and the retained reader archive) named its archive, response headers and extracted files by fixed paths in the staging directory, so an operator's delivery beside the host's own release agent removed the other's half-written headers and ended `…incoming.head: No such file or directory`. Staging now holds a lock in that directory naming its process: a second delivery while the holder runs ends `stage busy_<pid>`, and a lock left by a delivery that was killed is taken over, the leftover staging files removed. A restart failure line now says `absent` for an identity field the init system did not report, instead of printing it empty or as zero, and a launchd exit status followed by its name (`78: EX_CONFIG`) now counts as a failed run.

- **`stado host exec <target> -- stado resolver status --json` is approved:** a workstation's resolver refusal names a request another host holds unanswered and tells the reader to ask that host's `stado resolver status`, but the host-exec allowlist did not approve the command, so the held adapter, its phase and age, and the object API's vault consultations on that host could not be read through Stado. The fixed read-only verb is now an approved connectivity read; it reads the state files the resolver already published and changes nothing.

- **`stado placement move` keeps what the destination held at a state path instead of deleting it:** the move writes each state the profile declares over the destination's path behind a backup, and after the commit it deleted that backup, so a destination that held its own file there (its own audit journal, say) lost it although it was never part of the source. The backup is now renamed to `<path>.replaced-by-placement-<transaction>` beside the moved state, and the receipt lists each such path under `kept_replaced_state` (`kept what <host> held there before the move: <path>`); a backup that could not be settled is listed under `unsettled_state` with its cause instead of a warning nobody reads. A state read that marks its file present without a payload is now refused naming the state, rather than read as an empty file.

- **`stado placement move` can move a profile to a host that stands by for it:** `placement standby` writes the destination into the directory as a `standby` address, while the move's cutover required an `endpoints` entry for it, so a move to a standby host started the destination, retired the source and was then refused at the commit with `service route for profile … has no endpoint on …` and rolled back. The cutover now moves the destination's standby address into `endpoints` in the committed document, and a destination the directory names under neither map is refused before the source is fenced, naming the service and the `placement standby` that would name it.

- **A consumer grant the service directory declares no longer lapses on a clock or stays bound to a bearer its product no longer holds:** a declared grant the vault still recorded with an end (issued before declared grants were minted until revoked, or by hand with `--ttl-seconds`) expired, and a grant whose recorded bearer was not the one in its declared file refused every read; either way every read its product made was refused with Skarbiec's 403 although nothing revoked it. The agent on the host that holds the owner vault now lists the vault's grants on every tick. A declared direct grant whose service is placed on that host is asked whether its declared bearer file opens it (`skarbiec grant verify`), and when it has an end or the file does not open it, it is re-issued until revoked against that file with the capabilities and audience it holds, then asked again; a declared file missing on its own host is a failure. A declared grant whose service is placed on another host and that has an end is kept until revoked through `skarbiec grant keep`, its path never read here, and that its bearer is checked where it lives is said. A direct grant with an end that no declaration owns keeps its end and is named once; a host without the owner vault, or a replica, does nothing. A failure is logged as `declared grants: renewing or binding the grant failed for <consumer>: <cause>`. `stado credentials grant renew` runs the same pass after the agent grant and exits 1 naming such a failure or a read that failed; Stado Desktop's operation is now **Renew this host's agent grant and keep declared consumer grants**. Real journey: `tests/credentials/declared_grant_keep.mjs`.

- **A product whose own dependency requires its new verb can be installed:** installing Oko builds its Stado dependency first, and that Stado's requirement of `oko admit` was judged against the older Oko still installed, so the install stopped in Stado's finish with `oko cli needs verb admit` and no Oko carrying the verb could be installed through its normal install. `stado product install` now keeps the installations in progress with the revision each builds; a verb is met by one of them when that revision's `contracts/verbs.json` declares it, and the decision says so. A dependency Stado builds for itself is finished by the binary it built, so the handoff passes the installations in progress in `STADO_PRODUCT_ENCLOSING`, and a value there that is not that list is refused naming the variable. A revision that does not declare the verb is judged as before.

- **A registry read from a machine that declares no resolver is bounded by the authority's own interval:** a read that asks the registry authority over SSH was abandoned at the refresh interval this machine's resolver publishes or its registry record declares, and a machine whose record declared no resolver had no measure, so its read of an authority that accepted SSH and answered nothing waited without end. Such a read is now measured by the interval the authority's own resolver is declared with in this machine's last-known-good copy, the interval at which it serves its snapshot; it is abandoned at that interval, remembered as unanswered, and the reader goes on to its copy. Only a read no record declares an interval for waits. Real journey: `tests/host_silence/silent_authority`, case `a_reader_declaring_no_resolver_is_bounded_by_the_authority_interval`.

- **An outage names this machine's failing Stado unit:** when the host Stado process exits at every start (a release whose parser refuses its unit's own argument vector), its supervisor restarts it without end and every command that needed its object API, resolver or local API failed with a refused connection and nothing more. A command that fails with `infra_down` now reads this machine's Stado unit and, when its supervisor holds it loaded with no process and a nonzero last exit, prints `this machine's <unit> runs no process: its last run exited <code> and its supervisor has started it <runs> time(s); its last log line: <line>` after the error line, and carries it as `host_unit` in `--json`. A read of the unit that fails is said, never taken for a running unit.

- **`stado release history` rewrites a line that merged its upstream:** a merge in the unpushed range refused every plan with `… holds merge commits`, so a checkout that had once taken the remote's commits through a merge could never fold its format commits or fixups before a push. A merge whose other parents the upstream already holds adds nothing the base lacks; the plan now names only the line's single-parent commits, they are replayed onto the upstream without the merge, and the tree check still refuses a merge that carried a change of its own. A merge of a second unpushed line is refused with `… holds the merge <merge> of <parent>, which <upstream> does not hold`. Real journey: `tests/release/history/merged.rs`.

- **An EC2 state the provider cannot place is refused, and an interrupted spot VM is recognised:** the `aws` existence read answered false for every state other than `pending` and `running`, so a state word EC2 adds later read as no VM and the reaper put back a job whose VM might still run it; and the provider had no lifecycle read, so a spot instance EC2 interrupted was reported as `instance gone (lifecycle=None)` instead of `Spot preempted`. The documented EC2 states now place a VM as running (`pending`, `running`), stopped (`stopping`, `stopped`) or ended (`shutting-down`, `terminated`) for both reads, and a word outside that list is refused with `EC2 instance <id> returned unknown state <word>; existence cannot be decided`. The `aws` accelerator census counts per accelerator without a counter seeded by hand.

- **Stado works without Skarbiec everywhere a file credential store is selected:** `STADO_CREDENTIALS_STORE=file:///…` moved only the `stado credentials` commands and build secrets onto the file, while every read through Stado's own grant still dialed Skarbiec: the object, release, machine, registry, service and integration API verifiers, `stado service secret-sync`, the dashboard's operator sign-in, the public status checks, the release catalogue's publishers and a local agent's workload secrets. Stado's own client now reads, lists and rotates through the selected store, a field read (`read_field`) is routed like every other read, and `stado azure` reads the operator session from the store it writes it to. With Skarbiec selected the vault is asked exactly as before.

- **Fleet SSH keys work with a file credential store:** the host channel's key read and `stado fleet key add|generate|rotate` took Skarbiec's administrative coordinates before reading anything, so with `STADO_CREDENTIALS_STORE=file:///…` and no Skarbiec address they were refused with "this machine has no Skarbiec address" even though the key was in the file. Both now use Stado's own client, which reads the selected store; a failed read names that store. `STADO_HOST_SSH_KEY_FILE` still comes first, and its owner-only check reads the mode through the shared file-mode helper.

- **The fleet's GitHub identity is found in a file credential store:** the route the identity declaration names (`stado-rs/data/fleet/github-identity.json`) was resolved only by Skarbiec's route table, so with `STADO_CREDENTIALS_STORE=file:///…` the runner precheck, `stado runner credential` and `stado ci` stopped with "Stado cannot reach Skarbiec to resolve the GitHub route …". With a file store the route's resource is now the item's id and its only string field is the credential, which is what `stado credentials put github:org-runner-admin < token` writes; a missing item, an item that is not an object, or one with several string fields is refused naming the file, the fields it holds and that command. With Skarbiec selected the route table is asked exactly as before, and the route-report diagnostics now say when Skarbiec reported no route table or no reason instead of substituting one.

- **The precheck runner's Skarbiec reads beside Brama take the vault commands' search path:** the Probierz agent credential lookup and the model review bearer mint ran Skarbiec with a `PATH` of their own, without GPG Suite's directory or the account's `~/.local/bin`. Both now take `primitives::tool_path::vault_assignment` for the Brama host's home, like every other Skarbiec command Stado runs on a host.

- **The Weles trust document is rendered with the vault commands' search path, and a refusal is quoted whole:** the renderer ran its Skarbiec reads with a `PATH` of its own; it now takes `primitives::tool_path::vault_assignment`, so a host whose `gpg` is in GPG Suite's directory or `~/.local/bin` renders like the rest. A refused render quotes the host's whole failure with its exit status instead of its last line.

- **The recovery verifier's Skarbiec metadata reads take the fleet's search path and quote failures whole:** the verifier ran `skarbiec grant list`, `vaults` and `list` with a `PATH` of its own; it now carries `primitives::tool_path::assignment`. A failed read quotes Skarbiec's whole failure with its exit status, and an answer that is not JSON is quoted with the parser's reason.

- **Capability routes are read with the vault commands' search path, and a broker failure is quoted whole:** the capability broker ran Skarbiec with its own `PATH`, without the GPG Suite and `~/.local/bin` directories, so on a host whose `gpg` lives there every route answered `does not open: spawn gpg`. It now takes `primitives::tool_path::vault_assignment`. A failed broker command and an unreadable vault environment quote the host's whole failure with its exit status instead of its last line.

- **Grant sync and revoke run Skarbiec on the declared vault search path:** the host programs that re-issue and withdraw a consumer's grant exported their own `PATH`, without the GPG Suite and `~/.local/bin` directories the other vault commands carry, so a host whose `gpg` lives there could list its vault but not change a grant. Both now export `primitives::tool_path::vault_assignment`. A service file's mode is checked against the owner-only file and program modes read from the platform's own mode bits, and the refusal prints them in octal.

- **Skarbiec commands on a host take one declared search path, and the seed-state read says why it failed:** the vault commands and the TOTP seed-state read each spelled their own `PATH` with GPG Suite's and the account's `~/.local/bin` directories. Both now take `primitives::tool_path::vault_assignment`, the fleet's declared search path followed by those two. A failed seed-state read quotes Skarbiec's whole failure with its exit status, and an unreadable answer is quoted with the parser's reason.

- **A LaunchAgent's domain reason no longer names "nobody" for a console it could not read:** the launchd domain resolver read `/dev/console`'s owner with errors discarded and called an unreadable console `nobody`, and a console the account owned while launchd had no `gui/<uid>` was reported as belonging to someone else. The reason now quotes `stat`'s words for an unreadable console and says when the account owns the console but launchd answers no graphical domain.

- **The bootstrap says why it did not reuse an installed Stado:** the check for a reusable Stado read its release marker with errors discarded, so a marker that could not be read looked like one naming no version, and the bootstrap then printed only "installed stado is missing or unmarked". The check now names a missing marker, a marker naming another version (with both versions), and lets `cat` say why a marker cannot be read; the `[install]` line quotes the check's own words and exit status.

- **`stado credentials vault list` says why a host's Skarbiec did not list its vaults:** the host program discarded `skarbiec vaults`'s stderr and called every failure "skarbiec here predates the vaults command", so a vault Skarbiec could not read looked like an old release holding none. The host's answer now carries `error` with the binary and Skarbiec's own words, and an answer that does not parse is quoted with the program's whole failure.

- **`stado space volume unmount` refuses when it cannot read fstab:** the check for an fstab line Stado did not write discarded `awk`'s errors, so an `/etc/fstab` that could not be read looked like one declaring nothing and the volume was unmounted. It is now refused with `awk`'s words before anything changes; a host without fstab still declares nothing. A failed fstab backup and a failed `systemctl daemon-reload` keep their programs' words, and a program that ended without a finding is reported with its whole failure.

- **A delivery says whether it wrote its release receipt:** the activate program wrote `release-receipt.json` with its errors sent to `/dev/null` and `|| true`, so a receipt that could not be written left a host with no record of who installed the bytes and no word why. The program now says `receipt` with the path it wrote, or `receipt_unwritten` with the path and the shell's own words, and the delivery report carries both fields.

- **A machine submission's work file is created once and refused with its path:** creating the owner-only file a machine submission stages its source through tried up to sixteen fresh names and then refused with no path. Its name ends in a fresh random UUID, so a file already there was not left by this process: it is now created once, and any failure is refused naming the file and the operating system's cause.

- **Unit directories are read from one declaration in four more places, and a remote file retirement says why it failed:** the unit-domain classifier, the misdeclared-domain finding, the precheck runner's daemon check and file retirement spelled `/Library/LaunchDaemons` and `/Library/LaunchAgents` for themselves; they now read `deploy::service`'s unit-path declaration, compared by path component rather than string prefix. The misdeclared-domain finding holds its account as present or absent instead of an empty string. A file retirement the host's Stado refused now quotes its whole failure with the exit status, and a report that does not parse is quoted with it.

- **The object-API and release-store repairs quote the host program's whole failure:** a repair the target's older Stado refused reported only the last stderr line, `For more information, try '--help'.`, hiding the line that named the refused verb. Both repairs now quote every line the host program printed, with its exit status, through the host channel's new `whole_failure` reader.

- **The object-evidence cleaner says when a link stands in its root's path:** a symbolic link or file in place of a directory on the way to an evidence root was only counted as `root_not_a_directory`, so a root the cleaner never cleans under looked like a quiet pass. It is now also named among the pass's errors with that component's path and the operating system's refusal; the cleaner still does not follow it.

- **Release publication names what a build receipt got wrong:** a receipt that disagreed with its run in any of eleven ways was refused as `release job returned mixed or invalid output`, leaving the operator to diff it by hand. The refusal now names the job and every field that disagrees with both values, an absent artifact with the archive's digest, and a failed status with the failure the receipt states. A release job that failed without an error now says it ended in its state without one, instead of printing the state as the error.

- **`stado resources rationalize` says why a source was not read whole:** the source table's `ERROR` column printed only an `error` field and left every other cell blank, so a source blocked because the queue is on device-local storage, or one unsupported by this build, showed no cause and no remedy. The column is now `WHY`: empty for a source read in full, and otherwise the error, reason and `remedy:` the source gave, or `not reported` when it gave none.

- **`stado release staged activate` says why it stopped:** an env file whose bytes did not arrive intact was reported as one that "could not be read (read)", a staged installer that failed was never checked and the run went on to compare versions, and a run that did not report the runtime link after the settle window was refused as one "put back to" an empty link. The env-file refusal now carries the fetch's own report (missing is not found; unreadable or corrupted is an infrastructure failure), a failed installer is refused with its exit and last error line, and a missing link reading is named as missing.

  constant), each unmeasured figure null with its cause in `<name>_unread`, and nothing pending is
  null. The agent publishes its volume's `disk_total_bytes`, `disk_free_bytes` and, when it cannot
  read it, `disk_unread`; builder placement judges a build's scratch against those bytes instead of
  rebuilding them from a rounded GiB figure and a percentage.
  A failed disk write probe now publishes the operating system's reason in
  `home_write_probe_error` and logs it, instead of a bare `home_write_probe_ok: false`. Every
  published disk cause names the fleet volume rather than its local path, as the capacity
  diagnostics promise, and the disk gate's log lines state their figures in GiB. All disk readings
  of the agent, the janitor and the build worker go through the disk-full rule's one volume reader.
  The fleet-volume probe also checks removal explicitly; a failed unlink refuses admission with
  its own cause instead of being discarded by temporary-file cleanup.
- **Staging leaves a RAM-backed `/tmp` for a mount chosen by its device:** the agent passed over
  mounts whose filesystem name was on a fixed list, so an unlisted RAM or network filesystem could
  be chosen. A candidate is now a mount whose source is a block device. Mount paths are decoded
  before use; an unreadable device is skipped with its cause. The write probe creates its own
  file exclusively and refuses a candidate if writing or removing it fails. An unidentified
  medium ranks after identified disks and is never reported as an HDD.
  Partition media comes from the kernel's device hierarchy rather than a partition-name regex
  or trailing-digit removal, so different block-device naming schemes use the same reading.
  Explicit staging paths retain their whitespace and use path-component comparisons, so a
  directory whose name only starts with `tmp` is not treated as a child of `/tmp`.
  An empty or non-UTF-8 filesystem-type answer is reported as an unreadable `/tmp`, not as
  proof that staging is already disk-backed.
  Root-owned staging handover corrects both UID and GID and reads them back, refusing a candidate
  whose ownership cannot be observed rather than accepting an unchanged group.
  An empty staging-user override, an account row without a name, or an effective UID absent
  from the account table is refused with its cause instead of substituting an unknown owner.
  A non-root agent refuses another account's UID instead of ignoring its staging selection.
  The resolved account is reused across candidates rather than rereading the account table.
  Mount-table fields use space and tab separators, preserving other whitespace inside names.
  Kernel-escaped hash marks in device sources are decoded alongside whitespace and backslashes;
  each escape is interpreted once.
  The startup redirect covers ramfs as well as tmpfs, retaining the observed filesystem name
  in diagnostics instead of labelling every RAM-backed /tmp as tmpfs.
  Repeated mount points use the final source for medium lookup; overwritten source fields
  are not decoded and allocated only to be discarded.
- **Pending staging size must be measured completely:** unreadable entries invalidate the total
  and refuse admission instead of being skipped and counted as spare room. The publication
  carries `largest_pending_raw_dir_gb_unread`; an absent pending root remains nothing pending.
  Tree measurements do not traverse symbolic links and reject byte counts that cannot fit.
  A disk-gate refusal also carries its measured cause as admission_detail, so host gates and
  Desktop do not stop at the generic disk_gate_refused label.
  Write, flush, sync and removal failures name their own operation rather than combining a
  persistence failure with a write failure.
  Fleet and staging probes explicitly attempt removal even after an earlier operation fails,
  preserving both causes if the failed probe also cannot be removed.
  CLI host gates and Desktop also retain a supplied refusal detail when the publication has no
  reason label, rather than discarding that cause for a generic busy-or-gated message.
