# Changelog 0.22.18 – 0.22.19

Released entries, moved out of `CHANGELOG.md` so that file stays editable.
The current entries live there; this file is history and does not grow.

## 0.22.19

- `stado host user delete USERNAME --target T` requires `--confirm USERNAME` (cli.md rule 16): the account, and its home directory unless `--keep-home`, cannot be restored, so a missing or different confirmation is refused with exit 2 before the host is contacted, naming what would be removed. `--json` prints the target, SSH target, username, status, OS and whether the home was kept (rule 13).
- `stado fleet key ls --json` prints each stored SSH host key's item, key type and fingerprint as JSON (cli.md rule 13). A key whose context cannot be read now fails the listing with `cannot read the context of credential item <item>: <error>` instead of printing it with two blank columns.
- `stado vast list`, `unlist`, `status` and `monitor` print one `key: value` line per field for a person and the same answer as JSON with `--json` (cli.md rule 13); before, they printed JSON only. Stado Desktop's Earning screen passes `--json`.
- Read commands print text for a person and the same answer as JSON with `--json` (cli.md rule 13): `stado cost report` and `cost estimate` (the JSON carries every completed job's row and each bucket), `stado resources operations list` and `show`, `stado optimize explain` and `optimize policy show`, and `stado-coverage list`, `verify` and `retry`. `stado cost allocation|forecast|anomalies|savings` without `--json` now print one `key: value` line per field instead of indented JSON.
- `stado schedule show ID` prints the schedule's fields as text; `--json` prints the full persisted record it printed before. The MCP tools `stado_schedule_show`, `stado_cost_report` and `stado_vast_status` pass `--json`.
- `stado config show` and `stado host config-show TARGET` print the config file and every resolved key as `key: value` lines; `--json` prints the document they printed before (cli.md rule 13). Every caller that reads it — `host config-set`/`config-unset`, the host gates and Stado Desktop's enrollment entrance — asks with `--json`, so a host still on an older Stado refuses that flag by name until it updates. `stado config` with a missing key or value, or an unknown subcommand, now exits 2 as a usage error, and the unknown-subcommand refusal lists `get`.
- `stado serve --api-local-store PATH` serves the object API from the local root PATH while the process's other roles — worker, resolver, release agent — use the storage the host's config names. It is `--api-storage` for a local primary spelled as a path, because a unit argument cannot carry the JSON's quotes, and it is what an operator's machine declares: its worker publishes capacity to the fleet's store through the `stado` route, and its API serves its own store. With `WC_STORAGE_BACKEND=local` on the whole process, the worker published to a store "that does not answer for the fleet" and the host built nothing. `stado bootstrap --local` folds the option like every other serve option.
- The catalog's `stado` service declares `--api-local-store $HOME/.stado/local-storage` instead of `WC_STORAGE_BACKEND=local` on the whole process. `service ensure` applies the catalog's environment to every declaration of the unit, so on an operator's machine, whose config names the fleet's `stado` route, the worker and release roles were pinned to the host's own store and the host published no capacity the fleet could see; now only the API serves the local store.
- `stado service ensure … --unset-env NAME` withdraws a variable from a unit's declared environment. A declaration kept every variable it was ever given, whatever `--from` re-declared, and `--env` could only add or override, so a host whose unit carried `WC_STORAGE_BACKEND=local` from an older catalog could not be moved onto its config's fleet store through the product.
- `stado serve` starts the worker, the release agent, the cleanup watch and the coordinator after its own `--resolver` role publishes `serving` when its storage backend is the client route `stado` at a loopback URL — the adapter that resolver binds. Before, each of those roles read the store as it started, answered "connection refused", ended with it and took the process down, and launchd ran the same race again (`component=worker … tcp connect error`, `the cleanup report names no check_interval_seconds`). The wait is on the resolver's own publication, woken by the kernel's notification, with no interval of the process's choosing.

## 0.22.19

- `com.wisent.stado` takes the API listener over from a predecessor unit that declares no storage variables. The takeover resolves the predecessor's root the way its own process does: `WC_STORAGE_BACKEND`/`WC_LOCAL_STORAGE_PATH` from its environment, else the `storage` section of the config file it starts with (`STADO_CONFIG`, then the candidates under its `HOME`), else `local` and `~/.stado/local-storage`. Before, a first-generation unit such as `com.wisent.always-on.stado-object-api`, written without those variables, was reported as serving backend `None` root `None`, the takeover failed, and `stado serve --api` refused to start under the one unit on every host that still loaded it. A predecessor that resolves to another root is still refused, and the refusal now names the backend, the root and where it came from.
- A predecessor whose primary backend is the client route `stado` (or `stado-object`) is taken over like a `local` one: that route addresses an object API, and the API the predecessor's own process runs serves `storage.local.path`, which is how an operator's machine shares the fleet's one registry. Before, the takeover compared the backend word to `local` alone and refused `com.wisent.always-on.stado-object-api` on lukasz-macbook with `it serves backend "stado"` for the very root the one unit was about to serve. A backend that serves no local root (`s3`, `azure`, `gcs`) is still refused.
- A registry whose rollout strategies predate `readiness_poll_seconds` is read again. The field became required on 2026-10-01 without a declaration in the canonical registry, so every reader of the registry — `stado registry set`, `stado registry pull`, `stado release agent`, the `release` component of `stado serve` and with it `com.wisent.stado` — refused with `registry.release_control: missing field readiness_poll_seconds`, including the one command that could have declared it. A strategy that does not declare the field now reads 5 seconds until the operator declares one with `stado registry set --path release_control.products.<product>.strategy.readiness_poll_seconds --value <seconds>`; a declared `0` is still refused by validation.
- A registry whose resolver adapters still carry `idle_seconds` or `connect_seconds` is read again. Both fields were retired on 2026-10-01 while the canonical registry still declared `connect_seconds` on charless-mac-mini's adapters, so the resolver role refused the authority document with `registry.targets[charless-mac-mini].service_resolver: unknown field connect_seconds`, `stado serve --resolver` stopped, and with it `com.wisent.stado` and every `stado://` adapter on the host. The two fields are accepted and ignored.
- `stado bootstrap --local` folds a unit that already runs `stado serve` under another label into `com.wisent.stado`. The first-generation `com.wisent.always-on.stado-object-api` ran `stado serve --worker --disk-cleanup --resolver --release-interval-seconds` that way; the merge counted only single-role units (`stado work agent`, `stado resolver serve`, …) as resident roles and left it as it is, so the one unit came up with none of those roles and the host's resolver adapters went dark. Every role the predecessor runs is now a role of the one unit; an option both declare differently is refused naming the unit, the option and both values; a predecessor worker without `--poll-seconds` is refused with the `stado service ensure stado --host <host> --from <stado> --arg=serve --arg=--worker --arg=--poll-seconds=<N> …` declaration to make instead.
- The resolver's "one of the two has to move" refusal — its adapter bind equals `storage.stado.url` — applies only to a process whose registry backend is that client route. `com.wisent.stado` reads its registry from the local store it serves (`WC_STORAGE_BACKEND=local`), and the URL the operator's config keeps for the other clients on the host is not an address it reads through; refusing it left lukasz-macbook without a resolver, so every `stado://` adapter on the host, including the one at `127.0.0.1:18776` that `storage.stado.url` names, answered connection refused.
- `stado service ensure stado --host <this machine>` records its pass. The ensure restarts `com.wisent.stado`, which carries the resolver adapter the command's own registry route goes through when `storage.backend` is `stado`, and the record was written straight after the restart, so every pass on the operator's machine ended with `recording the completed ensure failed: … 127.0.0.1:18776 … Connection refused` and the declaration never reached the registry. When the ensured unit is this machine's own `stado serve --resolver` and the route is that client one, the record is written after the restarted process publishes `serving` in `~/.stado/resolver-state.json`, woken by the kernel's change notification on that directory, with no interval of the command's choosing; a resolver that publishes `failed` ends the pass with its own reason.

## 0.22.19

- `stado schedule edit ID [--command C] [--cron EXPR] [--tz ZONE] [--json]` changes what a schedule submits or when, through the same compare-and-swap update pause and resume use; an enabled schedule's next run is recomputed from now unless an occurrence is already leased. Naming none of the three is a usage error, and an invalid cron or a timezone the next run cannot be computed in is refused before anything is written.
- `stado artifact alias remove ALIAS_REF --expected-target VERSION [--json]` deletes an alias while it still targets VERSION; an alias retargeted since is refused with `ARTIFACT_ALIAS_CONFLICT` and nothing is removed, the versions stay, and an absent alias answers `removed: false`.
- `stado host gpu-power-limit-unset TARGET [--json]` withdraws a declared board power cap: it removes `gpu_power_limit_watts` from the registry target through the same compare-and-swap write `gpu-power-limit` uses, then sets every GPU back to the driver's `power.default_limit` and prints what the driver reports. A failed host step names the registry generation already written and the host's own error.
- `stado space volume unmount TARGET --mount-point PATH [--json]` is the inverse of `volume mount`: it unmounts the filesystem and removes the `# stado-volume` fstab line for that mount point, leaving the disk's data alone. A busy filesystem is refused with `umount`'s own error and fstab is left unchanged; a mount point declared by an fstab line stado did not write is refused by name; a mount point neither mounted nor declared answers `not_mounted` and changes nothing.
- `stado fleet unassign TARGET` takes a registered machine out of its fleet by clearing the target's `fleet` field through the registry's compare-and-swap write; the machine stays registered, an unknown target is refused, and a target in no fleet is reported unchanged. `fleet delete`'s refusal for a fleet with members now names both `fleet assign` and `fleet unassign`.
- `stado credentials grant agent-renew` decides its exit status from the renewal's own outcome instead of searching its log lines for words: a grant listing that cannot be read, a declared role that cannot be granted, or a Skarbiec launcher that cannot be found now exits 1 with that step's sentence, where before they exited 0 because their wording held neither " failed" nor "could not". `--json` carries `renewed` and `failed` from the same outcome.

## 0.22.19

- `stado credentials` has one name: the `secrets` alias is gone, and every help text, refusal, example and the desktop's database form name `stado credentials`; `stado-database` reads a credential field with `stado credentials get`. `stado install-disk-cleanup`, which only refused, is removed; the cleanup watch is the `--disk-cleanup` role of `com.wisent.stado`.
- A GitHub pre-check runner is a role of the host's one Stado unit, not a unit of its own: `stado serve --precheck-runner ROOT` runs `ROOT/start-runner.sh` under passwordless sudo, and the launcher drops to the runner's account before GitHub's listener starts. `stado runner install` writes the launcher, retires the daemon `com.wisent.stado-precheck-runner` or the service `wisent-stado-precheck-runner.service` (and every other profile's unit) on the host, and ends by asserting `com.wisent.stado` with the option through `service ensure`; the report carries `role`. `stado runner restart TARGET --profile P [--repository R]` takes the role off and switches it back on, then reads GitHub's view of the runner; the host-side restart programs and their waits on the runner log are gone. A re-registration takes the role off before the installer runs and the installer refuses a listener still alive. `runner status` and `runner diagnostics` read the launcher and the Stado unit's state, and a leftover daemon is a refusal. On Linux the retired service's sandbox directives are gone with it; the runner's confinement is its account and its nftables table. The memory policies that restarted the runner's unit restart `com.wisent.stado`. The catalog lists the retired runner units as `role_units` of `--precheck-runner`.
- The storage-root transaction's worker is a child of the host's one Stado process, not a transient unit: the launcher hands the worker's program, arguments, environment and log to the host process over its control socket (`adopt_transaction`), the host process runs it as the managed account and answers `inspect_transaction` with the worker's pid and exit, and the worker records that process as its manager (`service` is the catalog's `com.wisent.stado`). No `com.wisent.stado-storage-root-reconcile.<transaction>` daemon or service is written, and nothing is read from launchd or systemd for it. A host whose Stado process is not running refuses the launch with `the host process is not running, so no transaction worker can be adopted`.
- Stado installs no LaunchAgent for Probierz's desktop driver: Probierz's own process starts the CuaDriver app on demand and owns its socket, so `stado host gui-automation enable` retires `com.wisent.probierz-cua-driver` and the label Stado minted before it, reports the socket as owned by Probierz, and `stado host gui-automation status` names a leftover agent as a defect. The catalog retires both labels under Probierz.
- `GET /api/machine/status?job_id=<id>&until=terminal` holds the read until the job ends and then answers with its terminal record, so a caller no longer re-reads job status on a timer. The local store arms the kernel's own directory watch (kqueue on macOS, inotify on Linux) on the terminal prefixes before the first read, so an end written by any process on the device wakes it. Any other store refuses with `HOLD_UNAVAILABLE` naming the reason; a watch that fails mid-hold answers `HOLD_FAILED` with the kernel's error. `job_id` alone still answers at once, and any other query is `INVALID_REQUEST`.
- `stado machine status JOB_ID --until terminal` is the same held read on the command line: it prints the job's one JSON envelope once the job is completed, uploaded, failed or cancelled, with no timer and no re-read. A store without change notification answers `HOLD_UNAVAILABLE`, a watch that fails mid-hold `HOLD_FAILED`, and `--until` with any other value is a usage error. The HTTP route and the CLI now share `MachineFacade::status_until_terminal`.
- `stado job watch JOB_ID --follow` replaces `--follow-seconds N`: it arms the same local store change watch on the terminal prefixes and the job's `status/<id>/output/` log directory, prints new log bytes on each wake and ends when the job does, with no timer. A store without change notification refuses `--follow` with its reason, and a failing watch ends the command with the kernel's error.
- `stado build status --wait` and `stado build newest --wait` replace `--wait-seconds N`: the read holds on the local store's change watch (the build record under `runs/build/<id>`, the terminal prefixes and, while following, each platform job's output directory) until every platform's job is queued and has ended. No timer remains; a store without change notification refuses `--wait` with its reason.
- The service reconciler installs a product's one process where it is missing. A host whose registry declares units a catalog product replaced (`retired_units` or `role_units`) but not that product's own service gets `stado service ensure <product> --host <host>` on the next pass, recorded as `ensure_replacement` with the old units in its detail; the pass after it retires the old units as before. Report mode and the emergency pause record the plan only, and a refused ensure is a `repair_failed` row with ensure's own sentence. Hosts that kept `com.wisent.always-on.skarbiec`, `com.wisent.compute.service.oko-autonomy`, `com.wisent.compute.service.probierz`, `com.wisent.always-on.skrzynka`, `com.wisent.compute.service.transcript-lake` or the Weles and Stado predecessors because nothing declared `com.wisent.<product>` there now converge to one process per product.
- Stado runs on a host as one process, `com.wisent.stado`. Product updates are `stado serve --product-sync-interval-seconds N --product-sync-surface SURFACE` (repeat the surface), which runs `stado product sync --surface SURFACE --fetch` inside that process; `stado product schedule` and the hourly `com.wisent.products.cli-sync` and `com.wisent.products.desktop-sync` agents it installed are removed, and the catalog retires both agents once `com.wisent.stado` declares the role. Stado Desktop no longer offers the three update-agent actions. Host health is `serve --health-interval-seconds`; the separate release-agent and resolver launchd units are gone. `stado bootstrap --local --target failure-fixer|watchdog|<daemon or cron coordinator>` and `stado install-disk-cleanup` no longer install units of their own: each refuses, naming the `stado serve` option that carries the role and `stado service ensure stado --host <host>`. A Stado Desktop local deployment runs as `com.wisent.stado` and removes the `ai.wisent.stado.deployment.*` agents earlier releases installed.
- No wait, sleep or timeout is invented any more; a failure is the failing operation's own error. HTTP clients carry no request timeout and no pool or keep-alive timers. The authority SSH command, docker inspect, nvidia-smi, the fleet-shape host sweep and the release wall predicate run to completion. Retry loops that slept are gone: release promote, the object gateway's 502/503, coverage HEAD 429s and launchd bootstrap each answer once. `fleet ingress up` binds its port and hands the socket to the listener (`stado dashboard --inherited-listener`, refused with `--bind`/`--port`), reads `cloudflared`'s address and first registered connection from its output, then asks Cloudflare's DNS and the public address once each. The resolver no longer backs off (a failed refresh waits for the next declared tick, a failed startup read exits `failed`), no longer cuts idle connections or sniffs refused ones (every refusal is a 502 naming the cause), and `service_resolver` must declare `refresh_seconds` and `max_stale_seconds`; adapter `idle_seconds` and `connect_seconds` are removed and refused as unknown fields. The dashboard no longer closes keep-alive connections after 120 s or holds invite refusals to 250 ms. `web route` checks the hostname once. Azure long-running operations are polled at the `Retry-After` Azure names, and an answer without one is an error.
- The worker (`stado work agent`, `stado serve --worker`) requires `--poll-seconds`, the operator's period between queue polls; the agent's own ten-second cadence, its 90 s and 300 s store budgets and every pacing sleep inside a tick are gone. A store read runs to completion and a failing one ends the tick with its error; the capacity heartbeat republishes on the same period and only while the tick has moved since its last republish; a failed agent loop exits with its error instead of restarting itself after a delay. Jobs receive the period as `STADO_POLL_SECONDS`. Yielding no longer has a grace window (`--yield-grace` and `yield_grace_seconds` are removed): the hook runs to completion and a job still running afterwards gets SIGTERM and is waited for, as a cancelled job is. `stado queue drain` pauses and reports whether running/ is empty, exiting non-zero while it is not (`--wait` and `--timeout` are removed); recovery and storage-reconcile fences check the drain once (`--drain-timeout` is removed). `stado job watch --follow` became `--follow-seconds N`, and a job that is not found yet is an error. `hosts disk-cleanup --watch` runs on the declared `check_interval_seconds` with no 60 s floor.
- `stado build status --wait` and `build newest --wait` became `--wait-seconds N`: the build is re-read every N seconds until every platform's job is queued and ended, with no 20-minute queueing limit. Publishing reads each release job's terminal record once; a job still queued is an error naming its pinned host, and the optional-platform 15-minute claim grace is gone. Promotion runs the target's release agent pass after pass until it reports Committed or a refusal phase, with no 5 s poll, no 60 s slack and no convergence deadline; an agent that returns no state for the product is an error. Service lifecycle mutations take the reconciler's per-unit lease once (held by another mutation is an error) and no longer wait for a newer reconcile report; the handoff receipt drops `reconciler_fence`. `service retire`/`remove` retire once; `service ensure` reads the registry once after a host change; `service refresh-image` reads the unit once after `kickstart -k`. The storage-root repair, the link repair and the precheck runner report the state they observe instead of polling.
- A release policy's `strategy` must declare `readiness_poll_seconds`, the period between readiness probes inside its `readiness_timeout_seconds`; the agent's own 500 ms and 200 ms probe gaps and its 30 s lost-readiness confirmation are gone (confirmation now uses the declared readiness window). `stado release agent` needs `--interval-seconds` unless it runs `--once`; the 15 s default and the 5 s floor are gone. The precheck runner's GitHub registration, a host release's stable binds, the privileged launchd bootout and restart, the CuaDriver socket, the storage write fence lock, the systemd self-update replacement pid and the storage-reconcile label read are each read once and fail with what they observed. The watchdog's diagnostic commands and MCP's CLI dispatch run to completion (the per-command and 600 s timeouts and `timed_out` results are gone).
- A machine request reservation no longer expires after 15 minutes or renews itself every five: it is held until its submission records a result or releases it (state `released`), and a held reservation refuses another submission of the same id. The disk janitor no longer waits 5 s for a consent-gated folder: the first open runs on a helper thread and the folder reports pending until it answers. The unused Hugging Face rate-bucket waiter is removed. `vast auto-list` needs `--poll-interval-s` unless `--once`, and the worker's Vast bridge polls on `--poll-seconds` and needs `--vast-idle-window-s`. The watchdog loop needs `--interval-s` (the 60 s default and 10 s floor are gone; `serve --watchdog` takes `--watchdog-interval-seconds` without a default). A registry coordinator must declare `interval_seconds`. A running job's heartbeat is written on the agent's poll period and on every agent tick, not every 60 s.
- GCE zone operations are awaited through Compute's own `operations.wait` method, asked again while the operation runs, with no client-side 1 s poll. The Box transport has no request timeout (`BOX_API_TIMEOUT_SECONDS` is gone) and the unused `wait_for_state` poller is removed. The unused GCE/Azure self-terminate module, whose metadata probes were cut off after 2 s, is removed.
- Inline `#[cfg(test)]` modules that returned without an approval are removed again, from `deploy/host_exec/allowlist/arguments.rs` and `skarbiec/roles.rs`. `tama tests list` approves no test path.
- Numbers nobody chose are gone, together with what they drove. `doctor` no longer cuts a probe off after 8 s (or a multiple of it); each row answers when its dependency does. `billing watch --interval` and `host unit-log --lines` have no default and must be given. `config migrate` is removed with the config `schema_version` it existed to add; configs, the storage layout marker, autonomy records and resource plans no longer carry a schema stamp. Billing account health alerts on the first non-`ok` report instead of after an hour. An operator's resource plan no longer expires after a day and its operation lock no longer lapses after two hours (it is held until released); postconditions are read once after the provider operation finishes, and GCP operations are awaited through Compute's own `wait` method. Placement relief judges each host on its current publication (no 15-minute pressure window, no 30-minute cooldown). The optimizer prices by the calendar month and reads every feedback record; it no longer assumes a 120 s cloud startup or guesses GCP CPU/memory per shape. Release run listings read until the requested runs are found instead of stopping at 120. The Azure support ticket is polled on Azure's own `Retry-After`. Inference plan and route ids are the full SHA-256.
- A quarantine's cause is no longer guessed from English sentences in the candidate's log. The release agent names the cause where it observes it: a manifest without rollback compatibility is `rollback_compatibility_undeclared`; a candidate pid that is gone while another process listens on its port is `stable_bind_occupied`, and gone with the port free is `release_process_vanished`; a readiness request the HTTP client gave up on is `readiness_probe_unanswered`. A product's own `wisent-errors` envelope in the candidate's log still outranks what the agent saw. A log line without an envelope names no cause, so a record that only a sentence list used to classify now reads `unclassified`.
- No failure code is guessed from an error's wording any more. A failure's code is what the code that failed stated (`CmdError::failure`); one that states none is `unknown`, so only a stated retryable failure exits 69. `service ensure`'s registry read retries only a failure stated retryable.
- The service reconciler's row classification (`identity_unresolved`, `declaration_incomplete`, `repair_failed`) is stated by the repair that refused, not read from its sentence.
- A launchd stop or bootout treats exit status 3 or 113 (the job is not loaded) as the stopped state it asked for; the error text is not read.
- The Skarbiec recovery payloads exit 3 when the host was healthy and nothing changed; `host recover` and the memory pass read `recovered` from the exit status instead of looking for the word.
- `fleet enroll --install-key` no longer sorts ssh's exit 255 into "unreachable" or "rejected" by phrases; it says ssh could not open the session, quotes ssh's sentence whole and names both repairs. Stado Desktop's enrollment, invitation and adoption failures no longer pick a title by searching the command's sentence; they say what the step guarantees was left untouched and show Stado's sentence verbatim.
- `doctor`'s Skarbiec read-contract check passes on the broker rejecting an item-wide read as invalid (HTTP 400 or 422), not on the words `field required`; a 403 from Skarbiec always carries the grant-rebind repair; `quota azure-replies` and `azure-escalate` report az's own stderr instead of rewording a Forbidden they found by its words; a precheck runner target the registry cannot resolve is refused with the resolver's sentence.
- The cloud inventory no longer guesses `missing_permissions` from words like "forbidden" in a provider's error; the field is gone from inventory sources and plan details, and the provider's error is kept whole in `upstream_error`. A queue agent's Skarbiec grant diagnosis is chosen by the broker's 401/403 status, not by its sentence.
- `stado product surface [--package-path DIR] [--module NAME] [--json]` replaces wisent-desktop-auth's Python versioning gate (`Tests/Versioning/*.py`, pip-installed into a venv by its workflow). It builds the package's library product at the newest tag the remote serves (a published GitHub release outranks a bare tag; the local tag must name the commit the remote holds) and at the working revision, dumps both public surfaces with the toolchain's `swift api-digester`, and reads the change from the digester's verdict: a breakage is `breaking`, a differing dump with no breakage `additive`, equal dumps `internal`. The declared version is the version tag pointing at the revision, else `version.json`'s `version`, which `.wisent-release.json` names as the release version; the command refuses when that disagrees with the required next version (`0.x` breaking changes move the minor), prints the digester's diagnosis, and exits 1. No frozen `released-surface.json` is kept: the released tag's tree is the artifact, and the dump is the compiler's reading of it rather than a scan of source text.
- `stado release version-gate app-surface|app-baseline` read Python distributions, replacing the Python gates wisent-1b, uncensorbench and wisent-extractors kept under `tests/`: `--pyproject` (every `[project.scripts]` key is a `console-script:` name; its `[project]` version is the declared version), `--setup-py` (the literal `version=` of `setup()`), `--python-all MODULE` (`__all__` entries as `api:` names, repeatable), `--python-argparse MODULE` (subparsers registered with `help=` as `cli:` names; one without a help text is unlisted and private) and `--python-manifests DIR --manifest-suffix SUFFIX` (every string key of the dict or list literal assigned to a module-level constant ending with a suffix, as `<family>:<key>` with the family being the first directory below DIR). Nothing is imported: the same reader measures the released tag's blobs and the candidate. `app-surface` now prints the declared `version` beside the surface, so a workflow compares it with the baseline's without a second reader. The tree loader lists a directory in the shape `git show rev:dir` does, so a source may be a directory. Those three repositories' `released-surface.json` files are gone: the baseline is read from the newest version tag at the remote on each run.
