# Changelog 0.22.18 – 0.22.19

Released entries, moved out of `CHANGELOG.md` so that file stays editable.
The current entries live there; this file is history and does not grow.

## 0.22.19

- A queued job's secret reference is written under the key every Stado in the fleet reads again; 0.22.18 wrote it under `role`, and every older Stado refused the whole queue with `missing field item`.

## 0.22.19

- The object, release, machine, service, registry and host-health boundaries read their verifier items as the configuration names them again. Stado 0.22.18 looked each declared item up as a role, found none, and every object API boundary answered `503 object authorization unavailable`. Fleet keys and GitHub identity routes, which Stado mints or a route declares, are read as named too; only a secret a release recipe names by role is selected by `stado:role:<role>`.

## 0.22.18

- `stado database destroy NAME [--host HOST] [--json]` undoes `create --provider fleet`: it removes the managed unit that serves a postgres database, deletes the declared credential item from the owner vault, then withdraws the declaration, so a run that stops part-way can be run again. The data directory stays and is named. `remove` still withdraws only the declaration. Stado Desktop's operations list carries the same command.

## 0.22.18

- `stado registry host` gains `edit` and `remove` beside `show` and `add`. `edit HOST [--ssh] [--kind] [--release-platform] [--json]` rewrites the fields `add` declares and writes nothing when they already hold those values. `remove HOST [--json]` retires a target and is refused, with every registry path listed, while another entry still names the host. Both write under the generation they read. Stado Desktop's Hosts inspector runs both from **Edit or remove registry declaration…**.

## 0.22.18

- `stado build submit --platform <platform>` builds only the named declared platforms. The build records the manifest narrowed to them and their deliveries, so its secret enrollment, its jobs and any release of it cover exactly those platforms. A product whose other platform needs a secret the vault cannot answer yet still releases the platform its own host runs.
- Stado carries no tests the operator has not approved with `tama tests approve`: the integration tests, the `stado-source-checks` package, Stado Desktop's test targets, the inline test modules, the recipe's `tests` stages and the post-build qualification in `deploy/release/build_stado.sh` are removed, and `stado release verify-platform`, which only ran those journeys, is gone from the CLI and Stado Desktop.
- A required platform that declares no post-build test qualifies on its passing build: `stado release changes` no longer leaves it `awaiting_tests`, `stado release catalog enroll` and `audit` no longer refuse it, and `build submit` no longer warns about it. A platform that declares tests still qualifies only on all of them passing.
- `stado release catalog adopt` writes no test stage and no `release/test.sh`, and `--kind npm` no longer requires `scripts.test`.
- `stado web smoke` is removed: starting a site and fetching a page is a smoke check, which does not count as a test.

## 0.22.18

- `stado database create` no longer assumes Postgres on Supabase. It takes `--engine` (postgres or sqlite) and `--provider`, and the default provider is `fleet`: Stado runs the database itself on a fleet host (the vault owner unless `--host` names another) through the new `stado database place`, which initialises the data, issues the database's own certificate authority, writes `<name>-database` into the owner vault and installs the managed unit `<name>-database`. Supabase stays as `--provider supabase`, with `--anchor` and `--accept-monthly-usd` refused for any other provider.

- Stado carries no tests the operator has not approved with `tama tests approve`. The integration tests under `stado-rs/tests/`, the source checks package `stado-source-checks`, Stado Desktop's test targets, every inline `#[cfg(test)]` module, the release recipe's `tests` stages and the post-build qualification in `deploy/release/build_stado.sh` are removed. `stado release verify-platform`, whose only work was running those journeys on a host, is removed from the CLI and from Stado Desktop's Releases operations.

## 0.22.18

- `stado config validate` refuses the retired `agent.skarbiec.items`, and `stado config migrate-identities` removes it and points each release publisher entry at its `<product>-release-publisher` role, so a host moves from item names to roles with one product command followed by `stado release catalog enroll`.

## 0.22.18

- Secrets are asked for by role, never by vault item. A release recipe's `secret_env`, a job, a schedule, `agent.skarbiec.secret_fields` and every credential Stado reads name a role (`role#field`), and the vault decides which item plays it by the Skarbiec tag `stado:role:<role>`; an item's id is random and decides nothing, so renaming an item changes no behaviour. `agent.skarbiec.items` is replaced by `agent.skarbiec.roles` (`WC_AGENT_SKARBIEC_ROLES`). `stado credentials item put --host H --role R --type K` rotates the item playing R or creates one under a random id with the tag; `stado credentials grant role-read` replaces `grant item-read`. Two items in one role are refused. Release publishers play `<product>-release-publisher`; Stado's own credentials play `huggingface`, `cloud-aws`, `cloud-gcp`, `cloud-azure`, `vast`, `box`, `anthropic`, `alerts`, `twilio`, `host-health-api`, and backend messaging plays `apns`, `fcm`, `device-registry`, `email-provider`.

## 0.22.18

- On macOS, available memory is the kernel's own `kern.memorystatus_level` share of `hw.memsize` (what `memory_pressure` prints as the free percentage), in the host's memory pass, in `stado space report` over the host channel and in the runner diagnostics. The three readers summed only free, speculative and purgeable pages and left out the cache the kernel reclaims, so a host could publish well under a GiB available against its watermark while the kernel's level read most of its memory reclaimable.

## 0.22.18

- A handoff made after a build froze its batch, whose commit that build contains, is bound to it in an additional batch `runs/build/<build id>/changes-<digest>.json` the next time the build is submitted, and reads that build's verdict. It used to stay `queued` for good: every `stado build newest --queued` picked the product again and answered with the same passed build (c187756d).

## 0.22.18

- A worker claims one release build per build cache at a time. A build job whose product and platform share their Cargo target directory with a build already running on that host stays queued, and the scan publishes it under `claim_declined` with the reason, which `stado host gates` prints as a `declined:` line. A host that claimed several builds of one product at once left the newest `Blocking waiting for file lock on build directory` inside a claimed slot.

## 0.22.18

- A new build cancels the product's older builds it supersedes. After `stado build submit` or `stado build newest` queues a build, the jobs of every older build of that product still `waiting` whose commit is an ancestor of the new one are cancelled on each platform the new build queued, one stderr line each. An older build could otherwise compile for over an hour after a descendant was queued, holding the Cargo lock the new build waited on (28f4a7af).
