# Changelog 0.23.68 (part 3 of 10)

Released entries, moved out of `CHANGELOG.md` so that file stays editable.
The current entries live there; this file is history and does not grow.

## 0.23.68

### Fixed

- **A host Stado unit replaces its renamed API predecessor:** the predecessor runs `stado serve` and
  held the role lock, which refused the new unit before the API takeover that retires the
  predecessor could run, so the unit restarted beside it without end. When the role is held, the
  takeover now runs before the lock.
- **Bootstrap downloads Stado from the fleet's declared release origin:** the installer fetched from
  `api.url`, which can name a site that serves no release object at all (every download answered
  404). It now uses the `public_origins` declaration that publishes `/api/release/object`, and says
  which origin it used.
- **Bootstrap reads the workload-agent grant this host declares:** it refused unless
  `agent.skarbiec.consumer` was one fixed name. It now hands over the declared consumer and bearer
  file when they are distinct from the control plane's own, and otherwise provisions the machine
  without one, saying so: the machine runs jobs that declare no secret and leaves the others queued.
- **`stado credentials token mint` refuses a retired agent identity:** it minted a grant for a
  consumer such as `stado-local-agent`, and only the host's own configuration refused it later,
  after the bearer had been minted and delivered. The mint now refuses with `credentials token mint
  refuses consumer <name>: "<name>" is a retired agent identity that no host's configuration
  accepts; use "stado" locally or a new scoped *-agent consumer`, which is the same rule the
  configuration check applies.

- **A push to `main` runs the pushed commit's `lint` gates, not only its `format` gates:** a commit
  pushed straight to `main` skipped the clippy gate the submit queue and every installation run,
  so `main` went red for every session building from it. `stado quality check --pre-push` now
  runs the `lint` gates a commit pushed to `main` declares on fleet hosts exactly as `stado change
  run` runs them (`stado host cargo` for a Cargo gate, the action cache answering a tree that
  already passed, Oko asked to admit the compile as the pushing session's work) and refuses the
  push with each refused gate's own report. The queue records the commit it is about to push as
  the candidate's `landing`, and the pre-push check lets that exact commit through without
  running its gates again. The hosts come from their capacity publications; `--host HOST`
  names them by hand, and a push no host can take is refused naming the queue, whose pass
  names its hosts. A Stado that cannot read the queue's records (a newer queue wrote a state it
  does not know) says so and runs the commit's gates, instead of refusing every push.

- **A resident unit that starts Stado with an option it refuses is rendered again by that Stado:**
  a unit written by an older release, or edited by hand, made the installed executable exit on
  its argument vector at every start, and init restarted it without end. When the refused
  argument vector is exactly the resident unit file's, the refusing executable now starts its own
  `stado service ensure stado --host <this host>` before it exits, says so on stderr and writes
  the converge's answer to `~/.stado/logs/resident-converge.log`.
- **`stado product cargo` and `swift` ask Oko about the product they build:** they named no
  product, so `oko admit build` judged every one of them as a build of every product and a consent
  the operator gave for one product never admitted it. The product is now the catalog product whose
  owner or surface repository is the GitHub origin of the repository holding `--manifest-path`
  (`--package-path`, else the current directory); a tree outside every catalogued repository is
  still asked as every product's build.

- **A `Cargo.lock` moved without republishing `private-cargo-sources` is refused at push:**
  the input was compared with the lock only by the release build, so a commit that moved a
  private Git package passed every check and every build of it was then refused. `stado quality
  check` now compares the pinned input's provenance with the pushed tree's lock and refuses a stale
  input naming each package it lacks or carries beyond the lock and the `input pin --cargo` that
  repairs it; `stado release catalog input check <checkout>` asks the same of a checkout.

- **Stado no longer asks the person at a Mac about Apple Music, Photos, Contacts or Files and
  Folders it does not need:** the janitor's build-cache walk descended `~/Library`, where it opened
  the Photos syndication library and the media library, and the always-on host process made macOS
  ask for photos and the media library; every beacon opened `~/Documents`, `~/Desktop` and
  `~/Downloads` to measure them; the janitor opened all three each pass to decide where Cargo
  builds; and `stado space report` ran one `du` over the whole home. Every walk of a home now
  refuses one list — `Pictures`, `Music`, `Movies`, `Library`, `.Trash`, and each of `Documents`,
  `Desktop` and `Downloads` that `targets[].privacy_grants` does not declare for the program macOS
  holds responsible for the walk (the running Stado here, `/usr/libexec/sshd-keygen-wrapper` for a
  script walk over SSH on another Mac) —
  and nothing is opened to find out whether macOS allows it. The beacon measures only declared
  folders (`not measured` for the rest), and the `du` inventory walks the home one top-level
  entry at a time so a refused one is never opened; `~/Library/Caches` is no longer an inventory
  root.
- **A body larger than one object API chunk uploads again:** `put` named each staged part with
  a width of its own (three digits for a 514-part body) while composition and the deletion
  authorizer read the shared eight-digit part name, so composition refused every chunked upload
  with `chunk 0 is outside the target upload` — `stado release catalog input pin --swiftpm`
  among them. Parts are now named by the one shared spelling.
- **`stado quality check` gives a gate the history records the release build gives it:** the
  check exported the revision with no `.wisent-provenance/` records, so an application's version
  gate (`stado release gate app check`) refused every check with `the source archive carries no
  verified baseline provenance`. The check now writes the verified baseline provenance and the
  published diff into its export, made the same way the release snapshot makes them.
- **A throttled Cost Management query no longer leaves the Azure balance unread:** on HTTP 429
  the reader holds the longest wait Cost Management names (`x-ms-ratelimit-…-retry-after` or
  `Retry-After`), announced as a wait, and asks again; a 429 naming no wait is refused with its
  body. Before, one throttled read made every Azure create refuse for an unknown balance.
- **An Azure machine size is priced as a VM, not as its Cloud Services (classic) role:** the
  Retail Prices API lists both under the same `armSkuName`, and the credit gate took the higher
  one (5.696 instead of 2.752 USD an hour for `Standard_D64as_v5`). Only products named
  `Virtual Machines …` are quoted now.
- **`stado repair skarbiec --step crypto` runs Skarbiec's `keyring recover`:** Skarbiec 0.4.16
  renamed `recover-daemons` and made it end every gpg child stranded on the stopped agent; the
  payload still called the old name, so on a 0.4.16 vault owner the repair could not run, and on
  0.4.15 it replaced the daemons while the stuck gpg children kept every item read waiting.

- **`stado host upgrade TARGET` brings a host's Stado to a newer committed revision:** a host
  whose own Stado cannot read the registry authority, or holds no checkout to build from, had no
  product path to a newer release, so each one was upgraded by a hand-written sequence. The verb
  fetches origin/main without asking for a credential (or takes `--source-commit`, which
  origin/main must carry), refuses a revision older than or beside the one the host runs, builds
  it on a host of the target's release platform (`--builder`, else this machine when it shares
  that platform, else the target), signs it here with the fleet's signing role or
  `--signing-keychain`/`--signing-identity`, delivers it into a run of its own, lets the
  incoming program judge the host's configuration (`config validate`) and install it
  (`release local install`), and reads the registry, the host's own registry read, its vault
  (`skarbiec doctor`) and every declared service at its port before and after. A check that
  answered before and no longer does puts the kept previous program back and says so. When the
  signature changes the program's code identity, the verb lists each macOS dialog the host and
  this Mac will show with its answer, runs only from a terminal, and starts when the host's
  name is typed back. `--join-network` joins the host to Stado's network afterwards; `--plan`
  reads and reports every step and changes nothing. Stado Desktop has both the plan and the
  upgrade.
- **`release local install --announced-identity REQUIREMENT`:** an install over the host
  channel that changes the installed program's code identity was refused for want of a terminal
  even when the caller had told the person at the Mac what macOS would ask; it now installs when
  the candidate's designated requirement is exactly the one the caller announced, and refuses any
  other change as before.
- **`release local restore --kept-previous SHA256`** puts `~/.stado/bin/stado.previous`, the
  program the last install replaced, back byte for byte when it has that digest, and recycles
  the units running the image it replaces: the rollback for a host whose previous Stado no
  delivery retained as an archive.
- **`stado product install|update` of a Cargo surface compiles the revision it was given:** an
  installation keeps one Cargo target per platform for every revision of a checkout, and Cargo
  names a workspace crate by its path inside the workspace, so every revision's crates share their
  names there and a crate is fresh when none of its sources is newer than its last compile. A
  revision committed before another revision's later compile kept that compile's build: the install
  of stado 460c2a55 failed clippy with `no field max_changed_lines on type SubmitPolicy` against a
  stado-product built from b4433964d. Every file of the revision's cached source is now dated at the
  last minute of 9999, as `stado host cargo` dates its delivered tree, so the revision's own crates
  are compiled again under Cargo's lock; dependencies from registries stay compiled.
- **A reviewed candidate no longer holds the head of the submit queue:** a harsh review before
  landing whose reviewer staged repairs, rewrote only the message, or ended with no round covering
  what it left kept the candidate queued at the head, so every `stado change run` ran the same
  review again first (an hour for a 50-commit chain) and no candidate behind it moved. Such a
  candidate is now `repaired`: its record names the reviewer's commit and tree (`repairs`), and
  that commit (the reviewed one when nothing was staged) is queued at the tail as its follow-up,
  carrying the same defects; a message-only repair is the reviewer's message over the reviewed
  tree, whose gates the action cache answers. A follow-up whose own review ends that way is
  refused, naming the commit for its author. `stado change list --state repaired` lists them.
- **The harsh review judges a candidate as written by the session that submitted it:** Tama took
  the author of a tree no harsh-review queue entry names to be the session invoking the review,
  which was the session running the pass, so a candidate the queue reviewed for another session
  was judged as that runner's own. Before the review the candidate is entered in Oko's harsh-review
  queue (`oko review harsh enqueue`) as staged by its submitting session (the operator when none
  did). Oko keeps one open entry per author, so when the author's earlier entry still waits for
  its round the review runs anyway and its record begins with why the author was not entered.
- **A high-risk change that names no defect is refused at submit:** `stado change submit` took
  `--defect` as optional, and `stado change run` refused such a candidate as `names no defect`
  only after all its gates had run. A candidate the risk rules already call high over its own
  commits and declared gates (a critical product, a review path, more lines than
  `low_risk_max_changed_lines`, no compiling gate) and that names no defect is now refused at
  submit: `<commit> is high risk (<reasons>), so it is reviewed before it lands, and that review is
  scoped to the defect it repairs; submit it with --defect ID`.
- **A declared gate the submit queue runs on a fleet host finds Stado:** `stado change run` ran a
  gate whose argv calls Stado (Trends' `stado release gate app check …`) in host cargo's prelude,
  whose `PATH` holds no `~/.stado/bin`, so it exited 127 `stado: command not found` on every host
  and refused the candidate for the host's environment. A declared gate now runs with the host's
  installed Stado as `STADO_BIN` and its directory first on `PATH`, as a release worker's job runs
  the worker's own Stado.
  A declared gate also reads the history records a release build's archive carries beside the
  commit's files (`.wisent-provenance/baseline.json` and the published diff), so an application's
  version gate no longer refuses every candidate with `the source archive carries no verified
  baseline provenance`.
- **`stado host cargo` compiles the revision it was given:** the delivered export carries its
  commit's time on every file and the host's Cargo target is shared by every run, so a revision
  committed before that target's last compile kept the earlier revision's build of each workspace
  crate, and a check, clippy or test of it judged code it was never given. Every delivered file now
  takes the latest time `touch -t` states, so no compile — not even one of another revision that
  held the target's lock while this run waited — is newer than its sources; dependencies from
  registries stay compiled.
  A Cargo run that exits 0 without Cargo naming the manifest's own package as compiled or checked
  is refused instead of passed: `<host>: cargo <operation> of <commit> exited 0 without compiling
  or checking <package>, so its verdict is another run's output; run it again`.
- **A product operation turned away for the disk janitor's turn says retrying helps:** without
  `--wait`, `stado product install` (and every building product operation) found the janitor
  asking running work for its turn and refused as a rule, `retrying will not help`, exit 1, though
  the turn ends once the pass has run. It is now a retryable wait: exit 69, `retry later`, and the
  sentence says to run it again once that pass has run or with `--wait`.
- **A published release installs itself on the hosts that run its product:** a delivery whose
  target selects a product went only to the hosts someone listed with `stado release destinations
  set`, so a product nobody listed (Skarbiec among them) was published and reached no host. With no
  declaration, its destinations are now every registry target whose `managed_versions` names the
  product; a declaration still places a product on a host that does not run it yet, and
  `destinations show` reports `running` or `declared`. A product no host runs and no declaration
  places is refused naming both ways.
- **An object body that stops arriving after its headers is named, not waited on forever, and the
  store reads a range alone:** the object route's GET read its body outside the wait mechanism,
  so a 1.6 GB input whose headers came and whose bytes did not held a check for over half an hour
  at no CPU. Every body of the object route (object, release and metadata answers) is now read as
  a wait, said on stderr with the byte it starts from, and ends as stalled when no byte arrives
  for the refresh interval of this host's resolver, the interval the route's sends are already
  abandoned at: `<operation> of <uri>: no byte arrived for <n>s, the refresh interval <who
  declares it>, after <bytes> bytes of this body`. An object is read one chunk-sized range at a
  time from its first request, and a range that stops after some of its bytes arrived is asked
  again from the first byte it lacks; a range that brings no byte ends the read with its cause.
  The store reads each range of a stored object alone instead of the whole object per range.
- **`placement evacuate --drop-release-targets` names why a release-controlled route stays:** a
  product whose only target is the host being emptied was refused with `stado release policy
  remove` alone, although its route stayed only because `--profile-fixed-routes` could not draft
  its profile (a unit with no file, no probe), which the run kept to itself. The refusal now adds
  `or move its route: it stays on <host> because --profile-fixed-routes could not draft its
  profile: <the draft's cause>`.

- **A role move with `--with-authority` and `placement evacuate --authority` reach the
  destination's own object API at its real port:** the address was the catalog's host process
  `--bind` and `--port` taken as written, and the catalog names the port only as
  `$STADO_LISTEN_PORT`, so the check asked `http://<loopback>:$STADO_LISTEN_PORT`, was refused as
  an invalid URL, and refused every authority move. The address is now the catalog's line
  resolved for the destination: a `$STADO_LISTEN_PORT` port is the one the service directory
  records for it, refused by name when it records none, and a literal port is used as written;
  a `--port` that is no port is refused. That address becomes the route's endpoint after the
  move.

- **`stado workload start omp-session --context` publishes its instructions where the queue may
  write:** the context went under `workload-sessions/`, a prefix no object API grants, so every
  start with `--context` was refused `object_grant_does_not_cover_key`. It now goes under the
  queue's own `runs/workload-session/<run>/`, beside the inputs release runs and builds stage.
- **An installation that names no source coordinate builds the product's published revision, never its checkout's head, and never an older one than is installed:** a product installed as another's dependency (or by `stado product install|update|sync` without `--source-commit`) was built from `git rev-parse HEAD` of its canonical checkout. A checkout other sessions were working in stood on a head published history had long passed, so every install of Oko rebuilt its dependency Tama from that stale head over a newer Tama, undoing a fix each time. The unpinned revision is now the product's `origin/main`, fetched with `GIT_TERMINAL_PROMPT=0`, else the revision the delivery routine last qualified green (`~/.stado/ci-main.json`); when that is an ancestor of the installed source revision, the installed revision is built again instead. Standard error says `<product>/<surface>: no source coordinate was named, so it builds <revision>: <why>`, and `--plan` names the same revision. With neither a fetchable origin nor a qualified revision the installation refuses naming both causes and `--source-commit`.
- **`stado space reclaim` keeps the version a rollback returns to:** `delivered_trees` and the
  release trees of `delivery_leftovers` kept only what `current` names and the newest delivery,
  so a product whose `current` was its newest kept one version and an install that had to go back
  had nothing to go back to. Each version directory now also keeps the newest delivery after those.
- **`stado space reclaim` keeps every tree the host's registry service declarations name:** a
  stage kept a tree only while a process or a unit file named it, so a delivery tree the registry
  still declared as a service's program (`targets[].services[].program`), with no unit file
  naming it, was taken and the declaration was left naming nothing. Every stage now keeps a tree
  that holds, or is held by, a declared `program`, unit `path` or absolute argument, and reports it
  as `a registry service declaration names <path>; retained`; a `services` field that is not a
  list refuses the reclamation.
- **No check formats or lints a tree:** `stado quality check --pre-push`, `stado release changes
  submit` and the delivery queue's gate step check the committed source alone (lock resolution,
  module declarations and reach) and run no gate; a push to `main` no longer runs `lint` gates on
  fleet hosts and asks Oko no admission, and `--host` on `--pre-push` is gone with it. The full
  `stado quality check`, release submission and `stado change run` run only `test` gates; a
  `format` gate runs only under `stado quality format`, which writes. Whether code compiles is
  learned from reading it and from the tests that compile it. A refused web gate is named as a
  web gate whatever its kind, and the source-only delivery check that ran beside the format
  gates is gone with them.
- **`stado product install` and `update` build without formatting, linting or checking first:** a
  source install ran every quality gate its platform declares (`cargo fmt --check`, `cargo clippy`,
  `stado errors check`) before the build step, recompiling a revision the push had already checked
  and holding the install for many minutes, and a recorded gate failure refused the revision before
  it was exported. An install now exports the committed revision, builds and places it; whether the
  code compiles is learned from its tests and from reading it, and a revision that does not build
  fails the build step naming its evidence. The `install-failures` records are no longer written
  or read, and the next install of a checkout removes the ones an earlier Stado kept in its build
  area. Stado's own manifest declares no `format` or `lint` gate any more (`fmt`, `clippy`,
  `error-standard`), so no push, queue pass or release of Stado runs them either; its test gate
  stays.
- **`stado release submit`'s CLI audit no longer runs a declared launcher:** the member a release
  manifest's `runtime.launcher` names (`bin/start`) is started by release control with the binary,
  port and runtime directory it assigns, so the audit no longer reads its `--help`. Run bare,
  Skarbiec's launcher exited 1 on `SKARBIEC_BIN` and refused the release.
- **`stado release submit` carries a published diff that is not UTF-8:** a committed binary file git
  reads as text (Skarbiec's compressed inflate test vectors) put bytes that are not UTF-8 into the
  diff the source archive records for its gates, and the submission was refused with `answered
  non-UTF-8`. The record now carries exactly the bytes `git diff` gave, as `diff` when they are
  UTF-8 and as `diff_base64` when they are not, and its `sha256` is the digest of those bytes, so
  it can be checked against `git diff` itself.
- **A placement move carries every state as a file, and copies it before the fence:** a file state
  travelled as base64 inside the read script's output and the write script's heredoc, held whole
  in the move's memory with the source fenced for the whole copy, so a state of a few gigabytes
  held its service down for hours and then failed with `bash: xrealloc: cannot allocate`.
  Every state, file or directory, now goes through `rsync -a` into a staging copy on the machine
  running the move and on to a stage beside its path on the destination, renamed over it after the
  previous file or tree is renamed to the backup. The preflight and a first copy of each state
  (`copy <state> while it serves`) run before the move claims its transaction, since an open
  transaction refuses the profile's services to every consumer; the claim is then laid on the
  registry as it stands and refused when the profile moved meanwhile. After the fence each state
  is read again by content (`read what changed in <state>`), so the services are refused for what
  changed in between; a role move copies its store the same way before it arms the store fence.
  The staged copies are removed once installed, when the move rolls back and when it fails before
  its claim, and the local staging room counts every state.
- **A Stado built from an exported tree no longer claims the enclosing checkout's revision:** the
  build asked `git rev-parse`, which walks up to any enclosing work tree, so a tree exported inside
  another checkout reported that checkout's HEAD with `-dirty`. Git is now asked only when the
  package's parent is the root of its own work tree; otherwise the build embeds the revision
  `STADO_SOURCE_REVISION` states, or `unknown`.
- **A move of the fleet vault can commit:** the move stopped the vault's unit as its fence, and
  the registry authority asks that vault for its store bearer's version on every write, so a move
  of the vault off the authority's host copied every state and then failed at `commit the
  placement` and rolled back. The profile carrying `skarbiec` now holds the vault's writes with
  `skarbiec fence arm --transaction <T>` (step `hold the vault's writes`), so every read keeps
  answering through the commit. After the commit the source host's resolver is asked to follow
  and the source's units are retired, then the retired copy's fence is lifted so a later move back
  finds no fence standing; each of those that fails is listed under
  `unretired_source` and does not roll back a committed move. A move that fails before the commit
  lifts the fence instead of restarting units that never stopped. The preflight refuses a source
  whose Skarbiec has no write fence, a source whose `skarbiec` unit does not run that Skarbiec or
  whose own `registry doctor` reports the unit's process as not executing its installed file (an
  old process ignores the fence on its writes), and a source whose own Stado reads the vault at
  the unit the move retires, naming the configuration that sends it through its resolver adapter
  instead.
