## 0.23.68

### Fixed

- **A route taken from a silent host answers at once, not after the dead connection ends:**
  every reader of the object API refused with "this host's resolver holds 1 connection(s) on
  that adapter unanswered longer than the 300s refresh interval" after `stado-object-api` was
  taken on another host, because the connection still hanging on the switched-off host was
  counted against the route that had moved away from it. A held wait now counts only while the
  service's route, in this host's registry copy, still names the host it waits on; the
  resolver opens the next connection to the new active host, and the old one says nothing
  about it. The port the taking host serves on is also read from the registry the command
  acts on, not through the silent store, so `role take` no longer stands on the host it takes
  from.
- **A second copy of a service is found by what it runs, not by what it is called:** a host
  carried a second `stado serve` under `com.wisent.always-on.stado-object-api` beside
  `com.wisent.stado`, and the label checks never saw it, because they matched names the fleet
  had retired (`com.wisent.compute.`) and each new spelling slipped past them. The fleet-shape
  sweep (`stado doctor`, and the coordinator's tick) now groups every loaded unit this fleet
  wrote by the program it declares — the binary without its directory, and its first
  subcommand — and reports `one-unit-per-service` for each program more than one unit runs,
  naming every label and the one the registry declares, with `stado service bootout` for the
  others. Units started on a schedule are jobs, not copies, and are not compared. It measures
  how many units it compared, so a quiet sweep says what it looked at.
- **A host whose store a placement move fences keeps serving:** the worker took the fence's
  refusal of a write (`local storage writes are fenced by …`) for an error of its own, so the
  agent loop ended and the host's one Stado process exited with it at every start, taking its
  object API, resolver and forwards down for as long as the move's fenced copy lasted. A fenced
  store now ends the worker's tick as a store that does not answer: the tick says so with the
  fence's own sentence, which names its transaction and how to lift it, the next poll runs again,
  and the process goes on serving reads and its other roles.

- **Choosing a host's path no longer starts the Tailscale client:** Stado judged every declared
  SSH path, its own network's `<host>.stado.internal` and LAN names included, by asking this
  machine's `tailscale status --json` whether the tailnet carried traffic to it. A Tailscale client
  that never answered therefore held every host command and the resolver's authority read on a
  fleet that does not route through Tailscale at all. A path is now judged by the tailnet only
  when its host is a MagicDNS name or an address Tailscale assigns (100.64.0.0/10,
  fd7a:115c:a1e0::/48), read from the destination's own text; every other path is tried as
  declared and the client is never started for it. A storage URL whose address is outside those
  ranges is likewise refused as plain HTTP without asking the client whether the address is a
  tailnet node.
- **A host its own network reaches never waits for Tailscale:** a host declaring its own-network
  primary, a LAN name and a Tailscale address as a last alternate still asked the client to judge
  that alternate. While a host declares any path that does not go through a tailnet, all its
  paths are now tried as declared and the client is not asked; only a host reached through the
  tailnet alone has its expired-key paths left out.
- **A public edge on a host the registry does not hold is refused up front:** `stado web route`,
  `stado web edge hostnames` and `stado web origin declare --publication web-edge` failed only
  while delivering, naming a missing target and not the edge declaration that named it. They now
  refuse before planning: `the public edge is declared on <target>, which the canonical registry
  does not hold, so no hostname can be published through it`, followed by the `stado web edge
  provision` and `stado web edge declare` commands that fix it.
- **A product the update policy marks `tested` installs only a revision its gates passed on:** an installation built whatever revision it chose, so a commit no test had run on reached a host as soon as it was pushed. `stado product policy set PRODUCT --mode automatic --tested` (Desktop: Set a product's update rule → Install only a revision the main check recorded green) makes every installation of that product, by `sync` or by hand, refuse before building a revision the main check record (`stado ci run`) never checked or recorded red, naming the last green revision and the `--source-commit` that installs it, or, when no revision ever passed, that none installs until one does; a red run that records no refusals is named with the run itself. Journey: `tests/product/update_policy.mjs`.
- **A push, submit or queue pass names its agent session to Oko without Tama:** `oko admit` was told the session from `tama sessions self` alone, so with Tama uninstalled no session was named, a consent the operator held to one session (and its subagents) never reached its pushes, and his older withdrawal refused every gate. With no Tama installed, the session is now the one `PI_SESSION_FILE` names, read from that transcript's session record; a run no harness names is still asked as no one's, and a variable naming a file that is gone or holds no session is said with what to do. Journey: `tests/change/session_without_tama.rs`.
- **The host janitor no longer deletes the queue's run records:** under the disk-full rule its object-evidence pass removed every regular file directly under `ecosystem/probierz/runs`, which is where the queue keeps each run's manifest (`runs/<run_id>.json`). On a full fleet store every `stado submit`, `stado workload start` and `stado quality check --place` then ended `run manifest … disappeared` seconds after writing it, and finished runs lost the record their reaper retains outcomes into. Files directly under that root, and the `quality`, `workload-session` and `release-pipeline-unfinished` directories, are kept; product evidence in directories beneath it is still reclaimed. Journey: `tests/space_reclaim/evidence/results.rs`.
- **`stado host cargo` measures the volume the compile writes to:** its disk gate read the host's home volume, so a host whose root volume is past the disk-full threshold refused every build although its declared work root, where the build cache lives, had terabytes free, and a full work-root volume was never measured. The gate now runs `df -P` on the build cache (its nearest existing directory) and refuses naming that volume's mount and usage; the receipt's `free_bytes_before`/`free_bytes_after` read that same volume.
- **Delivery to a host whose account is root keeps the delivered tree its own:** `rsync -a` kept the sending account's owner and group, which rsync applies when it runs as root on the receiving host, and the commit step then refused the staging path as `transferred staging path is not owned by the approved account`. Every `stado host run deliver` and `stado host cargo` to such a host (the Linux builder) was refused. The transfer now passes `--no-owner --no-group`.
- **The command-tree review no longer decides gates it does not own:** when `stado quality check` obtains no model judgment of a CLI's command tree (Brama or Oko's call does not answer), the review is reported as not run with its cause — `stado quality check: the <product> CLI command-tree review of <revision> was not run: <cause>; the gates above decided this check` — and the check passes or fails on its gates alone. The attestation fallback it replaced is gone. Journey: `tests/quality/command_tree/unjudged.rs`.
- **A quality check no longer compiles every dependency again:** each gate and the candidate build of `stado quality check` run with `CARGO_BUILD_BUILD_DIR` set to one `cargo-build` directory in the checkout's build area under `~/.stado/products/builds`. Cargo named the build directory from the export's path, which changes with every run, so every check rebuilt from nothing. Finished artifacts stay in the export's `target`, where `stage` reads them.
- **Azure sponsorship credit is read when Azure reports no balance:** the credits balance call answers 204 for a sponsorship grant. The billing section's `available_balance` is now the grant less the subscription's actual cost since the grant began, read from Cost Management. `balance_source` names the grant, the cost, the period and its scope, or why it could not be read. The credit gate decides a VM create or start on that balance.
- **A fleet host reaches another by its `.local` name without multicast DNS:** A registry SSH path that names a host by its multicast DNS name (`<name>.local`) now connects from a host whose resolver does not speak multicast DNS: Stado asks the link itself (RFC 6762) when the system resolver answers nothing, and a name neither answers is refused naming both answers. A Linux host without nss-mdns could reach no fleet store through such a path, so its beacon and capacity publications were refused while the tailnet path was down.
- **`stado release newest --plan` ignores non-directory entries:** regular files and symlinks are not checkout directories; an entry whose type cannot be read still refuses with its path and filesystem cause. Journey: `tests/release/newest/push-order.mjs`.

### Added

- **Fleet-owned gVisor sandboxes:** `stado sandbox fleet` inspects registered Linux hosts, creates digest-pinned environments with enforced CPU, RAM and process limits, reads actual state, updates limits, executes foreground and detached commands with retained output, stops and resumes workspaces, and verifies container and volume deletion. Docker must provide `runsc` and cgroup v2; no ordinary-container fallback or server purchase occurs. Stado Desktop exposes the same operations under Compute providers → Fleet sandboxes. The real remote lifecycle journey is `tests/sandbox/fleet.mjs`; compilation and prerequisite inspection are not lifecycle qualification.

- **A declared database states how old its last backup may be, and `stado registry doctor` names one whose copy could not be restored today:** a database whose host stops answering is restored only from a backup this machine kept, and nothing said whether one was kept or how old it was, so the gap was found on the day the host was gone. `database_api.databases.<name>.backup_every_hours` (a whole number of hours above zero; anything else is refused when the configuration is read) is the period, and `registry doctor` names, per declared postgres database, `database-backup-undeclared`, `database-backup-missing`, `database-backup-stale` (with when the newest complete backup was taken) and `database-backup-unread`, each with the `stado database backup <name>` that clears it. Journey: `tests/database/backup-migrate.mjs` declares a period of one hour, reads `database-backup-missing` before the first backup and no backup finding after it.


- **`stado database backup [NAME]` and `stado database migrate NAME --to fleet --port PORT [--host HOST]` copy a declared Postgres database out of whatever provider hosts it and move it onto a fleet host:** a database on a hosted provider (a Supabase project) had no way out but the provider's own dashboard, so a provider that stops serving an organization took every row with it. `backup` reads the credential item from the owner vault from any host, reaches the server on its `session_url` with `db_password` in libpq's environment and verified against `ca_certificate`, and keeps a custom-format `pg_dump` archive of the server's own major version under `~/.stado/database-backups/<name>/<UTC time>/` (owner-only) with `manifest.json`: every readable table's exact row count, the roles and extensions in use, the schemas and tables the item's user may not read (left out and named), the archive's size and SHA-256; the archive is read back with `pg_restore --list` first. Without NAME every declared postgres database is backed up and each refusal is named (exit 1). `migrate` takes a backup, keeps the item as `<name>-database-previous`, places a fleet PostgreSQL of the source's version, restores the archive (roles first; extensions in the schemas the archive names, those the target lacks reported) and counts every table again; equal counts leave `<name>-database` on the fleet server with the declaration and consumers unchanged, while a difference, or a placement that stored the fleet coordinates and then failed, puts the source's coordinates back, keeps the fleet ones as `<name>-database-fleet-pending` for a second run and names the cause. `stado database place --version MAJOR` places a PostgreSQL of that major version from the Homebrew keg `postgresql@MAJOR`, refusing by name when the host has none. Stado Desktop's Databases screen gains **Back up all**, and **Back up** and **Move to fleet…** on each row.

- **`stado database rest place NAME --port PORT --key-valid-days DAYS [--rotate-keys]` serves the hosted provider's REST API in front of a fleet Postgres database:** a consumer built on the provider's client library calls its HTTP API, not Postgres, so a database moved to the fleet left it calling the provider. PostgREST is placed beside the database as the unit `<name>-rest`, the roles `anon`, `authenticated`, `service_role` (`NOLOGIN`) and `authenticator` (`LOGIN`, generated password) are made on it, `~/.stado/databases/<name>/postgrest.conf` is written owner-only, and `rest_url`, `jwt_secret`, `anon_key` and `service_role_key` (HS256, issuer `stado`, valid the stated days) are written onto `<name>-database` for consumers to read. A placed API is reused; `--rotate-keys` mints a new secret and restarts the unit. `stado database rest retire NAME` is the inverse, and `destroy` retires the API before the database. Stado Desktop's row menu gains **Serve REST API…** and **Retire REST API**.

- **`stado database backups [NAME]` lists the backups this machine keeps and `stado database backup --keep N` removes complete backups beyond the newest N:** a fleet database has no provider taking backups, so a scheduled `stado database backup --keep N` is its retention, and an incomplete backup is listed with why and never removed. Stado Desktop gains **Kept backups**.

- **`stado database cost --provider supabase` reads what Supabase bills, from its management API:** per project the compute and add-ons with their stated prices, the month's total (compute only while the project runs), seven days of gateway requests and the declared database its item names; per organization the plan, its compute credit and the month's usage after it; a read that fails is named on its row and exits 1. The plan fee and the credit balance are not in the API and are named as read on the billing page. `--provider fleet` and `external` are refused as having no bill. Stado Desktop gains **Read the Supabase bill**.

- **`stado billing watch` reads Supabase's notices:** mail from `supabase.com` (failed payment, pending shutdown) is read beside the Microsoft and Google notices.

- **`stado config get KEY` reads back the dotted keys `config set` writes:** `host.scan_load_ceiling`, `database.postgres_tls` and every other dotted key the documentation shows set and read were refused as `configuration resolves no value`; a key `config show` does not resolve is now read from the config file on disk, and a key the file does not hold is refused naming the file and the resolved keys.

- **`stado placement evacuate --drop-release-targets`:** each release-control product that rolls out
  to the emptied host stops being released there, through the same verified write as `stado release
  policy remove-target`. A product released only to that host is refused before anything moves,
  unless the run stands the destination by for it; the report carries `release_targets_dropped`.
- **`stado placement holds` names what keeps acting on a host after its services leave:** the
  release-control products that roll out to it (`rolled_out_by`, with the `remove-target` command for
  an emptied host) and the schedules pinned to it (`pinned_schedules`, or
  `pinned_schedules_unread` with the store's cause). Without a host, each row says whether that host
  is `emptied`.
- **An evacuation states its verified end:** `verified_emptied` in the report, and the text form
  ends with `the registry places no profile and no role of the host Stado process on A now`.
- **`stado registry doctor` names schedules pinned nowhere:** `schedule-pinned-nowhere` for a live
  schedule whose pin no registry target names (by name or `<kind>-<hostname>` identity, the rule the
  claim path uses), `ambiguous-schedule-pin` and `unreadable-schedules`. Pins written by

- **A stopped evacuation resumes when run again:** the stop names it, an authority the destination
  already holds is reported as `already_authority` instead of refusing the rerun, and an emptied host
  is accepted when schedules or release targets are still to hand over. `placement history` keeps the
  run's whole report with its reason and prints plain lines. The schedule hand-over reads the store
  back and names any schedule still pinned to the emptied host; a release target dropped meanwhile is
  passed over.
- **The Desktop operation check covers options:** `Stado --operation-paths` prints each operation's
  field options, and `tests/desktop_api` names every option the command's help does not take.
- `stado product signing report` without a product reads every installation recorded on the
  machine, each row naming its product and surface, and exits 1 when any native file is not
  stably signed (ad-hoc, unsigned), so one read names every installed program that asks the
  privacy questions again on each build.
- `stado waits measured [--over SECONDS] [--json]` lists every operation that completed a wait on
  the machine with its longest completed wait, longest first: the one place to see which builds,
  child processes and requests take long, and whether a repair made one shorter.
- `stado network up|status|down|serve|connect`: Stado runs its own host network and makes it
  every host's preferred path. Each host keeps a node (its own launchd job or systemd user unit)
  that speaks the Noise IK handshake (`snow`, the construction WireGuard uses) and admits only
  keys the registry declares for a fleet host; `targets[].network` carries the public key, the
  measured endpoints and an optional relay declaration. A host's address is
  `<host>.stado.internal`: Stado's SSH client dials it through the node, OpenSSH through
  `ProxyCommand=stado network connect %h %p`. `up` makes it the `primary` path only after the
  host's own SSH server answered through the node, and files the previous primary under `lan`,
  `tailscale` or `direct`. Hosts no peer can dial attach to a relay, which carries the end-to-end
  session as ciphertext. Tailscale is an optional alternate path, never required.

- **`stado host processes TARGET [--json]` names what each process on a host spent:** a saturated
  host could only be read with `top` or `ps`, which an agent session, a sandbox or the host-exec
  allowlist can be refused, and `ps` counts CPU in whole seconds. The host's own Stado now reads

  and written to storage from the kernel, and reports each against the reading it kept before,
  with the interval measured; the first run says it has nothing to compare with yet. Every beacon

- **A host routine runs under its job identity and keeps its output:** the host store's runner

- **`stado host exec TARGET -- log show --last 1h --style compact --info --no-pager --process tccd`

  the process that asked for Documents, local network or Full Disk Access, so a prompt Stado raised

- **A Mac takes work on battery as on mains, and stays awake while it runs work:** the agent
  publishes `power_source` and `battery_percent` and holds `caffeinate -i -s` while it runs work,
  releasing it when idle; no power setting is changed. The power source refuses no work: a host on
  battery accepts it, so an unplugged laptop still builds and installs. `stado host gates` adds a
  `presence` section and line: whether the host answered, when it last published, and its power.
- **The janitor takes what nothing uses on every pass, not first at the disk-full rule:** below
  the rule a pass returned `healthy_noop` without running a cleaner, so a finished job's outputs
  and work tree, ended sessions' registered scratch, proven replica twins, release versions nothing
  names, run evidence and delivered copies piled up until the volume was full and the host refused
  all work. Every pass now runs those cleaners; only what a later build or run reuses (model blobs,
  the compiler cache, build caches, package downloads, harness logs, local snapshots) and the
  service logs wait for the rule or for the room the next build takes. A pass that begins and ends
  under the rule still reports `healthy_noop`; one that brings the volume under it reports
  `reclaimed_below_threshold`. A host entry the pass cannot resolve is now said in the report.

  its own store gave it, refused the registered one, and published no beacon.

- **`stado host cargo TARGET build|check|clippy|test --manifest-path PATH --revision REV [--bin NAME]… [--json] [-- ARGS]`**
  runs one Cargo operation on a committed revision on a fleet host in one command. The revision is
  exported from its canonical checkout, delivered into a fresh managed run on the host and run
  there `--locked` with the revision's own `rust-toolchain.toml`, the declared compiler cache and
  the host's shared Cargo target in its build cache (below the registry's `work_root` when the
  host declares one). `build` is `--release` and brings each `--bin` back to
  `<manifest directory>/target/host-cargo/<commit>/`. The run is removed whatever Cargo answered,
  and the exit status is Cargo's. The build is given `WISENT_SOURCE_COMMIT` and
  `WISENT_SOURCE_SHA256`, as a release worker gives them, so a build script that stamps its
  revision does so without a Git directory. The receipt holds the commit, the archive digest,
  Cargo's streams, the binaries with their SHA-256, and the free space the run took.
- **Workload kind `omp-session`:** `stado workload start omp-session --workspace REPO --task TEXT
  --max-time DURATION [--target HOST] [--model M] [--allow-write] [--allow-command]` places one OMP
  coding-agent session on the fleet host with the most room, as a detached queue job. The host
  works in its own checkout of REPO at `~/Documents/CodingProjects/Wisent/REPO`. That checkout is
  cloned from this machine's origin when absent and fetched when present. The session pushes with
  the fleet's GitHub credential, which the host's agent hands over as a job secret and git reads
  through an environment-declared credential helper. It writes result lines into
  `$STADO_SESSION_RESULTS/<name>.jsonl` below the job's output. `stado job watch` follows it and
  `stado cancel` stops it. `--max-steps` stays `jeden-session`'s bound. The harness's model
  requests go to the gateway the declaration names (`harness.gateway`): the host's own Stado
  resolves its loopback route for the declared consumer, and each declared provider is routed
  there with the gateway bearer the job is handed in `harness.secrets`. The harness's agent
  directory lives in the job's work tree, so nothing is written into the host account's own
  harness configuration and no provider credential reaches the host. `--context FILE`, which can
  be repeated, gives the session its starting instructions. The files are read here in order,
  published to the job store as the harness's own `AGENTS.md`, and declared as the job's input,
  so the host's agent writes them into the session's agent directory before it starts.
- **`stado workload harness status|install KIND --target HOST`:** the harness a session kind
  declares (`harness` in `data/work/workloads.json`). `install` carries this machine's copy to the
  host's managed path through a managed run, checks it there with its own `--version`, and
  replaces the old copy with one rename on the host's volume. A host whose declared
  `release_platform` is not this machine's is refused before anything is copied: `<HOST> declares
  release platform "<P>" and this machine's <program> is built for <Q>; install the harness from
  a <P> machine of the fleet`.
- **`stado workload results JOB --into DIR`:** reads the result lines a detached session wrote on
  its host. It appends to `DIR/<name>.jsonl` every line that file does not already hold, so
  repeated runs while the session works add only what is new.
- **`stado quality hooks install|status|remove --product P|--all [--json]`:** the pre-push gate
  of a product's checkouts on this machine. Every repository the catalog names for the product
  (owner, surfaces, installations) has its canonical checkout found, and `install` writes Stado's
  Git `pre-push` hook there, which hands every push to `stado quality check --pre-push
  --if-declared` through the installed Stado. Running it again changes nothing; a hook another
  Stado wrote is repaired; a hook that is not Stado's (a Git LFS upload) is kept as
  `pre-push.chained` and runs after the gate with the same ref updates. A checkout whose
  `core.hooksPath` sends Git to another directory is left and named, since that directory's
  `pre-push` decides what a push runs. `status` reads each checkout's state (`installed`,
  `outdated`, `absent`, `foreign`, `governed`, `no-checkout`, or `unreadable`, which exits
  non-zero) and `remove` takes the hook out and puts back the chained one. Stado Desktop's
  Releases operations run all three.
