# Changelog 0.22.17 – 0.22.18

Released entries, moved out of `CHANGELOG.md` so that file stays editable.
The current entries live there; this file is history and does not grow.

## 0.22.18

- **`stado dns` works from a host that reads the fleet vault from its owner** (7db47e80): the registrar credential's read grant is made on the vault owner over the host channel, through the same `settle_consumer_reads` `stado fleet key generate` now uses, instead of in a retired local vault copy. Grant progress goes to stderr.

## 0.22.18

- **A stale unit-image revisit block no longer stops the registry** (000d82b6): the `release_unit_image_revisit` block is judged by its own readers (the release agent's revisit pass and the stale-unit-image annotations report a refusal on their own line) and by a write that changes it, not on every registry read. The `com.wisent.<product>` rename would otherwise have made every command refuse the live registry, which still authorised `com.wisent.compute.service.probierz`.

## 0.22.18

- **`stado fleet key generate` on a host that reads the fleet vault** (7db47e80): the key pair is stored in the vault owner's vault over the host channel, the `stado` consumer is granted both fields there, and the public key is read back through the broker. It used to refuse on the host's own retired vault copies.

## 0.22.18

- **The web edge is a role of `com.wisent.stado`** (1e14440a): `stado serve --edge-caddy <program> --edge-caddyfile <path>` runs Caddy with `--watch` inside the host's one Stado process instead of a separate edge unit. `stado web edge hostnames` and `stado web route` prove the live process carries `--edge-caddyfile` before delivering, and no longer restart anything after a delivery.

## 0.22.18

- **Web units are named `com.wisent.<product>`** (263eaf97): `stado web deploy` installs a web product as `com.wisent.<product>` instead of `com.wisent.web.<product>`, and retires the old unit first because both bind the same port; if it cannot be retired nothing is installed.

## 0.22.18

- **One service per repository, named `com.wisent.<product>`** (263eaf97): the catalog refuses a `service.unit` other than `com.wisent.<product id>`. Brama, Weles, Skarbiec, Probierz, Skrzynka, Oko and Transcript Lake move from `com.wisent.always-on.*`, `com.wisent.weles-admission` and `com.wisent.compute.service.*` to `com.wisent.brama`, `com.wisent.weles`, `com.wisent.skarbiec`, `com.wisent.probierz`, `com.wisent.skrzynka`, `com.wisent.oko` and `com.wisent.transcript-lake`; each old label is in `retired_units`. `stado service ensure` now retires a product's `retired_units` before starting its unit, so the renamed unit can bind the port the old label held, and refuses to start it when one of them cannot be retired.

## 0.22.18

## 0.22.18

- **A refused channel no longer queues every adapter connection behind new SSH handshakes (d73f4df5):** while the remote object API refused channels, every refusal dropped the healthy SSH session, so the next connection opened a new session, and every open ran under the one lock all services and consumers share; connections queued behind each other's handshakes for 2 to 11 minutes and every agent hook that reached Brama through Stado hung with them. A session is now opened outside the shared lock and dropped only when it is closed; a channel the service refuses is reported to the caller at once and the session stays.

- **The resolver adapter says which channel opens are still waiting (d73f4df5):** on 2026-09-30 connections through the local object-API adapter waited 2 to 11 minutes while its log showed only the opens that failed at once. Every channel open to a remote host now logs when it is sent, how many opens are waiting for an answer, and when it is answered (open or refused) with its elapsed milliseconds, so a connection held without end names the host and the time it has waited.

- **`stado host ping` answers while the object store is down (ffd7f928):** the command opened the beacon store before anything else and exited `infra_down` when it could not, so during an object-API outage nobody could ask whether a host answered ssh. The store's failure is now the beacon half's answer (`unreadable: the beacon store did not open: …`), and the ssh half is still probed and reported.

- **`service directory connect` reads the registry once (a29cca4c):** the verb read the registry for the directory, then twice more to learn which host it runs on and where the service is placed. On 2026-09-29, with the object API refusing, each read spent its retries before falling back to the last-good copy, so one connect outlasted the 30-second limit of every agent hook that asks for Brama's address and every hooked tool call of every session was refused. All three answers now come from the one document it read.

## 0.22.17

- **A LAN connection path names the host, not its leased address (5850951d):** charless-mac-mini's `lan` fallback named `10.0.0.253` after the router had moved the host to another address, so the fallback answered "Host is down" for a host that was up. The registry now refuses an `ssh_fallbacks` destination that is a private-network or link-local IPv4 address, naming the address and asking for the host's network name, and accepts a path that dials the host by one of its own declared `hostnames` (its `.local` name), which `registry host path set` refused before as a duplicate identity. Two paths naming one identity are still refused.

- **A second session's handoff of already-submitted work is accepted, and a real disagreement names its fields (17384960):** `stado release changes submit` compared the session of a stored ticket with the new handoff and refused with the unattributed `pending change identity mismatch`, though the ticket id binds repository, product, task and commit and not the session. A ticket with the same id written by another session is now the same handoff and is returned as it stands; any other disagreement is refused as `pending change <id> at <path> disagrees with this handoff: <field> stored <value>, asked <value>`.

- **The host-health reverse forward is a role of the one Stado process (7c58a346):** `stado serve --forward-destination …` already reconciles the reverse SSH listener inside the host process, but `stado service serve-roles` did not report that role and the catalog listed no unit for it, so `com.wisent.stado-host-health-forward` (a launcher that execs `ssh -N -R` for the same forward) kept running as its own persistent process. `serve-roles` now reports `--forward-destination`, and the `stado` service declares `com.wisent.stado-host-health-forward` as a role unit on that flag: `stado service ensure` and the reconciler retire it on a host whose live `stado serve` was started with `--forward-destination`, and keep it everywhere else.

- **A corrected catalog recipe supersedes an unfinished install instead of demanding a rollback (641f08db):** the skarbiec service recipe set `object_api`, `release_api` and `service_api.skarbiec.url` through `stado host config-set`, which every host now refuses as retired, so `stado product update weles --surface service --host charless-mac-mini` stopped in skarbiec's after-install step. The catalog now sets only `secrets.skarbiec.url`; and an install left unfinished under the old recipe no longer answers `unfinished installation is bound to another recipe or host; roll it back first` (rollbacks are forbidden): its plan is superseded by a fresh preparation of the current recipe, and its backups stay in the new install's `previous` record. An unfinished install on another host is still refused.

- **A single-file build input is fetched, not replaced by a checkout (641f08db):** `stado product install|update` mounted the local canonical checkout in place of every `stado://sources/` input, including ones the build reads as one file (`extract: false`, such as Weles' `weles-client.bundle`), so `stado product update weles --surface service` failed in the build's `install` with `Inappropriate file type or format`. A checkout now stands in only for an extracted source tree; a single-file input is fetched from the object store and held to its declared SHA-256. Its `WISENT_INPUT_<KEY>_DIR` now names the file itself, as the release worker sets it, instead of the file's directory, which gave every single-file input of a product the same value. An input declared without `extract` is extracted, as the release contract and worker already read it; the installer had read it as a single file.

- **The `agent_logs` cleaner expires what the coding-agent harnesses leave (dcba1498):** no cleaner covered harness logs, and OMP had written 54 GiB of request dumps under `~/.omp/logs` that nothing reported or reclaimed. A host that declares `agent_logs` (`stado space cleaners declare <target> --cleaner agent_logs --min-age-seconds 604800`, seven days at least) has its janitor remove regular files past that age from `~/.omp/logs`, `~/.claude/debug`, `~/.codex/log`, `~/.factory/logs` and `~/.kimi-code/logs`, within the pass's item budget and only when enforcing, reported under `cleaners.agent_logs`. The roots are fixed in the product; a declaration with a `root` is refused.

- **A build that would fill the disk is refused before it starts (c756da48):** a source install, a local build, a cargo install and `stado product swift` compare the free space under their run directory with what the newest earlier run of that kind holds, and with less free refuse before writing anything: `<free> GiB are free under <parent> and the previous run there, <run>, took <size> GiB; a build now would fill the volume. Free space on this host first (`stado space reclaim <host>`), then run it again`. A full volume fails every process on the host, not only the build that filled it.

- **Every per-run directory a Stado command writes in a checkout keeps only its newest runs (10421cb1):** the three-run retention of install evidence now lives in `common::runs` and covers the other parents that grew the same way: a local build's `.build/local-install/` and `.wisent-output/local-install/`, a cargo install's `.wisent-output/cargo-install/` target directories and `stado product swift`'s `.wisent-output/native/` source copies keep three runs, recorded commands under `.wisent-output/commands/` two hundred. A run holds `<run>/.in-use` exclusively while its command works, so a long build started before newer ones is never removed under it.

- **A source install that fails leaves no build behind, and a revision that failed a quality gate is refused before it is exported again (f867d8ef):** `stado product install|update` exported the committed source and ran its `fmt` and `clippy` gates inside the export, so every refused attempt left its gigabyte of export and build output, and repeating the same revision repeated all of it to print the same refusal. A failed install now removes its run's `source/` and `inputs/`, keeping the logs and receipt. A failed quality gate is recorded under `<checkout>/.wisent-output/install-failures/` for that product, platform, revision and catalog recipe, and the next install of that revision is refused before anything is exported: `<product> <revision> already failed quality <gate> at <time>: <error>; build evidence: <path>. The same revision fails the same gate; commit a repair and install that revision`. A failed build step is not recorded, since a build can fail for a reason outside the tree.

- **A host that builds without pause still gets its disk cleanup (e4e0ce0f):** every running job holds the janitor's lock in shared mode, and a shared hold names no owner, so a pass that met one answered `lock_busy_unattributed`, "held with no holder record", `active_job_count: 0`, and on a host whose release jobs overlapped the janitor never got the lock while the disk filled. Each workload hold now writes a record beside the lock (`~/.cache/wisent-compute/disk-cleanup-holds/`) that is removed with the hold; a pass that finds workloads reports `lock_busy_workloads`, counts them and names each job, pid and age. Below the declared `low_free_gb` that pass also writes `disk-cleanup-turn.json`: for up to thirty minutes no new workload takes a hold (the claim and the admission probe answer `cleanup_in_progress`), the running jobs drain, and the next pass takes the lock and clears the request. A preview never writes or clears it. Stado Desktop's cleanup outcome shows the new state as "Waiting for running jobs". `tests/cleanup` holds the journey.

- **`stado space report` survives an interrupted build-cache walk (d52360cb):** BSD `find` abandons its whole walk on one interrupted read (`find: fts_read: Interrupted system call`), which left the verdict `scan-failed` and failed the whole report with "the command failed and we could not attribute the failure" after every other section had been printed. The build-cache walk now walks again when `find` failed before printing any tag, up to `STADO_CACHE_SCAN_ATTEMPTS` times (three when unset), and a walk that still ends `scan-failed` is printed as `<target> build cache verdict incomplete:` with the host's `find` lines, exit 0, as a timed-out verdict already was. A host that refused the read still fails the command.

- **Malformed values and unknown names a caller passes are stated refusals (5b190748):** `artifact` labels without `=` or with an empty key, an empty or spaced `host config set|unset` key and an empty registry `HOST`/`PATH` are usage errors (exit 2). A name or id the caller gave that the fleet does not hold — a registry target (`host users`, `identity apple issue`, `hosts agent`, `release rollout reconcile`, `registry host path`), an inference deployment, a schedule, a job to cancel, a release run, a build, a resource, an autonomy decision — together with removing the primary SSH path, a run of another product, a stale resource revision and a target that is not this host, keeps exit 1 and is now stated `refused` instead of reaching the operator line as an unattributed failure.

- **Argument checks built as failures are stated refusals too (5b190748):** twenty-nine checks on a flag or positional argument (`service ensure --as-launch-agent` on a non-Darwin host, `--repo`/`--ref` of `host verify-release-platform`, `--authorization-id`, `--agent`, the account identity and `--ttl-seconds` of the Apple identity commands, `--retry-token`, `--ssh`, `--priority` (also on the primary path), `HOST` and `PATH` of the registry host commands, `--from` with `--from-artifact`, the absolute-path flags of `service env set` and `service files`, `--repair` without `--variable`/`--env-file`, `--ttl-seconds`, `--item`, `--field` and `--token-file` of the grant sync, `--deadline-at`, `web origin --query`) were built with the failure constructor, so they exited 1 and read as an unattributed Stado failure. They are usage errors now: exit 2, stated `refused`, same message.

- **A command invoked wrongly is reported as a refused request, not as Stado failing (5b190748):** every `CmdError::usage` refusal (a malformed `--commit`, a missing `--subscription`, an unknown database name, a path outside its allowed form, over a hundred sites) reached the operator line as `error_code unknown`, "the command failed and we could not attribute the failure … retrying will not help", because it carried no stated code and the wording classifier found nothing to read. Usage errors now state `refused` where they are built, so the operator line names the request as the cause; the message, the exit code 2 and `--json` output are unchanged. A well-formed `--commit` that the repository does not hold (`release submit`, `release changes submit`) was reported as `git cat-file -t … failed` the same way; it is now told apart by `git cat-file -e`'s exit status and refused as `--commit … names no object in <repository>`, while git failing for any other reason is still reported as git's failure.

- **`stado release changes submit` states its refusals (35184d65):** a checkout that is not on main, a missing work id or session, a commit not on origin's main and an origin without main were reported as "the command failed and we could not attribute the failure". They are now stated refusals: the branch refusal names the checkout and the branch it has open and says to return it to main, keeping any other session's edits; the ancestry refusal names the repository and origin's head.

- **A job that stops its own agent is declared, not guessed from its command (69df09a8):** the reapers finalized a running job as completed whenever its command text contained `pkill` or `kill ` together with `wc agent`, so a job that merely mentioned killing a process was closed as a success when its agent vanished, and a maintenance job worded differently was requeued into the next agent generation. `stado submit --terminates-agent` now records `terminates_agent` on the job; the three reapers (orphan, running pass, queue expiry) read only that field, and `stado job rerun` carries it over. `stado machine submit` accepts the same boolean `terminates_agent` request field; a request without it keeps its earlier idempotency digest. The command-text check is removed.

- **GCP machine families and GPU models come from the Pricing API's product taxonomy (69df09a8):** a composite GCP price picked its core, memory and GPU SKUs by finding the family (`n1`, `g2`, `a2`) or the GPU name inside the SKU's description, and dropped custom shapes when the description said "custom instance"; `find_hourly` for every provider also matched a machine or accelerator anywhere in a quote's description. The GCP reader now reads `productTaxonomy.taxonomyCategories` from the Pricing API (`v2beta/skus`, Compute Engine) and joins it to the v1 prices by `skuId`: `GCE › … › Cores: Per Core | Memory: Per GB › <family>` sets the quote's new `family`, `GPUs › … › <model>` sets `accelerator_type` through a table of the taxonomy's model names, and a model with no Stado accelerator id is not priced. Composites and `find_hourly` compare those fields exactly. Custom shapes need no exclusion: they share their family's taxonomy and never undercut the predefined rate the cheapest-quote choice takes. A failed taxonomy read marks the GCP source blocked with the Pricing API's error.

- **GCP price quotes take the purchase option from the SKU's category (69df09a8):** a SKU was quoted as Spot when its description contained "spot" or "preemptible", and commitments, reservations and sole tenancy were dropped when the description contained those words. The Cloud Billing Catalog's `category.usageType` now decides: `OnDemand` is on-demand, `Preemptible` is Spot, and every other usage type (commitments, reservations) is not quoted; sole-tenant SKUs are dropped by `category.resourceGroup`.

- **Azure inventory and quota-reply triage read structure, not words (69df09a8):** inventory called any resource Stado's when its `managedBy` text contained `stado` or `wisent`; it now counts a resource as Stado's only when it carries Stado's own `wisent_managed` creation tag, or when its `managedBy` is exactly the ARM id of a resource the same read found tagged (the OS disk and NIC ARM creates for a Stado VM). A name beginning `stado-` or `wisent-` no longer makes a resource Stado's. Quota-reply triage kept Open tickets whose classification display name contained "quota" or "subscription limit"; it now keeps tickets whose `serviceId` names Azure Support's "Service and subscription limits (quotas)" service, from both the Azure CLI query and the REST reader.

- **`stado product supabase verify` gives the scratch database its own host ports (0f8ea17f):** the scratch copy got its own `project_id`, but kept `config.toml`'s fixed host ports (API 54321, database 54322, shadow 54320, pooler 54329, studio 54323, inbucket 54324), and every schema product declares the same ones or, like weles-web, omits them and takes the CLI's default 54322, so two verifications on one worker, or a verification beside a developer's local stack, failed `supabase db start` on a taken port. The scratch `config.toml` is now parsed as TOML: every integer `*port` value at any depth gets a free port reserved on 127.0.0.1, and `db.port` is set even when the product omits it; a config that is not valid TOML or has no string `project_id` is refused before anything starts. The product's own `config.toml` is untouched.

- **`stado product supabase verify` stops only the scratch database it named:** the cleanup ran `supabase stop --no-backup` even when renaming the scratch copy's `project_id` failed, and a `config.toml` without a `project_id` line was left on the CLI's default name, so a failed or unnamed verification could remove a developer's local database of that product. The cleanup now runs only after the scratch `project_id` is written and stops that id explicitly (`--project-id verify-<uuid>`); a `config.toml` without exactly one `project_id` line is refused before anything starts. A migration failure is reported ahead of a failure to remove the scratch copy.

- **`stado product supabase verify` runs each verification under its own local project id:** the local Supabase stack names its containers and volumes after `config.toml`'s `project_id`, so two verifications of one product on one worker, or a developer's own local stack of that product, shared one database and the first `supabase stop --no-backup` removed the other's. The unpacked scratch copy's `project_id` is now `verify-<uuid>` before `supabase db start`; a bundle without `supabase/config.toml` is refused naming the path.

- **`stado product supabase verify` is the post-build test of a supabase-source platform (0f8ea17f):** the five schema products (weles-web, wisent-trade, wisent-supabase-oko, -preferences, -wisent-app) built a `supabase-source.tar` with no test, so batch qualification left every schema change at `awaiting_tests`. The step unpacks the staged bundle as `deliver supabase` does, runs `supabase db start` on it (the CLI applies every migration in order to a scratch local database with the auth, storage and extension schemas production has) and `supabase stop --no-backup`; a migration Postgres refuses fails the test with the CLI's own report. The runner needs the Supabase CLI and Docker; without them the step refuses by saying so. All five manifests declare it as `migrations-apply`.

- **`stado product supabase verify` and `deliver supabase` take `--project-dir DIR` (35184d65):** both ran the Supabase CLI at the bundle root, so a repository that keeps `supabase/` below its root (trading-autonomy's `web/supabase`) could neither be verified nor pushed. `DIR` is resolved inside the unpacked bundle; an absolute path or one with `..` is refused. It defaults to the root, so the existing manifests are unchanged.

- **`stado product deliver supabase` reconciles the migration history before it pushes (35184d65):** it read the history from the CLI's text table, whose cells the current CLI wraps in backticks, so no version ever parsed and a split migration's parts were never carried in; it now reads `migration list --output-format json`. A bundle may also declare `supabase/baseline.json` `{"applied": [...], "retired": [...]}` for a database built before its migrations were release-managed: `applied` versions absent from the history are recorded as applied, `retired` versions present in it are recorded as reverted (a history row no local file carries makes `db push` refuse), and only then does `db push --include-all` run. The receipt's `repaired` lists both sets and the CLI's answers.

- **`stado product deliver supabase` needs no database password:** it refused without `SUPABASE_DB_PASSWORD`, so a project whose password nobody holds (trading-autonomy's) could not be delivered, although the Supabase CLI signs in to a linked project with a temporary login role it creates through the Management API from the access token alone. The password is now optional; when a delivery maps it, it is passed as before.

- **`stado release status` refuses a product it does not hold instead of failing unattributed:** `stado release status echo-web` answered `no matching release product` as "the command failed and we could not attribute the failure", so a typo, a product without a release-control entry and a product with no run among the newest ten all read as Stado's own fault. A product that release control does not hold is now refused with the configured products listed; a held product without a rollout target and without a recent run is refused naming that; `--run`/`--version` filters that match nothing are refused as well.

- **A delivery can wait for others: `after` in `.wisent-release.json`:** every delivery of a run was queued before any verdict was read, so a manifest could not make its application wait for the schema migration it reads; a failed `stado product deliver supabase` still let `stado web vercel deploy` publish code for a schema that was never applied. A delivery may now name earlier deliveries in `after`; it is queued only when each has passed in the same run, and otherwise recorded failed with `not queued: delivery <name> did not pass` and queued again on resume once that delivery passes. Deliveries without `after` are still queued together. Manifest validation refuses an `after` entry that is not an earlier delivery, so no ordering can loop.

- **The host Stado process runs as `com.wisent.stado`, and `com.wisent.always-on.stado-object-api` is handed over to it:** the one Stado process per host (object API, release API and every role folded into it) ran under a label that named only its object API, which is how a reload came to be aimed at "the object API unit" as if it were a separate process. The catalog's `stado` service is now `com.wisent.stado`, running `$HOME/.stado/bin/stado` (the tree the `stado-release` installer writes), and lists the old label (launchd and systemd) as `role_units` with `--api`, not as `retired_units`: `stado service ensure` and the autonomy reconciler retire it only where the live `com.wisent.stado` process is proven to run `--api`, never unconditionally. The old unit runs the same program on the same port and holds the only reconciler that would retire it, so the API listener of `stado serve --api` and `stado dashboard`, when the init system started them under the catalog unit (`XPC_SERVICE_NAME` on launchd, the process's cgroup on systemd), boots those units out and withdraws their autostart before binding; each outcome is logged as `[stado] predecessor UNIT: STATE (DETAIL)`, and a unit that cannot be retired is the error the process exits with. A process started any other way retires nothing. `stado host recover-object-api` installs the LaunchDaemon under the label the host's own Stado declares (`host object-api-local paths` prints it as a sixth field) and refuses with `host_stado_names_no_unit` when the host's Stado predates it; the storage-root rollback restores the unit under the label it captured; the deploy, product-release and submission workflows read the unit from `stado product catalog --output`. `stado release catalog declare-publisher --reload HOST=UNIT` now refuses any unit that is not the host Stado process, not only a retired one, because only that process serves the release API.

- **Only the host Stado process's own takeover retires the old API units, and its record keeps them from being repaired:** ensure and the reconciler used to retire `com.wisent.always-on.stado-object-api` wherever the live process's arguments carried `--api`, but a flag in an argument vector proves neither a bound listener nor the same storage root, and `stado dashboard` serves the API without that flag, so the reconciler could bring the old unit back beside a dashboard that had taken it over. Those units now declare `readiness: api-takeover`: ensure and the reconciler keep them (`kept`, naming the process that retires them), the takeover at API start writes `~/.stado/role-handoffs/<unit>` with state `taken_over` and its pid for each unit it retires (a takeover it cannot record is a failed start), and the reconciler's repair check reads that record, also while the replacement is stopped.

  The catalog validator accepts `readiness: api-takeover` for `--api` beside `resolver-state` for `--resolver` (anything else is refused naming both), so the embedded catalog that `host_process()` reads stays valid. The takeover writes its `taken_over` record before it retires a unit and rewrites it as `takeover_withdrawn` when that retirement fails, so the unit is repaired again. The reconciler asks for the record once more after it takes the unit's lease, and after every repair attempt of an API unit, failed ones included (ensure enables autostart before it judges startup), it retires the unit again when a takeover recorded itself meanwhile, so whichever of the two finishes last, the old unit ends retired. An app now names its surface sources (`--info-plist` for `bundle-id:` and `url-scheme:` and the declared version, `--products` for the executable products of a `Package.swift`, repeatable `--appended-paths` for the path literals a Swift file appends) and declares `stado release version-gate app-check` as a quality step. `app-check` runs AutoVersion's fixtures against Stado's rule, refuses a baseline whose `.wisent-provenance/baseline.json` record is missing, incomplete, recorded for another `WISENT_SOURCE_COMMIT` or marker, or whose tag is not the newest version tag `origin` served, and refuses an Info.plist version the change does not require. `app-baseline` writes `released-surface.json` from the newest version tag `origin` serves, or the working revision while there is none.

  An npm package names `--package-json` instead of (or beside) an Info.plist: its `package:` name, every `export:` key and every `bin:` command are its surface, and its `version` is the declared version when no Info.plist is named.

- **A source snapshot carries verified baseline provenance:** a product's version gate running in the release build read an archive with no git history, so it could check that `released-surface.json` named a plausible `git-archive:<tag>` but not that the tag existed or named the right commit. `stado build submit` now reads the committed `released-surface.json` and adds `.wisent-provenance/baseline.json` to the snapshot: the baseline's marker, every tag `origin` serves (so a gate can refuse a baseline a newer tag supersedes, or a `head:` baseline that ignores a published tag), and for a `git-archive:<tag>` marker the tag's commit and tree after resolving it in the checkout and requiring `origin` to serve it at the same commit. A tag this checkout cannot resolve, that `origin` does not serve, or that `origin` serves at another commit refuses the snapshot with the command to run.

  The record also carries `origin_tag_versions`: for every tag `origin` serves, the commit it serves (peeled for annotated tags) and the version that commit's tree declares, read with the product's own `version_source` from the manifest being submitted, or `null` when that tree cannot be read here or declares none. A gate can then judge a baseline and its freshness by the versions the tagged artifacts declare rather than by tag spelling, which a floating tag such as `v1` does not carry and a moved tag misstates.

- **`stado release catalog audit` refuses catalogued releases whose required platforms declare no post-build tests:** enrolment and `build submit` already named such platforms, but a product enrolled before that check, or registered through `catalog sync` alone, stayed in the catalog, built on every batch and left each of its tasks `awaiting_tests` without any report. - **`stado quality check` refuses a committed `Cargo.lock` that does not resolve its manifest:** a product could add a dependency to `Cargo.toml` and reach `main` with a lock that never named it, and the check passed because it ran only the `fmt` gate; the install's `cargo build --locked` was the first thing to refuse. - **`stado quality check [--root <checkout>]` reads the declared `fmt` gate of the tree an install would build, without writing:** like `stado product install|update`, it exports the committed revision — `origin/main` when the tracked tree is clean and behind it, `HEAD` otherwise — into `.wisent-output/quality/` and runs the gate from that tree's `.wisent-release.json` there, so another session's uncommitted edit neither fails nor rescues it. It refuses with the gate's name, the revision and the checkout when the tree is not formatted, so the verdict of a source install can be read before anyone runs `stado product update`. `stado quality format` still writes what the gate reads.
- **`stado product install|update <product> --check-arguments` checks the command line and exits without installing:** clap's pairing of `--release-version` with `--source-commit` does not appear in the usage line, so a command that omitted one was only refused when run. With `--check-arguments` the whole line is parsed — required pairs, the product in the catalog, the surface — and the command answers `{"arguments":"accepted"}` or the refusal it would give, so a command can be proven runnable before it is handed to anyone.
- **An unfinished source installation whose checkout has moved on is superseded, not resumed:** `stado product install|update <product> --surface cli` resumed the plan a receipt left `installing` had retained, so a plan that was wrong (tama's, which placed no `share/tama`) failed its `after_install` the same way on every attempt and only `stado product rollback` led on. - **`stado credentials token mint --store-item <item>` gives a product its own Brama bearer in one command:** a newly minted bearer could be printed (`--raw-token`) or kept in a file on the vault owner (`--token-file-name`), but not written into the owner-vault item a product reads it from (`<product>-model-router#token`). Piping the printed bearer into `stado credentials put` stored it as `value` in whichever local vault that machine selected, and into `credentials item put` was refused for a payload without `kind`. `--store-item` first creates the item with a fresh bearer as its `token` field (kind `token`, the canonical `skarbiec.item.v2` envelope) on the vault owner only when it does not exist yet — `skarbiec set-json --if-absent`, decided and written under one vault generation, so of two concurrent runs only one writes (a Skarbiec without the flag, before skarbiec@9dc9415, ignores it and overwrites) — and then registers the item's own value for the consumer, as `--token-item` does; the bearer is never printed. A failed, repeated or concurrent run therefore never leaves a registered bearer that no item holds: running it again registers the same stored value. `--json` reports `token_registered` with `token_source`, and `stored_item` (before/after state and revision) when the item was created. It cannot be combined with `--token-item`, `--raw-token` or `--token-file-name`. Example: `stado credentials token mint --host charless-mac-mini wisent-model-model-router-client --capabilities 'call:brama#best' --audience wisent-model --store-item wisent-model-model-router`. Stado Desktop's host bearer sheet offers the same choice as "Store bearer in owner-vault item".
