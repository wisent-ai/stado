## 0.23.68

### Added

- **An edge on a host the registry does not hold is refused where it is read:** `stado config
  validate` (from the registry the store or this host's last-known-good copy holds) and `stado web
  edge status` refuse it as route, hostnames and origin declare already did, with one sentence
  naming the host and the full provision and declare commands. Test: `tests/web/edge_target.rs`.
- **A failing board, disk or link withdraws a Vast offer:** the follow loop now also withdraws a
  host whose board reports uncorrected ECC errors, whose disk is at the disk-full rule's threshold
  (in place of a fixed free-space figure), or whose measured link is below the declared
  `host.bandwidth_floor_mbps`; the maintenance notice names `gpu`, `disk` or `network`, lasts the
  idle window, is announced again when it ends, and the recovery is logged. Readiness and the loop
  read the bandwidth from the host's published beacon, since only the publisher measures it.
- **The janitor prunes Docker's data at the disk-full rule:** the new `docker` cleaner asks the
  daemon to remove images, build cache, stopped containers and volumes nothing uses
  (`docker system prune --all --volumes --force`), keeping running containers, their images and
  mounted volumes, and nothing while a job runs or when the daemon's root is not on the volume the
  rule judges; the report carries what the daemon called reclaimable and what it reclaimed. Test:
  `tests/space_reclaim/docker_reclaim.mjs` against a real daemon.
- **The janitor removes build source snapshots nothing names:** each `build submit` and `release
  submit` publishes one `stado://sources/<product>/<sha256>/source.tar.gz`, and nothing removed
  them; the new `source_snapshots` cleaner takes, at the disk-full rule, every snapshot no release
  catalog entry, live job or unfinished release, build or quality record names, keeping each
  product's newest and every pinned dependency input, and keeping everything while a record
  cannot be read. Test: `tests/space_reclaim/source_snapshots.rs`.
- **The janitor removes old backups of installed binaries:** the backups an install leaves beside
  each binary in `~/.stado/bin` were swept only by the hand-run `delivery_leftovers` stage; the new
  `bin_backups` cleaner takes, at the disk-full rule, every backup but each binary's newest, never
  the binary, its `.previous` rollback target or its coordinate. Test:
  `tests/space_reclaim/bin_backups.rs`.
- **A credential that did not resolve states the class the vault answered with:** `stado market
  status|list|unlist --provider vast` without a key, a peer fleet's bearer and the `stado data
  export` key were always refused as `config`, so a vault that was down read as a setting to fix;
  each now carries the credential channel's own class (`infra_down`, `refused`, `not_found`,
  `config`), and readiness prints it as `skarbiec_failure`, shown on Stado Desktop's Earning screen.
- **A public origin that does not resolve names the way to the fleet's own edge:** `stado web
  origin status` for an origin whose name no public resolver knows (a Funnel `*.ts.net` name
  included) now names the declared web edge, or the command that declares one, and the exact
  `stado web declare`, `stado web route`, `web origin declare --publication web-edge` and
  `converge` commands for that origin's own name, target, upstream and paths.
- **`stado web origin converge --apply --github-variable REPOSITORY/NAME`** writes the origin that
  now serves to a GitHub Actions variable, so a workflow reading `vars.<NAME>` (the version check
  reads `vars.STADO_API_URL`) asks the serving origin and not a name written into a workflow;
  refused without `--apply`, for a malformed name or a repository outside the organization. Stado
  Desktop's Converge review takes the variables.
- **Every Vast.ai offer ends when Stado says:** `stado market list|follow --provider vast` and the
  worker's bridge (`--vast-contract-hours`) require `--contract-hours`, send it as the offer's
  `end_date`, and the follow loop moves it a whole window ahead while the host stays idle once less
  than half is left, so a renter cannot hold the host past the window the fleet spares; zero is
  refused, as are a peer fleet's and HandToHuman's listings with it. A Vast.ai follow without a key
  now refuses with the class the vault answered. Stado Desktop's Earning screen takes the hours.
  Test: `tests/market/offer_end_date.mjs`.
- **Market readiness exits with each verdict's own class, and the isolation check no longer holds a
  runtime thread:** `stado market readiness --provider vast|stado` without `--json` exits `refused`
  for a marketplace or peer that refused, with the credential channel's class for `unknown`, and
  `config` only for what the host must provision; the peer document carries `skarbiec_failure` too,
  shown on Stado Desktop's Peer fleets panel. The renter-isolation reads (`ip`, `ss`, the
  `DOCKER-USER` chain) are awaited child processes.
- **Each source valued per board-hour, and a node runs only while its source pays most:** `stado
  market sources --target HOST` prints what each source earned the host per board-hour over the
  autonomy policy's `freshness.pricing_max_age_seconds` (kept payouts over the hours its nodes ran,
  kept under `state/market/node-hours/`; Vast.ai's kept days over their hours) beside the best other
  source, or why it has no value. `stado market node follow` stops a node while another source
  with a value earns more. Desktop's Registry operation takes the host. Test
  `tests/market/source_value.mjs`.
- **`stado inference apply` refuses a sold deployment whose model declares no license:** before
  touching the host, a deployment with a priced unrevoked caller, a pay-per-call offer or a listed
  network node serving it is refused while its model license is unread or its chain declares
  none, naming each sale and what the license lacks. Test `tests/inference/sale_license.mjs`.
- **Queued work takes a Vast-listed host only when it is worth more than the offer:** the Vast
  follow loop weighs a queued job (its stated income, else the policy's
  `budgets.internal_usd_per_gpu_hour`) against the offer's `--price-gpu` before unlisting; the
  offer stays listed when worth at least as much, the decision kept for `stado market decisions`.
  A job running here, or one whose value cannot be read, still takes the host, said in the log.
- **Peer lending drains only when our queued work is worth more:** `stado market follow
  --provider stado` keeps an active session while our work is only queued and the peer pays at
  least what that work is worth per GPU-hour; the weighing is one function
  (`allocate::offer_or_queue`) shared with the Vast loop, each decision kept for `stado market
  decisions`.
- **A network node runs only while the host meets its network's connection requirements:**
  `stado market node add|edit --min-download-mbps --min-upload-mbps --requirements-source PAGE`
  keeps what the network's own page requires; `follow` starts the node only while the host's
  measured bandwidth is current and at or above it, naming the shortfall otherwise. Desktop's
  Registry node operations take the fields. Test `tests/market/node_requirements.mjs`.
- **What a product is called is decided in one place, and a former name still finds it:** `stado product name list|show|check|set|forget|adopt` (Desktop: Products → Rename a product and the five operations beside it). `set PRODUCT --id NEW --name "New" --decided-by WHO --reason WHY` records the decision as the record's `naming`, keeps the names it had in `former_names`, carries a new id into every other record's integrations and dependencies, keeps under the former id the service label, directory key, release name and documentation site hosts and releases still answer to, moves this machine's receipts, and names every repository, release manifest and site still carrying the former id with the command that moves it. A name, current or former, belongs to one product; every catalog write refuses two products sharing one. `show NAME` answers which product a name belongs to; `check NAME` exits 1 when it is taken; `product sync` moves receipts left under a former id on every pass. `registry set --name` is gone: a name changed there left no record of who decided it or what it was before. `~/NAMES.md` lists former names. Journey: `tests/product/name_decisions.mjs`.
- **A Mac nobody is at needs no click:** `stado host console show|record|unset TARGET [--json]` measures, through the host's declared connection, who owns `/dev/console` and which display panels macOS reports online (the built-in panel, or a monitor that names itself; the stand-in display of a Mac with no monitor is not one), and records `targets[].console` as `headless` or `attended`; the registry refuses a record its own evidence contradicts, and on a headless host refuses `privacy_grants` and a `work_root` in Documents, Desktop or Downloads. On a headless Mac, `service ensure` installs Stado's own units as launchd daemons run as the host's account, which macOS never asks about the local network (other units too, unless the host declares a graphical workload); the domain no longer follows the `always-on` role word. When ensure installs a daemon over a LaunchAgent of the same label it stops the agent, reads the daemon until it serves its declared port, and only then removes the agent's file, loading the agent again when the daemon does not answer; `bootstrap --local` and `network up` move their agent the same way. `stado host upgrade` measures the console, records it before the install, has the install move Stado's host unit into the system domain after `sudo -n -l` confirms root's steps, plans no dialog on a headless Mac and refuses, naming the dialog and its cause, any step that would raise one; folder dialogs come from declared grants and the work root, no longer from an old beacon, and a terminal is needed only when a dialog is planned. `registry doctor`'s `misdeclared-domain` finding names the console and the `service ensure --as-daemon` that fixes it. Stado Desktop runs all three console operations.
- **A quality check runs as placed work on the fleet:** `stado quality check --place [--target NAME]` places the check of a committed revision on the fleet host with room for it and follows it to its end. The host is chosen from each host's capacity publication: it must be live, run the work (`placed_work`), and run no CI job (`ci_jobs_running`, counted from its process table); a machine whose registry role is `interactive` comes last. The check is an exclusive queue job, so a host runs one check at a time and the rest queue. A newer revision's check of the same product cancels the older one, queued or compiling, and a check of a revision already in flight follows that job. The revision travels as a Git bundle in the fleet store and the host runs `stado quality check --bundle KEY --revision REV`. Capacity publications now state `ci_jobs_running` (with `ci_jobs_unread` when the process table cannot be read) and `placed_work`. Stado Desktop's committed-gates check carries the same two choices. Journey: `tests/quality/placed.rs` (`cargo test --test scheduler -- quality_placed::`).

  takes `--provider stado --peer NAME` beside `--provider vast`. `stado market

### Changed

- **The sandbox provider is Boat, and Stado speaks Boat Public API v1:** Box was renamed Boat, and its legacy API (`ascii.dev/api/box/v1`, `/boxes`) answers with a `Sunset` notice. The provider id is now `boat` (the `box` and `box-ascii` names are gone), its settings are `boat.ttl_seconds`, `boat.release_mode` and `boat.api_url` in the profile with the environment overrides `BOAT_TTL_SECONDS`, `BOAT_RELEASE_MODE` and `BOAT_API_URL` (the `BOX_*` variables are no longer read), and its key is the Skarbiec item tagged `stado:role:cloud-boat`, which a workload grant may not carry. Requests go to `https://boat.dev/api/v1/sandboxes` with Boat's own response types; a deletion carries the confirmation Boat requires and accepts Boat's background deletion; a sandbox Boat cancelled for want of a machine fails its job by name; an account at its active-sandbox limit is refused with both counts; and an answer that echoes the API key has it replaced by `[REDACTED]` before it becomes an error.
- **The release role of `stado serve` keeps its declared cadence and says when it cannot retire a product:** `--release-interval-seconds` now starts a pass once per period, as every other resident role does, and a pass that outlasts the period starts the next one at once and skips the missed ticks, instead of sleeping the whole period after each pass so that every slow rollout pushed the next one later. A host whose `HOME` cannot be read now prints `[release-agent] host=<host>: retiring products release control no longer targets here could not run, HOME is not readable: <reason>` each pass, where it used to skip that retirement without a word.
- **`stado service release` takes `--readiness-window-seconds` with `--readiness-url`, refused at parse when it is zero:** the window was `--readiness-timeout-seconds`, a `u64` that a release without readiness filled with zero internally and that only the host probe refused when zero. The URL and its window now travel as one value or not at all, clap refuses `0` before anything is installed, and a release-control replace whose policy declares a zero readiness window is refused as a declaration naming the product. The registry key `release_control.products.<product>.strategy.readiness_timeout_seconds` is unchanged.
- **`WC_WEB_API_PRODUCTS` is read as the web product table by every reader, and a refused override is never "nothing declared":** `stado web list`, `stado web status`, the edge's routes, the origin owner lookup and `stado web declare --path-prefix` each asked the config file whether `web_api.products` existed and, when it did not, answered as if no product was declared, so an override the config file did not repeat listed nothing, rendered no edge routes and owned no hostname, and an override that was not valid JSON was swallowed as an empty plane. The override and the file are now read in one place: no table in either lists nothing, as before; a table in either that does not parse is refused with its problems; and a reader that needs the table is told `web_api.products is not declared, in WC_WEB_API_PRODUCTS or the config file`.
- The connection vocabulary (`stado-rs/data/fleet/connections.json`) names `direct` and says that
  Tailscale, Nebula and WireGuard are outside networks the operator runs, not ones the fleet
  configures.
- Every Stado install runs the incoming binary's `config validate` (after `config migrate`) before
  it replaces the running one: `stado product install stado`, `stado release local install` with
  or without a version, and the remote activation of a host delivery. `config validate` reports a
  host whose resolver needs `ssh.keepalive_seconds` and `ssh.keepalive_count_max`, and every
  keepalive refusal names the exact `stado config set` commands.
- The host Stado process (`com.wisent.stado`) runs the resolver role on every host. The registry
  authority answers every other host's registry read from its resolver's held generation, so an
  authority without it refused every read with "the resolver that published its state … is not
  running".
- **`stado release local install` and `release local restore` refuse a program without a stable
  signing identity:** macOS keeps every privacy decision per signing identity, so an ad-hoc signed
  build placed in `~/.stado/bin` was a new program to it and asked every question again. A native
  program that is not Developer ID or Apple Development signed is refused, naming its signature
  state and `stado product install NAME --source-commit <commit on origin/main>`, and the
  installed program stays.

- **The network node keeps the code identity macOS decided Local Network for:** its unit runs its
  own copy of Stado, `~/.stado/libexec/stado-network`, which only `stado network up` places, so a
  Stado install or a background restart of the node never makes macOS ask "find devices on your
  local network" again. `network up` says before placing the copy which question macOS will ask
  and why, and run with no terminal it refuses to change the identity of a node already placed,
  naming `stado network up` at that Mac. `network down` removes the copy with the unit.
- **`targets[].privacy_grants` declares Local Network** (`"folder": "local_network"`), and
  `stado host privacy TARGET --since WINDOW` prints each such grant `granted`, `denied`, `pending`
  or `not measured` from what macOS's `nehelper` logged for the program's code identifier;
  `--json` carries the decisions under `local_network`. Stado Desktop's grant form offers Local
  Network.
- **A Stado install that changes the installed program's code identity is made at the Mac:** macOS
  keeps every privacy decision per designated requirement, so an install under another identity
  made the always-on host process ask again for each declared need (Documents, for one) with
  nobody watching. On a Mac, `release local install` and `restore` refuse, with no terminal, a
  program whose designated requirement differs from the installed one's, naming both; at a
  terminal they say first that macOS will ask again for the declared grants.
- **The beacon reads launchd's event log only over the time since it last looked at a unit:**
  each changed unit read an hour of the log, many minutes per unit on a busy Mac, so a host
  process that had just started published no beacon for half an hour. A cadenced read now covers
  the time since this process last compared the unit (its first read, the declared
  `WC_HEALTH_INTERVAL_SECONDS`); one-off inspections keep the hour.
- **`stado release catalog input pin --swiftpm` resolves the commit's own tree:** it resolved the
  source checkout's working tree and refused when that tree's `Package.swift` or
  `Package.resolved` differed from the revision, so pinning a commit of a checkout in active use
  needed a second clean clone of it. The revision's tree, with its submodules and links resolved,
  is now materialized under the checkout's `.build/release-input` and resolved there, and the
  working tree may hold anything.
- **`stado storage abort` discards the parts of an upload staged under the earlier part names:**
  before the uploader named parts as composition reads them, it padded each index only to the
  width of the part count (`000` of 514), and the object API's deletion authorizer recognised
  only the current eight-digit names, so those parts read as immutable release objects and
  nothing could remove them. Removal now reads both spellings; composition still reads only the
  current one.
- **`stado release catalog input retire <uri> --root <dir>` removes a sources input no manifest
  names:** every product checkout under the root is fetched and its `origin/main` release
  manifest read, and so is every release catalog entry; a reference, or a manifest that cannot
  be read, refuses the retirement naming it. `--dry-run` reads and retires nothing. The object
  API removes a `stado://sources/` object only for this request, under the product's publisher
  bearer; built releases stay immutable.
- **`stado space reclaim`'s `tagged_build_caches` stage prunes the privacy list too:** its `find`
  over the home opened `Library`, `Pictures` and the rest, the one home walk the list did not
  reach; it now refuses the same folders every other walk refuses.

  tagged or not, each whole once no process names it or holds a file below it on two applies and
  it did not change in between. Only the two fixed levels are listed; nothing inside is walked.

  bodies as cloud hosts (`providers::azure::public`), and its delete now follows each Azure
  operation to its end before confirming the resource is gone.
