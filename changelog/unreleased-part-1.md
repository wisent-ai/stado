# Changelog Unreleased (part 1)

Entries of the release being prepared, moved out of `CHANGELOG.md` so that file stays editable.
The version bump gathers them into the release's own file and removes this one.

## Unreleased

### Fixed

- **An authority takeover survives the old authority's next answer:** the resolver recorded the
  old authority's lower directory generation into the last-known-good copy before refusing it, so
  `placement move --authority` was undone. The copy is now recorded after the generation is judged,
  and every copy write refuses a lower generation as `directory-rollback`, naming `stado resolver
  accept --generation N`; an accepted generation is recorded as the resolver adopts it.

- **One command reads a remote registry authority once:** its snapshot is kept in the process for
  the refresh interval reads of that authority are measured by, said on stderr when it answers, and
  forgotten after a registry write, instead of one whole SSH snapshot per registry read.

- **A placement move names the step it stands on:** claim, preflight, fence, state read and write,
  routes, start, retire and commit are each a `stado::wait` naming transaction, profile and host,
  listed by `stado waits` and Stado Desktop's open waits.

- **A change hand-off records source and builds nothing:** `stado release
  changes submit` ran every gate a product installation runs (format, lint
  and test) before writing its ticket. It therefore compiled the product,
  spent build budget and was refused whenever building was not admitted,
  although its contract records a commit without compiling. It now runs the
  pre-push check on the handed-off commit (lock resolution, module
  declarations and format-kind gates). A commit those refuse is still not
  handed off, and the batch build that takes the change runs the remaining
  gates. Journey: `tests/quality/gate_kind/handoff.rs`.

- **A delivery pass that could not finish is a named stall:** `stado ci run`
  keeps why a pass stopped in its last pass's `failed`, and `stado ci delivery`
  (and Stado Desktop, which reads it) lists it under `stalled` until a pass
  finishes, instead of reading "the delivery path stands" while nothing was
  checked or installed since.

- **Host-local schedules submit into their selected store:** immutable plans,
  replay lookups, claims and queued jobs no longer reopen the configured fleet
  backend. Host routines can finish while the fleet store refuses connections;
  store-bound submissions refuse a mismatched bucket before writing anything.

- **A product build names the defect it serves:** `stado product cargo`, `install`, `update` and `swift`
  asked `oko admit build` with no purpose, so a consent the operator limited to one defect never admitted
  them. Every `stado product` operation takes a repeatable `--purpose DEFECT`, passed to Oko's admission
  and to the host a service operation runs on; Stado Desktop's Cargo and Swift operations carry the field.

- **A product outside release control is no longer called an unknown release product:** `stado release
  status|promote|rollback` and the quarantine commands refused it as `unknown release product`, which was
  read again and again as "no release of it exists" for products whose archives stood published. The
  refusal now says `release control holds no rollout policy for "<product>"; this does not say whether a
  release of it was published`, and its help names the read that lists them, `stado storage objects
  releases <product>/`, beside the products release control holds.

### Added
- **Fleet-owned gVisor sandboxes:** `stado sandbox fleet` inspects registered Linux hosts, creates digest-pinned environments with enforced CPU, RAM and process limits, reads actual state, updates limits, executes foreground and detached commands with retained output, stops and resumes workspaces, and verifies container and volume deletion. Docker must provide `runsc` and cgroup v2; no ordinary-container fallback or server purchase occurs. Stado Desktop exposes the same operations under Compute providers → Fleet sandboxes. The real remote lifecycle journey is `tests/sandbox/fleet.mjs`; compilation and prerequisite inspection are not lifecycle qualification.


- **`stado database backup [NAME]` and `stado database migrate NAME --to fleet --port PORT [--host HOST]` copy a declared Postgres database out of whatever provider hosts it and move it onto a fleet host:** a database on a hosted provider (a Supabase project) had no way out but the provider's own dashboard, so a provider that stops serving an organization took every row with it. `backup` reads the credential item from the owner vault from any host, reaches the server on its `session_url` with `db_password` in libpq's environment and verified against `ca_certificate`, and keeps a custom-format `pg_dump` archive of the server's own major version under `~/.stado/database-backups/<name>/<UTC time>/` (owner-only) with `manifest.json`: every readable table's exact row count, the roles and extensions in use, the schemas and tables the item's user may not read (left out and named), the archive's size and SHA-256; the archive is read back with `pg_restore --list` first. Without NAME every declared postgres database is backed up and each refusal is named (exit 1). `migrate` takes a backup, keeps the item as `<name>-database-previous`, places a fleet PostgreSQL of the source's version, restores the archive (roles first; extensions in the schemas the archive names, those the target lacks reported) and counts every table again; equal counts leave `<name>-database` on the fleet server with the declaration and consumers unchanged, while a difference, or a placement that stored the fleet coordinates and then failed, puts the source's coordinates back, keeps the fleet ones as `<name>-database-fleet-pending` for a second run and names the cause. `stado database place --version MAJOR` places a PostgreSQL of that major version from the Homebrew keg `postgresql@MAJOR`, refusing by name when the host has none. Stado Desktop's Databases screen gains **Back up all**, and **Back up** and **Move to fleet…** on each row.

- **`stado database rest place NAME --port PORT --key-valid-days DAYS [--rotate-keys]` serves the hosted provider's REST API in front of a fleet Postgres database:** a consumer built on the provider's client library calls its HTTP API, not Postgres, so a database moved to the fleet left it calling the provider. PostgREST is placed beside the database as the unit `<name>-rest`, the roles `anon`, `authenticated`, `service_role` (`NOLOGIN`) and `authenticator` (`LOGIN`, generated password) are made on it, `~/.stado/databases/<name>/postgrest.conf` is written owner-only, and `rest_url`, `jwt_secret`, `anon_key` and `service_role_key` (HS256, issuer `stado`, valid the stated days) are written onto `<name>-database` for consumers to read. A placed API is reused; `--rotate-keys` mints a new secret and restarts the unit. `stado database rest retire NAME` is the inverse, and `destroy` retires the API before the database. Stado Desktop's row menu gains **Serve REST API…** and **Retire REST API**.

- **`stado database backups [NAME]` lists the backups this machine keeps and `stado database backup --keep N` removes complete backups beyond the newest N:** a fleet database has no provider taking backups, so a scheduled `stado database backup --keep N` is its retention, and an incomplete backup is listed with why and never removed. Stado Desktop gains **Kept backups**.

- **`stado database cost --provider supabase` reads what Supabase bills, from its management API:** per project the compute and add-ons with their stated prices, the month's total (compute only while the project runs), seven days of gateway requests and the declared database its item names; per organization the plan, its compute credit and the month's usage after it; a read that fails is named on its row and exits 1. The plan fee and the credit balance are not in the API and are named as read on the billing page. `--provider fleet` and `external` are refused as having no bill. Stado Desktop gains **Read the Supabase bill**.

- **`stado billing watch` reads Supabase's notices:** mail from `supabase.com` (failed payment, pending shutdown) is read beside the Microsoft and Google notices.

- **`stado config get KEY` reads back the dotted keys `config set` writes:** `host.scan_load_ceiling`, `database.postgres_tls` and every other dotted key the documentation shows set and read were refused as `configuration resolves no value`; a key `config show` does not resolve is now read from the config file on disk, and a key the file does not hold is refused naming the file and the resolved keys.

- **The Supabase adapter refuses what it used to pass over:** a project's pooler that cannot be read refuses `adopt` with the API's answer instead of rewriting the item without `pooler_url` and `session_url`; `create` keeps the new project's password and says why the pooler is missing; a project listed without its name is refused instead of stored under its ref.

### Changed

- **The sandbox provider is Boat, and Stado speaks Boat Public API v1:** Box was renamed Boat, and its legacy API (`ascii.dev/api/box/v1`, `/boxes`) answers with a `Sunset` notice. The provider id is now `boat` (the `box` and `box-ascii` names are gone), its settings are `boat.ttl_seconds`, `boat.release_mode` and `boat.api_url` in the profile with the environment overrides `BOAT_TTL_SECONDS`, `BOAT_RELEASE_MODE` and `BOAT_API_URL` (the `BOX_*` variables are no longer read), and its key is the Skarbiec item tagged `stado:role:cloud-boat`, which a workload grant may not carry. Requests go to `https://boat.dev/api/v1/sandboxes` with Boat's own response types; a deletion carries the confirmation Boat requires and accepts Boat's background deletion; a sandbox Boat cancelled for want of a machine fails its job by name; an account at its active-sandbox limit is refused with both counts; and an answer that echoes the API key has it replaced by `[REDACTED]` before it becomes an error.
- **The release role of `stado serve` keeps its declared cadence and says when it cannot retire a product:** `--release-interval-seconds` now starts a pass once per period, as every other resident role does, and a pass that outlasts the period starts the next one at once and skips the missed ticks, instead of sleeping the whole period after each pass so that every slow rollout pushed the next one later. A host whose `HOME` cannot be read now prints `[release-agent] host=<host>: retiring products release control no longer targets here could not run, HOME is not readable: <reason>` each pass, where it used to skip that retirement without a word.
- **`stado service release` takes `--readiness-window-seconds` with `--readiness-url`, refused at parse when it is zero:** the window was `--readiness-timeout-seconds`, a `u64` that a release without readiness filled with zero internally and that only the host probe refused when zero. The URL and its window now travel as one value or not at all, clap refuses `0` before anything is installed, and a release-control replace whose policy declares a zero readiness window is refused as a declaration naming the product. The registry key `release_control.products.<product>.strategy.readiness_timeout_seconds` is unchanged.
- **`WC_WEB_API_PRODUCTS` is read as the web product table by every reader, and a refused override is never "nothing declared":** `stado web list`, `stado web status`, the edge's routes, the origin owner lookup and `stado web declare --path-prefix` each asked the config file whether `web_api.products` existed and, when it did not, answered as if no product was declared, so an override the config file did not repeat listed nothing, rendered no edge routes and owned no hostname, and an override that was not valid JSON was swallowed as an empty plane. The override and the file are now read in one place: no table in either lists nothing, as before; a table in either that does not parse is refused with its problems; and a reader that needs the table is told `web_api.products is not declared, in WC_WEB_API_PRODUCTS or the config file`.

### Fixed

- **The monthly budget is judged against what the month has already billed:** the cost forecast read the month's spend from `gcp.latest_month.net_cost` or `gcp.net_cost`, fields the billing snapshot never writes, and read every month as unspent, so `budgets.monthly_usd` passed with the month already spent and the month-end projection was the current burn alone. The forecast now sums each enabled billing provider's `monthly` row for the calendar month (a month with no row has billed nothing); a missing snapshot, a section that is not `ok`, or a provider whose section reports no monthly spend (Azure's reports a credit balance) leaves `month_spent_usd` and `end_of_month_usd` null with the cause in `month_spent_unknown`, and while a monthly budget is declared the coordinator places no new cloud capacity and logs `autonomy budget guard: budgets.monthly_usd is declared but this month's billed spend is unknown (<cause>); new cloud placement blocked`. An overrun is present only when its budget is declared and exceeded, a budget anomaly's `expected_value` is the budget it exceeds (null for spend that should not exist), and `stado overview` prints `billed this month: <amount>` or `billed this month: unknown, <cause>`.
- **Listing schedules reads them side by side:** `stado schedule list`, the coordinator's due-schedule pass and the web schedules page read every schedule one after another, so a listing took as long as all of its reads together and a slow fleet store made it take minutes; the schedules are now read under the crate's one bulk budget, in the same order, each listed once and a removed one not at all (`tests/schedule/listing.rs`).

- **The name register says what a claimed repository is when GitHub does not:** `stado product catalog --names` wrote `(no description on GitHub)` for every repository without a GitHub description, including the ones a catalog product claims and describes, so most rows of the register named nothing. A repository with no GitHub description now says what the catalog says it is: a product's owner repository carries the product's catalog description, and any other repository the product claims carries its surface kind and the product before it (``desktop surface of `weles`: …``), so a desktop app or client library never reads as the product itself. A new `from` column says whether each row's text came from `GitHub` or the `catalog`; a repository described by neither reads `(no description on GitHub or in the catalog)`. A repository `gh repo list` gives no `nameWithOwner` is refused by name instead of being looked up under its bare name.

- **A registry read on a host that is not the authority answers from the generation this host's resolver holds:** every command's registry read (`database resolve`, `registry pull`, `schedule`, host commands) asked the authority's `stado resolver snapshot` over SSH first, so a slow or silent authority held every command on every other host for as long as it stood, though each host's own resolver held the same generation. The read now asks this host's resolver on its loopback API first and says `stado: registry generation <N> read from this host's resolver, …; the authority was not asked`; only when the resolver holds none it may answer from (none runs, or its generation is past max-stale) does it ask the authority, saying why. `placement move --authority` and `registry push --last-known-good` still ask the authority itself whether it answers.

- **`stado placement move` runs on the host it is called on:** a move whose registry authority was another host ran the whole transaction as a second `stado` over SSH on that host, so a move off the authority host waited on that host's own process, silently, for as long as it stood. The move now reaches the source and the destination through their own channels from the calling host and commits through the registry's compare-and-swap, as every registry writer does; a refused source channel fails the move with its error, and a standing one is a wait `stado waits` names.

- **Stado no longer trusts the eight compromised eMudhra intermediates:** it locked rustls-webpki 0.103.13 and webpki-roots 1.0.9 (RUSTSEC-2026-0382, RUSTSEC-2026-0381), and the AWS SDKs' default `rustls` feature pulled in their legacy hyper 0.14 client on rustls 0.21 and rustls-webpki 0.101.7, for which no fixed release exists. The SDKs now take their default features less `rustls`, so every AWS call uses `default-https-client`, and the lock carries rustls-webpki 0.103.16 and webpki-roots 1.0.10: a connection to a host serving one of those chains is refused with `invalid peer certificate: CertDistrusted`.

- **A Swift package's tests and programs run under `stado product swift` keep their Git transports:** the one `swift` process that compiled the package also ran its tests or program with `GIT_ALLOW_PROTOCOL` set empty, so a test that used Git itself (a fixture repository over `file://`) failed with `transport file not allowed`, as the Cargo operations did before their run left resolution.
