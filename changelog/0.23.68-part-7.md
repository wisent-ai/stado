## 0.23.68

### Added

- **`stado host privacy TARGET --since WINDOW`** lists every privacy request macOS's `tccd`
  recorded on TARGET in the window against its Stado program and the programs it started — time,
  service, check or access, whether a dialog was shown, the answer, the accessing program and who
  asked — read from TARGET's unified log through its declared connection, and exits non-zero when
  one reached for protected data no grant declares (`UNDECLARED`). `--json` carries `requests`
  and `undeclared_requests`.
- **The beacon says which declared role the host process does not run, and the resident unit is
  rendered again for it:** the `roles` block carries `declared_not_running`, the `stado serve`
  roles the registry declares for the publishing process's own serve unit (the declared serve
  lines taking its role lock) that the process was not started with, read from both command lines
  by serve's own definition, with the units compared and any line the parser refused;
  `{"no_declared_unit": <lock>}` when no declared line takes the lock. When roles are missing and
  the process is the host's resident unit, the pass starts the same detached `service ensure` the
  executable starts when its unit's argument vector is refused, records the line it was started
  for, and starts none again for that line; `converge` says what happened. A unit rendered without
  `--resolver` keeps serving its API while every reader of the registry it would refresh goes
  stale; `stado host health` now prints `roles: declared but not running: --resolver (<unit>);
  rendered again: …`. A beacon collected by hand carries `null`. Journey:
  `tests/host_health/beacon/declared_roles.rs`.

- **`stado cloud host create|list|delete|reap --provider azure` rents fleet hosts from the cloud
  under the operator's credit floor:** `create NAME --location L --size S --disk-gb N
  --idle-minutes M` prints the projected hourly burn (the new machine's on-demand hour and that
  of every cloud host already running) and holds the create to the Azure credit gate with all of
  them counted, measures the public address of each host `cloud_hosts.admit_from` names (each asks
  the product site's `/api/egress` over its host channel) and admits only those to SSH, mints the
  host's fleet key as `fleet key generate` does, creates the public address, security group,
  interface and VM (cloud-init installs the build toolchain and keeps sshd key-only), enrolls it
  through the verified `fleet enroll` path, records `targets[].cloud`, waits for the first boot
  to end and reports the toolchain it answers. A host that cannot be enrolled is deleted again.
  `reap [--apply]` readmits the fleet's current addresses and deletes each host whose run area has
  stood empty longer than its idle minutes; the coordinator runs the applied pass on every tick
  when Azure is enabled. `delete NAME` deletes the VM, disk, interface, security group and address
  and only then the registry entry and the fleet key.
- **`stado change`, the submit queue, one per repository:** `stado change submit CHECKOUT
  --commit SHA [--defect ID]...` queues a commit an agent made on any `main`; `stado change run
  CHECKOUT [--host NAME]... [--integrated DIR]` takes the repository's queued candidates oldest
  first, one at a time, writes each candidate's own commits again on the remote `main` (no working
  tree or index of the checkout is touched), runs the product's declared gates on the result —
  the locks, module declarations and `format` gates here, every `lint` and `test` gate of every
  declared platform on that platform's hosts at once (a Cargo gate as `stado host cargo` runs it,
  any other exactly as the manifest declares its argv, in the delivered tree), a `cargo test`
  gate that selects no target cut into one shard per test target, each compiling action asked of
  Oko as the work of the agent session that submitted the candidate (`oko admit --session`) —
  answers a shard that already passed on the same tree from its action cache, classifies the
  change's risk from the product's catalog `submit` declaration (criticality, review paths,
  changed lines, whether a compiling gate checks it), has a high-risk change reviewed by Tama's
  harsh review before it lands and a low-risk one after, queues the reviewer's repairs once as a
  follow-up candidate (a follow-up's own repairs are named for its author, not queued again),
  pushes to `main` as a fast-forward (a `main` that moved takes the candidate back to the rebase),
  and records each defect repaired in Oko and, with `--integrated`, as one backlog line per
  defect; a register write that is refused is kept on the candidate. A candidate the pass cannot
  judge (the remote, the fleet or the harsh review does not answer) stays queued and the pass
  exits non-zero with the cause; one whose gates Oko's admission does not admit (a ruling, a
  closed defect) or does not answer for stays queued while the candidates behind it run, and the
  pass then exits non-zero naming it; a later pass also takes a candidate a stopped pass left
  running. A change of a product whose catalog record declares no `submit` is refused, naming
  the declaration to add, and so is a high-risk candidate that names no `--defect`, since the
  harsh review is scoped to one. A host that cannot run its shard is left out of the pass and the
  shard given to the platform's other hosts. `stado change status|list|cancel` read and withdraw
  candidates. Stado Desktop's Queue screen carries the same five operations. The catalog gains
  the optional per-product `submit` declaration (`criticality: critical|standard`,
  `low_risk_max_changed_lines`, `review_paths`); Stado and Oko declare themselves `critical`,
  Trends `standard` (low risk up to 40 changed lines outside its manifests and workflows).
- **The submit queue refuses a change too big to review whole:** the catalog `submit` declaration
  gains `max_changed_lines`, the most lines (added plus removed) one change of the product may
  change. `stado change submit` refuses a commit whose own commits change more past their merge
  base with `main`: `<commit> changes <n> lines in <f> files past its merge base <base> with main,
  more than the <max> one change of <product> may (its catalog submit.max_changed_lines); split it
  into changes of at most <max> lines and submit each`, and a product whose declaration states no
  number. Stado and Oko declare 2000, Trends 400.
- **`stado workload harness install` reaches hosts on another platform:** a harness declaration
  may name where its maker publishes builds (`releases` in `stado-rs/data/work/workloads.json`:
  the version prefix `--version` prints, the download address, the checksum list and one asset per
  release platform). A host on this machine's platform still receives this machine's copy; any
  other host fetches the build of the same version published for its platform, checks it against
  the release's SHA-256 list and its own `--version`, and only then replaces the managed program.
  `omp-session` declares OMP's builds for `darwin-arm64` and `linux-amd64`, so Linux hosts can run
  sessions. The run directory is removed on failure too.
- **The registry records which bearers a host holds (`targets[].bearers`):** every bearer file
  `stado credentials token sync` delivers and every owner file `stado credentials token mint
  --token-file-name` writes is recorded on its host as `{consumer, file}`, so
  `stado registry host show HOST` says which of the fleet's credentials sit on a shared computer.
- **`stado credentials token remove CONSUMER --host HOST --token-file FILE`:** takes a bearer file
  off a host and its record out of the registry, the counterpart of `sync`. It is refused while
  the vault owner still records a grant for CONSUMER, while the registry records the file as
  another consumer's, and while the host's configuration reads a bearer from it; a symbolic link,
  a file another account owns and a path outside the account's home are never removed. A file
  already absent is reported as `token_absent`.
- **What one product calls another for has alternatives, and Stado hands out the one that
  answers:** a product that needed a model, a browser, a secret, a mailbox or a transcript dialled
  the product that provides it, so Oko and Weles stopped whole when Brama did not answer. The
  capability catalog now declares the families products resolve through Stado (`inference`:
  Brama, then the OpenAI-compatible endpoint `capabilities.inference.endpoint.url` names, asked
  for `capabilities.inference.endpoint.model` with the key of the item playing role
  `capabilities.inference.endpoint.key_role`; `secrets`: Skarbiec, then the owner-only file store;
  `browser-automation`: Weles; `mail`: Skrzynka; `transcripts`: Transcript Lake).
  `stado capabilities resolve FAMILY --consumer C [--failed P] [--json]` answers the first
  alternative in the selected order that is proven to answer, with every one before it that did
  not; when none answers it exits with the `infra_down` code and its `details.unreachable` names
  each alternative's product, route and cause. A proof stands for the directory refresh interval
  this host's resolver declares, so a down first alternative costs one proof per interval, and a
  caller refused by the alternative it was handed reports it with `--failed` to have it proven
  again at once. Every answer is kept in `~/.stado/capabilities.json` (`STADO_CAPABILITIES_RECORD`
  moves it), and `stado capabilities [FAMILY]` prints each family's order, each alternative's
  last proof and which alternative served which consumer, a fallback marked as one.
  `stado capabilities select FAMILY --order A,B` writes `capabilities.<family>.order` after
  refusing a name the family does not declare or names twice. Stado Desktop's Compute providers
  screen runs both.
- **A product that dials another product's service itself is refused before it is pushed:**
  `stado quality check`, which every product's pre-push, change hand-off, release submission and
  delivery gate run, now refuses a revision whose added lines reach a service a capability
  family offers alternatives for (Brama, Skarbiec) through `stado service directory connect
  <service>` or its forward marker, naming each line and the `stado capabilities resolve
  <family> --consumer <product>` that replaces it. Only the lines the revision adds against the
  published main are judged; prose, `tests/`, `docs/` and `.github/` are not read, and Stado,
  which serves the directory, is not judged by it.
- **`stado product policy show|set|remove`, the host's update policy:** per product (or as the
  default) whether `stado product sync` installs a newer origin/main by itself (`automatic`,
  optionally only inside a local `--window HH:MM-HH:MM`) or holds it (`held`, with a required
  `--reason`), kept in `~/.stado/products/update-policy.json`; without the file every product is
  automatic. Sync rows carry the rule as `policy` and say `held` or `deferred` with the release
  command; `stado product status --json` reports it as `update_policy`; Stado Desktop → Products
  shows, sets and removes it. A policy that cannot be followed is refused as `[config]`.
- **An update product sync made that fails its check is rolled back:** after installing, sync
  checks the receipt's readiness and the recipe's new `health` argv; a failure restores the
  installation before it (`rolled-back`), records the revision in `SURFACE.refused` so later
  passes hold it while origin/main stays there, and the next commit installs as usual.
- **A held product is never installed as another product's dependency:** one whose receipt says
  installed is used as it is, without checking or rebuilding it (its program deleted by hand, its
  recipe changed); one that is not installed is skipped for a dependent the catalogue gives an
  alternative, and refuses a dependent bound to it, naming the hold and its reason.
- **A dependency sync rolled back is not rebuilt for its dependent:** a rolled-back installation
  (the predecessor put back whole) read as incomplete to a dependent's installation, so the
  dependent the same pass installed next rebuilt the dependency at the very revision sync had just
  refused for failing its readiness check. A rolled-back installation is now complete to its
  dependents, as an installed one is.
- **Adding a machine to the fleet declares every way it fails:** `stado fleet enroll`, `stado
  fleet join` and `stado fleet approve` raise only declared causes (`fleet.enroll` 57, `fleet.join`
  10, `fleet.approve` 63), each naming what failed, why, the state observed and what fixes it, with
  its code and exit status: the registry read and write by the class the store answered, the
  enrollment catalog's gates with the methods the fleet does allow, the channel key, the
  `--install-key` session, each way OpenSSH ends the probe (unresolvable, refused, timed out, no
  route, key refused, host key changed), the platform, the install and its rollback, and the
  network join. A failure prints `fix: ...` under its `Error:` line and names its cause; `--json`
  answers it as JSON with `cause` and `remedy`.
- **`stado errors list|show|check`:** `list` names the operations that declare a failure catalogue,
  `show OPERATION` prints each cause with its fix, code, exit status and test (`--json`,
  `--markdown` for the documentation page), and `check` is the new `error-standard` quality gate:
  it refuses a catalogue that is not one and an error message holding a generic sentence ("did not
  succeed", "operation failed") beyond `stado-rs/errors-baseline.json`, which may only shrink.
- **The submit queue runs by itself:** the Stado CLI installation declares a host routine
  (`stado schedule create --host-store`, every ten minutes, overlap skipped) running `stado change
  run` with no checkout, which carries every repository of this machine's queue that has a
  candidate waiting, each from the checkout its candidate was submitted from. Nobody ran the pass
  before: it ran inside agent sessions, whose end killed it, its reviewer and the candidate it
  carried. `stado schedule create --host-store` declares any routine into this host's own store.
- **Each candidate without a verdict says what it waits on:** `stado change list` and `status`
  print `waits on: <the next pass | a pass | the remote | Oko's admission of its gates | a host for
  its gates | a harsh review round>` with the command that unblocks it, and `--json` carries it as
  `waits`; the record keeps the step as `waits_on`.
- **`stado change review ID --findings FILE --improvements FILE`:** records a review round over a
  queued or running candidate beside its record (`<id>.rounds/`), by the agent session the command
  runs in as its harness names it (`tama sessions self`, else the transcript `PI_SESSION_FILE`
  names), never a name typed; the submitting session and a command no session runs are refused. The
  round is over the commit the next pass lands (the candidate as the last pass wrote it on `main`)
  and keeps its tree: a round over a tree a moved `main` replaced decides nothing. At the review
  before landing each reviewer's newest round over the tree counts, so one reviewer never clears
  another's findings: any finding refuses the candidate naming it, and rounds that all found nothing
  admit it. Tama's harsh review is one adapter, run only when no round is recorded; without Tama
  the candidate waits on `a review round over commit <sha> by a session that is not its author`,
  naming this command.
- **A host whose worker cannot reach the fleet store says why in `stado host gates`:** every
  capacity write, every agent start and every tick that met a store that did not answer leaves its
  outcome on the host in `~/.stado/logs/capacity-publication.json` (step, time, the store's words,
  since when it refuses, the Stado version). `host gates` reads it over the host channel, which needs
  no store, and prints `its worker cannot reach the fleet store: its <step> at <time> was refused,
  refused since <time> (Stado <version>): <error>` where it said only `nothing published`; a host
  with no record is named as one whose worker never ran under a Stado that keeps one. `--json`
  carries it as `publication_attempt`.
- **`stado space candidates [--min-bytes N] [--json]`** ranks what holds this machine's disk as
  the next cleanup candidates: agent output first (tagged build trees, Cargo build directories, job
  work trees, harness logs, a checkout's `.build`/`.build-*`/`target`), then caches (compiler,
  model, package, Xcode), then the owner's own large files and folders (a game library among them)
  as proposals only. Each row has its bytes, producer, safety (`rebuildable`, `refetchable`,
  `scratch`, `user_owned`), whether the janitor's pass takes it (`automatic`) or only proposes it,
  and the cumulative bytes; the answer says how much must go to be under the 80% rule and lists
  the janitor's newest removals. Desktop shows it in Settings, "Cleanup candidates on the API host".
- **The janitor's pass at the 80% rule takes Cargo's build directories itself
  (`cargo_build_dirs`):** every `$CARGO_HOME/build/<xx>/<hash>`, tagged or not, whole, unless a
  build holds a `.cargo-lock` in it (`held_by_build`) or Stado runs from it; before, only the fleet
  stage `space reclaim --stage cargo_build_dirs` did, and a laptop at the rule kept tens of GiB.
- **The janitor records what it removed** in `~/.cache/wisent-compute/reclaimed.jsonl`: one line
  per tree (path, bytes, freed bytes) and one per other cleaner per pass (items, bytes). A damaged
  line is refused by `space candidates` naming the line and the fix.
- **`stado space scratch register|list|forget`: the scratch register.** A job, an agent or a verb
  registers a tree it made (an export under a checkout's `.build/`, say) with its creator, purpose,
  owner session and owner process; at the 80% rule the janitor's new `registered_scratch` cleaner
  removes every registered tree whose owner process has ended, least recently changed first, keeps
  the rest (`owner_session_running`), records each removal in `reclaimed.jsonl` and forgets the
  row. A tree that was never registered is never taken. `space candidates` ranks registered trees
  as automatic agent output. A path outside the home, inside `~/.stado`, the janitor's state or
  `~/.ssh`, a link, a path through a link or with `.`/`..`, an absent tree, a registration
  without `--owner-pid` and a damaged register are refused naming them and the fix; the register
  keeps the tree's real path, and a tree that no longer resolves to it is kept, not removed.
- **The janitor takes Xcode's per-project build directories at the 80% rule
  (`xcode_derived_data`):** each `~/Library/Developer/Xcode/DerivedData/<project>-<hash>` whole,
  unless a running process has a file in it open (`lsof`) or names it (`held_by_process`); when
  either table cannot be read it takes none (`process_table_unread`). `ModuleCache.noindex`,
  archives and device support are never touched. Each removal is in `reclaimed.jsonl`, and `space
  candidates` ranks each project directory as automatic agent output.
- **The janitor's second tier: package managers' download caches (`package_caches`).** When the
  agent output a pass took leaves the volume at the 80% rule, or without room under it for the
  next build, the pass takes Cargo's git `checkouts/` (never `db/` or the registry), npm, Bun,
  SwiftPM, pip, uv, Homebrew and VS Code's update staging, largest first, and stops once the
  volume has that room (`room_for_the_next_build`). A cache a running process holds (a file
  open, a working directory, its path in arguments; Cargo's package-cache lock for its
  checkouts) stays (`held_by_process`), and Cargo's checkouts stay while any `cargo` or `rustc`
  runs (`build_running`). A cache is moved aside in one rename right after its holders are read,
  so a tool starting during the removal makes a new one. Each removal is in `reclaimed.jsonl`;
  `space candidates` ranks them as automatic caches. Products' own application caches and the
  owner's files stay proposals.
- **A pass leaves room under the rule for the next build (`margin`).** A pass that stopped just
  under 80% left the host under a GiB, and the first build put it back over and closed its gates.
  The room is measured, not declared: the largest Cargo build directory the pass measured under
  Cargo's home, or that `reclaimed.jsonl` says a pass took in the last 7 days. A host under the
  rule but short of that room runs a pass too, which takes only the package managers' caches:
  agent output (an idle agent's build directory and its incremental state) goes only at the rule.
  Each report carries `margin` (bytes, the directory it was measured on, and where that
  measurement came from).
- **A crash-looping declared unit pages the operator.** The first health pass that reads a unit
  failing (no process, a nonzero last exit, the supervisor's run count) sends one page through the
  registry's `operator_contact` channels with the unit, the verdict and the last line it wrote to
  stderr, and keeps what the channels answered in `~/.stado/failing-units.json`. A page no channel
  took is tried again on the next pass. The unit's beacon `detail` says `operator page: …; Oko
  defect: …`.
- **`stado change prioritize ID --reason TEXT`:** the queue took candidates strictly oldest first,
  so the change that keeps its own gate hosts able to run gates waited behind every candidate
  submitted before it. A queued candidate moved ahead goes before every candidate not moved ahead,
  after those moved ahead before it; its reason, the agent session that moved it (`the operator`
  when none) and when are kept beside it in `<id>.priority`, which a pass writing the record cannot
  undo, and shown by `stado change list` and `status` (`moved ahead by session <id> at <time>:
  <reason>`, `priority` in `--json`). An empty reason, a candidate at a verdict, and one stacked on
  a waiting candidate that was not moved ahead (whose commits it would land as its own) are
  refused, each naming the fix.
- **Pictures and web searches are called through Stado, as model requests are:** a product that
  needed a picture or a search had no family to hand it to, so it named a vendor or did without.
  `stado capabilities call image --consumer C` takes `{"plan": EDIT_PLAN, "inputs": [PATH…],
  "output": PATH}`, an Obraz edit plan (`obraz operations` lists its steps; `generate` makes a
  picture from a description), and Obraz runs it with `obraz edit --plan - --json
  --allow-provider-cost`; the answer is `obraz edit --json`'s (`output`, `mime_type`, `width`,
  `height`, `bytes`, `steps`). An Obraz usage refusal is the request's fault and refuses the call;
  any other Obraz failure passes to the next alternative. `stado capabilities call search
  --consumer C` takes `{"query": TEXT, "count": N}` (1 to 100) and answers `{"results": [{"title",
  "url", "snippet"}…]}`; its `search-endpoint` alternative is the address
  `capabilities.search.endpoint.url` declares (`https://` only), sent the query as `POST` JSON with
  the `token` of the item playing `capabilities.search.endpoint.key_role` when one is declared,
  and proven by any HTTP answer from it. In both families `attestation` answers a request no
  alternative before it answered: the request is kept and refused naming the command that answers
  it, and `stado capabilities attestation record image|search` takes the answer in the family's own
  shape, refused when it is not that shape. An answer an alternative gives in another shape is
  that alternative unable to answer, and the next one is asked. The orders are
  `capabilities.image.order` and `capabilities.search.order`.
- **A recipe role's kept keychain is on the user's search list only while Stado signs with it:**
  keeping a role's identity put `$HOME/.stado/signing/<name>.keychain-db` first on the search list
  and left it there. After a restart the keychain stayed listed but locked, and a product's own
  build script asking the list for a signing identity found the fleet's key there, so macOS showed
  "codesign wants to use the <name> keychain" to the operator. Keeping now takes the keychain off
  the list (an entry an earlier release left is removed on the next installation); a signature
  lists it and unlocks it just before `codesign`, and the scope's close takes it off again.
- **Every reader of the product catalog reads the committed one:** `stado product catalog`,
  `status`, `dependencies`, `advisories`, `build-trees`, `documentation`, `registry check-claims`
  and Stado's `change` and `quality hooks` read a catalog its checkout tracks at the committed
  head (or `origin/main` when the head is behind), as installations already did. One session's
  uncommitted edit of the shared checkout that does not validate no longer refuses every other
  session's read: it is named on stderr with its error and not read. `catalog --json` names the
  revision it read as `catalog_read`, and `registry add|set|rm` say under `uncommitted` that
  readers see the edit once it is committed, with the command that commits it. A `--catalog`
  file no checkout tracks is read as it stands.

- **A program moves once from its retired `ai.wisent.` identifier to `com.wisent.<product>`:**
  signing a product's own program or app under any other spelling is refused, naming the
  convention name. A replacement for an installed copy signed `ai.wisent.<product>.<name>` (or a
  bare nested name such as `skarbiec`) is accepted under its convention name: its continuity is
  checked against the installed designated requirement with the identifier clause renamed, so the
  anchor, team and certificate still have to match. The shared identity's Keychain names
  (`ai.wisent.identity`, `ai.wisent.identity.keychain-helper`) keep their spelling, since every
  signed-in session's Keychain item trusts them by name.
