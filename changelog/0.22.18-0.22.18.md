# Changelog 0.22.18 – 0.22.18

Released entries, moved out of `CHANGELOG.md` so that file stays editable.
The current entries live there; this file is history and does not grow.

## 0.22.18

- `stado database create` no longer assumes Postgres on Supabase. It takes `--engine` (postgres or sqlite) and `--provider`, and the default provider is `fleet`: Stado runs the database itself on a fleet host (the vault owner unless `--host` names another) through the new `stado database place`, which initialises the data, issues the database's own certificate authority, writes `<name>-database` into the owner vault and installs the managed unit `<name>-database`. Supabase stays as `--provider supabase`, with `--anchor` and `--accept-monthly-usd` refused for any other provider.

- Stado carries no tests the operator has not approved with `tama tests approve`. The integration tests under `stado-rs/tests/`, the source checks package `stado-source-checks`, Stado Desktop's test targets, every inline `#[cfg(test)]` module, the release recipe's `tests` stages and the post-build qualification in `deploy/release/build_stado.sh` are removed. `stado release verify-platform`, whose only work was running those journeys on a host, is removed from the CLI and from Stado Desktop's Releases operations.

## 0.22.18

- `stado config validate` refuses the retired `agent.skarbiec.items`, and `stado config migrate-identities` removes it and points each release publisher entry at its `<product>-release-publisher` role, so a host moves from item names to roles with one product command followed by `stado release catalog enroll`.

## 0.22.18

- Secrets are asked for by role, never by vault item. A release recipe's `secret_env`, a job, a schedule, `agent.skarbiec.secret_fields` and every credential Stado reads name a role (`role#field`), and the vault decides which item plays it by the Skarbiec tag `stado:role:<role>`; an item's id is random and decides nothing, so renaming an item changes no behaviour. `agent.skarbiec.items` is replaced by `agent.skarbiec.roles` (`WC_AGENT_SKARBIEC_ROLES`). `stado credentials item put --host H --role R --type K` rotates the item playing R or creates one under a random id with the tag; `stado credentials grant role-read` replaces `grant item-read`. Two items in one role are refused. Release publishers play `<product>-release-publisher`; Stado's own credentials play `huggingface`, `cloud-aws`, `cloud-gcp`, `cloud-azure`, `vast`, `box`, `anthropic`, `alerts`, `twilio`, `host-health-api`, and backend messaging plays `apns`, `fcm`, `device-registry`, `email-provider`.

## 0.22.18

- On macOS, available memory is the kernel's own `kern.memorystatus_level` share of `hw.memsize` (what `memory_pressure` prints as the free percentage), in the host's memory pass, in `stado space report` over the host channel and in the runner diagnostics. The three readers summed only free, speculative and purgeable pages and left out the cache the kernel reclaims, so a host could publish well under a GiB available against its watermark while the kernel's level read most of its memory reclaimable.

## 0.22.18

- A handoff made after a build froze its batch, whose commit that build contains, is bound to it in an additional batch `runs/build/<build id>/changes-<digest>.json` the next time the build is submitted, and reads that build's verdict. It used to stay `queued` for good: every `stado build newest --queued` picked the product again and answered with the same passed build (tama 5654e49f on 2026-09-30) (c187756d).

## 0.22.18

- A worker claims one release build per build cache at a time. A build job whose product and platform share their Cargo target directory with a build already running on that host stays queued, and the scan publishes it under `claim_declined` with the reason, which `stado host gates` prints as a `declined:` line. A host that claimed several builds of one product at once left the newest `Blocking waiting for file lock on build directory` inside a claimed slot.

## 0.22.18

- A new build cancels the product's older builds it supersedes. After `stado build submit` or `stado build newest` queues a build, the jobs of every older build of that product still `waiting` whose commit is an ancestor of the new one are cancelled on each platform the new build queued, one stderr line each. On 2026-09-30 build 652b6c96 (c6a63931) compiled for over 77 minutes after 03baf850 (063d095f, a descendant) was queued, holding the Cargo lock the new build waited on (28f4a7af).
