# Changelog 0.23.12 – 0.23.15

Released entries, moved out of `CHANGELOG.md` so that file stays editable.
The current entries live there; this file is history and does not grow.

## 0.23.15

- **`stado product install` finds `cargo` inside the host's own agent:** a source installation ran each recipe step's bare program name on the caller's PATH, so the same install that ran over a host channel failed in a job the host's agent ran (`quality "fmt" failed … starting "cargo" … No such file or directory`), where the LaunchAgent PATH carries no `~/.cargo/bin`. Install steps and release-worker steps now resolve their program through one resolver (`~/.stado/bin`, `~/.local/bin`, `~/.cargo/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, then PATH) (c4cc3821).

- **A gate program the host could not start no longer condemns the revision:** `stado product install|update` recorded a quality step that never started (`starting "cargo" … No such file or directory`) as the revision failing that gate, and refused every later install of the revision with `already failed quality … commit a repair`, though nothing in the tree was wrong. Only a gate that ran and refused the tree is recorded now, as a `gate-verdict`; a record written before this release, which cannot say which it was, no longer refuses.

- **`stado release resume` delivers a published run that had failed:** a run whose platforms are all published is put back into `delivering` as soon as its coordinates read back, in the same write that clears its failure, before any failed delivery is queued again. It used to stay `failed` until the deliveries were requeued, so every delivery its host claimed in between refused itself (`refusing the stale coordinate: the run is Failed, not delivering`), the resume failed on those refusals, and each host had to be converged by hand. A platform is still marked published only once its `release.json` and archive read back, so no delivery is queued against an absent archive (9c4956cf).

- **`stado schedule create --id` can be repeated:** the same declaration again under the same identity answers `schedule <id> is already declared as asked; nothing changed` and exits 0, so an installation can declare the schedule it needs on every run. A different command, cron, timezone, enabled state, pinned host, provider, secret environment, repository, pre-command or overlap policy under that identity is refused naming what differs, and a deleted record under it is refused too; nothing is overwritten. Without `--id` every create is a new schedule, as before.

- **No product, unit, port or vault item is compiled into Stado's boundaries and recovery any more:** the config validator no longer requires a built-in list of object namespaces or deployed service units (`object_api.namespaces` and `service_api.deployers` are the declarations); `stado blast-radius` reports the roles `agent.skarbiec.roles` declares that no item plays, instead of checking for an item named `huggingface`; the Weles trust document finds the Skarbiec unit plist from the catalog's Skarbiec unit; the Skarbiec address comes from `WC_SKARBIEC_URL`, `secrets.skarbiec.url` or the service directory's `~/.stado/forwards/skarbiec.local`, with no built-in port; and the local object-API recovery reads its bind address and port from the catalog's host Stado process.

- **A release recipe declares the product CLIs its post-build tests run, and the builder installs them first:** a platform's `test_products` (`[{"product": "oko", "surface": "cli"}]`) is installed with `stado product install` on the builder after the build and before the first test, each as its own receipt step `test-product:<product>:<surface>`, and the tests run with `~/.stado/bin` first on PATH. A product that cannot be installed fails the job with that step's cause instead of a test panicking on a missing program. Tama's learning journey, which drives `oko`, declares it (5f10baf5). A Stado older than this refuses `test_products` at submission as an unknown recipe field, so submit with this Stado or newer.

- **Signing unlocks its own keychain right before each `codesign`, and a failed signature names the keychain and the state it was found in:** the temporary keychain Stado makes for a release build was unlocked once when it was made and read by `codesign` minutes later, so a keychain that had locked in between failed a finished build with `errSecInternalComponent`. Each signature now unlocks it first (a keychain the operator named is never touched), and a `codesign` failure carries `signing keychain <path>` with what `security show-keychain-info` answered for it (55167f6e).

- **A failure carried in from an operating-system, JSON or configuration error states its class:** an `io::Error` reaching a command states `not_found`, `auth`, `timeout`, `infra_down` or `refused` from the kind the kernel returned, a JSON document that does not parse or does not fit states `refused`, and a configuration error states `config`, where all three used to print `the command failed and we could not attribute the failure`. A `stado product` operation that fails states the class of the first such typed error in its cause chain (5b3bd385, in part: messages built with `CmdError::click` still state nothing).

- **Replacing an installed program checks the commands installed products were seen running of it:** every `stado` invocation records, once per caller and command, which executable started it and which command it ran (`~/.stado/callers/`). `stado product install|update` and `stado release install-local` read the records whose callee is the program being replaced, keep those whose caller is another product's installed path and has not changed since, and ask the incoming program for each recorded command with `--help`; one it does not answer refuses the installation with the product, its source revision, the caller and the command, so a Stado that dropped `secrets get` no longer replaces the binary an installed Oko still calls it through. No list of callers or commands is kept by hand (4aade303).

- **`stado web vercel` is gone; every web product builds with `stado web build` and is hosted by Stado:** the last of the six products that built and delivered through Vercel (wisent-trade) now runs `stado web quality` and `stado web build` on its `web` platform, so `stado web vercel build`, `stado web vercel deploy` and the enrolment refusal that named them are removed. A manifest that still names the command fails at the step that runs it with clap's unknown-subcommand error (357b0c1f).

- **The units a product's one process replaced are found on each host from what they run; the catalog lists none:** `retired_units` and `role_units` are gone from `catalog/products.yml`, and the catalog validator refuses either key. A unit on a host that runs a catalog product's program under any label but that product's one unit is its predecessor: a program in the product's own service tree, the exact program the catalog declares, or a file named after the product wherever it was installed. Any product but Stado replaces such a unit whole; for Stado the unit's work is read from its own command line by Stado's own command definitions (`serve` options, `dashboard`, `agent`, `coordinator`, `resolver serve`, `release agent`, `product sync`, the beacon commands, `stado-watchdog`, `stado-fix`) or matched to the live process's runner root, edge program or forward destination, and it is retired only once that process is proven to run every such role; one with no role is reported `kept` with the reason. `stado service ensure`, the autonomy reconciler, the API takeover at start, the object-API recovery, `service retire`, the registry doctor, the release-unit revisit block and the deployer configuration all decide from this one rule, so an old unit found on a host needs no catalog edit and no release. The reconciler now also retires an undeclared fleet unit no product owns when nothing runs it and no launchd domain holds it, and reports each live one as `undeclared_live` with its program instead of leaving it unnamed. `service list --undeclared` and every reader of a host's units read Linux systemd unit files too, where a Linux host used to answer that it held no unit. `stado service serve-roles` also prints `STADO_SERVE_ROLE_PATHS`.

- **The managed-product declaration names only Stado's own unit:** the old labels listed under `stado` in `stado-rs/data/catalog/products.json` are gone. After a new Stado binary is installed, the host release restarts its own unit and every registry unit on the host that still runs the Stado program under another label, found from that program.

- **Signing and installation secrets are read by role, never by item name:** `stado product install` and `stado product signing` no longer name the vault item `desktop-signing-apple-development`; they read the certificate and key of the item playing `stado:role:macos-development-signing`, and `WISENT_CODESIGN_ROLE` replaces the removed `WISENT_CODESIGN_CREDENTIAL_ITEM`. A source installation reads each `role#field` of a release manifest's `secret_env` by role, as the release path already did. The general read is `stado credentials get --role ROLE [--field F]`; no item in the role, or several, is refused with the role and the command that stores it. Before this release signs anything, the vault owner must run a Skarbiec that registers the `stado:role:` namespace and the signing item must carry the role: `stado credentials item retag --host <vault owner> <item> --tags stado:role:macos-development-signing`.

## 0.23.15

- `stado release status` no longer reports a build job as lost while its builder runs it, or after it finished. In-flight jobs were looked for under running before queue, so a job claimed between the two reads was under neither; and a finished release build whose queue record the retained run sweep had already retired was under no prefix at all. Either way the run failed with `the job was lost … submit the release again`. The lookup now follows the lifecycle (queue, running, completed, uploaded, failed, cancelled), walks it twice, and then reads the build's receipt in `status/<job>/output/`, as the release agent itself does, before calling a job lost.

- `stado product install|update` names what occupies a canonical checkout path it cannot use: not a directory, a directory with no Git checkout, a checkout with no origin, or the origin it declares. It said only `<path> exists and does not identify <repository>`, which on a host reached through `--host` nobody could look at.

- The darwin release worker's `macos-code-signing` step rewrites the line of every file it signs in a staged `SHA256SUMS` beside it. Signing changes the file in place, so a checksum the build wrote before it named bytes the release no longer carries, and a product that checks its binary against `SHA256SUMS` (Oko's judge journey) refused its own release.

## 0.23.14

- `stado release submit --source` binds a version to its commit only after the committed tree is snapshotted and the product is enrolled. A submission refused for a symlink in the tree, or for a release publisher it cannot declare, no longer spends the version: the same version can be submitted again from the commit that repairs it, instead of being refused `already attests source revision …`.

- `stado product install` signs on a Mac whose keychains lack Apple's WWDR G3 intermediate. The vault item holds the certificate alone, so the temporary keychain held a certificate with no chain and `security find-identity -v` listed no valid identity: every source install that signs on such a host stopped with `Apple signing identity is missing or invalid … 0 valid identities found`. Stado now carries the public intermediate and imports it into the temporary keychain with the certificate.

## 0.23.13

- **`stado service reap` works on Linux hosts:** on a non-Darwin host the reap program printed an unsupported marker nobody read and exited 0, so a reap of a Linux host answered an empty table that looked like "no duplicates". It now builds the keep set from each declared systemd unit's `MainPID` (system and user manager) and keeps every process in a declared unit's cgroup, so a child a double fork left without a parent is still held by its unit. The help now says what `--apply` does: SIGKILL, then a wait for each process to exit, not SIGTERM.

- **`stado service list --unowned` judges Linux processes by their program path:** Linux `ps -o comm` is the bare process name, never a path, so a program started as `/root/.stado/bin/<program>` with no arguments matched its root in `pgrep` and was then never judged (`matched 2, under 0`). The scan now also reads the first word of the argv, and a judged row names its owner as `claimed by <pid or systemd unit>` instead of always saying launchd.

- **Bootstrap no longer installs `wisent-compute-watchdog.service`, and Stado retires it:** the unit ran `stado-watchdog` with no `--interval-s`, which the program refuses, so a fresh unit could only restart every 30 seconds while an old process kept running unmanaged. `stado bootstrap` on Linux installs the agent unit alone, and the catalog lists the watchdog unit in Stado's `retired_units`, so `stado service ensure stado` and the service reconciler withdraw it. Diagnostics run as the `--watchdog` role of a host's `stado serve` where a host declares it.

## 0.23.12

- `stado product install` unpacks a build input that `git archive` produced. Its pax global header (the archive's commit id, not a member) was refused as `archive contains a special file: pax_global_header`, so a product with such an input could not be installed on any host.
- `stado service list --unowned` and `stado service reap` also find processes whose working directory is under a managed root (on macOS through `lsof -d cwd`, on Linux through `/proc/<pid>/cwd`), not only processes whose program or entry point is a path under it. A process a job started with relative paths (`bash release/stado-build.sh`, `node node_modules/playwright-core/cli.js install ffmpeg`) named no such path, so it was never listed or reaped, and a reaped download was started again by an installer nobody could see.
- `stado product catalog --json` serves every product record whole. It served a fixed projection (id, name, family, description, surfaces, installations), so the `rivals`, `benchmark` and `roadmap` a record declares never reached `probierz benchmark rivals`, which refused every product with `the catalog names no rival for <product>`.
